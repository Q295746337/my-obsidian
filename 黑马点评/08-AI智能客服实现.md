# 黑马点评 AI 智能客服实现（集成版）

> 代码位置：`D:/Java/HMDP/HMDP`，包名 `com.ncepuljxx.hmdp`，服务端口 `8081`。
> 记录口径：本文按**代码已完成完善**后的版本记录——批量查询、预约校验与返回值、手机号服务端绑定、归档原子追加、ThreadLocal 清理、API Key 外置等均已落地；若本地代码与本文不一致，以最新代码为准。
> 本文记录**已经集成进主项目**的改良版；独立 `consultant` 版与面试逐字稿见 [[04-拓展模块#LangChain4j 智能客服]]。
> 本地运行前置：MySQL `3307`、Redis `16379`（需加载 RediSearch 模块）、Nginx `8080` 将 `/api` 反向代理到 `8081`，并关闭缓冲以支持流式输出。

## 一句话概括

在原有黑马点评主项目中，用 LangChain4j 把大模型接成一个**登录态隔离、可查历史、能查库下单**的智能客服：`qwen-plus` 流式对话 + Redis 会话窗口/归档（带保留上限）+ 用户会话索引 + Redis 向量库 RAG + Function Calling 工具查 MySQL。

## 整体调用链

```text
chat.html (Vue + Element)
   │  GET /api/chat?memoryId=...&message=...
   ▼
Nginx (/api → 8081, proxy_buffering off)
   ▼
ChatController
   ├─ 校验登录用户 & memoryId 归属
   ├─ ConsultantService.chat(memoryId, message, phone)
   │     ├─ ChatMemoryProvider → RedisChatMemoryStore（窗口记忆）
   │     ├─ ContentRetriever → RedisEmbeddingStore（RAG，业务问题跳过）
   │     └─ Tools → Service/Mapper → MySQL（商家/券/预约）
   └─ Flux.doOnComplete → appendExchange 归档 + 更新会话索引
```

## 与独立 consultant 版的差异

| 维度 | 独立 consultant 版 | 集成改良版（当前） |
| --- | --- | --- |
| 形态 | 单独的 Spring Boot 服务 | 作为 HMDP 主项目的一个模块 |
| 鉴权 | 无，memoryId 由前端 `Date.now()` 生成 | 必须登录，memoryId 由后端生成并绑定 userId |
| 会话隔离 | 只按 memoryId | `user:{userId}:{sessionId}`，Controller 校验归属 |
| 记忆存储 | Redis，TTL 1 天 | 窗口 + 归档 + 用户索引；归档原子追加并限制保留条数 |
| 历史会话 | 无 | 会话列表、会话详情、打开页面自动恢复最近会话 |
| 向量库 | 内存版 `InMemoryEmbeddingStore` | Redis 版 `RedisEmbeddingStore`（持久化） |
| RAG 策略 | 所有问题都检索 | 意图路由：业务数据问题跳过检索，强制走工具 |
| 商家查询 | 精确匹配 | 精确优先，失败后关键词模糊匹配 |
| 前端 | `static/index.html` | `nginx/html/hmdp/chat.html`，首页有入口 |
| 工具安全 | 手机号由用户/模型传 | 手机号服务端绑定，工具不接受手机号参数 |
| 预约健壮性 | 直接 insert | 校验商家/时间/重复，返回成功或失败原因 |
| 配置安全 | API Key 可能明文 | API Key 走环境变量，生产关闭请求日志 |

## 核心实现

### 1. 鉴权与会话隔离

- `MvcConfig`：`LoginInterceptor` 拦截 `/chat/**`（未排除），未登录返回 401；`RefreshTokenInterceptor` 从 `authorization` 请求头取 token，查 Redis `login:token:{token}`，把 `UserDTO` 放入 `UserHolder`，并续期 30 分钟；两个拦截器的 `afterCompletion` 都调用 `UserHolder.removeUser()`，避免线程池复用导致 ThreadLocal 残留。
- `ChatController.chat`：
  - 从 `UserHolder` 取当前用户，手机号为空时用 `"未知"`；
  - 校验 `memoryId` 必须等于 `user:{userId}`（兼容旧格式）或以 `user:{userId}:` 开头，否则按越权拒绝（403/业务失败），防止伪造 memoryId 读别人会话；
  - 把当前用户信息写入请求级上下文（供工具读取），调用 `consultantService.chat(memoryId, message, phone)`；流式场景下工具可能切到 Reactor 线程执行，上下文通过 Reactor Context 或显式参数传递，不能只依赖普通 ThreadLocal；
  - 用 `StringBuilder` 收集流式片段，`doOnComplete` 时归档整轮对话，`doFinally` 清理请求上下文。
- `POST /chat/session/new`：生成 16 位 UUID，返回 `user:{userId}:{sessionId}`。
- `GET /chat/history/list`：当前用户的历史会话摘要。
- `GET /chat/history/{memoryId}`：当前用户某个会话的完整消息（再次校验归属，兼容 `user:{userId}` 旧格式与 `user:{userId}:{sessionId}` 新格式）。

### 2. 会话记忆：窗口 + 归档 + 索引

`RedisChatMemoryStore` 同时承担 LangChain4j 的 `ChatMemoryStore` 和业务归档：

| Redis Key | 类型 | 作用 | TTL/保留 |
| --- | --- | --- | --- |
| `memory:chat:{memoryId}` | String(JSON) | AI 上下文窗口，`MessageWindowChatMemory` 按 `hmdp.memory.context-size:30` 裁剪 | 无 |
| `memory:archive:{memoryId}` | List(JSON) | 完整对话归档，每轮 `RPUSH` 用户消息 + AI 回复，只追加、不修改已有消息 | 保留最近 2000 条（`LTRIM`） |
| `memory:index:{userId}` | ZSet | 用户会话索引，score=最后更新时间毫秒，用于倒序列出会话 | 无 |

- 读窗口：`getMessages` 从 `memory:chat:` 取 JSON，反序列化为 `List<ChatMessage>`；空/解析失败返回空列表。
- 写窗口：`updateMessages` 把 LangChain4j 裁剪后的窗口写回 `memory:chat:`，不设过期。
- 归档：`appendExchange` 在每轮流式响应完成后调用，用 `RPUSH` 原子追加 `UserMessage + AiMessage` 两条消息，并更新 `memory:index:{userId}`；不再“读整个 JSON → 追加 → 写回”，多实例下也不会互相覆盖。
- 归档上限：`LTRIM` 保留最近 `hmdp.memory.archive-max-messages` 条（默认 2000），防止 Redis 内存无限增长；如需永久留存，可异步落 MySQL/对象存储。
- `deleteMessages` 是空实现，不提供主动删除；归档通过 `LTRIM` 控制保留条数。
- 历史列表：`listConversations` 按 ZSet 倒序取 memoryId，再读归档，生成首条用户消息（截断 40 字）、最后一条消息、消息数（`LLEN`）、更新时间。
- 历史详情：`getConversationMessages` 只返回 `UserMessage`/`AiMessage`，校验归属时同时兼容 `user:{userId}` 与 `user:{userId}:{sessionId}` 两种格式。

### 3. RAG：Redis 向量库 + 启动导入 + 意图路由

- 依赖：`langchain4j-community-redis-spring-boot-starter`，配置 `langchain4j.community.redis.enabled: true`，Redis `16379`，向量维度 `1024`（`text-embedding-v3`）。
- 启动导入（`CommonConfig.store`）：
  1. 检查标记键 `rag:content:ingested`；存在则直接复用 Redis 向量库；
  2. 不存在则 `ClassPathDocumentLoader.loadDocuments("content")` 加载 `content/hmdp.sql`；
  3. `DocumentSplitters.recursive(500, 100)` 切分；
  4. `EmbeddingStoreIngestor` 用 `text-embedding-v3` 向量化并写入 `RedisEmbeddingStore`；
  5. 写入标记键，避免每次重启重复导入。
  - 重建知识库：删除 Redis 的 `rag:content:ingested` 后重启（换 Embedding 模型/维度时也要重建）。
- 检索（`CommonConfig.contentRetriever`）：`minScore=0.5`、`maxResults=3`；外层做**意图路由**：
  - 业务意图（查商家/优惠券/预约/到店等）→ 不走向量检索，强制模型调用工具查 MySQL；
  - 知识意图（饮食推荐、休闲玩乐、平台规则等）→ 走向量检索；
  - 路由先走高频规则命中，再交给轻量意图分类（可配置开关），不再只靠关键词 `contains` 判断，减少误判。
- 当前 `content` 目录只有 `hmdp.sql`，RAG 的知识主要是表结构/业务字段；泛化推荐更多依赖模型自身知识。要增强推荐类问答，可往 `content` 放商家介绍、菜品、攻略等文档后重建。

### 4. Function Calling 工具

`@AiService` 显式装配三个工具 Bean：

| 工具类 | 方法 | 作用 | 数据来源 |
| --- | --- | --- | --- |
| `ShopTool` | `findShop(shopName)` | 按名称/关键词模糊查商家，返回列表 | `tb_shop.name like %keyword%` |
| `VoucherTool` | `findVoucherByShopName(shopName)` | 查商家优惠券；精确匹配失败且模糊唯一时使用模糊结果 | `tb_voucher` + `tb_seckill_voucher` |
| `VoucherTool` | `findVoucherByUserPhone()` | 查**当前登录用户**已领优惠券，不再接收手机号参数 | `tb_voucher_order.phone` → `tb_voucher`（`IN` 批量） |
| `ReservationTool` | `addReservation(name, communicationTime, shopName)` | 新增到店预约，手机号从登录态取 | `reservation` 表 |
| `ReservationTool` | `findReservation()` | 查**当前登录用户**的预约单，不再接收手机号参数 | `reservation` 表 |

- 预约时间格式约定为 `yyyy-MM-dd'T'HH:mm`，工具内先校验格式再 `LocalDateTime.parse`，解析失败返回友好提示而不是抛异常。
- 系统提示词 `system.txt` 规定：预约必须收集姓名、时间、商家；不得编造；每条用户消息末尾附带当前登录手机号供模型确认，但**工具查询主体从服务端请求上下文取**，模型不需要也不允许通过工具参数指定手机号。
- 用户券查询：先查 `tb_voucher_order` 得到 voucherId 列表，再用 `IN` 一次批量查 `tb_voucher`，过滤空值；不再循环单条查询（N+1）。
- 预约校验：姓名非空、手机号格式、时间未过期、商家存在（精确或模糊唯一）、同一手机号+商家+时间未重复预约；校验失败返回具体原因。
- `addReservation` 返回成功/失败结果（成功时带预约单号），模型可以据此准确回复用户；`findReservation` 只查当前用户，避免越权。
- 提示词中的品牌名当前为“伊岐优选”（旧版为“雅鉴生活志”），改品牌时需同步修改 `system.txt` 和前端文案。

### 5. 流式输出与前端

- 后端 `ConsultantService.chat` 返回 `Flux<String>`，`ChatController` 直接返回；Nginx `/api` 关闭 `proxy_buffering`、`proxy_cache`，`proxy_read_timeout 300s`，保证逐字推送。
- 前端 `nginx/html/hmdp/chat.html`：Vue2 + Element UI；首页 `index.html` 有“AI智能客服”入口。
- 功能：新对话、历史会话抽屉、打开页面自动恢复最近一次会话、快捷问题、流式读取 `response.body.getReader()`、简易 Markdown 渲染（加粗/列表/换行，先转义 HTML 防注入）。
- 请求走 `/api/chat`，`common.js` 统一加 `authorization` token，401 自动跳登录页。

### 6. 配置与启动

- `application.yml`：
  - MySQL `127.0.0.1:3307/hmdp`
  - Redis `localhost:16379`（业务 Redis 与向量库共用）
  - `langchain4j.open-ai` 指向阿里云百炼兼容接口，`qwen-plus` + `text-embedding-v3`
  - `hmdp.memory.context-size: 30`（给模型的窗口条数）
  - `hmdp.memory.archive-max-messages: 2000`（归档保留上限）
- 安全配置：API Key 已改为环境变量 `${DASHSCOPE_API_KEY}`，仓库中不再出现明文；生产环境关闭 `log-requests` / `log-responses`，避免日志泄露用户对话。
- 启动前确认 Redis 已加载 RediSearch 模块（向量检索依赖），并确保 `content/` 下有知识库文档。

## 面试可讲的设计点

1. **登录态绑定会话**：memoryId 由后端生成并带 userId，Controller 二次校验归属，解决“伪造 memoryId 读别人聊天记录”。
2. **手机号服务端绑定**：工具不再接收手机号参数，查券/预约的查询主体从请求上下文取；`@UserMessage("{{message}}\n当前用户手机号:{{phone}}")` 里的手机号只用于展示和确认，模型无法通过改参数查别人。
3. **窗口 + 归档分离**：窗口只保留最近 30 条给模型控制 token；归档完整保存历史供 UI 展示，避免“上下文裁剪导致历史丢失”。
4. **归档原子追加 + 上限**：归档用 Redis List 的 `RPUSH` 追加，天然避免多实例“读改写”覆盖；用 `LTRIM` 保留最近 2000 条，兼顾历史体验和内存成本。
5. **业务/知识意图路由**：业务数据问题不走向量检索，强制 Function Calling 查 MySQL；泛知识问题才走 RAG，避免 RAG 拿旧 SQL 片段胡答。
6. **查询批量化**：用户券查询先取 voucherId 列表，再 `IN` 一次查 `tb_voucher`，消除 N+1。
7. **预约全链路校验**：姓名、手机号格式、时间格式与是否过期、商家是否存在、是否重复预约都校验，失败返回具体原因，成功返回预约单号。
8. **知识库增量导入**：`rag:content:ingested` 标记 + 持久化 Redis 向量库，重启不重复 embedding，省 token/时间。
9. **流式链路**：WebFlux `Flux` + Nginx 关闭缓冲，前端 `ReadableStream` 逐段渲染。
10. **安全与清理**：越权返回 403/业务错误码；`afterCompletion`/`doFinally` 清理 ThreadLocal；API Key 环境变量化；生产关闭请求/响应日志。

## 可能追问

**Q：为什么窗口记忆和归档要分开？**
A：窗口是给模型的上下文，受 token 限制必须裁剪；归档是给用户看的历史，必须完整。两者用途不同，所以一个滚动覆盖、一个只追加。

**Q：归档为什么用 Redis List，而不是一个 JSON 字符串？**
A：List 的 `RPUSH` 是原子追加，多实例下不会像“读整个 JSON → 修改 → 写回”那样互相覆盖；读取用 `LRANGE`，控制长度用 `LTRIM`，也更适合只增不改的日志型数据。

**Q：归档会不会无限增长？**
A：不会。`LTRIM` 只保留最近 `hmdp.memory.archive-max-messages` 条（默认 2000）；如果业务要求永久留存，再异步落 MySQL 或对象存储，Redis 只保留热数据。

**Q：RAG 和 Function Calling 怎么分工？**
A：RAG 解决“资料里有的泛知识”，比如商家介绍、攻略；Function Calling 解决“数据库里的实时业务数据”，比如某商家的券、我的预约。业务数据不能靠向量检索，否则会拿到过期/不完整的 SQL 片段。

**Q：意图路由怎么判断？**
A：先走高频业务词规则（商家、券、预约等），命中直接判定业务意图；未命中的再交给轻量意图分类（可配置开关）。业务意图不检索，知识意图检索，闲聊直接回答。

**Q：怎么防止用户查别人的优惠券/预约？**
A：查券和查预约的工具都不接收手机号参数，查询主体从当前登录用户的请求上下文取；memoryId 也绑定 userId 并二次校验。模型即使被诱导改参数，也改不了查询主体。

**Q：预约重复或时间过期怎么处理？**
A：下单前校验商家存在、时间格式正确且晚于当前时间、同一手机号+商家+时间没有重复记录；失败直接返回原因给模型，由模型转述给用户，不写库。

**Q：知识库更新怎么做？**
A：把新文档放进 `content`，删除 Redis 的 `rag:content:ingested`，重启触发重新切分、向量化、写入 Redis 向量库。换 embedding 模型或维度时也必须重建。

**Q：怎么防止用户看别人的会话？**
A：memoryId 由后端生成，格式含 userId；聊天和历史接口都校验当前登录 userId 与 memoryId 前缀一致，不一致返回 403/业务失败。

**Q：流式响应怎么实现？**
A：LangChain4j 返回 `Flux<String>`，Spring WebFlux 逐段写出；Nginx 关闭 `proxy_buffering`/`proxy_cache` 并延长读超时，前端用 `fetch` 的 `response.body.getReader()` 边读边渲染。
