## 秒杀方案演变（可打印版补充）

为满足库存不超卖、一人一单且高性能，用户下单请求的处理方案经历了以下演变：

1. `update` 时 `where` 条件带上 `stock > 0`，保证库存不超卖。
2. 悲观锁（`synchronized`，适用于后端单机部署）+ 查数据库订单，保证一人一单。
3. 分布式锁（SetNX 实现，适用于后端集群部署）+ 查数据库订单，保证一人一单。
4. 分布式锁（Redisson 实现，适用于后端集群部署）+ 查数据库订单，保证一人一单。

但上述流程仍存在大量查询数据库、`update` 库存热点行锁竞争、分布式锁等问题，性能差，无法抗住高并发。

5. 秒杀优化：把下单资格判断移到 Redis 中完成（前提是把库存信息和订单信息都存入 Redis），利用 Redis 单线程执行命令 + Lua 原子性，仅靠 Redis 就能满足库存不超卖和一人一单。
6. 流程优化：同步改异步，下单后的扣减库存和生成订单放到消息队列消费者中完成。

## 秒杀防超卖与一人一单

是这样的， 我先说一下背景

1. 背景阐述

平台上商家可以发布一些折扣力度很大的优惠券， 这种优惠券是某个时间点限量供应的，所以在这个时间点会有比较大的流量进入，也就是一个秒杀场景，必须要保证的是在高并发的情况下， 防止库存超卖， 以及这种优惠券是限制每位用户只能购买一次。即防库存超卖和一人一单。

2. 问题剖析

其实防库存超卖和一人一单，要达到目的， 其实我们可以理解为只需要做好校验，校验用户是否有

资格下单， 如果库存不足或者用户已经下过单，则此时可认为用户是没有资格下单，拒绝请求。反之用户有资格下单则进行后续流程。

3. 方案构思

那我们如何做这个校验呢？首先很容易想到的方案是：

- 针对一人一单， 去数据库查用户是否已经下过单， 如果查到用户对应优惠券的订单，说明已经下过单，则拒绝请求。这个过程中为了防止同一个用户发起多个下单请求， 还需要使用分布式锁保证并发安全。

- 针对库存是否超卖， 只需要在减库存时， 即 update 库存的时候应该加上 where 库存 > 0 , 自然不会超卖。

但是在高并发的情况下，大量的请求 查询数据库和尝试更新数据（update是需要给记录加锁的，存在锁竞争）， 并且还使用了分布式锁，使得整个秒杀业务的性能受到很大影响。

我使用 JMeter 测试 QPS 1000， 200个库存的情况下， 平均响应时间是500ms， 比较慢

因此，我认为需要进行优化的，进行方案的改造，第一， 我不想因为 下单资格的判断 让MySQL数据库去承载高并发的查询和更新，那我觉得可以在Redis中完成用户下单资格的判断。

第二， 既然使用了Redis，那么我联想到 Lua 正好是原子性的， 可以解决一人一单的并发安全问题，也就不再需要使用分布式锁。

也就是说我把下单资格的判断 （防止库存超卖和一人一单） 在Redis的Lua脚本中完成

那么前提呢？就需要把 优惠券库存信息和订单信息 存储Redis里

- 存储在Redis的优惠券库存信息包括： 优惠券的库存、优惠券开始秒杀时间和结束秒杀时间

  - 使用 String 即可， key：业务前缀+优惠券的ID value：优惠券库存信息对象

  - 当想要校验库存是否充足时， 只需要判断Redis中的库存是否大于0，

  - 同时 当已判断用户有下单资格后，下单成功，也需要将Redis库存-1，相当于在Redis中预减库存

  - 这样， 只要Redis的库存减到0，后续的请求都会被拒绝，库存一定不会超卖（Redis单线

程执行）

- 存储在Redis的订单信息：其实只需要记录 优惠券被哪些用户购买过

  - 使用 Set 数据类型即可， key是：业务前缀+优惠券的ID value是：所有购买过该优惠券的用户ID

  - 当想要校验一人一单时， 只需要判断对应优惠券key的value中是否已有该用户ID， 如果已有说明购买过，拒绝请求

  - 同时， 当已判断用户有下单资格后，下单成功，也需要将该用户ID记录到该key的集合中。

  - 这样，就做到了一人一单

- 所以此时下单资格的判断（即达到库存不超卖、一人一单） 就完全不需要涉及MySQL数据库，都是在Redis中完成， 因为Redis是基于内存的， 因此大大提高了秒杀业务的性能。

修改后：JMeter 测试 QPS 1000， 200个库存， 平均响应时间是176ms，性能提高64.8%

响应时间受限于服务器的性能， 因为是本地运行的

4. 复盘总结

所以总结一下，秒杀场景非常重要的是要保证库存不超卖和一人一单。为了保证这两点， 即用户是否有资格下单， 一开始可能想到查询数据库、分布式锁等等，但是高并发场景下的秒杀， 需要高性能。所以使用Redis额外的存储库存信息、订单信息， 以此达到高效的用户下单资格的判断， 实现库存不超卖和一人一单

#### 常见面试题

1. 使用Set存储购买过优惠券的用户ID， 扩展一下， 如果是一人两单或一人N单呢？用Set还能做到吗？

**答**：Set 数据类型 只能记录用户 "是否购买过"， 无法记录 "购买了几次"。因此可以使用 Hash每个优惠券创建一个Hash结构

- Key 是：业务前缀+优惠券的ID

- Field：用户ID 作为字段名

- Value：该用户对该优惠券的当前已购买数量（甚至可以扩展，也记录下订单号、支付状态）此时只需要校验Value用户购买的数量即可完成一人N单的需求

2. 如果某个券允许购买的用户量很大， 用Set或Hash存储该券的订单数据， 会不会造成大Key？答：大Key是指 Value体积过大 （如String类型 > 2MB， Hash/List元素>5000个） 的Key

从业务上来讲， 一般情况下，一次秒杀活动中，针对单个优惠券，不会提供大量的库存， 即存在大Key的可能性较小

但如果真的有某个券的库存很多， 导致产生大Key，解决的方案是拆分大key为多个小key， 目前其实不会出现大Key的情况。备注：秒杀资格判断 (库存是否充足和校验一人一单) 编写 seckill.lua 脚本：（注意注释）

```lua
-- 优惠券id
local voucherId = ARGV[1];
-- 用户id
local userId = ARGV[2];

-- 库存的key
local stockKey = 'seckill:stock:' .. voucherId;
-- 订单key
local orderKey = 'seckill:order:' .. voucherId;

-- 判断库存是否充足  get stockKey > 0 ?
local stock = redis.call('GET', stockKey);
if (tonumber(stock) <= 0) then
-- 库存不足， 返回1
return 1;
end

-- 库存充足 ，判断用户是否已经下过单  SISMEMBER orderKey userId
if (redis.call('SISMEMBER', orderKey, userId) == 1) then
-- 重复下单， 返回2
return 2;
end

-- 库存充足 ，没有下过单，扣库存 、下单    注意这两行是必须要做的
redis.call('INCRBY', stockKey, -1);   -- Redis中预减库存
redis.call('SADD', orderKey, userId);  -- 记录这个人买过优惠券，也就是在这里其实可以改成Hash结构，记录下更多的信息，例如订单号 、支付状态等等，后续也可以用到
-- 返回0，标识下单成功
return 0;
```

## 秒杀流程优化

是这样的， 我先说一下背景

1. 背景阐述

平台上商家可以发布一些折扣力度很大的优惠券， 这种优惠券是某个时间点限量供应的，所以在这个时间点会有比较大的流量进入，也就是一个秒杀场景，在判断完毕用户有资格下单后，就会扣减MySQL的库存、生成订单

2. 问题剖析

在秒杀这个高并发的场景下， 扣减库存、生成订单， 其实是两次MySQL数据库操作，使得整个秒杀业务的性能受到很大影响。

3. 方案构思

这其实是一个同步流程， 判断资格、扣减库存、生成订单。

但是其实在判断完用户有资格下单 (库存不超卖、一人一单) 后，就意味着用户下单成功、秒杀成功

至于MySQL的库存扣减和订单生成， 完全可以异步的来做。

因为在之前已经把库存信息和订单信息存在Redis中了， 即使MySQL的库存和订单延迟更新也没有关系。

我们可以在判断用户有下单资格后，发送一个Kafka消息， 另外启动一个Kafka消费者监听消息，在消费者的逻辑内去扣减库存、生成订单。通过同步变异步，提高秒杀场景的并发性能。

并且， 如果以后业务有所扩展，例如用户下单成功后， 需要 额外的做一些事情(例如通知用户下单成功)，也可以放到Kafka消费者里去做， 而不是不断的新增在秒杀的同步流程中。

4. 复盘总结

所以总结一下，秒杀场景可能原来是同步的流程执行很多的事情，但是秒杀其实就是确定下来哪些用户可以购买，所以为了提高秒杀场景的并发性能， 我们可以在秒杀接口中就只做核心的事情：确定好哪些用户可购买就可以了， 而可以延迟做的（例如更新MySQL的库存、生成订单）， 完全可以异步的去做。

#### 常见面试题（2）

1. 你这里使用Kafka是什么语义？

**答**：最少传递一次——对应消息不丢失 At Least once 对于消息重复传递不敏感的场景

2. 如果重复消费消息， 会不会对业务有所影响？

**答**：这里在确定用户符合下单资格后就会生成一个唯一的订单ID， 而发送的Kafka消息中是携带着这个唯一的订单ID的，那么消费者接收消息后，就会去创建订单，也就是写入一条数据库记录， 而如果是重复消费的话，那么第二次及后续的消费都会写入数据库记录失败， 因为订单ID是主键唯一的， 如果是因为订单ID重复而导致创建订单失败，证明是重复消费，那么后续的流程也就不用再走了，所以即使重复消费消息也不会对业务有影响。

**答**：首先这场秒杀的一个核心要求：一人一单和库存不超卖， 是由 Redis 存储库存和订单信息，使用 Lua 完成用户下单资格判断 来保证的。 所以秒杀的核心要求其实是不受影响的。其次呢，如果消息丢失了， 其实只是MySQL中的库存信息不正确、以及用户的订单记录没有及时生成。也是数据一致性的问题

此时完全可以设计一个兜底策略。设置一个在秒杀结束后执行的定时任务， 去检查Redis的库存信息和MySQL的库存信息是否一致，检查订单是否都正常生成。如果有异常情况， 即可修复。

其实就是一个对账的思想/策略，也就是说上面其实可以不用Set存储购买过优惠券的用户ID， 而是

像前面说过的用Hash， 这样在最后定时任务可以去查Redis中的订单数据和MySQL中的订单数

据， 进行比对验证。如果一致就没问题， 如果不一致，那么可能是丢消息了或者系统执行异常了。可能需要人工介入排查。

7. 如果用户支付后订单记录还没生成怎么办？

**答**：用户支付本身不依赖于数据库的订单记录。我们后台在确定好用户具有下单资格后，生成唯一订单ID，然后是会调用第三方的接口去生成支付凭证信息， 给到前端后， 前端就可以拉起支付页

面，用户已经就可以支付了，用户支付完成后， 我们后台服务收到支付回调提示用户支付成功，此时我们想要去修改订单状态， 如果发现数据库中并没有此订单，那么证明有可能消息延迟了或者丢失了，此时可以去生成对应的订单。

## 秒杀压测：改造前后

压测

### 改造前

在 "没有引入消息队列异步处理秒杀流程" 和 “没有使用lua判断库存和一人一单" 的情况下的流程是：

1. 查询秒杀券信息 (一次MySQL查询数据)

2. 秒杀券的生效时间校验

3. 判断库存是否充足

4. 为正确校验一人一单， 需要先加Redisson分布式锁 （用户维度的锁）（一次加锁操作）

5. 查询是否存在用户订单记录 (一次MySQL查询数据)

6. 扣减库存（一次MySQL热点行的更新）

7. 创建订单（一次MySQL新增数据）

可以看到一次请求中有 两次MySQL查询、一次分布式锁加锁、一次MySQL热点行的更新、一次MySQL新增数据

一、5 个操作的耗时排名（从快 → 最慢）

1. Redisson 分布式锁加锁（第 4 步）

耗时：0.5ms ~ 2ms Redis 纯内存操作

2. 查询秒杀券信息（第 1 步）

耗时：1ms ~ 10ms 简单主键查询， MySQL 走索引， 非常快。

3. 查询用户订单记录（第 5 步）

耗时：1ms ~ 10ms 也是索引查询， 速度同样很快。

4. 创建订单（第 7 步）

耗时：10ms ~ 30ms 插入一条订单记录， 有事务，但不是热点， 速度尚可。

5. 扣减库存（第 6 步） 【绝对最慢 ・ 性能杀手】

耗时：50ms ~ 500ms+， 甚至直接卡死、超时

为什么它是最慢的？——MySQL 热点行锁竞争（最严重）

1000 个线程同时执行同一条 SQL：

```sql
UPDATE seckill SET stock = stock - 1 WHERE id = ?;
```

所有请求都在抢同一行数据的行锁。结果：

- 只有 1 个请求能拿到锁执行更新

- 其他 999 个全部阻塞等待

- 等待时间 = 前面所有请求执行时间总和这是秒杀里最主要的性能瓶颈。

### 改造后

### Ack 模式

有三种 Ack 模式：

1. auto-commit（自动提交）： 消费者在收到信息后立即向 broker 发送 Ack 信息。

2. after-processing（处理后）： 消费者只有在成功消费消息后才向 broker 发送 Ack 信息。

3. manual（手动）： 消费者在收到具体指令后才向 broker 发送 Ack 信息。Ack 模式决定了消费者如何处理从 Kafka 集群读取的消息。

我们可以配置几种 Ack 模式：

1. AckMode.RECORD：after-processing（处理后） 模式， 消费者会为其消费的每条信息发送 Ack消息。

2. AckMode.BATCH：手动模式， 消费者为一批消息发送确认， 而不是为每条消息发送 Ack。

3. AckMode.COUNT：手动模式， 消费者会在消费完一定数量的消息后发送 Ack 消息。

4. AckMode.MANUAL：手动模式， 消费者不会对其消费的报文发送 Ack 消息。

5. AckMode.TIME：手动模式， 消费者会在一定时间后发送 Ack 消息。

要在 Kafka 中实现消息处理的重试逻辑， 我们需要选择一种 AckMode。

这种 AckMode 应能让消费者向 broker 指出哪些特定消息已被成功消费。

这样， broker 就可以将任何未确认的消息重新发送给另一个消费者。

可以选择 AckMode.RECORD 模式

我们不应将确认模式（ack mode） 设置为 AckMode.BATCH 或 AckMode.TIME， 因为消费者将一次性确认多个消息。如果在处理消息时发生错误， 消费者不会重新投递批处理或时间窗口中的所有消息给自己。因此重试策略无法正确处理错误。

### 可重试异常和不可重试异常

我们可以指定哪些异常可重试， 哪些不可重试。

修改 ErrorHandler：例如设置 SocketTimeoutException 被认为是可重试的， 而 NullPointerException 被认为是不可重试的。

这里只是举例， 具体哪些异常需要被重试， 由具体业务去定义

这时候，会不会 有重复下订单、重复扣减库存的问题存在？

既然我们选用了 消息队列 保证最终一致性， 那么就可能会有多次重试的情况出现此时一定要保证的是 幂等性——即使多次重试， 最终结果是正确的

幂等性翻译到这个场景下， 就是即使消费重试多次， 也只会创建一个订单， 扣减一个库存

具体如何保证幂等性呢？保证幂等性的方法有很多。

例如 一个方法内要执行 A、B、C 三个操作第一次执行，A成功， B失败， 方法结束

进行重试，此时 A因为成功过了， 即使再执行A， 这时候要设计一个机制保证对结果不会有影响， 后面才执行B和C

有一种保证幂等的方法， 其本质就是要记录下你某个操作是否执行成功过

例如 A 就是扣减库存， 如果重复执行 A， 如果不加控制， 那么就会重复扣减库存因此， 如果扣减过一次库存， 就记录下来， 某订单号扣减过库存。

等到重试时， 先去看该订单号是否扣减过库存。如果扣减过， 那么扣减库存的操作就不执行了这样， 即使再重试多少遍，A 操作 可以保证是幂等的

举另外一种例子， 有一种操作， 它天然的就是幂等的

比如创建订单时(写入数据库记录)， 这时候要写入订单号字段， 订单号字段是唯一的， 有唯一索引因此创建订单的操作 如果某一次创建成功后。即使因为其他操作失败， 导致整个消费方法重试时创建订单的操作即使被重试多遍， 也不会创建多个订单， 因为重试多次时， 订单号是同一个

无法创建多个订单号一样的记录， 因为有唯一索引

```java
   }

  public static PurchaseResult fail(String message) {
       PurchaseResult result = new PurchaseResult();
       result.setSuccess(false);
       result.setStatus("FAILED");
       result.setMessage(message);
       return result;
   }
```

### 使用策略模式的好处

避免庞大的 if-else 逻辑符合开闭原则

- 对扩展开放：新增优惠券类型时， 只需添加新策略， 无需修改现有代码

- 对修改关闭：现有策略逻辑不会被意外破坏职责单一，易于维护

- 每个策略只关心自己的业务逻辑，代码更清晰、更易测试

这种设计让系统具备了很好的弹性， 能够轻松应对业务的各种变化和扩展需求。

## 秒杀场景下如何增加库存

秒杀的方案，是扣减库存

- Redis 预扣减库存 （借助Lua脚本的原子性， Redis执行命令的单线程特性）

- 发送 MQ 消息异步扣减 MySQL 库存

- 若消费失败借助重试机制重试，若失败次数达到重试最大次数，触发告警人工介入排查

在秒杀场景下如何增加库存，其实和 扣减库存 本质是相同的，只需要把扣减库存的方案照搬到增加库存上

- Redis 预增加库存（借助Lua脚本的原子性， Redis执行命令的单线程特性）

- 发送 MQ 消息异步增加 MySQL 库存

- 若消费失败借助重试机制重试，若失败次数达到重试最大次数，触发告警人工介入排查
