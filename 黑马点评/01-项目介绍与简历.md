## 简历撰写方法

### 前提和项目理解

对于简历上的项目

- 要把最熟悉的、最有含金量的内容写在前面

- 黑马点评的内容不少：登录、缓存、优惠券秒杀、点赞、好友关注、附近商铺地图搜索、用户签到、UV统计。但并不是要把所有内容都写到简历上， 因为有些功能黑马点评的实现并不是一个足够好的方案 (例如登录会话保持等都不会写到简历上)，所以我们只选择一些精华写到简历上， 同时对其进行拓展优化。但是如果面试官问你这个项目就只有这些内容吗？你的回

**答**：不是的， 还有其他的内容(如上)，但是写在简历上的这些是我个人觉得做了一些优化或者考虑的比较多的一些工作。

- 写到简历上的每一个职责点，都需要为其准备一套话术。当面试官问到某一个职责点是怎么实现时， 自己要能够完整地流畅地把这个职责点的这套话术说清楚。即使换成其他项目，也是这么描述

话术的结构：

1. 背景阐述

2. 问题剖析

3. 方案构思

4. 复盘总结

对于项目：没必要追求项目多独特， 并不会因此而加分， 面试官对于项目的考察点， 是面试者对于项目的思考、理解。因此面试者只需要思考如何清晰的描述展现给面试官即可， 如何体现你的思考、理解。

和是什么项目没有关系，不论黑马点评还是外卖 (前提是要能通过简历筛选)

你可以和面试官承认：项目是网上的开源学习项目， 出于探索学习目的，没有上线，在我学习的过程中， 我有一些不同的想法和修改， 比如 力， 这才是面试官想看到的东西

你的简历上的项目每一个点都应该准备好，优化好表述。并不是多创新独特，但应该是考虑周到全面和完善的， 回答的条理清晰的。就是问题的回答框架

根据我个人的面试经验和腾讯字节实习经历， 我觉得大厂更看重的或希望的是学生的思维是考虑完善的， 周全的，条理清晰的， 自己的项目都能考虑周全，会给人比较靠谱的感觉，那么公司的项目一些需求给你做，也是比较放心的

### 为什么区分用户表和用户详情表

```sql
CREATE TABLE `tb_user` (
`id` bigint(20) unsigned NOT NULL AUTO_INCREMENT COMMENT '主键 ',
`phone` varchar(11) NOT NULL COMMENT '手机号码 ',
`password` varchar(128) DEFAULT '' COMMENT '密码，加密存储 ',
`nick_name` varchar(32) DEFAULT '' COMMENT '昵称，默认是用户id',
`icon` varchar(255) DEFAULT '' COMMENT '人物头像 ',
`create_time` timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间 ',
`update_time` timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间 ',
PRIMARY KEY (`id`) USING BTREE,
UNIQUE KEY `uniqe_key_phone` (`phone`) USING BTREE
) ENGINE=InnoDB AUTO_INCREMENT=1013 DEFAULT CHARSET=utf8mb4 ROW_FORMAT=COMPACT;
```

```sql
CREATE TABLE `tb_user_info` (
`user_id` bigint(20) unsigned NOT NULL COMMENT '主键，用户id',
`city` varchar(64) DEFAULT '' COMMENT '城市名称 ',
`introduce` varchar(128) DEFAULT NULL COMMENT '个人介绍，不要超过128个字符 ',
`fans` int(8) unsigned DEFAULT '0' COMMENT '粉丝数量 ',
`followee` int(8) unsigned DEFAULT '0' COMMENT '关注的人的数量 ',
`gender` tinyint(1) unsigned DEFAULT '0' COMMENT '性别， 0：男， 1：女 ',
`birthday` date DEFAULT NULL COMMENT '生日 ',
`credits` int(8) unsigned DEFAULT '0' COMMENT '积分 ',
`level` tinyint(1) unsigned DEFAULT '0' COMMENT '会员级别， 0~9级,0代表未开通会员 ',
`create_time` timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间 ',
`update_time` timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间 ',
PRIMARY KEY (`user_id`) USING BTREE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 ROW_FORMAT=COMPACT;
```

区分用户表和用户详情表本质是 垂直分表 策略，分离核心数据表与扩展数据表（字段不同）

那么在一些实际的业务场景中， 其实只需要访问核心数据表的字段，那么就不需要查询扩展数据表。

此时因为核心数据表的字段少，就能提高查询效率。场景：

- 登录时验证，查核心数据表

- 只要不在用户的详情页 之外的场景， 基本就只需要用户的名称、头像，所以都只需要查询核心数据表

### 查询某分类频道下的"商家列表信息"

操作流程：

1. 先点击某分类频道，例如美食、例如休闲玩乐等等， 这不同的分类频道对应着不同的 type_id

2. 此时查询出在分类频道下的商家。但其实还可以根据条件筛选，例如 评分、距离

3. 那么此时查询条件可能是 type_id、某范围距离内、评分排序 三者的结合

4. 点评中查询的方案是：

  - 先把商家数据存入RedisGEO中

  - 查询时， 先根据用户的位置去RedisGEO中查出附近范围的商户的id， 且是分页的，也就是说查出来的数据已经很少了， 一般是5-10条

  - 再去数据库根据id查出商户信息， 并根据评分进行排序

5. 这个过程中， 其实在数据库查询这一块已经很快了， 因为是根据主键id查询 5-10条数据再排序。所以这一块没有必要再建索引优化了

6. 如果是更复杂的查询怎么办(可以去看看大众点评的查询筛选非常复杂)，例如设施、服务、价格、优惠、用餐场景， 这种复杂的聚合查询， 一般都不再使用MySQL查询， 而是使用专门适配聚合查询的 ES， 即 Elasticsearch

### 优惠券表是怎么设计的

这里黑马点评是把 秒杀优惠券、普通优惠券 分开存储两张表，但是我个人觉得可以融合到一张表

因为秒杀优惠券里的字段， 完全可以迁移到普通优惠券里，例如普通优惠券也可以有库存、生效时间等

融合到一张表说起来也没那么麻烦

```sql
CREATE TABLE `tb_voucher` (
`id` bigint(20) unsigned NOT NULL AUTO_INCREMENT COMMENT '主键 ',
`shop_id` bigint(20) unsigned DEFAULT NULL COMMENT '商铺id',
`title` varchar(255) NOT NULL COMMENT '代金券标题 ',
`sub_title` varchar(255) DEFAULT NULL COMMENT '副标题 ',
`rules` varchar(1024) DEFAULT NULL COMMENT '使用规则 ',
`pay_value` bigint(10) unsigned NOT NULL COMMENT '支付金额，单位是分 。例如20 0代表2元 ',
`actual_value` bigint(10) NOT NULL COMMENT '抵扣金额，单位是分 。例如200代表2元',
`type` tinyint(1) unsigned NOT NULL DEFAULT '0' COMMENT '0,普通券； 1,秒杀券',
`status` tinyint(1) unsigned NOT NULL DEFAULT '1' COMMENT '1,上架; 2,下架; 3,过期 ',
`create_time` timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间 ',
`update_time` timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间 ',

-- 个人从秒杀优惠券迁移过来的  三个字段
`stock` int(8) NOT NULL COMMENT '库存 ',
`begin_time` timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '生效时间',
`end_time` timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '失效时间',

PRIMARY KEY (`id`) USING BTREE
) ENGINE=InnoDB AUTO_INCREMENT=12 DEFAULT CHARSET=utf8mb4 ROW_FORMAT=COMPA CT;
```

字段有 主键、关联的商家ID、库存、标题、使用规则、支付金额、抵扣金额、券的类型(普通券/秒杀券)、券的状态 (上架、下架、过期)、生效时间、失效时间、创建时间、更新时间

字段中， 支付金额单位是用分表示的

在项目中， 关于优惠券表的场景有

- 查看某个商家下面有哪些券，所以要根据 shop_id 商家ID 建立单列索引，提高查询效率

### 优惠券订单表是怎么设计的

字段有 主键、购买的用户ID、优惠券ID、支付方式(余额、微信、支付宝、银行卡)、订单状态
