## 未支付订单到期自动关闭

是这样的， 我先说一下背景

1. 背景阐述

在优惠券下单后，用户如果超过一定时间内仍未支付，那此时需要关闭订单， 并且释放库存

2. 问题剖析

这个问题的本质是我们需要检测用户订单的支付状态。

3. 方案构思

那如何实现超时订单自动关闭呢？我调研了常见的几种方案

- 方案一：每分钟执行定时任务：扫描MySQL数据库 取出未支付且超时的订单

  - 实现细节：

  - select * from orders where status = '未支付 ' and order_time < (当前时间-15分钟) 为(status, order_time)创建联合索引

  - update orders set status = '取消 ' where id = ? and status = '未支付 ' 另外如果状态更新成功，才会去增加库存， 否则不增加库存， 这里可能又有一个问

题， 如果订单状态更新为关闭，但是库存增加失败了怎么办，解决方案也可以引入消息队列异步增加库存，若失败则消息队列重试补偿

  - 优点是实现简单

  - 缺点是在数据量很大时可能会对数据库造成一定的压力，但只要创建好索引查询效率也很快

- 方案二：利用消息队列 (RocketMQ) 的延迟消息，在订单创建时发送延迟消息，在一定时间后，消息被消费关单

  - 优点：通过延迟消息， 我们就可以将系统解耦， 只需关注生产及消费消息即可

  - 缺点：

  - 大量无效调度：大部分的消息可能都是无效的， 因为这些消息对应的订单可能都是已支付。

  - 消息可靠性：尽管消息队列能提供相对可靠的消息投递，但在极端情况下， 消息丢失或重复消费依然可能发生。这会给订单的准确关闭带来风险， 如订单未关闭或多次错误关闭

- 方案三：利用 Redis 过期监听，为每个订单设置一个带TTL的key，并接收key过期消息执行关单操作

  - 实现细节：在 redis.conf 中，加入一条配置 notify-keyspace-events Ex 开

启过期监听，然后在代码中实现一个 KeyExpirationEventMessageListener，就

可以监听key的过期消息了。这样就可以在接收到过期消息的时候， 进行订单的关单操作。

  - 优点： 由于redis 的高性能，所以我们在设置key， 或者消费key 时， 速度上是可以保证的。

  - 缺点：

  - redis 自动过期的实现方式是：定时任务离线扫描并删除部分过期键；在访问键时惰性检查是否过期并删除过期键。

  - 也就是说， 由于redis 的key 过期策略原因， 当一个key 过期时， redis 从未保证会在设定的过期时间立即删除并发送过期通知， 自然我们的监听事件也无法第一时间消费

到这个key，所以会存在一定的延迟。实际上， 过期通知晚于设定的过期时间数分钟的情况也比较常见。

综合考虑， 是单体项目订单量不太大，所以使用了 方案一：每分钟执行定时任务：扫描MySQL数据库 取出未支付且超时的订单 实现未支付订单到期自动关闭的功能。

这里还可以进行优化， 由于定时任务的执行时间的不精确性，有些时候，订单可能已经超时了，但是用户还能查看到待支付的订单， 这就是因为分钟级的定时任务恰好还没有执行， 这时候， 其实可以在用户查看订单时（即返回订单列表时），检查一下订单是否超时， 这时候就把订单状态给他改成关闭，然后用户看到的订单就是已取消状态。这其实是一种被动关单的思想，被动关单就是当用户来查看时才去关闭超时订单。

4. 复盘总结

如果后续订单量太大，定时任务扫描MySQL数据库耗时很长，每分钟扫描数据库的方案不再适

用，也可以考虑引入消息队列的延迟消息来完成。同时我们应该设计一个兜底策略，假如少量的消息丢失， 我们可以 (每天凌晨 / 每隔N个小时) 跑一次定时任务， 批量将未支付的订单进行关闭。

#### 常见面试题

1. **问题**：会不会存在重复关闭订单， 重复增加库存， 相当于增加了额外的库存？

**答**：不会， 因为我们关闭订单是执行的SQL 其实是

```sql
update orders set status = '取消' where id = ? and status = '未支付'
```

如果状态更新成功， 我们才会去增加库存， 因为where条件加上了 status = '未支付'

即使有定时任务重复调度/消息重复消费， 这个状态更新成功只能执行一次，也就只释放一次库存

2. **问题**：如果订单状态设置为关闭， 但是库存增加失败怎么办？

**答**：引入消息队列异步增加库存，若消费者内增加库存失败，则消息队列的机制重试补偿， 多次重试依然失败则触发告警，人工介入排查原因修复

## 支付和关单的并发

是这样的， 我先说一下背景

1. 背景阐述

优惠券的逻辑中有 "支付回调" 和 "订单超时取消"

2. 问题剖析

如果一笔订单在 "超时取消" 的那一刻 "用户刚好付款" 了， 怎么办？

这种情况在正常的业务场景中是有可能出现的， 其实就是订单的支付和关单的一个并发问题

3. 方案构思

支付成功的回调 和 超时关单 在并发的场景下，都查询到订单的 状态为 "未支付"

此时后台对于 "支付成功的处理" 以及 "超时关单的处理"。这两者应当是一个成功， 一个失败

所以要保证并发场景下一个成功、一个失败。我觉得有两种方案

- 方案一：数据库乐观锁

  - 超时关单的处理中：查询出未支付状态的订单后，执行 update orders set status = '取消' where id = ? and status = '未支付'

  - 支付成功的处理中：查询对应订单确认状态是未支付后，执行 update orders set status = '已支付' where id = ? and status = '未支付'

  - 注意这两个SQL中的where条件中都加了 status = '未支付'， 这就能保证只有一个执行成功， 另外一个一定失败， 这就是乐观锁的方式。 （当然如果你要使用version版本号的方式去实现乐观锁也可以）

- 方案二： 一锁二判三更新

  - 对于状态的变更， 如果有并发场景， 常见的解决方式是一锁二判三更新， 即第一步先加分布式锁，锁住该订单， 第二步判断订单状态是否未支付，若是则第三步更新订单状态。

对于方案的选择：

- 第一， 其实就是乐观锁和悲观锁的选择，针对于订单支付和关单的并发问题， 其实它是小概率事件， 而乐观锁的应用 更适合这种 冲突少/小概率冲突 的场景

- 第二，在这里因为超时取消任务的执行，有可能是批量查询出大量的超时订单， 如果每个订单都需要走一锁二判三更新的一个流程的话，性能有所影响

综上，所以我选择了方案一数据库乐观锁的方案。

根据乐观锁避免了并发， 其实就是"订单支付成功"和"订单超时取消"两种状态的“争夺”

此时就会出现两种情况：第一种情况："支付成功的回调" 处理成功， "超时关单" 处理失败

- 这种情况很简单， "支付成功的回调" 处理成功，状态更新为“已支付”， "超时关单"必然处理失败，此时我们无需额外的处理，业务上是完全没有问题的。

第二种情况："超时关单" 处理成功， "支付成功的回调" 处理失败

- 这种情况就需要额外的处理了， 因为"超时关单" 处理成功，状态更新为"取消"， 而 "支付成功的回调" 处理失败，就是用户已经支付了钱，但是业务上支付却没有成功，订单却超时关闭

了。这时候钱怎么办，所以这时候如果发现订单被关闭了，那么就需要触发原路退回的流程，把钱给用户退回。

4. 复盘总结

所以总结一下， 我考虑到特殊场景下的订单支付和关单的一个并发问题，在数据库乐观锁和一锁二判三更新的两种方案中选择了数据库乐观锁解决并发问题， 并且考虑到， 如果是订单超时取消状态取胜，那么此时需要原路退钱。

#### 常见面试题（2）

1. **问题**：第二种情况： "超时关单 " 处理成功， "支付成功的回调 " 处理失败， 为什么一定要退款，不能让订单变成 "已支付状态 "吗？

**答**：在超时取消的任务中， 已经将订单状态更新为取消/关闭，与之伴随的逻辑还有 释放库存，也就说库存已经释放了，所以订单的状态一定不能直接变成"已支付"。 另外，订单的状态是 取消/关闭， 这其实在业务上应当是一个终止态，终止态再流转到其他状态并不合理。

这里说的是 "支付结果回调" 和 定时任务 两个处理逻辑的竞争。

因为定时任务的代码在上面已经有了， 而 "支付结果回调"其实也不怎么需要代码参考了， 具体就是

对接第三方支付系统的代码，提供一个接口供第三方调用通知我们， 我们在接口里进行处理， 包括如果要执行退款也是调用第三方支付系统的一个接口而已。没什么好说的。所以只需要清楚两个逻辑里做什么事情， 怎么做， 流程是怎么样的， 竞争关系是怎么样的就好。

超时关单的处理中需要做哪些事：

- 查询出未支付状态的订单后，执行 update orders set status = '取消' where id = ? and status = '未支付'

- 释放库存

支付成功回调的处理中需要做哪些事：

- 查询对应订单确认状态是未支付后，执行 update orders set status = '已支付' where id = ? and status = '未支付'

- 发放对应的优惠券给用户

- 可扩展，例如发放积分等等

#### 1. 自定义限流注解 RateLimiter

自定义限流注解：包含限流key前缀、时间窗口大小、时间窗口内允许的请求数、限流提示信息、限流维度 window时间窗口大小 和 limit时间窗口内允许的请求数 这两个参数 取决于自己的系统的并发量

- 例如可以设置 1s 内 允许 100 个请求，则QPS最高是100

- 例如可以设置 0.5s 允许100个请求，则QPS最高是200

```java
package com.hmdp.limiter.annotation;
import java.lang.annotation.*;
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
@Documented
public @interface RateLimiter {
  /**
    * 限流key前缀
    */
   String key() default "rate_limit:";
  /**
    * 时间窗口大小（秒）
    */
   int window() default 10;
  /**
    * 时间窗口内允许的请求数
    */
   int limit() default 20;
  /**
    * 限流提示信息
    */
   String message() default "系统繁忙，请稍后再试";
  /**
    * 限流维度（ 默认按方法限流）
    */
   LimitType type() default LimitType.METHOD;
  enum LimitType {
      /**
        * 按调用方IP限流
        */
       IP,
      /**
        * 按用户ID限流
        */
       USER,
      /**
        * 按方法限流/全局限流（ 默认）
        */
       METHOD
   }
}
```

> 原文不一致：注解枚举只定义了 `IP / USER / METHOD`，但后面的示例使用 `RateLimiter.LimitType.GLOBAL`；此处按原文保留，实际运行需补齐枚举值。

#### 3. 滑动窗口限流Lua脚本 limiter.lua

```lua
local key = KEYS[1]
local window = tonumber(ARGV[1]) -- 时间窗口 (单位为秒)
local limit = tonumber(ARGV[2]) -- 时间窗口内限制的次数
local now = tonumber(ARGV[3])  -- 当前时间(单位为毫秒)
-- 校验传进来的参数是否为空 ,若为空直接返回错误
if not window or not limit or not now then
 return redis.error_reply("Invalid input parameters")
end
window = window * 1000  -- 单位由秒->毫秒
-- 删除超出时间窗口的数据
-- Redis命令ZREMRANGEBYSCORE: 从有序集合中移除指定分数区间的成员 。  删除所有分数在[0,now-window) 的请求记录
-- now是当前时间戳,window是时间窗口 , 0是最小分数,now-window是时间窗口外最大的分数 ,这样就能删除超出窗口的元素
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
-- 获取当前窗口内的请求数量
-- Redis命令ZCARD: 返回有序集合中成员的数量 ,因为已经删除了超出时间窗口的元素，所以直接返回集合的成员数量即可获取当前时间窗口的请求数量
local current = redis.call('ZCARD', key)
-- 若"当前时间窗口内的请求数量" 小于  "时间窗口内限制的次数"
if current < limit then
 -- 添加当前请求（使用毫秒时间戳+随机数作为member,时间戳作为score）
 math.randomseed(now)
 local random = math.random(1000000)
 redis.call('ZADD', key, now, now .. '-' .. random)
 -- 更新过期时间
 redis.call('EXPIRE', key, window / 1000)
 return current + 1
else
 -- 若"当前时间窗口内的请求数量" 大于等于  "时间窗口内限制的次数", 则应该限制本次请求 ,返回  0,表示限流
 return 0
end
```

关键点在于Lua脚本中实现的滑动窗口限流算法

利用Redis的ZSet数据类型， 首先传递进Lua脚本的参数为

- 限流键名key (不同的接口/资源，使用不同的key，不同的维度，也要使用不同的key)

- 时间窗口大小 window

- 限流阈值 limit 在时间窗口内允许访问的次数

- 当前时间戳 now进入Lua脚本的逻辑

1. 移除时间窗口之外的数据 redis.call('ZREMRANGEBYSCORE', key, 0, now - window)

2. 获取当前时间窗口内的已请求数量 redis.call('ZCARD', key)

3. 判断当前时间窗口内的已请求数量 是否 小于 limit 限制次数

  - 若小于，则把本次请求加入key中， 以当前时间戳为分数score， 以当前时间戳+随机数为成员member，更新过期时间，本次请求可放行，后续可执行业务逻辑

  - 若大于或等于，则返回本次请求应该限流

5. 常见面试题

1. **问题**：什么是滑动窗口限流算法

**答**：滑动窗口限流是一种流量控制策略，用于控制在一定时间内允许执行的操作数量或请求频率。它的工作方式类似于一个滑动时间窗口，在窗口内允许的操作数量是固定的， 窗口会随着时间的推移不断滑动。

![滑动窗口随请求推进而移动](file:///D:/Java/data/黑马点评/04-拓展模块/04-06-e649b486.png)

首先需要把时间划分成多个连续的时间片段，每一个片段都有一个固定的时间间隔， 如1s、1h等。

然后再定义一个时间窗口， 比如10s， 随着时间的推移， 这个窗口不断的向右移动。为了实现限流的功能， 我们通常需要定义一个计数器， 统计时间窗口内的请求数。

当时间窗口移动时， 需要把上一个时间片段中的请求数减掉， 当有新的请求或操作到达系统时， 系统会检查窗口内的计数是否已满。如果计数未满，请求被允许执行； 如果计数已满，请求被拒绝或进入等待队列， 或执行其他限流操作。

滑动窗口限流的主要优点是可以在时间内平滑地控制流量， 而不是简单地设置固定的请求数或速

率。这使得系统可以更灵活地应对突发流量或峰值流量， 而不会因为固定速率的限制而浪费资源或降低系统性能。

滑动窗口限流可以在分布式系统、API服务、网络通信等各种应用场景中使用， 以确保系统的稳定性和可用性， 防止过多的请求或操作对系统造成负担或崩溃。

2. **问题**：为什么要用Lua脚本

**答**： 假如不使用Lua脚本，会有并发问题，例如两个用户请求先后执行Redis命令ZCARD， 返回当前时间窗口内的请求数均为99，然后这两个用户请求都认为不应该限流，那么就都放行了，但实际上限制数量是100， 这两个请求应该有一个被拦截下来，所以限流逻辑内的 "查看当前时间窗口的请求数量"和"判断请求数量与阈值的大小比较"和"添加当前请求"， 这几个操作必须连贯，有原子性的要求，所以使用Lua脚本， 另外使用Lua脚本同时也能减少多次网络往返，提升性能

滑动窗口算法实现限流，将时间窗口细分为多个小窗口， 统计滑动窗口内的总请求数。随着时间推移， 窗口向前滑动， 旧的小窗口数据过期。

- 第一它可以提供精确的控制。

- 第二滑动窗口通过限制每个时间窗口内的请求数量， 通常能够有效应对脉冲攻击。即使攻击者试图在短时间内发起大量请求， 由于每个时间窗口内的请求数是有上限的， 滑动窗口可以有效抑制这种突发流量， 防止恶意脉冲攻击。

参考：万字解析三大限流算法： 时间窗口， 令牌桶， 漏桶-CSDN博客

当然这些功能在传统的项目中用户也是非常容易去操作的，但是这个智能AI顾问是否有必要存在呢

- 第一， 一些功能可能因为路径繁杂，对于中老年群体是不友好的，他们可能找不到这个入口，而智能AI客服就能够快速帮助这些群体去达到目的

- 第二，智能AI客服因为有大模型的能力， 它可以扩展出更多新的功能或玩法，例如结合具体商家的信息再去给用户饮食推荐或玩乐安排等等

3. 方案构思

为了实现智能AI客服， 首先我就去学习了LangChain4j这个Java调用大模型的工具框架， 其中印象比较深刻的是RAG和FunctionCalling

- 例如像用户的一些问题， 可能要结合平台的一些文档或数据才能够回答， 这时候就需要使用

RAG，

  - 我需要把平台的文档或数据向量化存储到RAG知识库(向量数据库)

  - 当用户发出问题后，Java服务会先根据用户的问题从知识库中检索对应的知识片段

  - 得到知识片段后，Java服务需要结合用户的问题以及知识库中检索到的知识片段组织要发送给大模型的消息

  - 大模型接收到消息后会同时根据用户的问题、知识库检索到的知识片段以及自身的知识储备，生成对应的结果响应给Java服务， 最终再返回给用户

![用户、AI 应用、大模型与数据流](file:///D:/Java/data/黑马点评/04-拓展模块/04-15-ed01d6ee.png)

- 例如像前面说到的查询商家的信息，查询商家的优惠券信息， 可能我一开始的想法是这些数据是不是也要向量化存储到RAG知识库呢？但是如果是预约到店消费服务呢， 这个功能本质上是要向预约表里插入一条数据，所以RAG知识库就不能实现了，所以更好的做法其实是用

FunctionCalling 函数调用

  - 首先我需要准备一些工具方法，例如查询商家信息、新增预约信息等等的方法

  - 当用户发出问题后，Java服务需要组织提交给大模型的数据， 而这些数据中需要描述清楚Java服务中有哪些函数能够被大模型调用。每一个函数的描述都包含三个部分， 方法名

称、方法作用、方法入参。

  - 当Java服务把这些数据发送给大模型后，大模型会先根据用户的问题以及上下文拆解任务，从而判断是否需要调用函数。如果有函数需要调用，则把需要调用的函数的名称， 以及调用时需要使用的参数准备好一并响应给Java服务。

  - Java服务接收到响应后需要执行对应的函数，得到对应的结果，接下来把得到的结果和之前信息一块组织好再发送给大模型。最后再响应给用户。

#### 话术/逐字稿（2） - 常见面试题

1. 使用Redis支持会话记忆是什么意思？

**答**：大模型不具备记忆能力，每次会话都是独立的。要想让大模型产生记忆的效果， 唯一的方法就是把之前聊天的内容和新的内容一起发送给大模型。也就是说我们需要存储一个会话的互相发过的消息。例如

- 用户发送消息A1，Java服务存储消息A1，发送消息A1给大模型

- 大模型响应消息B1，Java服务存储消息B1，发送消息B1给用户

- 用户发送消息A2，Java服务存储消息A2， 发送消息 [A1、B1、A2] 给大模型

- 以此类推

那么这个会话的消息是需要存储的，且不能只存储在内存里， 否则如果后端重启就消失了，所以需要持久化，所以存储在Redis中（String存储即可），有效期设置一天足够
