## 1. 线程池进阶教程

### 1.1 线程池的应用与踩坑

#### 1.1.1 应用

- **批量处理任务的并发处理**
  - 适用于任务量大、总耗时长、任务间相互独立的情况
  - 深入学习可关注 Fork/Join 框架、CompletableFuture 等并行框架

- **单接口 RT（响应时间）优化**
  - 适用于单接口下游调用多、下游 RT 长的典型高并发场景
  - 注意：线程池不是银弹，实际效果取决于具体场景

**单接口 RT 优化详细说明：**

当下游调用耗时影响了整个接口的耗时，存在典型的高并发场景："单接口下游调用多"或"多端口串行调用"。其常见的解决方案是：将多个下游调用并行执行，从而降低接口耗时，有效解决多次重复调用的问题。

**注意：线程池不是银弹**

- 生产者（调用端）比消费者（下游）快很多时，线程池并不是越多越好，此时线程池也会成为瓶颈。
- 线程池不是万能药，并且线程池内部的资源是可以互相竞争的。在当下游服务不稳定时（一般会出现 QPS 突刺），上游服务如果没有做限流，而是将请求都打满至线程池，会导致下游的服务挂掉。
- 上游服务也会出现问题，因为线程池只处理下游的调用。然而，在实际的系统中，大多数请求的接口调用数是越来越多的，基本上都是基于上游服务做的限流熔断。

**定义：二级端口多端口并行调用**

线上业务场景：多接口调用下游接口，导致整体接口响应时间变长。

**结果影响：**
- 服务调用耗时超过 100ms（用户体验 70-20 个用户是可接受的），每个端口平均 RT 10ms
- 单接口串行调用耗时超过 200ms，用户体验下降

**优化：**
- 对耗时高的服务进行线程池优化，可将耗时高的服务做异步调用，如：
  - 异步 + Future / CompletableFuture
  - RxJava / Reactor 等响应式编程框架
- 从而将串行调用化为并行调用，缩短总耗时。

#### 1.1.2 线程池打满后的应急机制

- 紧急扩容：快速扩容，但是会有核心切换开销
- 降级机制：在服务正常流量下，进一步切换降级预案。

#### 1.1.3 非核心功能异步化优化

- 场景描述：一些业务场景中，主流程有调用或返回结果，但是非核心操作，耗时耗钱的操作并不会影响主流程的正确性
- 核心异步化设计三原则：
  - 核心操作同步化，非核心操作异步化
  - 可延迟延迟，异步化处理即可
  - 解决方案：将非核心逻辑从主流程中剥离出来，避免阻塞主线程，从而"显著提升接口 RT（接口时间）"
- 优先级：通过异步线程池与队列 MQ 等异步通道解耦

#### 1.1.4 总结

| 应用 | 优点 | 适用场景 |
|------|------|---------|
| 批量处理 | 吞吐大，耗时短，任务独立 | 多线程批量处理，任务并行 |
| 单接口 RT 优化 | 并行调用，RT 短 | 接口 RT 优化，提高接口 QPS |
| 非核心功能异步化 | 解耦，异步化 | 非核心业务，异步化，提高接口 RT |

### 1.2 踩坑

#### 1.2.1 资源未隔离导致的故障传播

- 场景描述：SDK 将多个服务（appolo）作为最小的资源占用单元（如磁盘、内存、CPU），多个服务部署在同一个应用中，共享线程池等资源
- 故障描述：某一时刻，核心线程池被打满，由于缺乏资源隔离机制，同一应用内的非核心服务也被阻塞
- 原因：Java SDK 中没有提供资源隔离模式
- 解决方案：
  - 短期方案：临时调整核心线程数 + 紧急服务降级
  - 长期方案：将核心线程池与非核心线程池进行资源隔离，从而影响核心服务的可用性。

#### 1.2.2 线程死锁场景与隔离优化

- 问题背景：在父子任务场景（线程池里 + 提交子任务），这种方式其实存在一种问题：父子任务共用同一个线程池，当线程池已经满的情况下，子任务无法被执行，造成阻塞 → 线程池耗尽 → 系统雪崩
- 解决方案：
  - 线程池线程隔离，实现更细的线程池隔离。

#### 1.2.3 线程池任务积压问题及优化措施

- 任务过多，线程池被填满，抛出 RejectedExecutionException 异常，这说明线程池压力过大。
- 解决方案：
  - 调整线程池参数：增加核心线程数，扩大队列容量
  - 引入新的特性：引入 AdaptiveThreadPoolExecutor，能够保证线程池活性。

### 1.3 ThreadPoolExecutor 参数配置

#### 1.3.1 线程池核心参数说明

| 参数名 | 说明 |
|--------|------|
| corePoolSize | 核心线程数，线程池维护的最小线程数量 |
| maximumPoolSize | 最大线程数，线程池允许创建的最大线程数 |
| keepAliveTime | 非核心线程空闲超时时间 |
| unit | 时间单位 |
| workQueue | 任务队列，用于保存等待执行的任务 |
| threadFactory | 线程工厂，用于创建线程 |
| handler | 拒绝策略，当队列和线程池都满时的处理策略 |

#### 1.3.2 核心参数配置建议：corePoolSize 与 maximumPoolSize

**配置考虑维度：**
- 任务类型：计算密集型 / IO 密集型 / 混合型
- 单线程执行耗时：长 vs 短

**各类任务的线程数设置建议：**

| 类型 | 核心线程数 | 最大线程数 | 适用场景 |
|------|-----------|-----------|----------|
| 计算密集型 | CPU 核心数 | CPU 核心数 + 1 | 大量复杂计算，避免上下文切换 |
| IO 密集型 | 2 * CPU 核心数 | 2 * CPU 核心数 | 大量 IO 操作，线程阻塞时间长 |
| 混合型 | 按比例拆分 | 按比例拆分 | 同时包含计算和 IO 任务 |

**不同业务场景建议配置：**

- **执行时间短、耗时不多**：可设置为 CPU 核心数 + 1，最大化 CPU 使用率
- **执行时间长、计算密集**：
  - 假如业务时间长集中在 CPU 操作上，也就是 CPU 密集型的任务，因为 CPU 使用率并不占用 CPU，所以不要让所有的 CPU 都闲下来，可以适当增大线程池中的线程数目，让 CPU 处理更多的业务。
  - 假如业务时间长集中在 IO 操作上，也就是计算密集型任务，这个就没办法了，线程池线程数可以设置为 CPU 核心数 + 1，减少线程上下文切换的消耗。

**执行时间长，高并发：**
- 第一步看这些业务类型是密集型还是密集型
- 第二步：如果是密集型，第二步是优化线程池参数
- 第四步：业务执行时间长的问题，也可能需要分析一下，看看能不能使用中间件对任务进行拆分和解耦。

**实战建议公式：**
- 对于计算、耗时操作的线程数：线程数 = CPU 核心数 * (CPU 运行时间 / CPU 运行时间 + IO 时间)
- 对于 IO 密集型：可以适当调大线程数，按经验来

### 1.4 任务队列与拒绝策略配置建议

#### 1.4.1 常见任务队列类型

| 队列类型 | 特点 | 适用场景 |
|---------|------|---------|
| ArrayBlockingQueue | 有界队列，基于数组 | 固定大小任务量 |
| LinkedBlockingQueue | 无界队列，基于链表 | 任务量不确定 |
| SynchronousQueue | 不存储任务，直接交接 | 高并发短任务 |
| PriorityBlockingQueue | 优先级队列 | 任务有优先级区分 |

#### 1.4.2 队列大小配置原则

- 为什么线程池的队列不建议设置为无界？
  - 因为如果设置为无界，可能会导致内存溢出，而且会导致线程池的性能下降。
- 队列大小设置建议：
  - 需要根据实际业务场景来设置，一般来说，队列的大小应该设置为核心线程数的 2-3 倍。

#### 1.4.3 拒绝策略（饱和策略）

**四种内置拒绝策略：**

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| AbortPolicy | 直接抛出异常 | 默认策略，快速失败 |
| CallerRunsPolicy | 由调用线程执行任务 | 不希望丢弃任务 |
| DiscardPolicy | 直接丢弃任务 | 任务不重要 |
| DiscardOldestPolicy | 丢弃队列最老的任务 | 新任务更重要 |

**生产环境建议：**
- 生产环境中主要使用的是自定义的 Abort、CallerRuns、Discard、DiscardOldest 这四种策略。

---

### 1.5 总结配置建议

| 配置项 | 建议值 | 说明 |
|--------|--------|------|
| corePoolSize | CPU 核心数 | 计算密集型任务 |
| maximumPoolSize | 2 * CPU 核心数 | IO 密集型任务 |
| 队列类型 | ArrayBlockingQueue | 有界队列，可控 |
| 队列大小 | corePoolSize * 2 | 一般建议 |
| 拒绝策略 | AbortPolicy + 自定义告警 | 快速失败，便于监控 |

### 1.6 线程池健康度

**监控的核心指标：**
- 任务提交速率
- 任务执行速率
- 队列堆积情况
- 线程池活跃线程数
- 拒绝任务数

**监控维度：**
- 监控队列的堆积情况，如果堆积过多，说明任务处理速度跟不上任务提交速度
- 监控线程池的活跃线程数，如果活跃线程数接近最大线程数，说明线程池压力较大

**监控维度判断标准：**

| 维度 | 正常 | 警告 | 危险 |
|------|------|------|------|
| 队列堆积 | < 30% | 30% - 70% | > 70% |
| 活跃线程数 | < 50% | 50% - 80% | > 80% |
| 拒绝率 | 0 | < 1% | > 1% |

**理想状态总结：**

| 状态 | 说明 |
|------|------|
| 健康 | 队列堆积少，活跃线程数稳定，无拒绝任务 |
| 警告 | 队列开始堆积，活跃线程数上升，需要关注 |
| 危险 | 队列快满，活跃线程数接近最大值，有拒绝任务，需要立即扩容或降级 |

## 2. 架构设计与实现 - 负载感知型动态缓冲线程池

### 2.1 背景描述

#### 2.1.1 传统线程池存在的问题

在高负载场景下，传统线程池容易出现任务拒绝的问题，导致服务可用性下降。线程池参数配置困难，不同业务场景需要不同的参数配置。线程池的自适应能力不足，无法根据系统负载动态调整线程数。

传统线程池的核心问题：
- 高负载下任务拒绝率高
- 参数调优困难，需要根据业务场景反复调整
- 缺乏动态自适应能力

#### 2.1.2 解决方案

- 引入"缓冲扩展"和"强制入队"的思想，对 ThreadPoolExecutor 进行功能扩展
- 设计了 LADBTP（Load-Aware Dynamic Buffered ThreadPoolExecutor）
- 核心思想：通过缓冲队列来缓解任务压力，在高负载场景下，保护服务的可用性

#### 2.1.3 LADBTP 优势

- TPS（吞吐量）高
- Queue 队列任务堆积少
- 任务执行成功率高

---

### 2.2 核心设计：缓冲扩展 + 强制扩容（缓冲 TFP）

LADBTP 将任务分为两个阶段：核心队列的扩展、缓冲线程池的创建。在最大线程数都满，缓冲扩展通过强制入队模块的创建，来减小核心队列的压力。

**核心设计思想：**
- 缓冲扩展：当核心队列满时，创建缓冲线程池来处理任务
- 强制入队：当缓冲线程池也满时，将任务强制加入队列，保证任务不丢失

---

### 2.3 负载驱动的强制入队模块的原理与设计

强制入队模块在核心线程池、缓冲队列都满时，任务入队失败时，基于 CPU 利用率等指标自适应选择降级策略，以避免服务雪崩。

#### 2.3.1 负载驱动的三种降级策略

**(1) 直接拒绝策略**
- 适用场景：负载极高，任务队列已满，无法继续执行任务，为提升系统整体性能，可通过 FGC 来重新进入
- 缺点：服务可用性降低

**(2) 强制入队策略（Forced Enqueuing Strategy, FES）**
- 策略：修改核心队列的 put 方法，直接将任务加入队列
- 适用场景：适用于 CPU 密集型任务
- 优点：保证任务不丢失
- 缺点：可能导致队列过长，影响系统性能

**(3) 渐进式扩缩容策略**
- 通过 TPS 与 CPU 利用率的动态监控，选择合适的 FGC 策略

**三种策略对比：**

| 策略 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| 直接拒绝 | 负载极高 | 保护系统 | 任务丢失 |
| 强制入队 | CPU 密集型 | 任务不丢失 | 队列可能过长 |
| 渐进式扩缩容 | 混合型任务 | 自适应 | 实现复杂 |

**四种状态组合：**

| 状态 | TPS | CLL | CPU | 策略选择 |
|------|-----|-----|-----|---------|
| 低 TPS，低 CLL | 低 | 低 | 高 | BWS 释放 CPU 资源 |
| 高 TPS，低 CLL | 高 | 低 | 低 | BFS 充分利用 CPU 资源 |
| 高 TPS，高 CLL | 高 | 高 | 高 | 优先保证系统稳定性，放弃部分任务 |
| 低 TPS，高 CLL | 低 | 高 | 低 | 渐进式扩缩容 |

---

### 2.4 LADBTP 流程

LADBTP 的执行流程：

1. 任务提交
2. 核心线程数是否已满？
   - 否 → 创建核心线程执行
   - 是 → 进入下一步
3. 工作队列是否已满？
   - 否 → 加入工作队列
   - 是 → 进入下一步
4. 最大线程数是否已满？
   - 否 → 创建非核心线程执行
   - 是 → 进入下一步
5. 缓冲队列是否已满？
   - 否 → 加入缓冲队列
   - 是 → 进入下一步
6. 强制入队模块处理
   - 根据 CPU 负载选择相应策略

---

### 2.5 测试流程

#### 2.5.1 核心评价指标

- **平均有效执行时间（Average Effective Execution Time, AEET）**：用于衡量线程池处理动态任务的平均执行时间
- **线程创建数（Thread Creation Count, TCC）**：线程创建数
- **任务成功执行数（Task Execution Success Rate, TESR）**：表示成功执行的任务数占总提交任务数的比例。

**计算公式：**
- AEET = Total / (Rejected + Neglect)

#### 2.5.2 核心参数分析

- 核心线程数（corePoolSize, Ncore）：通常设置为 CPU 核心数（Ncpu）
- 最大线程数（maximumPoolSize, Nmax）：Nmax = Ncpu * (1 + 阻塞比)
- 队列容量（QueueCapacity, Qcap）：
  - 队列大小：Qcap = Ncore * (1 + 阻塞比)

#### 2.5.3 参数设计

初始参数设置：Ncore = 16，Nmax = 100，Qcap = 200。

#### 2.5.4 实验分析

**缓冲扩展策略实验分析：**
- 实验设置：不同线程池的对比实验
- 实验结果：LADBTP 在高负载场景下表现更优，任务成功率更高

**强制入队模块实验分析：**

- 实验设置：不同强制入队策略的对比
- 实验结果：渐进式扩缩容策略在不同负载下都有较好的表现

---

### 2.6 总结

实验结果表明，缓冲扩展策略能够有效提升线程池在高负载场景下的任务成功率，强制入队模块能够进一步降低任务拒绝率。LADBTP 在保证系统稳定性的同时，显著提升了线程池的吞吐能力和资源利用率。

## 3. LADBTP 面试问答

### 3.1 前期布局

#### 3.1.1 简历

**负责感知动态缓冲线程池项目 - 项目负责人**

- 项目背景：
  - 在高负载场景下，传统线程池经常出现拒绝策略，导致任务执行失败，且无法根据业务动态调整线程池扩展速率。当前市面缺乏有效的拒绝机制和缓解手段来应对高并发场景，限制了线程池在复杂业务环境下的稳定性和性能。

- 设计三种强制入队策略：借鉴 ScheduledThreadPoolExecutor 与 CMA 的设计中的缓冲中队列处理思想，针对线程池与 CPU 的负载状态设计了三种强制入队方式。通过简单动态测试，在常规配置下，JDK 线程池比 Tomcat 线程池的成功率约为 20%，而我做的线程池的成功率高达 95%，参数最优配置后可达 100%，有效解决高负载时任务丢失问题，线程池在高峰期任务时的成功率也能接近 99%。

- 引入线程池扩展策略：结合线程池的动态扩展，无法适应多样化业务场景。通过修改线程池的逻辑，并引入 Buffer Factor 概念，结合业务实际来调节扩展速率。测试验证后，自适应线程池能够通过修改 Buffer Factor 来适应更多业务场景，并且证明了线程池越多越能提升性能。合理设置 Buffer Factor 可以显著提升系统吞吐能力与资源利用率。

#### 3.1.2 专业技能

对于专业技能而言，我一般会用一个模块来描述线程池：

#### 3.2.3 讲一讲负载驱动的强制入队模块

负载驱动的强制入队策略：借鉴 ScheduledThreadPoolExecutor 与 CMA 的设计中的缓冲中队列处理思想，分别设计了阻塞等待、重试入队与直接丢弃三种强制入队方式，并根据 CPU 利用率和线程池的负载情况进行动态选择，并且经过测试表明，该机制在保证任务吞吐的同时，对系统性能的负面影响极小。

#### 3.2.5 这个 CPU 利用率你是怎么计算的？（问过两三次了已经）

这里我给你两种方案：
1. 你说这个 CPU 利用率用的是你们的已经被封装好的东西，你没有细看。
2. 第二个就是你代码中写的东西（画了一个周期性任务，可以参考一下），把流程说一下就好了。

```java
public static class BasicCalculate {
    private final SystemInfo systemInfo = new SystemInfo();
    private final CentralProcessor processor = systemInfo.getHardware().getProcessor();
    private double cpuLoad = 0.0;
    private ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(1);

    public BasicCalculate() {
        scheduler.scheduleAtFixedRate(this::updateCPULoad, 0, 5, TimeUnit.SECONDS);
    }

    // 获取系统 CPU 负载（0.0 - 1.0）
    public void updateCPULoad() {
        // 获取上一次 CPU tick（用于计算差值）
        long[] prevTicks = processor.getSystemCpuLoadTicks();
        try {
            Thread.sleep(1000); // 间隔 1 秒以获取采样差值
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            return;
        }
        long[] ticks = processor.getSystemCpuLoadTicks();
        long cpuCache = processor.getSystemCpuLoadBetweenTicks(prevTicks);

        // 计算 CPU 使用率（百分比）
        double d = cpuCache / 1_000_000_000.0;
        this.cpuLoad = d; // 用于计算差值
    }

    public double getCPULoad() {
        return cpuLoad;
    }

    public void shutdown() {
        if (!scheduler.isShutdown() && !scheduler.isTerminated()) {
            scheduler.shutdown(); // 或者 scheduler.shutdownNow();
        }
    }
}
```

#### 3.2.7 强制入队模块中，入队方式是怎么选择的？你又为什么要这样设计？

可以使用 BWIS 最大化任务执行成功率的：

1. **低 TPS，低 CLL**：任务量和线程池队列利用率低，但 CPU 使用率高，此时应该使用 BWS 释放 CPU 资源；
2. **高 TPS，低 CLL**：任务量大但线程池队列利用率低，但 CPU 使用率低，可以使用 BFS 充分利用 CPU 资源，提高入队成功率；
3. **高 TPS，高 CLL**：任务量大且线程池队列利用率高，且 CPU 使用率高，此时系统和线程池都处于高负载状态，应该优先保证系统稳定性，可以放弃部分任务来减轻线程池和系统的负担，使硬件使用资源 Qos 以最小化 CPU 消耗。

#### 3.2.8 你说你参考了 synchronized 的锁升级机制，你是怎么参考的？

主要是参考 synchronized 锁升级时从偏向锁到轻量级锁的方式，（synchronized 锁升级过程中，从轻量级锁到重量级锁，其实反映了不同的 CPU 资源利用的方式），synchronized 的锁升级是通过锁的升级过程，升级过程中通过锁的升级机制进行优化，如果线程数量多，多个线程频繁竞争会导致资源的浪费，此时就会升级到重量级锁，重量级锁由于线程阻塞，因此涉及到上下文切换，因此 CPU 不会空转。

参考这个设计，我是以大的 CMA 以及 CPU 的设计中的缓冲中队列处理思想，我们设计了退避等待和阻塞等待两种策略，以适用不同的 cpu 负载情况。

#### 3.2.9 对于 Buffer Degree 的取值，有没有什么指导性的建议？

说实话，这个问题确实很扯淡，如果你的成绩好的话，那么主要看是 IO 时长与总时长比值，以及业务场景的具体情况和需求。

1. IO 时长与总时长比值：如果这个比值接近于 1，那么就说明这个接口的 cpu 空转，此时就应该多创建线程，即 Buffer Degree 越接近于 0 时，也就是需要的线程越多，提升的性能一定的空间，这样并发可以提高线程池的处理能力。所以一般设置 Buffer Degree 为 0.2。

2. 业务场景的具体情况和需求：有时候，IO 时长的占比接近 0（即 CPU 密集型任务），但是哪怕是在这种情况下，Buffer Degree 还是有必要设置在 0.2 左右，原因就是这个业务场景对于性能要求高，或者是并发大。（具体可以参考"线程池进阶教程"的第二节"ThreadPoolExecutor 参数配置"，以下内容都来自于内部，刚好适合回答这个问题）

**执行时间短、耗时不多**：可设置为 CPU 核心数 + 1，最大化 CPU 使用率
**执行时间长、计算密集**：
- 假如业务时间长集中在 CPU 操作上，也就是 CPU 密集型的任务，因为 CPU 使用率并不占用 CPU，所以不要让所有的 CPU 都闲下来，可以适当增大线程池中的线程数目，让 CPU 处理更多的业务。
- 假如业务时间长集中在 IO 操作上，也就是计算密集型任务，这个就没办法了，线程池线程数可以设置为 CPU 核心数 + 1，减少线程上下文切换的消耗。

**执行时间长，高并发：第一步看这些业务类型是密集型还是密集型第二步：如果是密集型，第二步是优化线程池参数，第四步：业务执行时间长的问题，也可能需要分析一下，看看能不能使用中间件对任务进行拆分和解耦。**

#### 3.2.10 我看你的简历上说，你的线程池采用强制入队模块并不会造成过多额外负载，这我应该怎么理解？按理说不应该如此啊？

其实这涉及到一个我们的公式了，我们判断是否会造成负载的依据是成功执行单个任务的平均时长，平均有效执行时间 = Total / (Total - Rejected)。

这里我们分为两种情况：
1. 如果负载压力大，那么其执行拒绝策略的几率高。
   a. 对于传统线程池而言，如果需要执行拒绝策略，那么这个任务会把 execute 方法从头到尾执行一遍，然后执行拒绝策略，此时 Total 升高，但是 Rejected 升高，因此平均有效时长就会变长。
   b. 对于 LADBTP 而言，如果需要执行拒绝策略，那么这个任务会在 execute 方法从头执行到尾，然后执行强制入队策略，失败后再执行拒绝策略，但是由于 LADBTP 相比于传统线程池的入队状态会大（多个阶段的执行时长有时候会大于传统线程池的拒绝策略的执行时长），但是 Total 增加的没有传统线程池那么大，因此平均有效时长会优于传统线程池。
2. 如果负载压力小，那么执行拒绝策略的几率也越小，LADBTP 执行强制入队策略的几率也越少，因此两者最后反馈出来的情况其实也相差不大。

#### 3.2.11 如果我想要提高线程池性能，为什么不直接使用 ThreadPoolExecutor，让它的快速达到最大线程数？

从两个角度考虑：
1. 首先是资源利用的角度，这种方式其实会带来资源的浪费。
2. 然后是真实的反应，从我们的测试结果来看，并不是越快达到越好。我们测试了不同配置下 LADBTP 时对于同一批的任务，它执行的策略的次数，其中缓冲阶段的一些线程创建的次数，也会少于 ThreadPoolExecutor，但是其表现上来看，它执行拒绝策略的次数其实不是最低的，最低的其实是 BufferFactor=2，因此也需要对具体的任务设置合适的 BufferFactor。
