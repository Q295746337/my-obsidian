# 08-并发编程篇 面试笔记

> 范围：线程基础、synchronized、JMM/CAS/volatile、AQS/ReentrantLock、死锁、ConcurrentHashMap、并发三大特性、线程池、ThreadLocal。
> 主笔记：[[JUC/JUC 索引|JUC]]。源码、AQS 细节和并发模式以主笔记为准，本文保留面试问答与结论。

## 1. 线程基础

本节依次回答：1.1 进程与线程、1.2 并行与并发、1.3 创建线程的四种方式、1.4 线程状态、1.5 线程协作。

### 1.1 进程与线程

| 对比 | 进程 | 线程 |
| --- | --- | --- |
| 定义 | 正在运行程序的实例 | 进程中的一条指令流 |
| 内存 | 不同进程使用不同内存空间 | 同一进程内线程共享内存 |
| 开销 | 上下文切换成本较高 | 更轻量，切换成本较低 |

- 进程负责加载指令、管理内存和 IO。
- 一个进程可以包含一到多个线程。

### 1.2 并行与并发

- 并发：同一时间应对多件事情的能力，多个线程轮流使用 CPU。
- 并行：同一时间动手做多件事情的能力，多核 CPU 同时执行多个线程。
- 单核 CPU 下线程实际串行执行，靠时间片切换，微观串行、宏观并行。

### 1.3 创建线程的四种方式

1. 继承 Thread 类。
2. 实现 Runnable 接口。
3. 实现 Callable 接口，配合 FutureTask 获取返回值。
4. 线程池创建（项目中最常用）。

| 对比 | Runnable | Callable |
| --- | --- | --- |
| 返回值 | run 方法没有返回值 | call 方法有返回值 |
| 异常 | 异常只能在内部消化 | call 方法允许抛出异常 |
| 结果获取 | 无 | 配合 Future/FutureTask |

**run 与 start 的区别**

- `start()` 启动线程，由该线程调用 run 方法，只能调用一次。
- `run()` 只是普通方法，封装要执行的代码，可以被调用多次。

### 1.4 线程状态

| 状态 | 说明 |
| --- | --- |
| NEW | 新建，尚未启动 |
| RUNNABLE | 可运行 |
| BLOCKED | 阻塞等待监视器锁 |
| WAITING | 等待 |
| TIMED_WAITING | 计时等待 |
| TERMINATED | 终止 |

**状态变化**

- 创建线程对象是 NEW。
- 调用 `start()` 变为 RUNNABLE。
- 获取不到锁进入 BLOCKED，获得锁回到 RUNNABLE。
- 调用 `wait()` 进入 WAITING，被 `notify()` 唤醒回到 RUNNABLE。
- 调用 `sleep(50)` 进入 TIMED_WAITING，时间到回到 RUNNABLE。
- 执行结束进入 TERMINATED。

### 1.5 线程协作

**保证 T1、T2、T3 顺序执行**

- 使用 `join()`：`t2` 中调用 `t1.join()`，等 t1 执行完再执行 t2；`t3` 中调用 `t2.join()`。

**notify 与 notifyAll**

- `notify()` 随机唤醒一个 wait 线程。
- `notifyAll()` 唤醒所有 wait 线程。

**wait 与 sleep**

| 维度 | wait | sleep |
| --- | --- | --- |
| 归属 | Object 成员方法 | Thread 静态方法 |
| 唤醒 | 可被 notify 唤醒，也可等待超时 | 等待时间到或被中断 |
| 锁 | 调用前必须持有对象锁，执行后释放锁 | 不要求锁；在 synchronized 中不释放锁 |

**停止线程**

- 使用退出标志，让 run 方法正常结束。
- 使用 `stop()` 强行终止，不推荐，已作废。
- 使用 `interrupt()` 中断线程：打断 sleep/wait/join 会抛 InterruptedException；打断正常线程可通过打断状态标记退出。

## 2. synchronized 原理

本节依次回答：2.1 Monitor、2.2 对象内存结构、2.3 锁升级。

### 2.1 Monitor

- synchronized 采用互斥方式，同一时刻至多一个线程持有对象锁。
- 底层由 monitor 实现，monitor 是 JVM 级别的对象，C++ 实现。
- 对象关联 monitor 后，对象头 Mark Word 中设置指向 monitor 的指针。

| 属性 | 作用 |
| --- | --- |
| Owner | 当前获取锁的线程，只能有一个 |
| EntryList | 没抢到锁、处于 Blocked 状态的线程 |
| WaitSet | 调用 wait 方法、处于 Waiting 状态的线程 |

### 2.2 对象内存结构

- 对象头（Header）：Mark Word、Klass Word。
- 实例数据（Instance Data）：成员变量。
- 对齐填充：对象头和实例变量不是 8 的整数倍时补齐。

Mark Word 中记录 hashcode、分代年龄、锁标志、偏向线程 ID、锁记录指针或 monitor 指针等。

### 2.3 锁升级

| 锁 | 描述 |
| --- | --- |
| 重量级锁 | 基于 Monitor，涉及用户态/内核态切换和上下文切换，成本高 |
| 轻量级锁 | 线程加锁时间错开、无竞争时使用；修改对象头锁标志，用 CAS 保证原子性 |
| 偏向锁 | 长时间只被一个线程使用；第一次 CAS 设置线程 ID，之后只判断 Mark Word 中是否是自己的线程 ID |

- 轻量级锁加锁：线程栈创建 Lock Record，CAS 把 Lock Record 地址写入 Mark Word；失败说明有竞争，膨胀为重量级锁。
- 偏向锁在 JDK 1.6 引入，减少无竞争时的 CAS 开销。
- 一旦发生竞争，都会升级为重量级锁。

## 3. JMM、CAS 与 volatile

本节依次回答：3.1 JMM、3.2 CAS、3.3 volatile。

### 3.1 JMM

- JMM 定义共享内存中多线程读写操作的行为规范，保证指令正确性。
- 内存分为工作内存（线程私有）和主内存（线程共享）。
- 线程之间相互隔离，交互需要通过主内存。

### 3.2 CAS

- CAS 全称 Compare And Swap，比较再交换，是乐观锁思想。
- 三个值：当前内存值 V、旧预期值 A、即将更新的值 B。
- 当且仅当 A == V 时，把 V 改为 B 并返回 true，否则什么都不做返回 false。
- 失败时通过自旋重试，直到成功。
- 底层依赖 Unsafe 类调用操作系统 CAS 指令。
- 应用：AQS、AtomicXXX。

**乐观锁与悲观锁**

- CAS 是乐观锁：不怕别的线程修改，改了就重试。
- synchronized 是悲观锁：上锁后其他线程不能改。

**缺点**

- 竞争激烈时自旋频繁，效率受影响。
- 只能保证一个变量的原子性（基础 CAS）。

### 3.3 volatile

- 保证线程间可见性：一个线程对共享变量的修改对另一个线程可见。
- 禁止指令重排序：读写变量时加入内存屏障，阻止其他读写越过屏障。
- 使用技巧：写变量放在代码最后，读变量放在代码最开始。

**可见性示例**

```java
static volatile boolean stop = false;

new Thread(() -> {
    while (!stop) {
        // 没有 volatile 时，JIT 可能优化成一直读本地缓存
    }
}, "t3").start();
```

**指令重排**

- 处理器可能优化指令顺序，但保证最终结果与顺序执行一致。
- volatile 写屏障阻止上方写操作排到 volatile 写之后；读屏障阻止下方读操作排到 volatile 读之前。

## 4. AQS 与 ReentrantLock

本节依次回答：4.1 AQS、4.2 ReentrantLock、4.3 synchronized 与 Lock 的区别。

### 4.1 AQS

- 全称 AbstractQueuedSynchronizer，抽象队列同步器，是构建锁和同步组件的基础框架。
- 常见实现：ReentrantLock、Semaphore、CountDownLatch。
- 内部维护 FIFO 双向队列，存放排队线程。
- 内部属性 state 表示资源：默认 0 表示无锁，修改为 1 表示获取资源。
- 修改 state 使用 CAS 保证原子性。

**公平与非公平**

- 新线程与队列中的线程共同抢资源：非公平。
- 新线程只能到队列等待，只让 head 线程获取锁：公平。
- AQS 本身支持公平锁和非公平锁。

| 对比 | synchronized | AQS |
| --- | --- | --- |
| 实现 | 关键字，C++ | Java 语言 |
| 锁类型 | 悲观锁，自动释放 | 悲观锁，手动开启和关闭 |
| 竞争激烈 | 重量级锁，性能差 | 提供多种解决方案 |

### 4.2 ReentrantLock

- 可重入锁，支持可中断、超时、公平锁、多个条件变量。
- 基于 CAS + AQS 队列实现。
- 构造方法默认非公平锁，传 `true` 为公平锁。
- 公平锁吞吐量通常低于非公平锁。

```java
ReentrantLock lock = new ReentrantLock();
lock.lock();
try {
    // 业务
} finally {
    lock.unlock();
}
```

### 4.3 synchronized 与 Lock 的区别

| 层面 | synchronized | Lock |
| --- | --- | --- |
| 语法 | 关键字，JVM 实现 | 接口，JDK 实现 |
| 释放 | 自动释放 | 手动 unlock |
| 功能 | 互斥、同步、重入 | 额外支持公平锁、可打断、可超时、多条件变量 |
| 性能 | 无竞争时有偏向锁/轻量级锁优化 | 竞争激烈时通常更好 |

## 5. 死锁

本节依次回答：5.1 产生条件、5.2 诊断。

### 5.1 产生条件

一个线程需要同时获取多把锁，且获取顺序不一致时容易死锁。

```java
Thread t1 = new Thread(() -> {
    synchronized (A) {
        sleep(1000);
        synchronized (B) { }
    }
});

Thread t2 = new Thread(() -> {
    synchronized (B) {
        sleep(500);
        synchronized (A) { }
    }
});
```

t1 持有 A 等 B，t2 持有 B 等 A，程序不结束。

> 图：jstack 输出显示两个线程分别持有 `0x...5c5e8` 和 `0x...5c5f8`，又互相等待对方释放，形成循环等待。

### 5.2 诊断

- `jps`：查看 JVM 进程状态信息。
- `jstack -l <pid>`：查看线程堆栈，检查是否有死锁。
- 可视化工具：jconsole、VisualVM。

**回答模板**：先用 jps 找到进程，再用 jstack 看线程堆栈，找到互相等待的锁和代码行；jconsole/VisualVM 也能检测死锁。

## 6. ConcurrentHashMap

本节依次回答：6.1 JDK 1.7、6.2 JDK 1.8。

### 6.1 JDK 1.7

- 数据结构：分段数组 Segment + HashEntry 数组 + 链表。
- 每个 Segment 是一把锁，继承 ReentrantLock。
- 定位：先 hash 定位 Segment，再 hash 定位 HashEntry 数组下标。
- 锁粒度是 Segment，并发度受 Segment 数量限制。

### 6.2 JDK 1.8

- 放弃 Segment，数据结构与 HashMap 1.8 一致：数组 + 链表/红黑树。
- 并发安全：CAS + synchronized。
- CAS 控制数组节点添加。
- synchronized 只锁定当前链表或红黑树的首节点；hash 不冲突就不会并发。
- 锁粒度更细，性能更好。

| 版本 | 结构 | 加锁 |
| --- | --- | --- |
| 1.7 | Segment + HashEntry + 链表 | Segment 分段锁，ReentrantLock |
| 1.8 | 数组 + 链表/红黑树 | CAS 添加节点 + synchronized 锁首节点 |

## 7. 并发问题的根本原因

Java 并发编程三大特性：

| 特性 | 含义 | 解决方案 |
| --- | --- | --- |
| 原子性 | 操作不可暂停、不可中断，要么完成要么不执行 | synchronized、Lock |
| 可见性 | 一个线程对共享变量的修改对另一个线程可见 | volatile、synchronized、Lock |
| 有序性 | 指令重排可能改变执行顺序 | volatile |

**示例：ticketNum-- 不是原子操作**

- 读取、减一、写回三步可能被其他线程穿插，导致超卖。
- 加 synchronized 或 Lock 保证原子性。

## 8. 线程池

本节依次回答：8.1 七个核心参数、8.2 执行流程、8.3 拒绝策略、8.4 常见阻塞队列、8.5 核心线程数怎么定、8.6 Executors 的四种线程池、8.7 为什么不建议用 Executors、8.8 项目中的使用场景、8.9 如何控制并发访问线程数量（Semaphore）。

### 8.1 七个核心参数

| 参数 | 含义 |
| --- | --- |
| corePoolSize | 核心线程数 |
| maximumPoolSize | 最大线程数 = 核心线程 + 救急线程 |
| keepAliveTime | 救急线程生存时间 |
| unit | 时间单位 |
| workQueue | 核心线程忙时的任务队列，队列满才创建救急线程 |
| threadFactory | 线程工厂，可定制线程名、守护线程等 |
| handler | 拒绝策略，所有线程忙且队列满时触发 |

### 8.2 执行流程

1. 提交任务。
2. 核心线程未满，创建核心线程执行。
3. 核心线程已满，任务进入阻塞队列。
4. 队列已满，线程数小于最大线程数，创建救急线程。
5. 达到最大线程数且队列满，触发拒绝策略。
6. 线程执行完任务后，会检查阻塞队列中是否有待执行任务。

### 8.3 拒绝策略

| 策略 | 行为 |
| --- | --- |
| AbortPolicy | 直接抛异常，默认 |
| CallerRunsPolicy | 用调用者线程执行 |
| DiscardOldestPolicy | 丢弃队列最前面的任务，执行当前任务 |
| DiscardPolicy | 直接丢弃任务 |

### 8.4 常见阻塞队列

| 队列 | 说明 |
| --- | --- |
| ArrayBlockingQueue | 数组结构的有界阻塞队列，FIFO |
| LinkedBlockingQueue | 链表结构的有界阻塞队列，FIFO |
| DelayedWorkQueue | 优先级队列，按执行时间出队 |
| SynchronousQueue | 不存储元素，插入必须等待移出 |

| 对比 | LinkedBlockingQueue | ArrayBlockingQueue |
| --- | --- | --- |
| 容量 | 默认无界，支持有界 | 强制有界 |
| 底层 | 链表 | 数组 |
| 节点 | 入队时创建 Node | 提前初始化 Node 数组 |
| 锁 | 两把锁（头尾） | 一把锁 |

### 8.5 核心线程数怎么定

| 任务类型 | 建议 |
| --- | --- |
| IO 密集型（文件、DB、网络） | 2N + 1 |
| CPU 密集型（计算、转换） | N + 1 |

更细的口径：

- 高并发、任务执行时间短：CPU 核数 + 1，减少上下文切换。
- 并发不高、任务执行时间长：IO 密集型 2N + 1；计算密集型 N + 1。
- 并发高、业务执行时间长：重点在架构设计，先考虑缓存，再考虑加服务器。

> 注：PPT 前一页把 IO 密集型和 CPU 密集型的建议写反了，这里按后一页的细分口径和通行公式整理。

查看 CPU 核数：

```java
Runtime.getRuntime().availableProcessors();
```

### 8.6 Executors 的四种线程池

| 方法 | 特点 | 适用 |
| --- | --- | --- |
| newFixedThreadPool | 核心数 = 最大数，无救急线程；LinkedBlockingQueue | 任务量已知、相对耗时 |
| newSingleThreadExecutor | 核心数 = 最大数 = 1；FIFO | 顺序执行 |
| newCachedThreadPool | 核心 0，最大 Integer.MAX_VALUE；SynchronousQueue | 任务密集、执行时间短 |
| newScheduledThreadPool | 支持延迟和周期执行；DelayedWorkQueue | 定时任务 |

### 8.7 为什么不建议用 Executors

阿里巴巴开发手册【强制】：

> 线程池不允许使用 Executors 去创建，而是通过 ThreadPoolExecutor 的方式，让写的同学更加明确线程池的运行规则，规避资源耗尽的风险。

| 线程池 | 弊端 |
| --- | --- |
| FixedThreadPool、SingleThreadPool | 请求队列长度为 Integer.MAX_VALUE，可能堆积大量请求导致 OOM |
| CachedThreadPool | 创建线程数量为 Integer.MAX_VALUE，可能创建大量线程导致 OOM |

### 8.8 项目中的使用场景

| 场景 | 方案 |
| --- | --- |
| ES 数据批量导入 | 线程池 + CountDownLatch，分页读取，避免一次性加载 OOM |
| 数据汇总 | 线程池 + Future，并行调用无依赖接口；串行 1800ms，并行 800ms |
| 异步调用 | 线程池异步执行不需要返回值的下游方法，提升响应时间 |

**CountDownLatch**

- 构造参数初始化计数。
- `await()` 等待计数归零。
- `countDown()` 计数减一。

### 8.9 如何控制并发访问线程数量（Semaphore）

Semaphore（信号量）是 JUC 包下的工具类，底层基于 AQS，用于限制同时执行的线程数量，常用于资源有明确访问数量限制的场景或限流。

| 方法 | 作用 |
| --- | --- |
| `new Semaphore(n)` | 创建信号量，初始化许可数量 |
| `acquire()` | 请求一个许可，许可数减一；没有可用许可时阻塞 |
| `release()` | 释放一个许可，许可数加一 |

```java
Semaphore semaphore = new Semaphore(3);
semaphore.acquire();
try {
    // 业务
} finally {
    semaphore.release();
}
```

**易错点**

- `acquire()` 必须在 `finally` 外或配合 `release()` 使用，避免异常时许可不归还。
- Semaphore 控制的是并发数量，不是任务的执行顺序。

## 9. ThreadLocal

本节依次回答：9.1 作用、9.2 基本使用、9.3 实现原理、9.4 内存泄漏。

### 9.1 作用

- 为每个线程分配独立的线程副本，解决变量并发访问冲突。
- 同时实现线程内的资源共享。
- 案例：JDBC 操作时把每个线程的 Connection 放入各自的 ThreadLocal，避免 A 线程关闭 B 线程的连接。

### 9.2 基本使用

```java
static ThreadLocal<String> threadLocal = new ThreadLocal<>();

threadLocal.set("itcast");
threadLocal.get();
threadLocal.remove();
```

### 9.3 实现原理

- 每个 Thread 内部有一个 ThreadLocalMap 成员变量。
- set：以 ThreadLocal 自己为 key，资源对象为 value，放入当前线程的 ThreadLocalMap。
- get：以 ThreadLocal 自己为 key，到当前线程的 Map 中查找。
- remove：以 ThreadLocal 自己为 key，移除关联值。

### 9.4 内存泄漏

- Entry 继承 WeakReference，key 是弱引用，value 是强引用。
- key 被 GC 回收后，value 仍可能被 Entry 强引用，导致内存泄漏。
- 解决：使用完主动调用 `remove()`。

**易错点**

- ThreadLocal 不是“每个线程各存一份 ThreadLocal”，而是每个线程各有一个 Map，ThreadLocal 作为 key。
- 线程池场景下线程复用，不 remove 更容易残留数据。

| ConcurrentHashMap | 1.7 Segment 分段锁；1.8 CAS + synchronized 首节点 |
| 三大特性 | 原子性、可见性、有序性 |
| 线程池 | 7 参数、核心 → 队列 → 救急 → 拒绝 |
| 核心线程数 | IO N+1，CPU 2N+1 |
| Executors | 队列或线程数无界，可能 OOM，建议 ThreadPoolExecutor |
| Semaphore | 许可数量控制并发，acquire/release |
| ThreadLocal | 线程私有副本；key 弱引用，value 强引用，记得 remove |
