# 02-Redis篇 面试笔记

> 范围：Redis 使用场景、缓存三兄弟、双写一致性、持久化、过期与淘汰、分布式锁、集群与高性能原理。
> 主笔记：[[Redis/Redis 索引|Redis]]。本文只保留面试问答与要点，命令细节、项目实战和源码讲解以主笔记为准。

## 1. 使用场景怎么答

**回答结构**：先说自己项目里的真实业务，再说技术方案，最后补一句数据类型或注意事项。

| 场景 | 回答落点 |
| --- | --- |
| 缓存 | 项目中缓存的热点数据 |
| 分布式锁 | 抢券、库存扣减等互斥场景 |
| 计数器 | 需要计数的业务 |
| 保存 token | 登录凭证 |
| 消息队列 | 项目中的异步消息 |
| 延迟队列 | 超时、定时类业务 |

**易错点**

- 不要只背“缓存、分布式锁”，要能落到一个具体业务上。
- 面试官追问“用的什么数据类型”时，回答要和自己描述的业务一致。

## 2. 缓存穿透

本节依次回答：2.1 什么是缓存穿透、2.2 解决方案一：缓存空数据、2.3 解决方案二：布隆过滤器。

### 2.1 什么是缓存穿透

查询一个不存在的数据，MySQL 查不到就不会写入缓存，导致每次请求都打到数据库。

**回答要点**

- 现象：请求 `api/news/getById/1`，Redis 没有，DB 也没有。
- 后果：恶意请求或不存在的 id 会持续压数据库。

### 2.2 解决方案一：缓存空数据

- 查询结果为空时，仍然把空结果写入缓存，例如 `{key:1, value:null}`。
- 优点：实现简单。
- 缺点：消耗内存；数据后续被创建时可能短时间不一致。

### 2.3 解决方案二：布隆过滤器

- 布隆过滤器底层是 bitmap（位图），每个单元只存 0 或 1。
- 存储：用多个 hash 函数计算位置，把对应位改为 1。
- 查询：用相同 hash 函数判断对应位是否都为 1；只要有一位是 0，就说明数据一定不存在。
- 优点：内存占用少，不会产生多余 key。
- 缺点：实现复杂，存在误判；数组越小误判率越高。
- 实现：Redisson、Guava。
- 使用时机：缓存预热时一并预热布隆过滤器；查询先过布隆过滤器，不存在直接返回。

**易错点**

- 布隆过滤器只能判断“一定不存在”，不能判断“一定存在”。
- 删除数据不能直接删布隆过滤器中的位，通常采用重建或计数布隆过滤器。

## 3. 缓存击穿

本节依次回答：3.1 什么是缓存击穿、3.2 两种解决方案。

### 3.1 什么是缓存击穿

某个热点 key 设置了过期时间，过期瞬间大量并发请求同时打到数据库，可能把 DB 压垮。

### 3.2 两种解决方案

| 方案 | 做法 | 一致性 | 性能 | 适用 |
| --- | --- | --- | --- | --- |
| 互斥锁 | 未命中时只有一个线程重建缓存，其他线程等待重试 | 强一致 | 较差 | 对一致性要求高 |
| 逻辑过期 | 缓存不设 TTL，value 里带过期时间；发现逻辑过期后异步重建，先返回旧数据 | 最终一致 | 优 | 高可用、可容忍短时旧数据 |

**互斥锁流程**

1. 线程 1 查询缓存未命中，获取互斥锁成功。
2. 线程 1 查数据库、重建缓存、写回、释放锁。
3. 线程 2 未命中后获取锁失败，休眠后重试，直到缓存命中。

**逻辑过期流程**

1. 缓存中存 `{"id":"123","title":"黑马程序员","expire":153213455}`，不设置 Redis TTL。
2. 线程发现逻辑时间已过期，获取互斥锁成功，开启新线程重建缓存。
3. 其他线程获取锁失败，直接返回过期数据。

**易错点**

- 互斥锁要保证“查库 + 写缓存”在锁内完成。
- 逻辑过期返回的是旧数据，要能接受短时间不一致。

## 4. 缓存雪崩

本节依次回答：4.1 什么是缓存雪崩、4.2 四个解决方向。

### 4.1 什么是缓存雪崩

同一时段大量缓存 key 同时失效，或者 Redis 服务宕机，导致大量请求到达数据库。

### 4.2 四个解决方向

- 给不同 key 的 TTL 加随机值，避免同时过期。
- 用 Redis 集群（哨兵、分片）提高可用性。
- 给缓存业务加降级限流，例如 Nginx 或 Spring Cloud Gateway。
- 加多级缓存，例如 Guava、Caffeine。

**一句话补充**：降级可以作为系统的保底策略，穿透、击穿、雪崩都适用。

## 5. 双写一致性

本节依次回答：5.1 先删缓存还是先改数据库、5.2 强一致：Redisson 读写锁、5.3 最终一致：异步通知。

### 5.1 先删缓存还是先改数据库

| 顺序 | 问题 |
| --- | --- |
| 先删缓存，再改数据库 | 并发读可能在删缓存后、改库前把旧值写回缓存，产生脏数据 |
| 先改数据库，再删缓存 | 出问题概率更小，但仍有并发窗口 |

**延迟双删**：删除缓存 → 修改数据库 → 延迟一段时间再删除缓存。

- 为什么要删两次：第一次删掉旧缓存，第二次删掉并发读可能回填的旧值。
- 为什么要延迟：等并发读和数据库更新完成后再删。
- 缺点：代码耦合性高，仍有脏数据风险。

### 5.2 强一致：Redisson 读写锁

- 共享锁（读锁）：加锁后其他线程可以共享读。
- 排他锁（写锁）：加锁后阻塞其他线程读写。
- 适合读多写少、对一致性要求高的场景，例如抢券库存。
- 代价是性能较低。

### 5.3 最终一致：异步通知

- MQ 方案：业务服务写数据库后发消息，缓存服务监听消息并更新/删除缓存；需要保证 MQ 可靠性。
- Canal 方案：Canal 伪装成 MySQL 从节点，监听 binlog，通知缓存服务更新；业务代码不用改。
- Binlog 记录 DDL 和 DML，不记录 SELECT、SHOW。

**回答模板**

> 热点文章数据实时性要求不高，我们用 MQ 异步通知保证最终一致；抢券库存要求强一致，用 Redisson 读写锁。

## 6. 持久化

本节依次回答：6.1 RDB、6.2 AOF、6.3 RDB 与 AOF 对比。

### 6.1 RDB

- RDB 是 Redis 数据快照，把内存数据写入磁盘，重启时读取快照恢复。
- 主动备份配置：

```conf
# 900 秒内至少 1 个 key 被修改，则执行 bgsave
save 900 1
save 300 10
save 60 10000
```

- `bgsave` 会 fork 子进程，子进程共享主进程内存数据，然后读取内存写入 RDB 文件。
- fork 使用 copy-on-write：主进程读共享内存；主进程写时复制一份数据再写。

### 6.2 AOF

- AOF 记录每一个写命令，可以看作命令日志文件。
- 默认关闭，开启配置：

```conf
appendonly yes
appendfilename "appendonly.aof"
```

| 配置 | 刷盘时机 | 优点 | 缺点 |
| --- | --- | --- | --- |
| always | 同步刷盘 | 可靠性高，几乎不丢数据 | 性能影响大 |
| everysec | 每秒刷盘 | 性能适中 | 最多丢失 1 秒数据 |
| no | 操作系统控制 | 性能最好 | 可能丢失大量数据 |

- AOF 文件会越来越大，可以用 `bgrewriteaof` 重写，用最少命令达到相同效果。
- 自动重写阈值：

```conf
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
```

### 6.3 RDB 与 AOF 对比

| 维度 | RDB | AOF |
| --- | --- | --- |
| 持久化方式 | 定时对整个内存做快照 | 记录每一次执行的命令 |
| 数据完整性 | 不完整，两次备份之间会丢失 | 相对完整，取决于刷盘策略 |
| 文件大小 | 有压缩，体积小 | 记录命令，体积大 |
| 宕机恢复速度 | 很快 | 慢 |
| 数据恢复优先级 | 低 | 高 |
| 系统资源占用 | 高，CPU 和内存消耗大 | 低，主要是磁盘 IO；重写时占用高 |
| 使用场景 | 可容忍数分钟丢失，追求启动速度 | 对数据安全性要求高 |

**回答模板**：如果对数据安全性要求高，实际开发中会结合 RDB 和 AOF 使用。

## 7. 过期删除策略

Redis 采用**惰性删除 + 定期删除**配合。

### 7.1 惰性删除

- 设置过期时间后不主动处理，访问 key 时才检查是否过期。
- 优点：对 CPU 友好。
- 缺点：对内存不友好，过期但一直不访问的 key 会占内存。

### 7.2 定期删除

- 每隔一段时间随机取出一定数量 key 检查并删除过期 key。
- SLOW 模式：定时任务，默认 10hz，每次不超过 25ms，可通过 `hz` 调整。
- FAST 模式：执行频率不固定，两次间隔不低于 2ms，每次不超过 1ms。
- 优点：限制删除时长和频率，减少对 CPU 的影响。
- 缺点：难以确定删除执行的时长和频率。

## 8. 内存淘汰策略

当内存不够用时，Redis 按淘汰策略删除数据。默认是 `noeviction`，内存满时不允许写入新数据。

| 策略 | 范围 | 规则 |
| --- | --- | --- |
| noeviction | 全部 | 不淘汰，写入报错 |
| volatile-ttl | 设置了 TTL 的 key | 剩余 TTL 越小越先淘汰 |
| allkeys-random | 全部 key | 随机淘汰 |
| volatile-random | 设置了 TTL 的 key | 随机淘汰 |
| allkeys-lru | 全部 key | 最近最少使用优先淘汰 |
| volatile-lru | 设置了 TTL 的 key | 最近最少使用优先淘汰 |
| allkeys-lfu | 全部 key | 访问频率最低优先淘汰 |
| volatile-lfu | 设置了 TTL 的 key | 访问频率最低优先淘汰 |

**LRU 与 LFU**

- LRU：用当前时间减去最后一次访问时间，值越大淘汰优先级越高。
- LFU：统计访问频率，值越小淘汰优先级越高。

**使用建议**

- 有明显冷热数据：`allkeys-lru`。
- 访问频率差别不大：`allkeys-random`。
- 有置顶需求：`volatile-lru`，置顶数据不设过期时间。
- 短时高频访问：`allkeys-lfu` 或 `volatile-lfu`。

**高频追问**

- 数据库 1000 万数据、Redis 只能缓存 20 万，如何保证缓存都是热点？用 `allkeys-lru`，留下经常访问的数据。
- Redis 内存用完了会怎样？看淘汰策略；默认 `noeviction` 会直接报错。

## 9. 分布式锁

本节依次回答：9.1 基于 setnx、9.2 Redisson 分布式锁。

### 9.1 基于 setnx

- `setnx` 即 SET if not exists，key 不存在才设置成功。
- 需要给锁设置过期时间，避免业务宕机后死锁。
- 过期时间难估：根据业务执行时间预估，或者给锁续期。

### 9.2 Redisson 分布式锁

- 底层基于 setnx 改进封装，加锁、设置过期时间等操作基于 Lua 脚本保证原子性。
- 看门狗 WatchDog：线程获取锁成功后，定期给锁续期，默认每隔 10 秒续期一次。
- 可重入：用 hash 结构记录线程标识和重入次数。
- 支持控制锁重试等待。
- 主从一致性：Redis 主从异步复制，主节点宕机可能导致两个线程同时持锁。
- RedLock（红锁）：在多个 Redis 实例上创建锁，要求 n/2+1 成功；性能差、运维繁琐、实现复杂。
- 如果业务必须强一致，建议用 Zookeeper 实现分布式锁。

**回答模板**

> 我们用的是 Redisson 分布式锁，底层是 setnx + Lua 脚本，带看门狗续期，支持可重入；主从场景下 Redisson 普通锁不能绝对保证一致，要求强一致可以用红锁或 Zookeeper，但性能会下降。

## 10. 集群方案

本节依次回答：10.1 主从复制、10.2 哨兵、10.3 脑裂、10.4 分片集群、10.5 怎么选。

### 10.1 主从复制

- 单节点并发能力有上限，主从集群实现读写分离：主节点写，从节点读。
- 全量同步：
  1. 从节点执行 `replicaof` 建立连接，请求同步。
  2. 主节点判断是否第一次同步，返回 replid 和 offset。
  3. 主节点执行 bgsave 生成 RDB，发送给从节点。
  4. RDB 生成期间的主节点命令记录到 `repl_baklog`。
  5. 发送日志文件中的命令，从节点执行。
- 增量同步：从节点重启或后续数据变化时，携带 replid 和 offset 请求，主节点从 `repl_baklog` 中取 offset 之后的数据发送。

### 10.2 哨兵

| 作用 | 说明 |
| --- | --- |
| 监控 | 不断检查 master 和 slave 是否按预期工作 |
| 自动故障恢复 | master 故障时提升一个 slave 为 master |
| 通知 | 集群故障转移后，把最新信息推送给客户端 |

- 主观下线：某个 sentinel 发现实例未在规定时间响应。
- 客观下线：超过 quorum 数量的 sentinel 都认为主观下线；quorum 最好超过 sentinel 数量的一半。
- 选主规则：先排除断开时间过长的从节点；再比较 `slave-priority`，越小越优先；再比较 offset，越大越优先；最后比较运行 id，越小越优先。

### 10.3 脑裂

- 主节点与 sentinel 处于不同网络分区，sentinel 提升新主，出现两个 master。
- 老主仍在接收写请求，网络恢复后被降为从节点，期间数据丢失。
- 解决配置：

```conf
min-replicas-to-write 1
min-replicas-max-lag 5
```

### 10.4 分片集群

- 解决海量数据存储和高并发写。
- 多个 master，每个 master 保存不同数据；每个 master 可以有多个 slave；master 之间 ping 监测健康。
- 16384 个哈希槽，key 经 CRC16 校验后对 16384 取模，决定槽位。
- 使用 `{tag}` 可以把相关 key 固定到同一槽，例如 `set {aaa}name itheima`。

### 10.5 怎么选

| 方案 | 解决的问题 | 适用 |
| --- | --- | --- |
| 主从 | 读并发、数据备份 | 读多写少 |
| 哨兵 | 主从自动故障恢复 | 一主一从，单节点内存不超过 10G |
| 分片 | 海量数据、高并发写 | 数据量大、写入压力大 |

## 11. Redis 为什么快

- 纯内存操作，执行速度快。
- 单线程执行命令，避免上下文切换和竞争条件，也不用考虑线程安全。
- 使用 I/O 多路复用模型，非阻塞 IO。
- 性能瓶颈通常是网络延迟，而不是执行速度。

**I/O 多路复用**

- 单个线程同时监听多个 Socket，某个 Socket 可读/可写时得到通知。
- select、poll 只通知有 Socket 就绪，需要用户进程逐个遍历确认。
- epoll 在通知的同时把已就绪的 Socket 写入用户空间，不需要遍历。

**Redis 6 的多线程**

- 命令回复使用多线程处理。
- 命令转换（协议解析）使用多线程。
- 命令执行仍然是单线程。
