# 05-微服务篇-项目链路追踪

> 范围：分布式链路追踪的必要性、JavaAgent 探针、SkyWalking 架构与部署、应用接入、UI 指标、告警配置。
> 主笔记：[[微服务/微服务 索引|微服务]]。

## 1. 为什么需要分布式链路追踪

微服务、分布式数据库、分布式缓存让后台服务组成复杂的分布式网络。一次前端请求要经过多个微服务、跨越多个数据中心才能返回结果。

![分布式调用网络](file:///D:/Java/data/面试/05-微服务篇-项目链路追踪/image-20210803222612693.png)

> 图：客户端请求经过多个服务和数据组件，调用关系复杂，人工很难还原完整链路。

由此带来的问题：

| 问题 | 说明 |
| --- | --- |
| 问题定位 | 某个服务节点失败导致调用失败，无法快速定位问题服务 |
| 性能分析 | 服务相互依赖，某个接口耗时过长会拖慢整条链路 |
| 服务拓扑 | 调用关系变化频繁，人工梳理困难 |
| 服务告警 | 服务出问题无法自动通知相关人员 |

分布式链路追踪把一次分布式请求还原成调用链路，集中展示各服务节点耗时、请求到达的机器、请求状态，并生成服务调用拓扑图。

## 2. JavaAgent 探针技术

本节依次回答：2.1 什么是 JavaAgent、2.2 两种 Agent。

### 2.1 什么是 JavaAgent

- JDK 1.5 以后可以构建独立于应用程序的代理程序（Agent），用于监测、运行甚至替换其他 JVM 上的程序。
- 可以实现虚拟机级别的 AOP，典型优势是**无代码侵入**。
- 常见应用：JRebel、Spring Boot 热部署、btrace、greys、Arthas。

### 2.2 两种 Agent

- 主程序之前运行的 Agent。
- 主程序之后运行的 Agent（1.6 以后提供，是前者的升级版）。

![JavaAgent 示意](file:///D:/Java/data/面试/05-微服务篇-项目链路追踪/image-20210803222647998.png)

> 图：左侧是 AOP 在业务方法前后织入逻辑；右侧是 JavaAgent 独立于应用 JAR 运行，在 JVM 层面对应用进行增强。

## 3. SkyWalking 核心概念与架构

本节依次回答：3.1 概述、3.2 三个名词、3.3 整体架构。

### 3.1 概述

- 2015 年由吴晟（华为开发者）主导开源，2017 年加入 Apache 孵化器。
- 是分布式系统的应用性能监控工具（APM），面向微服务、云原生、容器（Docker、K8s、Mesos）架构。
- 核心功能：指标分析、问题分析、服务拓扑、依赖分析、服务检测、性能优化、链路追踪、数据库监控、服务告警。

### 3.2 三个名词

| 名词 | 含义 |
| --- | --- |
| 服务 service | 业务资源应用系统 |
| 端点 endpoint | 应用系统对外暴露的功能接口 |
| 实例 instance | 物理机 |

![服务、端点与实例](file:///D:/Java/data/面试/05-微服务篇-项目链路追踪/image-20210803222738253.png)

> 图：一次 `/usr/queryAll` 请求经负载均衡落到用户服务集群的两个实例，用于说明服务与实例的层级关系；端点则是服务对外暴露的接口。

### 3.3 整体架构

![SkyWalking 架构](file:///D:/Java/data/面试/05-微服务篇-项目链路追踪/image-20210803222753214.png)

> 图：Agent 采集追踪与指标数据上报 OAP；OAP 负责接收、分析、聚合、存储并提供查询 API；Storage 可用 H2、Elasticsearch、MySQL；WebUI 展示数据。

**客户端**

- Agent 组件：基于探针采集跟踪数据和统计数据，上报给 OAP。

**服务端**

| 组件 | 作用 |
| --- | --- |
| OAP | Observability Analysis Platform，可观测性分析平台，接收、分析、聚合、存储数据，提供查询 API |
| Storage | 存储介质，默认 H2，也支持 Elasticsearch、MySQL 等 |
| WebUI | 图形化展示跟踪数据、指标数据 |

**易错点**

- OAP 就是链路追踪系统里的 Collector。
- 默认 H2 重启会丢数据，生产环境通常换成 Elasticsearch。

## 4. 环境搭建

本节依次回答：4.1 部署 OAP、4.2 部署 UI。

### 4.1 部署 OAP

```bash
docker pull apache/skywalking-oap-server

docker run --name skywalking -d \
  -p 1234:1234 -p 11800:11800 -p 12800:12800 \
  --restart always apache/skywalking-oap-server
```

- 默认使用 H2 存储，重启数据会丢失。
- 项目中已有 Elasticsearch 时，进入容器修改 `/config/application.yml` 指定 ES 地址，再重启容器。

### 4.2 部署 UI

```bash
docker pull apache/skywalking-ui

docker run --name skywalking-ui -d -p 8686:8080 \
  --link skywalking:skywalking \
  -e SW_OAP_ADDRESS=skywalking:12800 \
  --restart always apache/skywalking-ui
```

访问 `http://<服务器IP>:8686/`。

## 5. 应用接入

本节依次回答：5.1 启动参数、5.2 Gateway 支持。

### 5.1 启动参数

在应用启动时通过 `-javaagent` 指定 Agent：

```properties
-javaagent:D:\develop\agent\skywalking-agent.jar -Dskywalking.agent.service_name=heima-leadnews-user
```

- Agent 负责采集数据并提交到 OAP，默认地址是 `127.0.0.1`。
- 在 `agent/config/agent.config` 中修改 OAP 地址。
- 一个服务多节点部署时，服务名称要保证不一样。

### 5.2 Gateway 支持

当前 Agent 对 Spring Cloud Gateway 支持不好，需要把 `optional-plugins` 下的两个 Jar 拷贝到 `agent/plugins`：

- `apm-spring-cloud-gateway-2.1.x-plugin-8.2.0.jar`
- `apm-spring-webflux-5.x-plugin-8.2.0.jar`

**易错点**

- `-javaagent` 路径要指向自己机器上的 Agent。
- 网关、用户服务、文章服务等都要分别改启动参数。

## 6. UI 指标怎么看

本节依次回答：6.1 Apdex 用户满意度、6.2 cpm 每分钟请求数、6.3 SLA 服务等级协议、6.4 Percent Response 百分位、6.5 Heatmap 热力图。

### 6.1 Apdex 用户满意度

Apdex 是基于响应时间阈值的满意度指标。管理员定义阈值 T：

- 响应时间在 T 内：满意。
- 大于 T：不满意。
- 大于 4T：沮丧。

例如 T = 1.2 秒，0.5 秒完成是满意，超过 1.2 秒不满意，超过 4.8 秒沮丧。

### 6.2 cpm 每分钟请求数

- cpm 全称 call per minutes，是吞吐量指标。
- `185 cpm = 185 / 60 ≈ 3.08 请求/秒`。

### 6.3 SLA 服务等级协议

| 可用性 | 全年不可用时间 |
| --- | --- |
| 99% | 3.65 天 |
| 99.9% | 8.76 小时 |
| 99.99% | 52.6 分钟 |
| 99.999% | 5.26 分钟 |

全年只要发生一次较大规模宕机，4 个 9 基本没戏，一般平台 3 个 9 差不多。

### 6.4 Percent Response 百分位

- p50、p75、p90、p95、p99 表示对应比例的请求响应时间。
- `p99:390` 表示 99% 的请求响应时间在 390ms 以内。

### 6.5 Heatmap 热力图

- 颜色越深表示请求数越多。
- 纵坐标是响应时间，鼠标悬停可看具体数量。
- 可以直观感受整体流量和性能。

## 7. 告警配置

SkyWalking 6.x 新增告警功能，核心是一组规则，定义在 `config/alarm-settings.yml`。

### 7.1 两部分组成

| 部分 | 作用 |
| --- | --- |
| 告警规则 rules | 定义如何触发度量警报、考虑什么条件 |
| Webhook | 定义告警触发时通知哪些服务终端 |

### 7.2 规则字段

| 字段 | 说明 |
| --- | --- |
| Rule name | 规则名称，必须以 `_rule` 结尾 |
| Metrics name | 度量名称，取 OAL 脚本中的度量名 |
| Include names | 规则作用于哪些实体（可选） |
| Exclude names | 规则不作用于哪些实体（可选） |
| Threshold | 阈值 |
| OP | 操作符，支持 `>`、`<`、`=` |
| Period | 多久核实一次，是时间窗口 |
| Count | 一个 Period 内达到阈值多少次触发告警 |
| Silence period | 触发后静默时间 |
| message | 告警消息 |

### 7.3 默认规则

1. 过去 10 分钟的 3 分钟内，服务平均响应时间超过 1 秒达 3 次。
2. 过去 10 分钟内，服务成功率低于 80% 达 2 次。
3. 过去 10 分钟内，服务 90% 响应时间低于 1 秒达 3 次。
4. 过去 10 分钟内，服务响应时间超过 1 秒达 2 次。
5. 过去 10 分钟内，端点响应时间超过 1 秒达 2 次。

### 7.4 Webhook 与邮件告警

- SkyWalking 不直接发邮件/短信，只把告警信息 POST 到配置的 Webhook 接口。
- Webhook 是 Web 层面的回调机制，事件发生时调用配置好的接口。
- 只需要找一个“清闲”的服务实现 Webhook 接口，不需要所有服务都配。

配置示例：

```yaml
webhooks:
  - http://127.0.0.1/alarm/emailNotify
```

接收告警的 Controller：

```java
@RestController
@RequestMapping("/alarm")
@Slf4j
public class AlarmController {

    @Autowired
    private JavaMailSender javaMailSender;

    @PostMapping("/emailNotify")
    public void emailAlarm(@RequestBody List<AlarmDTO> alarmDTOList) {
        SimpleMailMessage mailMessage = new SimpleMailMessage();
        mailMessage.setFrom("itheim@163.com");
        mailMessage.setTo("xx@itcast.cn");
        mailMessage.setSubject("skywalking告警邮件");
        mailMessage.setText(alarmDTOList.toString());
        javaMailSender.send(mailMessage);
        log.info("告警邮件已发送");
    }
}
```

**易错点**

- Webhook 接口不需要配置到所有服务上。
- 告警规则名称必须以 `_rule` 结尾，否则不生效。
