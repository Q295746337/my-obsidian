## 1. 如何定位慢查询

本节依次回答：1.1 两种方案、1.2 回答模板、1.3 常见慢 SQL 类型。

### 1.1 两种方案

| 方案 | 工具/配置 | 说明 |
| --- | --- | --- |
| 开源工具 | Arthas、Prometheus、Skywalking | 监控接口耗时，判断是否是 SQL 问题 |
| MySQL 慢日志 | `slow_query_log`、`long_query_time` | 记录超过阈值的 SQL |

慢日志配置：

```conf
slow_query_log=1
long_query_time=2
```

日志位置通常为 `/var/lib/mysql/localhost-slow.log`。

### 1.2 回答模板

> 压测时发现一个接口大约 5 秒，先用 Skywalking 定位到是 SQL 问题，再开启 MySQL 慢日志，把阈值设为 2 秒，拿到慢 SQL 后用 EXPLAIN 分析。

### 1.3 常见慢 SQL 类型

- 聚合查询
- 多表查询
- 表数据量过大
- 深度分页

## 2. EXPLAIN 怎么看

使用 `EXPLAIN` 或 `DESC` 获取 SELECT 的执行信息。

| 字段 | 含义 | 关注点 |
| --- | --- | --- |
| possible_key | 可能用到的索引 | 是否有可用索引 |
| key | 实际命中的索引 | 是否真的走了索引 |
| key_len | 索引占用大小 | 联合索引用到了几列 |
| type | 连接类型 | 是否有全表扫描 |
| Extra | 额外优化建议 | 是否回表、是否使用覆盖索引 |

**type 性能从好到差**

`NULL` → `system` → `const` → `eq_ref` → `ref` → `range` → `index` → `all`

- system：查询系统表
- const：根据主键查询
- eq_ref：主键或唯一索引查询
- ref：普通索引查询
- range：范围查询
- index：索引树扫描
- all：全表扫描

**Extra 常见值**

| Extra | 含义 |
| --- | --- |
| Using where; Using Index | 使用了索引，且需要的数据都在索引列中，不需要回表 |
| Using index condition | 使用了索引，但需要回表查询 |

**回答模板**

> 用 EXPLAIN 看 key 和 key_len 判断是否命中索引；看 type 判断是否全索引扫描或全表扫描；看 Extra 判断是否回表，必要时加索引或修改返回字段。

## 3. 存储引擎与体系结构

本节依次回答：3.1 三种常见引擎、3.2 MySQL 体系结构。

### 3.1 三种常见引擎

| 特性 | MyISAM | InnoDB | MEMORY |
| --- | --- | --- | --- |
| 事务安全 | 不支持 | 支持 | 不支持 |
| 锁机制 | 表锁 | 表锁/行锁 | 表锁 |
| 外键 | 不支持 | 支持 | 不支持 |

- InnoDB 是 MySQL 5.5 之后的默认引擎，支持事务、行级锁、外键。
- MyISAM 不支持事务，只有表级锁，没有外键，使用较少。
- MEMORY 数据存内存，支持表级锁，没有事务和外键。

- 服务层：SQL 接口、解析器、查询优化器、缓存。

## 4. 索引底层数据结构

本节依次回答：4.1 为什么是 B+ 树、4.2 聚簇索引与非聚簇索引、4.3 回表与覆盖索引。

### 4.1 为什么是 B+ 树

- 索引是帮助 MySQL 高效获取数据的有序数据结构。
- InnoDB 使用 B+ 树：阶数多、路径短，磁盘读写代价低。
- 非叶子节点只存指针，叶子节点存数据。
- 叶子节点是双向链表，便于扫库和区间查询。

**B 树与 B+ 树对比**

- 磁盘读写代价 B+ 树更低。
- 查询效率 B+ 树更稳定。
- B+ 树便于扫库和区间查询。

### 4.2 聚簇索引与非聚簇索引

| 分类 | 含义 | 特点 |
| --- | --- | --- |
| 聚集索引（聚簇索引） | 数据与索引放在一起，叶子节点保存整行数据 | 必须有且只有一个 |
| 二级索引（非聚簇索引） | 数据与索引分开，叶子节点保存主键 | 可以有多个 |

聚集索引选取规则：

- 有主键时，主键索引就是聚集索引。
- 没有主键时，使用第一个唯一索引作为聚集索引。
- 都没有时，InnoDB 自动生成 rowid 作为隐藏的聚集索引。

![聚集索引 B+ 树](file:///D:/Java/data/面试/03-MySQL篇/slide024_img1.png)

> 图：聚集索引的叶子节点直接保存整行数据，按主键有序排列。

![二级索引 B+ 树](file:///D:/Java/data/面试/03-MySQL篇/slide024_img2.png)

> 图：二级索引的叶子节点保存主键或行定位信息，查询非索引列时需要按主键回到聚集索引，即回表。

### 4.3 回表与覆盖索引

- 回表：先走二级索引找到主键，再回聚集索引查整行数据。
- 覆盖索引：查询使用的索引中已经包含需要返回的全部列，不需要回表。
- 使用主键查询直接走聚集索引，一次扫描即可返回。
- 尽量避免 `select *`，返回列没有索引时容易触发回表。

**易错点**

- 覆盖索引不是一种索引类型，而是一种查询状态。
- 联合索引能否覆盖，取决于查询列是否都在联合索引中。

## 5. 超大分页

`limit 9000000,10` 需要排序前 9000010 条记录，只返回其中 10 条，排序代价很大。

优化：覆盖索引 + 子查询。

```sql
select *
from tb_sku t,
     (select id from tb_sku order by id limit 9000000,10) a
where t.id = a.id;
```

**回答要点**

- 问题：数据量大时，limit 越往后越慢。
- 方案：先在索引上取出主键，再用主键关联取整行。

## 6. 索引创建原则

1. 数据量较大且查询频繁的表建立索引。
2. 常作为 where、order by、group by 条件的字段建立索引。
3. 选择区分度高的列，尽量建立唯一索引。
4. 字符串字段较长时，建立前缀索引。
5. 尽量使用联合索引，减少单列索引，便于覆盖索引。
6. 控制索引数量，索引越多，增删改维护成本越高。
7. 索引列不能存 NULL 时，建表时加 NOT NULL 约束，便于优化器选择索引。

## 7. 索引失效场景

| 场景 | 说明 |
| --- | --- |
| 违反最左前缀法则 | 联合索引从最左列开始匹配，不能跳过中间列 |
| 范围查询右边的列 | 范围查询后的列不能使用索引 |
| 索引列参与运算 | 例如在索引列上做函数或表达式计算 |
| 字符串不加单引号 | 隐式类型转换导致索引失效 |
| 以 `%` 开头的 Like | 头部模糊匹配失效，尾部模糊匹配通常不失效 |

**回答模板**

> 我们建了 `(name, status, address)` 联合索引，查询时遵守最左前缀；范围查询后的列用不到索引；不在索引列上做运算；字符串参数加引号；Like 避免前置 `%`。

## 8. SQL 优化经验

本节依次回答：8.1 表设计、8.2 SQL 语句、8.3 架构层面。

### 8.1 表设计

- 数值类型按实际范围选择 tinyint、int、bigint。
- 字符串类型按场景选择 char 和 varchar：char 定长效率高，varchar 可变长度效率稍低。

### 8.2 SQL 语句

- SELECT 明确字段，避免 `select *`。
- 避免索引失效写法。
- 尽量用 `union all` 代替 `union`，`union` 会多一次过滤。
- 避免在 where 子句中对字段做表达式操作。
- Join 优化：能用 inner join 就不用 left join/right join；必须使用时以小表为驱动表。

### 8.3 架构层面

- 读写分离：读多写少时，避免写操作影响查询。
- 主从复制分担访问压力，解决存储压力。

## 9. 事务与 MVCC

本节依次回答：9.1 ACID、9.2 并发事务问题、9.3 隔离级别、9.4 redo log 与 undo log、9.5 MVCC 实现。

### 9.1 ACID

| 特性 | 含义 |
| --- | --- |
| 原子性 Atomicity | 事务是不可分割的最小操作单元，要么全部成功，要么全部失败 |
| 一致性 Consistency | 事务完成后所有数据保持一致状态 |
| 隔离性 Isolation | 事务在不受外部并发操作影响的独立环境中运行 |
| 持久性 Durability | 事务提交或回滚后，数据改变是永久的 |

### 9.2 并发事务问题

| 问题 | 描述 |
| --- | --- |
| 脏读 | 一个事务读到另一个事务尚未提交的数据 |
| 不可重复读 | 一个事务先后读取同一条记录，两次结果不同 |
| 幻读 | 一个事务按条件查询没有数据，插入时发现数据已存在 |

### 9.3 隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| Read uncommitted 未提交读 | √ | √ | √ |
| Read committed 读已提交 | × | √ | √ |
| Repeatable Read 可重复读（默认） | × | × | √ |
| Serializable 串行化 | × | × | × |

隔离级别越高，数据越安全，但性能越低。

### 9.4 redo log 与 undo log

| 日志 | 内容 | 作用 |
| --- | --- | --- |
| redo log | 数据页的物理修改 | 保证持久性，宕机后恢复 |
| undo log | 逻辑日志，记录修改前的信息 | 回滚；MVCC 版本链 |

- redo log 使用 WAL（Write-Ahead Logging），先写日志再刷脏页。
- undo log 记录反向操作：delete 对应 insert，update 记录相反的 update。

### 9.5 MVCC 实现

MVCC 指多版本并发控制，维护数据的多个版本，使读写不冲突。

**三个依赖**

- 隐藏字段：`DB_TRX_ID`（最近修改事务 ID）、`DB_ROLL_PTR`（回滚指针）、`DB_ROW_ID`（无主键时生成）。
- undo log：update/delete 产生的 undo log 不仅用于回滚，也用于 MVCC 版本链。
- ReadView：快照读时判断能访问哪个版本。

**版本链**：不同事务或同一事务对同一条记录的修改，通过回滚指针形成链表，头部是最新版本。

**ReadView 四个字段**

| 字段 | 含义 |
| --- | --- |
| m_ids | 当前活跃的事务 ID 集合 |
| min_trx_id | 最小活跃事务 ID |
| max_trx_id | 预分配事务 ID，当前最大事务 ID + 1 |
| creator_trx_id | ReadView 创建者的事务 ID |

**可见性规则**

1. `trx_id == creator_trx_id`：可以访问。
2. `trx_id < min_trx_id`：可以访问。
3. `trx_id > max_trx_id`：不可以访问。
4. `min_trx_id <= trx_id <= max_trx_id`：如果 trx_id 不在 m_ids 中，可以访问。

**RC 与 RR 的区别**

- RC：每次快照读都生成新的 ReadView。
- RR：只在事务中第一次快照读时生成 ReadView，后续复用。

**当前读与快照读**

- 当前读：`select ... lock in share mode`、`select ... for update`、update、insert、delete，读取最新版本并加锁。
- 快照读：普通 select，不加锁，读取可见版本，是非阻塞读。

## 10. 主从同步原理

MySQL 主从复制的核心是二进制日志 binlog，记录 DDL 和 DML，不记录 SELECT、SHOW。

1. Master 在事务提交时，把数据变更记录到 binlog。
2. Slave 读取 Master 的 binlog，写入自己的中继日志 Relay Log。
3. Slave 重做 Relay Log 中的事件，把变更反映到自己的数据。

## 11. 分库分表

本节依次回答：11.1 时机、11.2 拆分方式、11.3 分库之后的新问题。

### 11.1 时机

- 业务数据逐渐增多，或业务发展迅速。
- 优化已解决不了性能问题（主从读写分离、索引等）。
- 出现 IO 瓶颈（磁盘 IO、网络 IO）或 CPU 瓶颈（聚合查询、连接数太多）。
- 单表数据量达到 1000 万或 20G 以后。

### 11.2 拆分方式

| 方式 | 依据 | 解决的问题 |
| --- | --- | --- |
| 垂直分库 | 按业务把不同表拆到不同库 | 业务分级管理，提高磁盘 IO 和连接数 |
| 垂直分表 | 按字段属性拆表 | 冷热数据分离，减少 IO 争抢 |
| 水平分库 | 把一个库的数据拆到多个库 | 单库大数据量、高并发 |
| 水平分表 | 把一个表的数据拆到多个表 | 单表数据量过大 |

水平分库路由规则：按 id 取模（`id % 3`）或按范围路由。

### 11.3 分库之后的新问题

- 分布式事务一致性
- 跨节点关联查询
- 跨节点分页、排序函数
- 主键避重

常用中间件：ShardingSphere、MyCat。

**回答模板**

> 先说明业务数据量达到单表 1000 万或 20G；再讲拆分策略：水平分库解决海量存储和高并发，水平分表解决单表性能，垂直分库按业务拆分，垂直分表做冷热分离；最后补中间件和分布式事务等新问题。
