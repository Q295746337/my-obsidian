# 06-消息中间件篇 面试笔记

> 范围：RabbitMQ 消息可靠性、重复消费、延迟/死信队列、消息堆积、高可用；Kafka 可靠性、顺序性、高可用、存储清理、高性能设计。
> 主笔记：[[SpringBoot2/03-开发实用篇/08-整合第三方技术-消息|SpringBoot2 消息]]、[[Redis/实战篇/实战-消息队列|Redis 消息队列]]。

## 1. RabbitMQ 如何保证消息不丢失

消息可能在三个位置丢失：

1. 消息未到达交换机。
2. 消息未到达队列。
3. 消费者处理失败或未确认。

### 1.1 生产者确认机制

- `publisher confirm`：消息发送到 MQ 后，返回结果表示是否处理成功。
- `publish-confirm`：确认消息是否到达交换机，返回 ack/nack。
- `publish-return`：确认消息是否到达队列，路由失败时回调。

**失败处理**

- 回调方法即时重发。
- 记录日志。
- 保存到数据库，定时重发，成功后删除记录。

### 1.2 消息持久化

MQ 默认内存存储，开启持久化可保证缓存在 MQ 中的消息不丢失。

```java
@Bean
public DirectExchange simpleExchange() {
    // 交换机名称、是否持久化、没有队列绑定时是否自动删除
    return new DirectExchange("simple.direct", true, false);
}

@Bean
public Queue simpleQueue() {
    return QueueBuilder.durable("simple.queue").build();
}
```

```java
Message msg = MessageBuilder
        .withBody(message.getBytes(StandardCharsets.UTF_8))
        .setDeliveryMode(MessageDeliveryMode.PERSISTENT)
        .build();
```

### 1.3 消费者确认

| 模式 | 说明 |
| --- | --- |
| manual | 手动 ack，业务代码结束后调用 API 发送 ack |
| auto | Spring 监测 listener 是否异常；无异常 ack，抛异常 nack |
| none | 关闭 ack，消息投递后立即删除 |

### 1.4 消费者失败重试

- 利用 Spring 的 retry 机制本地重试，设置重试次数。
- 重试耗尽后仍失败，把消息投递到异常交换机，交由人工处理。

**四步回答**

> 开启生产者确认，确保消息到达队列；开启持久化，确保未消费前不丢；消费者确认设为 auto；开启失败重试，超过次数投递异常交换机。

## 2. 消息重复消费

本节依次回答：2.1 解决思路。

### 2.1 解决思路

1. 每条消息设置唯一标识 id。
2. 用幂等方案：分布式锁、数据库锁（悲观锁、乐观锁）。
3. 用业务唯一标识：支付 id、订单 id、文章 id。
4. 消费前校验业务 id 是否存在。

**适用范围**：Kafka、RabbitMQ、RocketMQ 等任何 MQ。

**易错点**

- 幂等是业务侧保证，不是 MQ 自动保证。
- “至少一次”投递必然可能重复，不能假设 MQ 只投一次。

## 3. 延迟队列与死信队列

本节依次回答：3.1 死信条件、3.2 TTL、3.3 延迟队列插件。

### 3.1 死信条件

消息满足以下任一条件成为死信：

- 消费者使用 `basic.reject` 或 `basic.nack` 拒绝，且 `requeue=false`。
- 消息过期，超时无人消费。
- 队列消息堆积满，最早的消息可能成为死信。

队列配置 `dead-letter-exchange` 后，死信投递到该交换机，即死信交换机（DLX）。

### 3.2 TTL

- TTL 即 Time-To-Live，消息存活时间。
- 两种设置：队列设置存活时间，或消息本身设置存活时间。
- 延迟队列 = 死信交换机 + TTL。

### 3.3 延迟队列插件

- DelayExchange 插件需要安装在 RabbitMQ 中。
- 本质仍是官方三种交换机，只是增加了延迟功能。
- 声明交换机时设置 `delayed=true`。
- 发送消息时添加 `x-delay` 头，值为超时时间。

**业务场景**：超时订单、限时优惠、定时发布。

**回答模板**

> 我们用死信交换机 + TTL 实现延迟队列：消息超时未消费变成死信，进入死信交换机，再由消费者处理；也用过 DelayExchange 插件，声明 delayed 交换机并设置 x-delay。

## 4. 消息堆积

本节依次回答：4.1 三种思路、4.2 惰性队列。

### 4.1 三种思路

1. 增加更多消费者，提高消费速度。
2. 消费者内开启线程池，加快消息处理速度。
3. 扩大队列容积，提高堆积上限。

### 4.2 惰性队列

| 特征 | 说明 |
| --- | --- |
| 存储 | 收到消息直接存磁盘，不存内存 |
| 读取 | 消费时再从磁盘加载到内存 |
| 容量 | 支持数百万条消息 |
| 性能 | 稳定，但受磁盘 IO 限制，时效性降低 |

声明方式：设置 `x-queue-mode=lazy`。

**易错点**

- 加消费者不一定能解决，要看瓶颈在消费逻辑还是数据库。
- 惰性队列牺牲时效性换容量。

## 5. RabbitMQ 高可用

| 模式 | 特征 | 缺点 |
| --- | --- | --- |
| 普通集群 | 节点间共享交换机、队列元信息，不共享队列消息；访问其他节点时转发 | 队列所在节点宕机，消息丢失 |
| 镜像集群 | 主从模式，交换机、队列、消息同步备份；主节点处理，同步给镜像；主宕机镜像接替 | 主从同步完成前主宕机可能丢数据 |
| 仲裁队列 | 3.8 以后，主从模式，基于 Raft 强一致，配置简单 | 需要较新版本 |

**回答模板**：生产环境用镜像模式搭 3 节点集群；镜像队列是一主多从，主宕机后镜像接替，但同步未完成时可能丢数据；可以用仲裁队列替代，基于 Raft 强一致。

## 6. Kafka 如何保证消息不丢失

本节依次回答：6.1 生产者发送到 Broker 丢失、6.2 Broker 存储丢失、6.3 消费者接收丢失。

### 6.1 生产者发送到 Broker 丢失

- 设置异步发送，失败回调记录日志或重发。
- 设置重试次数。

```java
props.put(ProducerConfig.RETRIES_CONFIG, 10);
```

### 6.2 Broker 存储丢失

发送确认机制 acks：

| 配置 | 说明 |
| --- | --- |
| acks=0 | 不等待服务器响应，速度最快，可能丢失 |
| acks=1（默认） | leader 收到消息就返回成功 |
| acks=all | 所有参与复制的节点都收到才返回成功 |

生产环境建议 `acks=all`。

### 6.3 消费者接收丢失

- 消费者默认每隔 5 秒自动提交偏移量。
- 发生重平衡时可能重复消费或丢数据。
- 解决：关闭自动提交，改为手动提交。
- 提交方式：同步提交、异步提交、同步 + 异步组合提交。

**三层回答**

> 生产者异步发送 + 失败重试；Broker 使用 acks=all；消费者关闭自动提交，手动同步 + 异步提交偏移量。

## 7. Kafka 顺序性

- Kafka 只保证一个分区内的消息顺序，不保证跨分区顺序。
- 一个 topic 的数据可能分布在不同分区，每个分区有自己的偏移量。
- 解决：
  - 发送消息时指定分区号。
  - 发送消息时按相同业务设置相同 key。
- 如果要全局有序，只提供一个分区。

**易错点**

- 增加分区会破坏原有的 key 到分区映射，顺序性需要重新评估。
- 顺序性和吞吐量需要权衡。

## 8. Kafka 高可用

本节依次回答：8.1 集群、8.2 分区副本、8.3 ISR。

### 8.1 集群

- Kafka 服务端由多个 Broker 组成。
- 某台机器宕机，其他 Broker 仍可对外提供服务。

### 8.2 分区副本

- 一个 topic 有多个分区，每个分区有多个副本。
- 一个 leader，其余是 follower，副本存储在不同 Broker。
- 所有副本内容相同，leader 故障时自动提升一个 follower 为 leader。

### 8.3 ISR

- ISR（in-sync replica）是需要同步复制保存的 follower。
- 副本分两类：ISR 与 leader 同步；普通副本异步同步。
- leader 失效后优先从 ISR 中选新 leader；ISR 都不行才从其他 follower 选。

**回答模板**：从集群和复制机制两个层面回答——多 Broker 保证单机故障不影响整体；多副本 + leader/follower + ISR 保证分区容错和自动选主。

## 9. Kafka 存储与清理

本节依次回答：9.1 存储结构、9.2 清理策略。

### 9.1 存储结构

- topic 的数据存储在分区上。
- 分区文件过大时分成多个 Segment。
- 每个 Segment 对应 `.index` 索引文件、`.log` 数据文件、`.timeindex` 时间索引文件。

**为什么要分段**

- 删除无用文件方便，提高磁盘利用率。
- 查找数据便捷。

### 9.2 清理策略

| 策略 | 说明 |
| --- | --- |
| 按时间 | 超过保留时间触发清理，默认 168 小时（7 天） |
| 按大小 | topic 日志文件超过阈值，删除最久消息；默认关闭，需手动开启 |

## 10. Kafka 为什么高性能

| 设计 | 作用 |
| --- | --- |
| 消息分区 | 不受单台服务器限制，处理更多数据 |
| 顺序读写 | 磁盘顺序读写，提升效率 |
| 页缓存 | 磁盘数据缓存到内存，把磁盘访问变为内存访问 |
| 零拷贝 | 减少上下文切换和数据拷贝 |
| 消息压缩 | 减少磁盘 IO 和网络 IO |
| 分批发送 | 消息打包批量发送，减少网络开销 |

| 问题 | 一句话答案 |
| --- | --- |
| RabbitMQ 不丢 | 生产者确认 + 持久化 + 消费者 auto ack + 失败重试/异常交换机 |
| 重复消费 | 唯一 id + 幂等（锁、唯一索引、业务 id 校验） |

| 消息堆积 | 加消费者、线程池、惰性队列扩容 |
| RabbitMQ 高可用 | 普通集群、镜像集群、仲裁队列（Raft） |
| Kafka 不丢 | 异步发送 + 重试、acks=all、手动提交 offset |
| Kafka 顺序 | 同分区有序；指定分区或相同 key；全局有序单分区 |
| Kafka 高可用 | Broker 集群 + 分区副本 + ISR 选主 |
| Kafka 存储 | Segment + index/log/timeindex；按时间或大小清理 |
| Kafka 高性能 | 分区、顺序读写、页缓存、零拷贝、压缩、批量 |
