## 1. 单点登录 SSO

本节依次回答：1.1 什么是单点登录、1.2 JWT 解决单点登录。

### 1.1 什么是单点登录

- 英文 Single Sign On，简称 SSO。
- 只需要登录一次，就可以访问所有信任的应用系统。
- 单体应用多个 Tomcat 时 session 不共享；微服务/分布式场景需要统一认证。

**常见方案**：JWT（常见）、OAuth2、CAS。

> 补充：来自新下载讲义。多系统 Session 不共享时，可选方案包括 Tomcat 集群 Session 全局复制（最多支持约 5 台，不推荐）、JWT、OAuth2、CAS，以及自己用 Redis + token 实现。

### 1.2 JWT 解决单点登录

1. 用户访问其他系统，网关判断 token 是否有效。
2. token 无效返回 401，前端跳转登录页。
3. 用户登录成功后，登录服务返回 token（JWT），浏览器把 token 写入 cookie。
4. 后续访问其他服务都携带 token，由网关统一校验后路由到目标服务。

**回答结构**

1. 先解释什么是单点登录。
2. 介绍自己项目中涉及的单点登录，即使没做过也可以说实现思路。
3. 以 JWT 为例介绍解决方案：网关统一校验、401 跳登录、token 存 cookie、携带 token 访问。

**易错点**

- SSO 解决的是“多个系统统一登录”，不是“一个系统内记住登录状态”。
- JWT 是无状态的，服务端不保存会话，但要注意过期和续期。

## 2. 权限认证 RBAC

本节依次回答：2.1 模型、2.2 鉴权流程。

### 2.1 模型

RBAC（Role-Based Access Control）基于角色的访问控制，三个基础部分：

- 用户
- 角色
- 权限

**表结构**

| 方案 | 表 |
| --- | --- |
| 5 张表 | 用户表、角色表、权限表、用户角色中间表、角色权限中间表 |
| 7 张表 | 在上述基础上增加菜单表、权限菜单中间表 |

### 2.2 鉴权流程

1. 用户登录系统。
2. 查询用户拥有的角色列表。
3. 根据角色查询拥有的权限。
4. 判断是否具备访问权限。

**权限框架**：Apache Shiro、Spring Security（推荐）。

**回答模板**：后台管理系统更注重权限控制，我们采用 RBAC 模型，5 张表描述用户、角色、权限及关联关系，登录后先查角色再查权限，框架用 Spring Security。

## 3. 上传数据的安全性

本节依次回答：3.1 基本方案、3.2 对称与非对称。

### 3.1 基本方案

使用对称加密或非对称加密：前端拿公钥加密数据，后台解密后处理。

### 3.2 对称与非对称

| 维度 | 对称加密 | 非对称加密 |
| --- | --- | --- |
| 密钥 | 加密解密使用同一个密钥 | 公钥加密，私钥解密 |
| 速度 | 快，效率高 | 慢 |
| 安全性 | 相对较低，不要保存敏感信息 | 更高 |
| 适用 | 文件较大 | 文件较小、安全性要求高 |

> 补充：来自新下载讲义。常见对称加密算法：AES、DES、3DES、Blowfish、IDEA、RC4、RC5、RC6、HS256；常见非对称加密算法：RSA、DSA（数字签名）、ECC（移动设备）、RS256（采用 SHA-256 的 RSA 签名）。非对称加密还可以用于签名：私钥签名，公钥验签，用来判断内容是否被篡改。

**回答模板**

> 文件很大建议用对称加密，但不能保存敏感信息；文件较小、安全性要求高，建议用非对称加密。

**易错点**

- 对称加密的密钥不能硬编码在前端。
- 非对称加密性能低，不适合大文件。

## 4. 日志采集

本节依次回答：4.1 为什么要采集日志、4.2 常见方式、4.3 ELK 三个组件、4.4 回答模板。

### 4.1 为什么要采集日志

日志是定位系统问题的重要手段，可以根据日志快速定位系统中的问题。

### 4.2 常见方式

| 方式 | 说明 |
| --- | --- |
| 常规采集 | 按天保存到一个日志文件 |
| ELK | Elasticsearch、Logstash、Kibana |

### 4.3 ELK 三个组件

| 组件 | 作用 |
| --- | --- |
| Elasticsearch | 全文搜索分析引擎，对数据存储、搜索、分析 |
| Logstash | 数据收集引擎，动态收集、过滤、分析数据，存储到指定位置 |
| Kibana | 数据分析和可视化平台，配合 ES 搜索、分析、图表化展示 |

**链路**：应用 logback 输出日志 → Logstash 收集 → Elasticsearch 存储 → Kibana 展示。

### 4.4 回答模板

> 我们搭建了 ELK 日志采集系统：Logstash 动态收集和过滤日志，Elasticsearch 存储和搜索分析，Kibana 做可视化展示。

## 5. 查看日志的命令

本节依次回答：5.1 实时监控、5.2 按行号查询、5.3 按关键字和日期、5.4 日志太多时。

### 5.1 实时监控

```bash
# 实时监控日志变化
tail -f xx.log

# 实时监控最后 100 行
tail -n 100 -f xx.log
```

### 5.2 按行号查询

```bash
# 查询尾部最后 100 行
tail -n 100 xx.log

# 查询头部开始 100 行
head -n 100 xx.log

# 查询 100 到 200 行
cat -n xx.log | tail -n +100 | head -n 100
```

### 5.3 按关键字和日期

```bash
# 查询包含 debug 的行号
cat -n xx.log | grep "debug"

# 按日期区间查询
sed -n '/2023-05-18 14:22:31.070/,/2023-05-18 14:27:14.158/p' xx.log
```

### 5.4 日志太多时

```bash
# 分页查看
cat -n xx.log | grep "debug" | more

# 过滤后输出到文件
cat -n xx.log | grep "debug" > debug.txt
```

**易错点**

- `tail -f` 会持续占用终端，排查完要退出。
- 大文件不要直接用 `cat` 全量输出，先 grep 再分页。

## 6. 生产问题排查

本节依次回答：6.1 基本思路、6.2 远程 debug、6.3 压测与监控、6.4 Arthas、6.5 回答模板。

### 6.1 基本思路

1. 先分析日志：业务日志、系统日志、日志文件，定位问题。
2. 远程 debug：通常只允许在测试环境，生产环境一般不允许。

### 6.2 远程 debug

前提：远程代码和本地代码保持一致。

远程启动参数：

```bash
java -jar -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=5005 project-1.0-SNAPSHOT.jar
```

**参数含义**

> 补充：来自新下载讲义。

| 参数 | 含义 |
| --- | --- |
| `-agentlib:jdwp` | 通知 JVM 使用 JDWP（Java Debug Wire Protocol）运行调试环境 |
| `transport=dt_socket` | 调试数据通过 socket 传输 |
| `server=y` | 以 server 模式运行，等待调试客户端连接 |
| `suspend=n` | 启动时不挂起，调试客户端连上后再调试 |
| `address=5005` | 调试端口，可换成其他端口 |

IDEA 中配置 Remote JVM Debug，启动后访问远程服务器，在本地代码打断点即可调试。

### 6.3 压测与监控

| 类别 | 工具/指标 |
| --- | --- |
| 压测工具 | LoadRunner、Apache JMeter |
| 压测指标 | 响应时间、QPS、并发数、吞吐量、CPU 利用率、内存使用率、磁盘 IO、错误率 |
| 监控 | Prometheus + Grafana |
| 链路追踪 | SkyWalking、Zipkin |
| 线上诊断 | Arthas |

**压测目的**：给出系统当前性能状况；定位性能瓶颈或潜在瓶颈。

**怎么快速定位系统瓶颈**：先压测拿到性能基线，结合 Prometheus + Grafana 看 CPU、内存、磁盘 IO，再用 SkyWalking/Zipkin 找慢接口和慢服务，最后用 Arthas 做线上诊断。

### 6.4 Arthas

- 官网：`https://arthas.aliyun.com/`
- 用于项目上线后的监控、排查。

### 6.5 回答模板

> 先看日志定位，再结合监控和链路追踪判断是哪个接口/服务；测试环境可以远程 debug；生产环境用 Arthas 等诊断工具，避免直接远程调试。

## 7. 棘手问题怎么答

面试官问“你负责项目时遇到了哪些比较棘手的问题”，按三段式回答：

| 段落 | 内容 |
| --- | --- |
| 背景 | 什么技术问题，影响范围多大 |
| 过程 | 如何排查、尝试了哪些方案、为什么选最终方案 |
| 结果 | 最终落地方案、效果指标、后续优化 |

**易错点**

- 不要只说“解决了”，要说出排查过程和取舍。
- 指标要真实，例如 QPS、响应时间、数据量。
