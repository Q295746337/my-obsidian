## 2. 注册中心

本节依次回答：2.1 Eureka 的四个动作、2.2 Nacos 的工作流程、2.3 Nacos 与 Eureka 的区别。

### 2.1 Eureka 的四个动作

1. 服务注册：提供者把服务名、IP、端口注册到 Eureka。
2. 服务发现：消费者拉取服务列表，有集群时用负载均衡选一个调用。
3. 心跳续约：提供者每 30 秒发送心跳。
4. 服务剔除：Eureka 90 秒没收到心跳，把实例剔除。

### 2.2 Nacos 的工作流程

- 临时实例：心跳监测，心跳不正常会被剔除。
- 非临时实例：Nacos 主动询问，不会被剔除。
- Nacos 支持服务列表变更的消息推送，更新更及时。

### 2.3 Nacos 与 Eureka 的区别

| 维度 | Nacos | Eureka |
| --- | --- | --- |
| 健康检测 | 临时实例心跳，非临时实例主动检测 | 心跳 |
| 实例剔除 | 临时实例会剔除，非临时实例不剔除 | 心跳超时剔除 |
| 变更推送 | 支持消息推送 | 不支持 |
| CAP | 默认 AP；存在非临时实例时 CP | AP |
| 配置中心 | 支持 | 不支持 |

**易错点**

- Nacos 不是只有注册中心，还支持配置中心。
- “临时/非临时实例”是 Nacos 特有概念。

## 3. Ribbon 负载均衡

本节依次回答：3.1 流程、3.2 常见策略、3.3 自定义策略。

### 3.1 流程

1. order-service 发起请求 `http://userservice/user/1`。
2. Ribbon 从注册中心拉取 userservice 服务列表。
3. 拿到 `localhost:8081`、`localhost:8082`。
4. 按策略选择一个实例发起调用。

### 3.2 常见策略

| 策略 | 说明 |
| --- | --- |
| RoundRobinRule | 简单轮询 |
| WeightedResponseTimeRule | 按权重，响应时间越长权重越小 |
| RandomRule | 随机 |
| BestAvailableRule | 忽略短路服务器，选择并发数较低的 |
| RetryRule | 重试机制 |
| AvailabilityFilteringRule | 先过滤非健康实例，再选连接数较小的 |
| ZoneAvoidanceRule | 按区域选择，区域内轮询（默认） |

### 3.3 自定义策略

- 全局：创建类实现 `IRule`，通过配置类注册 Bean。
- 局部：在客户端配置文件中指定某个服务的 `NFLoadBalancerRuleClassName`。

## 4. 服务雪崩、降级与熔断

本节依次回答：4.1 三个概念、4.2 Hystrix 熔断。

### 4.1 三个概念

| 概念 | 说明 |
| --- | --- |
| 服务雪崩 | 一个服务失败，导致整条链路的服务都失败 |
| 服务降级 | 服务自我保护或保护下游，避免请求突增导致服务不可用 |
| 服务熔断 | 监控调用情况，失败率达到阈值后快速失败，之后尝试恢复 |

![服务雪崩示意图](file:///D:/Java/data/面试/05-微服务篇/slide016_img1.png)

> 图：服务之间存在多级依赖，任一上游服务故障都可能沿调用链扩散到下游，形成雪崩。

### 4.2 Hystrix 熔断

- 默认关闭，需要在引导类加 `@EnableCircuitBreaker`。
- 10 秒内请求失败率超过 50% 触发熔断。
- 之后每隔 5 秒尝试请求一次，服务不可达继续熔断，可达则关闭熔断。
- 状态：Closed（关闭）→ 达到失败阈值 → Open（打开，快速失败）→ 熔断时间结束 → Half-Open（放行一次）→ 成功关闭 / 失败继续打开。

**易错点**

- 降级是业务兜底，熔断是保护机制，两者常配合使用。
- 降级太多会触发熔断。

## 6. 限流

本节依次回答：6.1 为什么要限流、6.2 实现方式、6.3 漏桶与令牌桶、6.4 Nginx 限流、6.5 网关限流。

### 6.1 为什么要限流

- 并发确实大（突发流量）。
- 防止用户恶意刷接口。

### 6.2 实现方式

| 位置 | 方式 |
| --- | --- |
| Tomcat | 设置最大连接数 |
| Nginx | 漏桶算法 |
| 网关 | 令牌桶算法 |
| 应用 | 自定义拦截器 |

### 6.3 漏桶与令牌桶

| 算法 | 机制 | 特点 |
| --- | --- | --- |
| 漏桶 | 请求先进入漏桶，桶以固定速率漏出 | 请求匀速处理，多余请求等待或丢弃，适合控制速率 |
| 令牌桶 | 固定速率生成令牌，请求拿到令牌才被处理 | 桶满后暂停生成，允许一定突发流量 |

### 6.4 Nginx 限流

- 控制速率：`limit_req`，漏桶算法。
- 控制并发连接数：
  - `limit_conn perip 20`：单个 IP 最多 20 个连接。
  - `limit_conn perserver 100`：虚拟主机总并发连接数 100。

### 6.5 网关限流

- 使用局部过滤器 `RequestRateLimiter`。
- `key-resolver`：定义限流对象（IP、路径、参数）。
- `replenishRate`：令牌桶每秒填充平均速率。
- `burstCapacity`：令牌桶总容量。

**回答模板**：先说明业务 QPS（例如平时 10–50，活动最高 2000），再用 Nginx 漏桶控制速率和并发数，网关令牌桶按 IP 或路径限流。

## 7. CAP 与 BASE

本节依次回答：7.1 CAP、7.2 BASE。

### 7.1 CAP

| 指标 | 含义 |
| --- | --- |
| Consistency 一致性 | 访问任意节点得到的数据必须一致 |
| Availability 可用性 | 访问任意健康节点必须得到响应 |
| Partition tolerance 分区容错性 | 网络故障导致分区时，系统仍能对外提供服务 |

- 分布式系统节点之间需要网络连接，分区 P 必然存在。
- 保证 A 就不能保证强一致 C，即 AP。
- 保证强一致 C 就要放弃高可用 A，即 CP。

### 7.2 BASE

| 思想 | 含义 |
| --- | --- |
| Basically Available 基本可用 | 故障时允许损失部分可用性，保证核心可用 |
| Soft State 软状态 | 允许一定时间内出现中间状态 |
| Eventually Consistent 最终一致 | 软状态结束后最终达到数据一致 |

- 最终一致思想：各分支事务分别执行并提交，不一致再恢复数据（AP）。
- 强一致思想：分支事务执行完不提交，等彼此结果后统一提交或回滚（CP）。

## 8. 分布式事务

本节依次回答：8.1 Seata 三个角色、8.2 四种方案。

### 8.1 Seata 三个角色

| 角色 | 作用 |
| --- | --- |
| TC 事务协调者 | 维护全局和分支事务状态，协调提交或回滚 |
| TM 事务管理器 | 定义全局事务范围，开始、提交或回滚全局事务 |
| RM 资源管理器 | 管理分支事务资源，向 TC 注册、报告状态，驱动提交或回滚 |

### 8.2 四种方案

| 方案 | 模式 | 一致性 | 性能 | 说明 |
| --- | --- | --- | --- | --- |
| XA | CP | 强一致 | 差 | 分支执行 SQL 不提交，等 TC 通知 |
| AT | AP | 最终一致 | 好 | 记录 undo log 快照，业务 SQL 直接提交 |
| TCC | AP | 最终一致 | 较好 | Try 预留、Confirm 确认、Cancel 释放，需要人工编码 |
| MQ | AP | 最终一致 | 最好 | 本地事务内发消息，异步通知下游 |

**AT 与 XA 的区别**

- XA 一阶段不提交，资源锁定周期长。
- AT 一阶段执行业务 SQL 并提交，记录 undo log；二阶段提交删日志，回滚用日志恢复。

**回答模板**：按业务选型——银行等强一致场景用 XA；互联网高并发用 AT、TCC 或 MQ；TCC 性能较好但需要人工编码；MQ 性能最好但要求最终一致。

## 9. 接口幂等

本节依次回答：9.1 什么是幂等、9.2 REST 请求的幂等性、9.3 三种实现。

### 9.1 什么是幂等

多次调用方法或接口不会改变业务状态，重复调用结果与单次调用一致。

**需要幂等的场景**

- 用户重复点击（网络波动）
- MQ 消息重复
- 应用失败或超时重试

### 9.2 REST 请求的幂等性

| 请求方式 | 说明 |
| --- | --- |
| GET | 查询，天然幂等 |
| POST | 新增，多次调用结果不同，不幂等 |
| PUT | 绝对值更新幂等；增量更新不幂等 |
| DELETE | 按唯一值删除，幂等 |

### 9.3 三种实现

| 方案 | 适用 | 说明 |
| --- | --- | --- |
| 数据库唯一索引 | 新增 | 重复插入会失败 |
| token + Redis | 新增、修改 | 第一次生成 token 存 Redis，第二次携带 token 校验，存在则执行业务并删除 |
| 分布式锁 | 新增、修改 | 性能较低，抢不到锁的线程快速失败 |

**易错点**

- token 要在第一次请求时生成并返回前端，不能每次请求都重新生成。
- 幂等和并发控制不是一回事：幂等解决重复提交，锁解决并发竞争。

## 10. xxl-job 分布式任务调度

本节依次回答：10.1 路由策略、10.2 任务失败怎么解决、10.3 大数据量任务怎么执行。

### 10.1 路由策略

| 策略 | 说明 |
| --- | --- |
| FIRST | 固定第一个机器 |
| LAST | 固定最后一个机器 |
| ROUND | 轮询 |
| RANDOM | 随机选择在线机器 |
| CONSISTENT_HASH | 一致性 Hash，固定选择某台机器 |
| LEAST_FREQUENTLY_USED | 使用频率最低的机器优先 |
| LEAST_RECENTLY_USED | 最久未使用的机器优先 |
| FAILOVER | 按顺序心跳检测，第一个成功的执行 |
| BUSYOVER | 按顺序空闲检测，第一个空闲的执行 |
| SHARDING_BROADCAST | 广播到所有机器，传递分片参数 |

### 10.2 任务失败怎么解决

- 路由策略选择故障转移，用健康实例执行。
- 设置重试次数。
- 查看日志分析，配置邮件告警通知负责人。

### 10.3 大数据量任务怎么执行

- 执行器集群部署，路由策略选择分片广播。
- 一次调度广播到所有执行器。
- 通过 `XxlJobHelper.getShardIndex()` 和 `getShardTotal()` 获取分片参数，按取模分摊数据。

```java
int shardIndex = XxlJobHelper.getShardIndex();
int shardTotal = XxlJobHelper.getShardTotal();
for (Integer id : list) {
    if (id % shardTotal == shardIndex) {
        // 当前分片处理
    }
}
```
