# 变电站多车协同巡检仿真 · 面试问答（技术篇）

> 使用提示：本问答面向面试复习，7 大类 33 题，每题都给了能口头复述的答案口径和可能的追问。先背"必问 + 常问"，"可能"过一眼即可。所有数字、功能、角色均以项目事实包为准，不夸大、不硬杠。

## A 项目整体与架构

### A1 用一句话介绍这个项目？它的定位是什么？
**难度：必问**

**答：** 这是一个课程作业项目（软件工程 + 软件体系结构两门课，共 3 学分、4 人小组），不是生产系统。题目是"基于黑板（Blackboard）架构的变电站多车协同巡检仿真"：几辆小车在一张栅格地图上自动协作探索，前端实时可视化。我以"核心开发"身份参与，时间 2026.05–2026.07，技术栈 Java 17、Redis、RabbitMQ、SQL Server、WebSocket、Docker。

**追问：**
- 是不是 AI 写的？课程真实情况是大量借助 AI 辅助开发，面试被问到就坦诚承认，不要装。
- "协同"体现在哪？多车共享同一张地图状态，目标分配、路径规划、避让都要考虑"别的车在干什么"，而不是各跑各的。
- 简历写"核心开发"怎么落到具体模块？四人是：PersonA = common + controller（公共库 + 调度核心 + 分布式联调）、PersonB = car + 认证、PersonC = 规划模块（navigator + target-planner + task-configurator）、PersonD = display + launcher。要能点出自己具体负责哪几块，而不是空说"核心"；即便只做一块，也要能把"一次 tick 主流程"讲完整。

### A2 为什么选黑板（Blackboard）架构？
**难度：必问**

**答：** 核心原因是"多个专家模块共享同一份状态、通过公共数据区异步协作"。要跑起来需要地图初始化、目标分配、路径规划、监督避让、执行移动等多个环节，职责不同、彼此独立，但都读写同一份"地图 + 车辆"状态。黑板模式正好把共享状态沉到公共黑板（Redis），各知识源（业务模块）只读写黑板、由调度器统一驱动，天然解耦。另一方面，这是课程的架构题目，我们要照着黑板架构来落地。

**追问（黑板模式的优缺点）：** 优点是知识源独立、易增删模块、状态集中一致；缺点是黑板成为瓶颈和单点——所以 Redis 的可用性和吞吐决定系统上限，这也是已知不足里"中间件短暂不可用时恢复不完善"的根源。

### A3 黑板三要素在你项目里分别对应什么？
**难度：必问**

**答：**
- 黑板 = Redis，是共享状态的唯一真相源，地图、车辆位置/状态、任务配置全在这里。
- 知识源（KS）= 各业务模块：TaskConfigurator、Navigator、TargetPlanner、StrategySupervisor、Car、Display。
- 控制器 = Controller，唯一调度器，按 500ms 节拍驱动整车队的协作流程。

**追问：** Display 也算知识源吗？算，它本质是"读黑板、把快照渲染并推给浏览器"的专家模块，只是它的"输出"是 WebSocket 而不是写回黑板。

### A4 项目分几个 Maven 模块？为什么简历写"7 个进程"但 Maven 有 9 个模块？
**难度：常问**

**答：** Maven 共 9 个模块 = 7 个独立进程 + 1 个公共库 + 1 个可选启动器。
- 7 个进程：TaskConfigurator（任务初始化，先生成地图/障碍、算密封区、分配出生点、写 TaskConfig）、Navigator（路径规划，写 Car 的 RouteList）、TargetPlanner（目标分配）、StrategySupervisor（路线监督）、Car（小车执行端，5 态状态机，可用 carId 跑多实例）、Display（HTTP :8887 静态页 + WebSocket :8888 推送）、Controller（唯一调度器，最后启动）。
- common = 公共库（Redis 黑板、MQ、SQL、共享模型、地图算法、认证/分析/回放），被所有业务模块依赖，不是进程。
- launcher = 可选的一键启动器。

所以写"7 个进程"是对的，但要能解释多出来的两个是 common（库）和 launcher（启动器），不是运行时进程。

**追问（启动顺序）：** TaskConfigurator 最先启动，Controller 最后启动（单实例驱动）。Car 可多实例、用 carId 区分。

### A5 模块之间为什么"零直接调用"？
**难度：常问**

**答：** 我们刻意做了强解耦：业务模块只依赖 common 公共库，互相之间没有方法调用、也不互相发 HTTP。模块 A 要影响模块 B，就写 Redis，或者发 RabbitMQ 消息给 Controller、由 Controller 中转。好处是进程可独立开发、部署、重启，符合黑板架构"知识源隔离"的本意。

**追问（代价）：** 所有状态同步都要过 Redis/MQ，多一跳网络，带来延迟——这也是多车 + 高密度障碍时偶发单 tick 到 ~800ms 的原因之一。

### A6 Controller 为什么必须单实例？怎么保证？
**难度：常问**

**答：** Controller 是全局唯一调度器，负责按节拍串行驱动"分配目标 → 规划路径 → 监督 → 移动"这条流水线。有多个 Controller 就等于两个大脑同时驱动同一支车队，指令会乱序。保证方式是启动时用 Redis 的 `SET controller:instance 1 NX EX 30` 抢一把带过期时间的分布式锁：`NX` 保证只有一个实例能写入成功（即抢到锁），`EX 30` 让锁 30 秒自动过期、崩溃后不永久占死。

**追问：** 为什么锁要带 30 秒过期？防止持锁进程崩溃后锁永远不释放（本项目实现里锁只在启动时抢一次、没有心跳续期）。

## B 算法与搜索

### B1 路径规划用了什么算法？
**难度：必问**

**答：** 线上实际是加权 Dijkstra 和加权 A*。Navigator 读车辆目标后算路径，写到 Car 的 RouteList。注意一个细节：代码里算法类型枚举名写的是 BFS 和 ASTAR，但实际实现并不是纯 BFS，而是加权 Dijkstra / 加权 A*（见 B2）。

**追问（栅格怎么建模）：** 四连通网格（只能上下左右走），每个格子的移动代价不是都等于 1，而是按"已探索 / 未探索"加权，所以要用带权最短路，不能简单 BFS。

### B2 为什么枚举里是 BFS/A*，你却说 Dijkstra/A*？
**难度：常问**

**答：** 这是命名与实现不一致，能主动讲清楚说明真读过代码。枚举 `AlgorithmType` 只有 `BFS`、`ASTAR` 两档：
- 选 `BFS` 档，实际调用 `ExplorationWeightedPathFinder` 的 WEIGHTED_DIJKSTRA，优先队列按纯 gCost 排序，语义上就是 Dijkstra。
- 选 `ASTAR` 档，实际调用 WEIGHTED_ASTAR，f = gCost + 曼哈顿距离启发。
- 真正的纯 BFS（`ShortestHopPathFinder`，每格代价 1）只在单元测试里做基线对比，不参与线上。

**追问：** 为什么不能直接用纯 BFS？因为格子代价不等权，BFS 默认等权，只有"每格代价都是 1"时才等价于最短路；我们为了"偏好未探索区"引入了非等权代价，就必须上带权搜索。

### B3 A* 的启发函数可采纳吗？
**难度：常问**

**答：** 可采纳。启发用的是曼哈顿距离，而我们是四连通网格（只能上下左右走），曼哈顿距离就是四连通下的真实最短步数下界，只会低估、不会高估（这正是 A* 可采纳的要求），A* 能保证最优；曼哈顿距离还满足一致性条件。

**追问（拓展，通识）：** 如果换成八连通网格，曼哈顿会高估（斜对角一步可达但曼哈顿算 2），就不适合当可采纳启发，应改用切比雪夫距离。我们项目只用了四连通网格。

### B4 "对未探索区加权"是什么意思？
**难度：常问**

**答：** 我们希望路径主动偏好没探索过的地方，提高探索效率。实现上给不同格不同的步进代价：已探索格代价 5、未探索格代价 1。这样算最短路时，走未探索区"更便宜"，规划出的路径天然倾向穿过没去过的地方，而不是在已探索区里绕。

**追问：** 会不会为了图便宜绕太远？会，这是权重权衡。所以监督模块有个 WeightedPathPlanner，用更温和的"已探索 3 / 未探索 1"，专门替换绕得离谱的低效路线；绕远判定用 `MAX_PATH_LENGTH_RATIO=2.0`，明显过长才换，并带 10-tick 冷静期避免反复打断。

### B5 多车怎么分配目标？
**难度：常问**

**答：** 用 GreedyTargetAllocator，两阶段：
- 探索率 < 85%：逐格前沿贪心——候选点由 FrontierCellFinder 找"未探索且邻接已探索"的边界格，按打分公式（B6）取分最小的当目标。
- 探索率 ≥ 85%：改用 UnexploredClusterFinder 找 4-连通未探索块做聚类收尾，选每块最优入口作为目标。
- 同一 tick 内维护 allocatedTargets 集合，防止多车被分到同一格。

**追问（为什么 85% 切策略）：** 贪心逐格前沿在未探索区变稀疏后会"分得很碎"、多车互相干扰；85% 以后剩余是零散的块，按块聚类收尾效率更高。实测探索率能到 80% 多，超过 85% 自动切聚类。

### B6 目标打分的公式每一项是什么含义？
**难度：可能**

**答：** 分数 = 路径长度 + 6×（与其他车路线/目标重合的格数）+ 20×（贴边惩罚）− 4×（连通未探索块大小）− 2×（路径上的未探索格）− 4×（深入内部深度）。逐项：
- 路径长度：基础代价，越近越好。
- 6×重合格数：惩罚去别人已要去的区域，避免多车撞目标/撞路线。
- 20×贴边惩罚：避免贴着地图边缘选点。
- −4×连通块大小：奖励选在"大块未探索区"附近，便于后续展开。
- −2×路径未探索格：奖励沿路顺便探新格。
- −4×深入内部深度：奖励深入未探索区内部，而不是只在边界徘徊。

**追问（系数怎么来的）：** 课程项目里是经验设定，不是严格调优/模型推导的结果，这点坦诚说。

### B7 "密封区"是什么？为什么要处理它？
**难度：常问**

**答：** 密封区是"本身是空格、但被障碍物完全包裹、根本走不进去"的格子。不处理会有两个问题：探索率分母虚高、永远到不了 100%；车还可能被往死胡同里派目标。所以 TaskConfigurator 初始化时算一次，存成 `mapSealed` 位图，探索率分母里剔除。

**追问（探索率公式）：** 已探索的可达格 / 可达格总数，其中可达格总数 = 总格数 − 障碍数 − 密封区数。

## C Redis

### C1 Redis 里都存了什么？
**难度：必问**

**答：** Redis 是黑板，是共享状态唯一真相源，键分几类：
- 地图：mapView / mapBlock / mapSealed（位图）、mapHeat（Hash 热力图）。
- 配置与元数据：TaskConfig（Hash）、explorationEvents（List 回放事件）、sim:run:*（场次元数据）。
- 车辆：Car{id} 的 Position / Target / RouteList / Status / Steps / EffectiveSteps / BlockedTick / History。
- 锁与会话：controller:instance（单实例锁）、pos:reserve:*（位置预约锁）、auth:session:*（登录会话）。

**追问（车辆是否只有一个 Status 键）：** 不是，围绕车是一组键，状态、目标、路线、步数、有效步数、受阻 tick、历史分开存，各模块只读写自己关心的字段。

### C2 为什么选 Redis 当黑板？
**难度：常问**

**答：** 三点：一是黑板要求"共享状态唯一真相源"，Redis 天生是多进程共享的内存键值库，7 个进程读写同一份状态。二是快，每 500ms 一个 tick 要频繁读写，内存 + 简单数据结构延迟低。三是自带带过期时间的原子命令（SET NX EX、EXPIRE），正好满足单实例锁、位置预约锁、串行化移动的需求。

**追问（为什么不能放进程内变量）：** 我们是多进程部署，进程内存不共享，必须有一个独立于所有进程的公共状态区，Redis 就是这个"板"。

### C3 地图位图怎么做？探索率怎么算？
**难度：常问**

**答：** 地图在 Redis 里用位图存，一格一位，0/1 表示"是否障碍 / 是否密封 / 是否已探索"，mapView / mapBlock / mapSealed 是不同类型的地图位。探索率 = 已探索的可达格 / 可达格总数，可达格总数 = 总格数 − 障碍数 − 密封区数。

**追问（为什么剔密封区）：** 密封区本就不可达，不剔除会让分母虚高、永远到不了 100%（见 B7）。

### C4 reset 时为什么保留 auth:session:*？
**难度：可能**

**答：** 因为"重置仿真"和"登出用户"是两件事。reset 清的是仿真运行态（地图、车、探索事件等 sim 相关键），auth:session:* 是登录会话，删掉会把在线用户踢下线。所以在键前缀上把"仿真状态"和"认证会话"分层，reset 只动前者。

**追问（体现什么设计）：** 命名空间/键前缀分层，"清运行态"和"清用户态"可以独立控制。

### C5 `SET key value NX EX 30` 是什么？项目里哪里用了？
**难度：必问**

**答：** 带条件的原子写入：`NX` 只在 key 不存在时写入（成功即"抢到锁"），`EX 30` 加 30 秒过期。组合起来是一把会自动过期的分布式锁。项目里关键用到两处：
- 单实例锁：Controller 启动抢 `controller:instance`，保证只有一个调度器。
- 车辆移动锁 / 位置预约锁：每车移动前用 `SET NX` 串行化移动，用 `pos:reserve:{x}:{y}` 的 `SET NX EX 3` 预约目标格，防止两车进同一格。

**追问（为什么要有过期时间）：** 防止持锁进程崩溃后锁永久不释放；预约锁 EX 3 说明一次移动动作很快，3 秒内不释放就自动失效。

## D RabbitMQ

### D1 RabbitMQ 在项目里是什么角色？
**难度：必问**

**答：** 它是模块间的消息总线和解耦手段。业务模块互不直接调用，指令和结果都走 MQ：Controller 给各模块发指令（ASSIGN_TARGET、PLAN_ROUTE、TICK_MOVE、REFRESH_ALL），模块处理完把结果（MOVED / ROUTE_DONE / BLOCKED 等）回给 Controller；Display 的上行命令也经 MQ 转投 Controller。一句话：Redis 负责"存状态"，RabbitMQ 负责"传消息 / 触发动作"。

**追问（已经有 Redis 为什么还要 MQ）：** 职责不同——Redis 是共享数据，MQ 是动作触发。用 Redis 轮询去发现"该分配目标了"要么有延迟、要么空转；MQ 让 Controller 能明确"发指令、收结果"，语义更清晰，还天然支持广播和异步解耦。代价是 MQ 也是延迟来源之一。

### D2 用了什么交换机/队列？Fanout 干什么用？
**难度：常问**

**答：** 关键是一个 Fanout 交换机 `UpdateView`：Controller 每拍处理完车队后发 `REFRESH_ALL`，Fanout 把它广播给所有绑定的队列，Display 收到后重新从 Redis 读全量快照并推给浏览器。命令侧走 ControllerCmd 队列，Controller 是唯一中转。

**追问（为什么用 Fanout 而非点对点）：** 刷新视图是广播语义，用 Fanout 贴合；将来加多个 Display 实例只需加绑定，不改发送端。

### D3 为什么所有消息必须由 Controller 中转，模块直连不行吗？
**难度：常问**

**答：** 这是黑板架构的调度约束。Controller 是唯一调度器，负责全局节拍和顺序；允许模块直连会出现"谁触发谁"的乱序、多车并发不一致，甚至多个模块互相直接驱动。统一中转后，任何模块都只能被动响应 Controller 指令，节奏和顺序可控。

**追问（Display 命令算不算直连）：** 不算。浏览器发 SET_CONFIG 等命令，Display 不做业务处理，原样转投 RabbitMQ 的 ControllerCmd 队列，仍由 Controller 处理后生效。

## E WebSocket 与前端

### E1 实时可视化怎么推给前端？是轮询吗？
**难度：必问**

**答：** 不是轮询。走 WebSocket 推送：Controller 每拍结束发 `REFRESH_ALL`（Fanout）→ Display 收到 → 重新从 Redis 读全量快照 → 构建 SimulationState JSON → WebSocket 广播给所有浏览器。是"有新快照就推下来"，不是浏览器定时 fetch。fetch 只用于登录/注册/改密/回放列表/统计分析/用户管理等非实时接口。

**追问（为什么选推送）：** 轮询在大地图高刷新下又慢又费；推送是"变了才发"，端到端目标 ≤200ms。注意"≤200ms"是设计目标值，不是 benchmark，被追问要按这个口径说，别硬杠成实测值。

### E2 一帧（SimulationState）里有哪些内容？
**难度：常问**

**答：** 含 tick、explorationRate（探索率）、taskConfig、cars 数组（每车的 position / target / route / status / steps / effectiveSteps）、三张地图位图、runStartedBy。

**追问（steps 和 effectiveSteps 的区别）：** steps 是总步数、effectiveSteps 是有效步数，两者在 simulation_run_stats 里一起用来换算效率、均衡度这类指标。

### E3 地图很大时前端怎么办？
**难度：可能**

**答：** 两个手段：一是地图格数 > 2500 时，位图传输前转 Base64 压缩体积；二是已知 3D Unity 视图最大只支持 70×70（100×100 时 2D 正常、3D 不支持）。诚实说，大地图 + 快节拍时每拍整图推送仍会导致前端卡顿，这是已知不足。

**追问（有没有增量/脏矩形）：** 当前没有，每帧仍是整图快照，这是可优化方向。

### E4 上行命令（浏览器操作）怎么走？
**难度：可能**

**答：** 浏览器发 SET_CONFIG / RESET / TOGGLE_PAUSE / SET_TICK_INTERVAL / ADD_CAR / REQUEST_REPLAY / TOGGLE_OBSTACLE 等命令到 Display，Display 不做业务处理，原样转投 RabbitMQ 的 ControllerCmd 队列，由 Controller 处理后生效并触发刷新。

**追问（为什么 Display 不直接改 Redis）：** 为保持"Controller 唯一调度/唯一写入口"的一致性，否则前端改动会和调度逻辑打架。

## F 并发与一致性

### F1 两辆车怎么避免撞车、抢同一目标？
**难度：必问**

**答：** 分"目标分配"和"移动执行"两边：
- 目标分配：TargetPlanner 同一 tick 内维护 allocatedTargets 集合，两车不会被分到同一格；监督模块再做路线去重叠与重规划。
- 移动执行（Car 端）三层防冲突：1) 每辆车用分布式锁（SET NX）串行化移动；2) 移动前对目标格 `SET pos:reserve:{x}:{y} NX EX 3` 预约，失败说明被别人占，连续失败 3 次转 BLOCKED；3) `isOccupiedByOtherCar` 再查一次占位兜底。

**追问（"全程无碰撞、无重复分配"是必然保证吗）：** 是演示观察结论，由锁 + 预约 + 同 tick 去重共同保证，不是形式化证明，别夸成数学承诺。

### F2 分布式锁和位置预约锁有什么区别？
**难度：常问**

**答：** 作用对象不同：
- 车辆分布式锁：锁的是"执行动作的权利"，让一辆车同一时刻只做一件事，串行化自己的移动，防自己并发操作自己。
- 位置预约锁 `pos:reserve:{x}:{y}`：锁的是"地图上某个目标格"，防止两辆车同时进同一格，是车与车之间的协调。
一个解决"自己别打架"，一个解决"互相别抢格"。

**追问（预约锁为什么 EX 3）：** 移动动作很快，3 秒足够完成；设过期是防止某车预约后崩溃、把格子永久占住。

### F3 监督模块怎么发现并处理低效/重叠路线？
**难度：常问**

**答：** StrategySupervisor 有两个评估器：
- RouteEvaluator：看路线"已探索比例过高"这条红线，红线随全局探索率从 0.3 动态爬升到 0.8。
- RouteOverlapEvaluator：只算"未探索区"上本车与他人路线的重合，重合 > 50% 触发重分配（只在未探索格算，避免高探索率误判）。
替换节奏上设了 `MAX_PATH_LENGTH_RATIO=2.0`（明显过长才换），并带 10-tick 冷静期避免反复打断。

**追问（为什么红线要动态爬升）：** 探索率低时对"已探索比例"可以更严格，探索到后期大片区域已探、还按 0.3 卡会频繁误触发，所以把容忍度逐步放宽到 0.8。

### F4 车在规划期间又动了怎么办（过期计划）？
**难度：常问**

**答：** 做"规划后复查"：规划链路算出路径、写回前，复查这辆车的当前位置是否和规划开始时一致。若位置已变（说明这期间车被别的 tick 移动过），就放弃本次规划，避免把过期计划写进去。

**追问（为什么会"变了"）：** 节拍是并发的，算路和移动可能交错——A 车算路的同时它自己或别的车已经推进了状态。用"计算时快照 vs 写回时现状"做校验即可。

### F5 单 tick 设计 500ms，为什么偶发到 ~800ms？
**难度：可能**

**答：** 500ms 是默认节拍（可调 100~2000ms），不是硬上限。偶发 ~800ms 主要是多车 + 高密度障碍下，MQ 消息加多进程调度开销叠加造成的抖动，判定不影响正确性。

**追问（是不是 bug）：** 是已知的工程权衡/不足，不是逻辑错误。要压平抖动，方向是减少每拍消息往返、合并批量操作，而不是改正确性。

## G 存储与数据库

### G1 SQL Server 里存了什么？
**难度：常问**

**答：** 库名 CarHomework（代码默认连接串库名是 substation-patrol），存需要"持久化、可查、带历史"的数据：users、registration_requests、operation_logs、simulation_runs（含三张地图位图 Base64 快照 + car_histories + exploration_events）、simulation_run_stats（探索率/耗时/总步数/有效步数/效率/均衡度等指标）。

**追问（simulation_runs 里的地图快照干嘛用）：** 把当时三张地图位图 Base64 存下来，配合 car_histories / exploration_events 做回放和事后分析。

### G2 仿真状态为什么放 Redis 不放 SQL Server？
**难度：必问**

**答：** 因为运行态是"高频写、低持久价值"的临时状态：每 500ms 车就动一次，位置/状态/热力图频繁改。放 SQL 每拍写库又慢又没必要，Redis 内存 + 简单数据结构符合低延迟。SQL Server 只存低频、需长期保存/可回放/可统计的数据。而且 SQL 是可选依赖，核心仿真只依赖 Redis + RabbitMQ，去掉 SQL 仿真照样跑。

**追问（Redis 宕机状态不就没了）：** 对，实时态本就不需强持久化；真正要留存的历史（回放、统计）已在 SQL 落库，持久化诉求是分开的。

### G3 密码怎么存？
**难度：常问**

**答：** 用 jBCrypt 做哈希存储，不存明文。

**追问（为什么不用裸 MD5/SHA）：** BCrypt 带盐、计算更慢、专为密码设计，能提高暴力破解成本。面试追问"有没有加盐"时，答"BCrypt 本身就是带盐的"即可。

## 附：必问速查卡（考前 10 秒背一遍）

- 定位：课程项目、黑板架构的多车协同巡检仿真、4 人、AI 辅助、非生产级。
- 黑板三要素：Redis = 黑板，业务模块 = 知识源，Controller = 调度器。
- 模块：Maven 9 个 = 7 进程 + common（库）+ launcher（启动器）。
- 通信：模块零直连；Redis 存状态、RabbitMQ 传消息、Controller 唯一中转。
- 单实例锁：`SET controller:instance 1 NX EX 30`。
- 算法：枚举 BFS/A*，实为加权 Dijkstra / 加权 A*；已探索代价 5、未探索 1；曼哈顿启发在四连通下可采纳。
- 目标分配：<85% 贪心前沿，≥85% 聚类；同 tick 用 allocatedTargets 去重。
- 探索率：已探索可达格 /（总格 − 障碍 − 密封区）。
- 三层防冲突：车锁（SET NX）+ 位置预约锁（pos:reserve SET NX EX 3，失败 3 次 BLOCKED）+ isOccupiedByOtherCar。
- 推送：REFRESH_ALL（Fanout UpdateView）→ Display 读 Redis 快照 → WebSocket 广播，非轮询。
- 存储：Redis = 实时态，SQL Server = 历史/可回放/统计；密码 jBCrypt。
- 实测口径：30×30 / 3 车 / BFS / 500ms → 约 3~5 分钟探索率至 100%；"≤200ms"是设计目标值；抖动偶发 ~800ms 不影响正确性。
