## 版本 A：1~2 分钟电梯版（开场介绍）

王老师/面试官您好，我重点讲一个我作为核心开发参与做的分布式仿真项目，它是一个「基于黑板架构的变电站多车协同巡检仿真」。

先说背景。这是软件工程加软件体系结构两门课的课程项目，3 个学分，4 人小组，我用 Java 17 作为核心开发参与，2026 年 5 月到 7 月完成。目标很具体：给定一个二维网格地图，有多辆小车，要协作地把地图上所有可达格子都探索一遍，并且实时可视化出来。

它的架构特点是「黑板模式」。系统拆成了 7 个独立进程——任务初始化、路径规划、目标分配、路线监督、小车执行、前端显示，再加一个唯一的调度器 Controller。这些进程之间没有任何直接调用，全都通过 Redis 作为共享黑板读写状态，通过 RabbitMQ 收发消息来解耦。

运行起来是这样的：Controller 以 500 毫秒一个节拍驱动整个车队。每一拍，它给空闲的小车分目标、规划路径，小车执行移动并把结果回传，前端通过 WebSocket 实时把地图和车辆状态推给浏览器。路径规划用加权 Dijkstra 和 A*，目标分配是贪心前沿加聚类收尾，再配合 Redis 分布式锁和位置预约锁，保证多车全程无碰撞、不重复分到同一格。

实测数据：30×30 的地图、3 辆车、用 BFS 档、500 毫秒节拍，大约 3 到 5 分钟探索率能到 100%，任务正常收尾。

当然我也要坦诚：这是课程项目，开发过程大量用了 AI 辅助，不是生产级系统。具体不足我在详细版里可以展开讲。

（如果时间紧，压缩成一句话版：）这是一个黑板架构的多进程协作探索仿真——Redis 当黑板、RabbitMQ 当消息总线、Controller 当唯一调度器，靠加权寻路加贪心目标分配加分布式锁，让多辆小车无碰撞地探索完整个地图。

## 版本 B：8~12 分钟详细版

### 1. 一句话定位与背景

这个项目一句话概括就是：**用黑板架构，让多辆小车在二维网格地图上协作探索、自动巡检，并实时可视化，直到把整张地图探索完。**

它不是一个生产系统，是软件工程和软件体系结构两门课的课程作业，3 学分、4 人小组。我的简历口径是「核心开发，2026 年 5 月到 7 月」，技术栈是 Java 17、Redis、RabbitMQ、SQL Server、WebSocket、Docker。这里我必须诚实讲一句：这个项目在开发过程中大量借助了 AI 辅助，架构方案和关键机制是小组一起定的，我负责的模块是我自己亲自调通的。面试官如果问「是不是 AI 写的」，我会坦诚说是「AI 辅助开发的人写的」，并马上用细节证明我对代码是懂的。

题目本身是「变电站多车协同巡检仿真」。为什么这么起名？变电站对应「有障碍、有封闭区域的地图」，多车对应「并发协作」，巡检对应「要覆盖所有可达格子而不是光找一条路径」，仿真对应「实时可视化 + 可回放」。

### 2. 整体架构：黑板三要素 + 为什么用黑板

架构用的是经典的黑板模式（Blackboard Architecture），三个要素一一对应：

- **黑板**：就是 Redis。地图位图、每辆车的当前位置/目标/路线/状态、任务配置，全部放在 Redis 里，它是唯一的共享状态真相源。
- **知识源**：就是各个业务模块——路径规划、目标分配、路线监督、小车执行这些。每个模块只干自己那件事，做完把结果写回黑板。
- **调度器**：就是 Controller，唯一的一个，用固定节拍驱动这些知识源干活。

这套设计最重要的纪律是「模块间零直接调用」：每个业务模块只依赖一个公共库 common，互相之间不 import 对方的包、不直接调方法，而是通过 Redis 读写共享状态、通过 RabbitMQ 收发消息来协作，而且**所有消息都由 Controller 唯一中转**。换句话说，TargetPlanner 不会直接跟 Navigator 说话，都是 Controller 说了算。

那面试官会追问：**「为什么用黑板，而不是简单写个单进程、或者微服务互相 RPC 调用？」** 我这么回答：

- 第一，这个问题的本质是「多个并发的智能体共享一张地图、彼此还要避让」，天然需要一块所有角色都能读写的公共状态板，黑板的「共享状态 + 多个独立知识源」正好对上。
- 第二，解耦之后职责特别清楚，每个模块能独立开发、独立测试、独立部署到不同机器——我们四个人就是按模块分工、最后联网联调的。
- 第三，扩展性直接拉起来：想加一个新的「知识源」模块，只需要让它依赖 common、声明一个消息队列，然后在 Controller 里注册一下队列和入口回调，别的模块一行都不用改。

补充一个容易被打的细节：Maven 里一共是 **9 个模块**，但简历里我说的是 **7 个独立进程**。为什么有 9 个？因为除了 7 个进程，还有 **1 个公共库 common**（它不是进程，是所有模块的依赖）和 **1 个可选的一键启动器 launcher**（同进程按顺序把 7 个模块都拉起来，方便单机演示）。所以「7 个进程、9 个 Maven 模块」是自洽的，面试官要问我能解释清楚。

### 3. 七个进程各干什么

快速过一遍，方便建立整体感：

1. **TaskConfigurator**：任务初始化。生成地图和障碍、计算密封区、给每辆车分配出生点、写入 TaskConfig。它必须最先启动。
2. **Navigator**：路径规划。给车规划从当前位置到目标格的路线，写进这辆车的 RouteList。
3. **TargetPlanner**：目标分配。决定这辆车下一步该去探索哪个格子。
4. **StrategySupervisor**：路线监督。检查已经规划好的路线质量，做去重叠、加权重新规划。
5. **Car**：小车执行端。一个 5 态状态机，负责真正移动和碰撞检测。它可以多实例，用 carId 区分，一辆车一个进程。
6. **Display**：前端服务。HTTP 8887 提供静态页面，WebSocket 8888 做实时推送，还负责动态加车和回放。
7. **Controller**：唯一调度器。500 毫秒一个节拍，驱动整个车队，必须最后启动，而且单实例。

这里有个关键点：**Controller 单实例怎么保证？** 它启动时用 `SET controller:instance 1 NX EX 30` 在 Redis 上加一个带过期时间的锁，只有抢到锁的那个进程才成为调度器。这样即使分布式环境下有人误起了第二个 Controller，也只有一个生效，避免出现两个大脑同时下指令打架。

### 4. 一次 tick 的数据流（这是核心，值得背下来）

这部分面试官最爱让展开，我用最口语的方式把一个节拍走一遍，默认 500 毫秒一拍，可调 100 到 2000 毫秒：

假设一辆车现在状态是 IDLE（空闲）。运气是这样转起来的：

1. Controller 发现它 IDLE，就往 TargetPlanner 的队列发一个 `ASSIGN_TARGET`。
2. TargetPlanner 收到后，算出一个目标格，写进 Redis 的 `Car{id}:Target`，然后回一个 `TARGET_ASSIGNED` 给 Controller。
3. Controller 再发 `PLAN_ROUTE` 给 Navigator。
4. Navigator 从 Redis 读这辆车的当前位置和目标，规划出一条路线，写进 `Car{id}:RouteList`，回 `ROUTE_PLANNED`。
5. 这里可选地会触发 StrategySupervisor 监督优化：如果路线太绕或者跟别人重叠，它会重新规划一条更好的。
6. 状态变成 READY（就绪）。Controller 统一给所有 READY 的车发 `TICK_MOVE`。
7. Car 执行原子移动，只走一步，然后回 `MOVED`、`ROUTE_DONE` 或 `BLOCKED` 给 Controller。
8. Controller 发 `REFRESH_ALL`，这是一个 RabbitMQ 的 Fanout 广播。
9. Display 收到刷新信号后，重新从 Redis 读一张全量快照——地图、所有车的位置/路线/状态——构造成 JSON，通过 WebSocket 广播给所有浏览器。

就这么一拍一拍滚下去，直到探索率到 100%，Controller 判定任务完成，收尾。

我要强调一个架构细节：**Display 不是靠轮询刷新的**。实时仿真走的是 WebSocket 推送，Controller 广播 REFRESH_ALL，Display 收到后去 Redis 拉快照再广播。前端用 fetch（HTTP）只在登录、注册、改密码、回放列表、统计分析、用户管理这些非实时场景里。

### 6. 三个最加分的亮点（重点展开）

#### 亮点一：黑板式的分布式解耦架构

前面已经讲了「零直接调用」，我这里再往深说一层「为什么这样设计是对的」。这个项目最像真实系统的就是它：7 个进程、一个公共库、一个调度器，模块边界靠「消息类型 + Redis Key」来约定，而不是靠函数调用约定。带来的直接效果是——我们四个人可以把规划模块、小车、前端分别部署在不同的机器上，只靠统一的 Redis 和 RabbitMQ 地址就能联调。这不是假装分布式，是真实跨机器的分布式联调。面试官如果问「解耦体现在哪」，我就举一个反例：任何模块崩了都不会把 Controller 带崩，Controller 下一拍该怎么调度还是怎么调度，中间件短暂不可用最多是那几拍不动，恢复后继续走（这里我也坦承，恢复机制还不够完善）。

#### 亮点二：加权 Dijkstra/A* + 贪心前沿 + 聚类收尾的「协同探索」

这是算法的关键。先说名字上的坑：我简历写「加权 Dijkstra / A*」，但代码里枚举其实叫 BFS 和 ASTAR 两档。这里我要主动澄清，别让面试官觉得我在乱写：

- 枚举里的 **BFS 档，内部实际走的是 WEIGHTED_DIJKSTRA**——优先队列按纯 gCost（累计代价）排序，就是标准 Dijkstra。
- 枚举里的 **ASTAR 档，内部走的是 WEIGHTED_ASTAR**——gCost 加上曼哈顿距离启发函数；因为地图是四连通网格，曼哈顿距离是天然可采纳的启发，不会高估。
- **权值怎么设的**：已探索格子的步进代价是 5，未探索格子是 1。这样一来，路径会「主动偏好往没探索过的地方走」，而不是在原地打转。
- **纯 BFS 在哪**：它只放在单元测试里做基线对比，每格代价都是 1，不参与线上运行。

面试官问「为什么是 Dijkstra 而不是直接 BFS」——因为一旦给格子加了 5 和 1 的权重，普通 BFS 按层扩散就找不出「权重意义下的最短路径」了，必须换成优先队列的 Dijkstra 才正确；而这个「最短」正好被我们设计成「既短又偏向未知区域」。

目标分配这边是 **GreedyTargetAllocator 的两阶段策略**：

- **探索率低于 85%**：逐格前沿贪心。先找「前沿格子」——就是那种还没探索、但紧挨着已探索区域的格子。对每个候选格打分取最小，公式是：路径长度 + 6 倍「跟别的车路线/目标重合的格子数」+ 20 倍「贴边惩罚」− 4 倍「它连着的未探索块大小」− 2 倍「路径上经过的未探索格」− 4 倍「深入地图内部的深度」。这个公式本质是在平衡三件事：走得近、不跟人抢、优先啃又大又深的未探索区域。
- **探索率到 85% 以上**：剩下的未探索格已经不连续了，逐格贪心会碎化。这时换成 **UnexploredClusterFinder** 找 4-连通的未探索块，按聚类收尾，给每个块选一个最优入口前沿格去清尾。
- 还有一个细节：**同一个 tick 内维护一个已分配集合**，防止两辆车被分到同一个格子。

这两块配合起来，就形成了一个完整的「协同探索」闭环：寻路保证单条路线高效且爱探索，目标分配保证车队整体分工不重叠。

#### 亮点三：Redis 锁 + 位置预约锁，保证「无碰撞、无重复分配」

这是最能体现并发控制功力的点。多辆车共享一张地图，最怕两辆车同一拍走进同一格，或者路线互相穿模。我们上了三层防线：

1. **每车分布式锁**（`SET NX`）：一辆车移动前先抢自己的锁，把「读状态 → 改为 MOVING → 预约位置 → 更新坐标」这一整段做成原子动作，串行化。
2. **位置预约锁**（`pos:reserve:{x}:{y}`，`SET NX EX 3`）：车子走之前先「预约」下一格，预约失败说明这格有人了，连续失败 3 次就转 BLOCKED。
3. **isOccupiedByOtherCar 二次查占位**：预约成功后，落子前再查一遍目标格有没有被别的车占着，防止竞态窗口里的漏判。

另外还配合了两个机制：静态障碍用的是 `mapBlock` 位图；还有一个很聪明的概念叫**密封区（mapSealed）**——那些被障碍完全包裹、本来就从出生点根本走不到的空格。它在计算探索率的**分母里会被剔除**，否则这些格永远探索不到，探索率就永远到不了 100%，系统会卡死收不了尾。

再加上前面 Navigator「写完路线前复查车位置有没有变、变了就放弃」的防过期计划机制，以及 TargetPlanner「同 tick 去重」，所以简历里那句「全程无碰撞、无重复分配」是演示时观察到的结论，背后是有这几层机制兜底的。

### 7. 量化成果（一定要按口径讲）

- 最硬的一条实测：**30×30 地图、3 辆车、BFS 档、500ms 节拍，大概 3 到 5 分钟探索率到 100%，任务正常结束**（这是小组报告里的联调实测）。
- 探索率能跑到 80% 多（答辩已经够用），**超过 85% 后 TargetPlanner 会自动切到聚类策略**去清尾。
- 测试矩阵：除了标准配置，还测过 5 辆车、3 到 10 辆车不同出生点、地图从 5×5 一路到 100×100、障碍密度 0%/20%/50%。
- 时间特性目标值（注意是「目标」不是 benchmark）：WebSocket 端到端 ≤200ms、地图初始化 <3 秒（30×30、5 车）、单次移动 <200ms。
- 实测抖动：多车加高密度障碍时，偶尔单拍会延迟到 800ms 左右，这是 MQ 加多进程调度的开销，判定不影响正确性。

这里我给一句防杠口诀：**「3~5 分钟到 100%」是实测，「≤200ms」是设计目标值，「无碰撞无重复分配」是演示观察结论 + 锁机制保证。** 面试官追问的时候，就按这个口径拆开答，别把目标值硬说成实测。

### 8. 存储设计（一句话带过，追问再展开）

双存储，职责清楚：**Redis 是热黑板，SQL Server 是冷归档。**

- Redis 里放的是运行时状态：三张地图位图（已探索 mapView / 障碍 mapBlock / 密封区 mapSealed）、热力图、TaskConfig、每辆车的 Position/Target/RouteList/Status/Steps/有效步数/历史轨迹、回放事件列表、场次元数据、单实例锁、位置预约锁、登录会话。
- SQL Server（库名 CarHomework，代码默认连接串里叫 substation-patrol）存的是：用户表、注册申请、操作日志、仿真场次（含三张地图位图的 Base64 快照 + 车辆历史 + 探索事件）、仿真统计表（探索率、耗时、总步数、有效步数、效率、均衡度）。密码用 jBCrypt 加密。
- 一个容易忽略的点：**SQL 是可选的**。核心仿真只依赖 Redis 加 RabbitMQ，SQL Server 只在用统计、回放、用户管理这些功能时才需要。

### 9. 坦诚收尾：这个项目的不足（主动讲，别等被问）

面试官问「这个项目有什么问题、哪里可以改进」时，不要兜圈子，直接列：

1. 它就是个课程项目，AI 辅助开发，不是生产级。
2. MoveExecutor 在写了 MOVING 心跳之后如果异常退出，没有显式回写 READY，状态可能会短暂卡在 MOVING。
3. 3D Unity 视图最大只支持 70×70 的地图，100×100 时 2D 正常但 3D 不支持。
4. 配置文件错了、Controller 长时间等不到 TASK_READY 时，报错提示不够醒目。
5. 大地图加快速节拍时，每一拍推送整张图，前端会卡。
6. Redis 或 RabbitMQ 短暂不可用时的恢复机制还不够完善。

然后补一句「如果继续做我会怎么改」：把 MOVING 心跳加上超时兜底自动回退 READY；快照改成增量推送或脏区裁剪；中间件加断线重连和指数退避；给配置错误加更醒目的启动自检。这几句能体现你「不仅知道问题，还想好了优化方向」。

### 高频追问 + 参考答案

| 追问 | 一句话答法 |
|------|-----------|
| 为什么用黑板架构？ | 多智能体共享一张地图，天然需要公共状态板 + 各自独立知识源；解耦后模块可独立开发、可跨机器部署、可低成本加新知识源。 |
| 简历写 Dijkstra/A*，代码却叫 BFS/A*？ | 枚举只有 BFS / ASTAR 两档；BFS 档实际是 WEIGHTED_DIJKSTRA，ASTAR 档是 WEIGHTED_ASTAR；纯 BFS 只在单测做基线。 |
| 为什么是 Dijkstra 不是 BFS？ | 格子有权重（已探索 5、未探索 1），按层扩散的 BFS 找不出加权最短路，必须优先队列按 gCost 才是 Dijkstra。 |
| 权值怎么定的？ | 已探索格代价 5、未探索格 1，让路径主动偏向未探索区；监督模块另用 3/1 的加权规划替换低效路线。 |
| 目标分配怎么防止撞车抢同一格？ | 打分里带「与其他车路线/目标重合格数 ×6」惩罚 + 同 tick 已分配集合去重；85% 后转聚类清尾。 |
| 无碰撞怎么保证？ | 三层：每车分布式锁 SET NX、位置预约锁 pos:reserve SET NX EX3、isOccupiedByOtherCar 复查；连续失败 3 次转 BLOCKED。 |
| 密封区是什么？ | 被障碍完全包裹、从出生点不可达的空格；探索率分母剔除，否则永远到不了 100%。 |
| Controller 怎么保证单实例？ | 启动 `SET controller:instance 1 NX EX 30` 抢锁，抢不到就不当调度器。 |
| 探索率怎么算？ | 已探索的可达格 ÷ 可达格总数（总格 − 障碍 − 密封区）。 |
| 前端怎么做到实时？ | 非轮询；Controller 每拍发 REFRESH_ALL（Fanout），Display 读 Redis 快照构 JSON，WebSocket 广播。 |
| 是不是 AI 写的？ | 坦诚：AI 辅助开发，架构和关键机制小组定，我负责的模块亲手调通过，可用细节证明。 |

### 模块口径（9 Maven 模块 = 7 进程 + 1 公共库 + 1 启动器）

7 进程：TaskConfigurator（最先）→ Navigator → TargetPlanner → StrategySupervisor → Car×N → Display → Controller（最后、单实例）。
公共库 common：Redis 黑板、MQ、SQL、共享模型、地图算法、认证/分析/回放，被所有业务模块依赖。
launcher：一键启动器，可选。
