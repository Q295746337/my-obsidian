## 1. 系统架构：7 个进程 + 9 个 Maven 模块

先说清一个面试容易追问的点：**为什么简历写「7 个进程」，Maven 里却有 9 个模块？** 因为 9 个模块 = 7 个独立进程 + 1 个公共库 + 1 个可选一键启动器。公共库和一键启动器不是常驻进程。

### 1.1 模块对照表

| # | Maven 模块 | 是否进程 | 职责 | 启动顺序 |
|---|---|---|---|---|
| 1 | TaskConfigurator | 是 | 任务初始化：生成地图/障碍、计算密封区、分配出生点、写 `TaskConfig` | 最先启动 |
| 2 | Navigator | 是 | 路径规划：加权 Dijkstra / A*，写每辆车的 `RouteList` | 随后 |
| 3 | TargetPlanner | 是 | 目标分配：贪心前沿 + 聚类 | 随后 |
| 4 | StrategySupervisor | 是 | 路线监督：去重叠 + 加权重规划 | 随后 |
| 5 | Car | 是 | 小车执行端：5 态状态机 + 移动 + 碰撞检测；**可多实例，用 carId 区分** | 随后 |
| 6 | Display | 是 | 前端服务：HTTP `:8887` 静态页 + WebSocket `:8888` 实时推送，动态加车，回放 | 随后 |
| 7 | Controller | 是 | 唯一调度器：500ms 节拍驱动全车队，**最后启动，单实例** | 最后启动 |
| — | common | 否 | 公共库：Redis 黑板、MQ、SQL、共享模型、地图算法、认证/分析/回放；被所有业务模块依赖 | 库，不启动 |
| — | launcher | 否 | 一键启动器（可选），把上述进程统一拉起 | 可选 |

**为什么拆成 7 个独立进程？** 这是黑板架构的落地方式——每个知识源（KS）是一个可独立运行/独立扩展的进程，通过共享黑板（Redis）和消息中间件（RabbitMQ）解耦，而不是一个进程内的类互相调用。

### 1.2 架构三要素映射

| 黑板架构抽象概念 | 本项目落地 |
|---|---|
| 黑板（共享状态唯一真相源） | **Redis** |
| 知识源 KS（各业务能力） | TaskConfigurator / Navigator / TargetPlanner / StrategySupervisor / Car（Display 偏展示面） |
| 调度器（驱动的控制流） | **Controller**（单实例） |

## 2. 通信模型：模块间「零直接调用」

- **依赖规则**：业务模块只依赖 `common`（公共库）；模块与模块之间**互相只通过 Redis 读写 + RabbitMQ 收发消息解耦**，不存在 A 模块直接 import 调用 B 模块的代码路径。
- **消息中转**：所有消息由 **Controller 唯一中转**，没有任意两模块私下点对点直连（业务层面如此）。
- **Controller 单实例保证**：启动时用 Redis 原子操作 `SET controller:instance 1 NX EX 30` 加锁——`NX`（不存在才写）+ `EX 30`（30 秒过期，需续约），保证分布式部署下也只有一个调度器活着。

**为什么这么设计？** 黑板架构的核心诉求就是「知识源彼此不直接耦合、都读写共享状态」，这样新增/替换一个知识源不影响其他知识源；Controller 作为唯一控制流，避免多调度器并发指挥造成状态冲突。

## 3. 一次 tick 的完整时序（默认 500ms/tick，可调 100~2000ms）

以「一辆待分配目标的车」为主线走一遍：

1. **IDLE 车** → Controller 发 `ASSIGN_TARGET`。
2. TargetPlanner 收到后分配目标，写 `Car{id}:Target` 到 Redis。
3. Controller 发 `PLAN_ROUTE`。
4. Navigator 规划路径，写 `Car{id}:RouteList` 到 Redis。
5. （可选）StrategySupervisor 监督优化该路线（去重叠 / 加权重规划、替换低效路线）。
6. 车状态进入 **READY**。
7. Controller 发 `TICK_MOVE`。
8. Car 执行一次原子移动，回 `MOVED` / `ROUTE_DONE` / `BLOCKED` 给 Controller。
9. Controller 发 `REFRESH_ALL`（RabbitMQ **Fanout** 交换机）。
10. Display 收到后从 Redis 读全量快照，WebSocket 广播给浏览器。
11. 探索率 100% 时收尾，任务正常结束。

**一个节拍为什么默认 500ms？** 这是一个可调节拍（100~2000ms），用来平衡「仿真推进速度」和「每个知识源 + 消息往返的完成时间」，避免消息堆积。

## 4. 路径规划算法（面试关键点）

### 4.1 「简历写加权 Dijkstra/A*，代码枚举叫 BFS/A*」——这是对的，但要能说清

| 代码枚举档位（`AlgorithmType`） | 实际调用 | 代价函数 | 本质 |
|---|---|---|---|
| `BFS` | `ExplorationWeightedPathFinder` 的 `WEIGHTED_DIJKSTRA` | 优先队列按纯 `gCost` | **真 Dijkstra**，不是逐层扩散的 BFS |
| `ASTAR` | `WEIGHTED_ASTAR` | `gCost + 曼哈顿距离启发` | **加权 A\*** |

- 枚举只有 **BFS 和 ASTAR 两档**，但 `BFS` 档内部跑的是加权 Dijkstra——面试时按「枚举名叫 BFS、实现是加权 Dijkstra」讲，别把枚举名当成算法事实。
- `ASTAR` 档的启发函数是**曼哈顿距离**，在四连通网格上是**可采纳（admissible）**的，不会高估真实代价。

### 4.2 权值与「偏好未探索」

- 步进代价（`ExplorationPathCosts`）：**已探索格代价 5，未探索格代价 1**。
- 效果：走未探索格「更便宜」，路径会主动偏好未探索区——这是「协同探索地图」而不是「单纯找最短路径」的关键。
- 纯 BFS（`ShortestHopPathFinder`，每格代价 1）**只用于单元测试里做基线对比，不参与线上**。

### 4.3 监督模块的替换规划

- StrategySupervisor 另有一个 `WeightedPathPlanner`：**已探索代价 3 / 未探索 1**，代价 = `gCost + 曼哈顿`，同样倾向未探索，用于**替换低效路线**。

**为什么给未探索格更低代价？** 因为这个系统的优化目标不是「到达」，而是「尽快覆盖整张地图」——用代价函数把「探索收益」编码进搜索，是最轻量的实现方式。

## 5. 目标分配：GreedyTargetAllocator 两阶段

### 5.1 阶段一：探索率 < 85% —— 逐格前沿贪心

- 候选格来自 `FrontierCellFinder`：**未探索且至少邻接一个已探索格**的格子（即「前沿」）。
- 每格打分，**取最小分**：

```
分数 = 路径长度
     + 6 × 与其他车路线/目标重合的格数
     + 20 × 贴边惩罚
     − 4 × 连通未探索块大小
     − 2 × 路径上的未探索格数
     − 4 × 深入内部深度
```

直观拆解：正的项把车「推开」（避免撞车、避免贴地图边），负的项把车「拉向」大的、深的、未探索密集的区域。

### 5.2 阶段二：探索率 ≥ 85% —— 聚类收尾

- 用 `UnexploredClusterFinder` 找 **4-连通未探索块**（上下左右连通），按簇收尾。
- 每个簇选一个**最优入口 frontier** 作为目标，避免后期目标碎片化、来回空跑。

### 5.3 去重

- 同一 tick 内维护 `allocatedTargets` 集合，**防止多辆车被分到同一格**。

**为什么 85% 分两阶段？** 前期地图开阔、前沿多，逐格贪心最快；后期剩下的是零散小块，逐格贪心会「捡芝麻」，聚类能一次性吃下一整块。

## 6. 监督与避障（StrategySupervisor + Car）

### 6.1 监督（StrategySupervisor）

| 机制 | 阈值/参数 | 含义 |
|---|---|---|
| `RouteEvaluator` | 已探索比例过高的红线**随全局探索率从 0.3 动态爬升到 0.8** | 探索率越高，「走已探索区」越不可接受，红线越严 |
| `RouteOverlapEvaluator` | 本车在**未探索区**与他人路线重合 > 50% 触发重分配 | 只在未探索格上统计重合，避免高探索率时误判 |
| 路径过长替换 | `MAX_PATH_LENGTH_RATIO = 2.0`，带 **10-tick 冷静期** | 路径明显过长才替换，且短期内不再反复打断 |

**为什么重叠只统计未探索区？** 高探索率时全图大部分已探索，若在已探索格也算重叠，任何两车都会「看着撞路线」，导致误触发重分配。

### 6.2 车端 5 态状态机 + 三层防冲突（Car）

状态机：**IDLE(空闲) → WAITING_ROUTE(等待路径) → READY(就绪) → MOVING(移动中) → BLOCKED(受阻)**。

三层防冲突（由下到上越来越「软」）：

1. **每车分布式锁**：移动时用 `SET NX` 抢锁，串行化本车移动（防同车并发指令交错）。
2. **位置预约锁**：目标格 `pos:reserve:{x}:{y}` 用 `SET NX EX 3` 预约；**连续失败 3 次转 BLOCKED**。
3. **占位复查**：`isOccupiedByOtherCar` 再查一次目标格是否被别的车占用。

**静态障碍与密封区**：

- 静态障碍 = `mapBlock` 位图。
- 密封区 = `mapSealed`：被障碍包裹、本来就不可达的空格；**探索率分母要把密封区剔除**，否则永远到不了 100%。

**过期计划防护**：规划完成后复查「车位置是否已变」，变了就**放弃本次规划**，防止把基于旧位置的计划写进黑板。

**为什么需要三层？** 多进程 + 多实例 Car 下，没有单进程内存互斥可用，必须靠 Redis 的原子操作（NX 锁 + 带过期 TTL 的预约）在共享黑板上实现互斥；每层兜不同的冲突类型，避免「写了位置但两车同格」。

## 7. 并发一致性小结（面试常问「怎么保证不撞车/不复用」）

| 问题 | 手段 | 性质 |
|---|---|---|
| 多调度器并发指挥 | Controller 单实例锁 `SET controller:instance 1 NX EX 30` | 全局唯一控制流 |
| 同一车指令交错 | 每车分布式锁 `SET NX` 串行化移动 | 车级互斥 |
| 两车进同一格 | 位置预约锁 `pos:reserve:{x}:{y}` `SET NX EX 3`，连续失败 3 次转 BLOCKED | 格级互斥 |
| 已有车占位 | `isOccupiedByOtherCar` 复查 | 最终兜底 |
| 同 tick 分到同一目标 | `allocatedTargets` 集合去重 | 分配层去重 |
| 拿旧计划覆盖新状态 | 规划后复查车位置是否变化，变了就作废 | 过期计划防护 |

> 口径提示：简历里「全程无碰撞、无重复分配」是**演示观察结论**，由上述锁 + 预约 + 同 tick 去重保证，属工程性保障，不是形式化证明。

## 8. 存储：双存储设计

核心仿真 **只依赖 Redis + RabbitMQ**；SQL Server 是**可选依赖**，用于登录/注册/日志/场次持久化与统计分析。

### 8.1 Redis 黑板键（共享状态真相源）

| 键类别 | 键 | 作用 |
|---|---|---|
| 地图位图 | `mapView` / `mapBlock` / `mapSealed` | 已探索 / 障碍 / 密封区 |
| 热力图 | `mapHeat`（Hash） | 探索热度 |
| 配置 | `TaskConfig`（Hash） | 任务配置 |
| 单车状态 | `Car{id}:Position / Target / RouteList / Status / Steps / EffectiveSteps / BlockedTick / History` | 每车的位置、目标、路线、状态机状态、步数、有效步数、受阻计数、历史轨迹 |
| 回放 | `explorationEvents`（List） | 回放事件流 |
| 场次 | `sim:run:*` | 场次元数据 |
| 锁/预约 | `controller:instance`、`pos:reserve:*` | 单实例锁、位置预约锁 |
| 会话 | `auth:session:*` | 登录会话 |

### 8.2 SQL Server：5 张表

数据库名 `CarHomework`（代码默认连接串里的库名为 `substation-patrol`）：

| 表 | 内容 |
|---|---|
| `users` | 用户（密码用 **jBCrypt** 哈希） |
| `registration_requests` | 注册申请 |
| `operation_logs` | 操作日志 |
| `simulation_runs` | 场次记录（含三张地图位图 Base64 快照，并承载 `car_histories` 与 `exploration_events`） |
| `simulation_run_stats` | 统计指标：探索率 / 耗时 / 总步数 / 有效步数 / 效率 / 均衡度等 |

### 8.3 探索率公式

```
探索率 = 已探索的可达格 / 可达格总数
可达格总数（分母）= 总格数 − 障碍格 − 密封区格
```

**为什么双存储？** Redis 提供低延迟、可被所有进程共享的内存黑板（实时仿真的真相源）；SQL Server 承担需要持久化、可查询、多用户相关的业务（账号、日志、历史场次、统计），二者职责分离。

## 9. WebSocket 实时推送线路

- 库：**Java-WebSocket**；Display 进程分别监听 **WebSocket `:8888`**（实时推送）和 **HTTP `:8887`**（静态页面）。
- **下行（服务端 → 浏览器）链路**：
  1. Controller 发 `REFRESH_ALL`（RabbitMQ **Fanout** 交换机 `UpdateView`）。
  2. Display 收到后**重新从 Redis 读全量快照**。
  3. 构建 `SimulationState` JSON。
  4. `broadcast` 给所有浏览器连接。
- **帧内容**：`tick`、`explorationRate`、`taskConfig`、`cars` 数组（每车 `position/target/route/status/steps/effectiveSteps`）、三张地图位图、`runStartedBy`。当地图格数 **> 2500** 时位图转 **Base64** 以压缩体积。
- **上行（浏览器 → 系统）**：浏览器发 `SET_CONFIG` / `RESET` / `TOGGLE_PAUSE` / `SET_TICK_INTERVAL` / `ADD_CAR` / `REQUEST_REPLAY` / `TOGGLE_OBSTACLE`，Display **原样转投** RabbitMQ `ControllerCmd` 队列，由 Controller 统一处理。
- **边界**：实时仿真走 **WebSocket 推送，非轮询**；`fetch`（HTTP 请求）只用于登录 / 注册 / 改密 / 回放列表 / 统计分析 / 用户管理。

**为什么是「Fanout + 重读快照」而不是增量事件推送？** 因为 Redis 是唯一真相源，Display 每次收到刷新信号都重读快照再广播，能天然保证各浏览器视图收敛到同一份状态，实现简单且不易出现增量丢事件不一致的问题（代价是每拍传整图，见不足 5）。

## 11. 已知不足（诚实清单，被问「有什么问题」直接讲）

1. 课程项目，AI 辅助，非生产级。
2. **MoveExecutor** 在写 `MOVING` 心跳后若异常退出，未显式回写 `READY`，状态可能短暂停在 `MOVING`（personB 报告）。
3. 3D 视图最大只支持 70×70。
4. `infra.local.json` 配置错误时，Controller 长时间等不到 `TASK_READY`，错误提示不够醒目（personA 报告）。
5. 大地图 + 快节拍时，每拍传整图会导致前端卡顿。
6. 中间件（Redis/RabbitMQ）短暂不可用时的恢复不够完善。

**怎么讲这些不足？** 主动承认「这是课程级黑板书架构的练手实现，追求把架构思想和并发协调跑通，而非生产级容错与性能」，再逐条列上述具体点，比被追问后被动承认更有说服力。

**口语金句（可复述）**：这是一套「Redis 当黑板、RabbitMQ 当总线、Controller 当唯一调度器、各规划/执行模块当知识源」的多进程黑板书架构；五条车的移动靠「每车锁 + 位置预约锁 + 占位复查」三层防冲突，路径用「未探索代价更低」的加权 Dijkstra/A* 驱动地图探索，目标分配在 85% 探索率前后切换贪心与聚类两阶段，最后靠 Controller 的 500ms 节拍 + Fanout 快照推送驱动整场实时可视化。
