## 0. 一句话自述（开场必背）

> 这是一个软件工程 + 软件体系结构两门课的课程项目，4 人小组、共 3 学分。题目是用黑板（Blackboard）架构做一个变电站多车协同巡检仿真：多辆小车自动去探索一张有障碍物和"密封区"的地图，边探索边做路径规划和目标分配，并通过 WebSocket 把过程实时推给浏览器可视化。

## A. 难点与挑战

### A1. 问：这个项目里最大的难点是什么？你是怎么攻克的？

**答案模板**（任选一条主线展开，讲你最熟的那条）：
- 主线一（协同正确性）：「最大的难点是**多车并发下的协同正确性**——多辆车同时移动，既要保证不撞车、不抢同一个目标格，又不能让车闲着等。我把它拆成三层来解决：① 每辆车一把分布式锁（Redis `SET NX`）串行化自己的移动；② 一个位置预约锁 `pos:reserve:{x}:{y}`（`SET NX EX 3`）防止两车同刻落到同一格，连续失败 3 次就转 BLOCKED；③ 每次移动前再用 `isOccupiedByOtherCar` 复查一次占位。目标分配这边，同一 tick 内维护一个 `allocatedTargets` 集合，保证多车不会被分到同一格。这样"无碰撞、无重复分配"就不是靠"运气"，而是靠锁 + 预约 + 同 tick 去重三层保证的。」
- 主线二（解耦架构）：「最大的难点其实是**7 个进程怎么真正解耦**。黑板架构要求各知识源模块之间零直接调用，只通过共享状态和消息通信。我的做法是：所有业务模块只依赖公共库 `common`，彼此只通过 Redis 读写 + RabbitMQ 收发来交互，所有消息由 Controller 唯一中转——车不知道 TargetPlanner 存在，只知道"收到 ASSIGN_TARGET 就去给车配目标"，谁发的它不管。这让模块可以被单独替换、单独重启动。」

**加分话术**：「讲难点时顺带讲"为什么这么设计"：调度和知识源分离，是为了满足体系结构课里黑板架构的约束；锁用 Redis 的 `NX` 是因为它是原子的，天然适合做分布式互斥。」

**避坑**：别只说"难，很多 bug"，一定要落到**一个具体的机制上**（锁 / 中转 / 去重任选一个讲透）。

### A2. 问：多车协同，怎么保证不撞车、不重复分配目标？

**答案模板**：
- 目标侧：TargetPlanner 在每个 tick 内维护 `allocatedTargets` 集合，同一批分配里已经给出去的格子会从候选里剔除，**同 tick 内不会出现两车同一个目标格**。
- 移动侧：三层防冲突——① 每车分布式锁（`SET NX`）把同一辆车的移动串行化（防同一辆车并发指令交错）；② 位置预约锁 `pos:reserve:{x}:{y}`（`SET NX EX 3`）锁定"下一格"，防两车同时进同一格；③ `isOccupiedByOtherCar` 再查一次实际占位。连续 3 次没抢到预约就转 BLOCKED，交给 Controller 重新规划。
- 结果口径：简历里"全程无碰撞、无重复分配"是**演示观察结论**，由这三层机制保证，演示和联调里观察成立。

**加分话术**：可以补一句「静态障碍是 `mapBlock` 位图、密封区是 `mapSealed`，探索率分母会剔除密封区，所以规划时不会把不可达的密封空格当成可探索目标」。

**避坑**：别承诺"100% 绝对无碰撞"，要说是"由机制保证 + 演示观察成立"，这是有据可依的准确说法。

### A3. 问：黑板架构下，7 个进程怎么做到"零直接调用"？

**答案模板**：
- 黑板 = Redis，是共享状态的**唯一真相源**；知识源 = 各业务模块；调度器 = Controller。
- 业务模块**只依赖 common**，互相不 import、不调用；通信就两条腿：**Redis 读写**（状态）+ **RabbitMQ 收发**（消息/指令）。
- 所有消息由 **Controller 唯一中转**：网页上行指令 → Display 原样转投到 ControllerCmd 队列 → Controller 再发 ASSIGN_TARGET / PLAN_ROUTE / TICK_MOVE 等给对应模块。
- Controller 单实例：启动时用 `SET controller:instance 1 NX EX 30` 抢锁（30 秒过期防占死；实现里没有心跳续期），保证分布式环境里只有一个调度器在跑，避免双调度器打架。

**加分话术**：「这样换任何一个模块，其他模块不用改——比如 Display 挂了，仿真还能跑，只是没人看；Display 重启后读 Redis 快照就能恢复画面。这就是解耦带来的好处。」

**避坑**：有人会把 RabbitMQ 当成"黑板"，要纠正清楚：**黑板是 Redis（状态），RabbitMQ 只是消息通道**。

### A4. 问：路径规划怎么让车"主动去探索未探索区"而不是原地打转？

**答案模板**：
- 用**带权图上的 Dijkstra / A***，权值不是每格 1，而是**已探索格步进代价 5、未探索格代价 1**（`ExplorationPathCosts`）。
- 这样最短路径天然会"绕开已探索区、主动往未探索区钻"，因为走未探索更便宜。
- 代码里 `AlgorithmType` 枚举只有 `BFS` 和 `ASTAR` 两档，但：档位 `BFS` 实际走的是 `ExplorationWeightedPathFinder` 的 **WEIGHTED_DIJKSTRA**（优先队列按纯 gCost）；档位 `ASTAR` 走 **WEIGHTED_ASTAR**（gCost + 曼哈顿距离启发，四连通网格上启发是可采纳的）。真 BFS（`ShortestHopPathFinder`，每格代价 1）只放在单元测试里做基线对比，不参与线上。

**加分话术**：主动提「监督模块 StrategySupervisor 另有一个 `WeightedPathPlanner`（已探索 3/未探索 1，gCost+曼哈顿）用来替换低效路线」——说明你不止一处用了"代价加权"这个思路。

**避坑**：别只说"用了 A*/Dijkstra"，一定要强调**权值设计**才是让它"主动探索"的核心，纯最短路只能走到最近的邻边，不会主动铺开探索。

### A5. 问：目标分配的策略是怎么设计的？为什么分两阶段？

**答案模板**：
- 探索率 **< 85%** 用 `GreedyTargetAllocator` 做**逐格前沿贪心**：候选是 `FrontierCellFinder` 找的"未探索且邻接已探索"的前沿格，打分取最小：`分数 = 路径长度 + 6×与其他车路线/目标重合格数 + 20×贴边惩罚 − 4×连通未探索块大小 − 2×路径上的未探索格 − 4×深入内部深度`。分数越低越优（越短、越少重叠、越往未探索连通块深处越好）。
- 探索率 **≥ 85%** 切 `UnexploredClusterFinder` 做**聚类收尾**：把剩下的 4-连通未探索块找出来，每块选一个最优入口 frontier，把零散的格子集中吃掉，避免末期一辆车追着一个孤格满地图跑。
- 为什么分两阶段：前期追求"快速铺开"，后期追求"收尾不漏"。

**加分话术**：「这套打分里每一项都能解释：`6×重合`是防止走别人路，`20×贴边`是想让车深入内部而不是沿着墙边蹭，`−4×块大小`是引导车去大块的未探索区。」

**避坑**：如果只背公式会被问"凭什么是这些系数"——诚实说「这些系数是**调出来的启发式**，主要依据是'越短、越少重叠、越深入内部越好'的目标，不是数学上最优解」。

### A6. 问：Controller 是唯一调度器，怎么保证它真的只有一个？

**答案模板**：启动时用 Redis 的 `SET controller:instance 1 NX EX 30`抢锁——`NX` 保证只有第一个能设成功，`EX 30` 是 30 秒过期（实现里没有心跳续期，锁只在启动时抢一次）。抢不到锁的实例就直接退/不调度。这样哪怕两个人同时点了启动，也只有一个 Controller 在发心跳和指令。

**加分话术**：补一句「这其实就是用 Redis 原子命令实现了一个简单的分布式锁（选主），课程项目够用；生产里一般会用更完善的选主协议如 Raft/ZooKeeper/etcd」。

**避坑**：别吹成"高可用主备切换"，这里只是防重复启动的单实例锁，没有自动 failover。

### A7. 问：实时可视化怎么做到"低延迟、非轮询"？

**答案模板**：
- 前端不是轮询，是 **WebSocket 推送**：Controller 每个 tick 结束发 `REFRESH_ALL`（走 RabbitMQ 的 Fanout 交换机 `UpdateView`）→ Display 收到后**重新从 Redis 读全量快照** → 组装成 `SimulationState` JSON → `broadcast` 给所有浏览器。
- 帧内容：tick、探索率、taskConfig、cars 数组（每车 position/target/route/status/steps/effectiveSteps）、三张地图位图、runStartedBy。地图格数 >2500 时位图转 Base64 压体积。
- 目标是 WebSocket 端到端 ≤200ms（这是**设计目标值**），单次移动 <200ms、地图初始化 <3 秒（30×30、5 车）。

**加分话术**：「推送链路的每个参与者只做一件事：Controller 发信号、Display 读快照、浏览器只收 JSON，避免 Display 自己算仿真逻辑，职责单一。」

**避坑**：这几项是**目标值不是 benchmark**，被追"实测多少"时按"设计目标值，有偶发抖动"的口径说，别硬杠"实测就是 200ms"。

## B. 已知不足与 bug（被问"项目有什么问题/缺点"时）

**总答法**（先给基调再逐条）：
> 这个项目最大短板就是**它是课程项目、AI 辅助、非生产级**——我不会把它说成能上线的系统。具体不足有这几条：……

逐条套话术「问题 + 为什么会出现 + 改进思路」：

**B1. MoveExecutor 写 MOVING 心跳后异常退出，未显式回写 READY，状态可能短暂停在 MOVING**（personB 报告）
- 怎么答：车进入 MOVING 后会写心跳，如果进程在移动中途异常退出，没来得及回写 READY，Redis 里 `Car{id}:Status` 可能短暂卡在 MOVING，直到心跳超时或下一轮被处理才纠正。
- 改进思路：给 MOVING 状态也加一个**超时自愈**（例如心跳 TTL 到期就视为失败并重置到 IDLE/READY），或者移动结束用更原子的状态回写 + 异常兜底。

**B2. 3D Unity 视图最大只支持 70×70**（100×100 时 2D 正常、3D 不支持）
- 怎么答：3D 视图有尺寸上限，70×70 以内正常，100×100 的地图 2D 正常显示但 3D 不支持。
- 改进思路：3D 渲染做 LOD/分块加载，或对大地图降采样抽稀，而不是一次性建全量 3D 网格。

**B3. infra.local.json 配置错误时，Controller 长时间等不到 TASK_READY，错误提示不够醒目**（personA 报告）
- 怎么答：基础设施配置指向了错误的 Redis/RabbitMQ 地址时，Controller 会一直傻等 TaskConfigurator 的 TASK_READY，界面/日志提示不明显，排查起来费时间。
- 改进思路：加一个**启动健康检查 + 超时告警**，启动阶段等 TASK_READY 超过 N 秒就明确报"连不上中间件/配置疑似错误"，把错误日志打醒目一点。

**B4. 大地图 + 快节拍时，每拍传整图导致前端卡顿**
- 怎么答：当前是每个 tick 把全量快照（含三张地图位图）重新推一遍，地图大、tick 快的时候，前端渲染和网络传输会卡。
- 改进思路：改**增量推送/差量更新**（只推本拍变化的格子 + 车的位置），或者位图做分块缓存，不必每拍全量重发。

**B5. 中间件（Redis/RabbitMQ）短暂不可用时的恢复不完善**
- 怎么答：如果 Redis 或 RabbitMQ 短暂宕机又恢复，各个进程的重连和状态自愈做得不完整，可能要靠重启进程才能恢复一致。
- 改进思路：给每个进程加**重连 + 幂等重放**，断线期间缓存未确认消息，恢复后从黑板重新读状态对齐。

**B6. 整体：课程项目、AI 辅助、非生产级**
- 怎么答：坦诚说是 AI 辅助开发的课程项目，没有做生产级的高可用、安全加固、压测和灰度；SQL Server 持久化是**可选依赖**，核心仿真只依赖 Redis + RabbitMQ。

**避坑（B 节总提醒）**：被问缺点时，**先承认再给改进思路**，一条都不要硬辩；面试官最欣赏的是"我知道它有什么问题、也想清楚了怎么改"，而不是"我的项目没有缺点"。

## C. 测试

### C1. 问：你们做了哪些测试？

**答案模板**：
- **单元测试（JUnit Jupiter 5.10.5，test scope）**：按模块各写各的。以 Car 模块为例，`CarAgentTest` 6 个（TICK_MOVE 正常处理、到终点 ROUTE_DONE、BLOCKED_TIMEOUT 的 IDLE/BLOCKED 状态、非法 JSON 不崩溃、未知消息类型不崩溃）+ `MoveExecutorTest` 13 个（正常移动/最后一步/障碍阻塞/各状态跳过/3×3 点亮/边界裁剪/History/热力图/分布式锁互斥/MOVING 心跳等），Car 共 19 个；Auth 另 22 个（`UserStoreTest` 16 个认证/改密/注册/锁定场景 + `SessionManagerTest` 6 个会话/过期/挤号场景）。Display 模块有 5 个测试文件，`WebSocketBridge` 通过注入 Mock `MqSender` 脱离 RabbitMQ 单独测。Navigator 的纯 BFS（`ShortestHopPathFinder`）也用来在测试里做基线对比。
- **集成/联调（四人分布式）**：四人各跑自己的进程，连到同一套 Redis + RabbitMQ，同一局域网按"标准演示配置 30×30 / 3 车 / BFS / 500ms"联调。

**加分话术**：点出「单测刻意把消息、Redis、RabbitMQ mock 掉，是为了让核心逻辑能脱离中间件快速回归」——这体现了测试分层意识。

**避坑**：别只报数字，报 1~2 个**具体用例名**更可信（比如"非法 JSON 不崩溃""挤号后旧 Token 失效"）。

### C2. 问：集成联调（四人）具体怎么测的？有没有量化结果？

**答案模板**：
- 测试矩阵覆盖：标准配置 30×30/3车/BFS/500ms；还测过 5 车、3~10 个出生点、地图 5×5~100×100、障碍 0%/20%/50%。
- 实测数字（出自四人正式报告）：personA 联调 30×30、3 车、BFS、500ms 下 **约 3~5 分钟探索率到 100%，任务正常结束**；personC 实测探索率能到 **80% 多**，超过 85% 后 TargetPlanner 自动切聚类策略。
- 抖动：多车 + 高密度障碍时**偶发单 tick 延迟到 ~800ms**（占默认 500ms 的一拍半），主要来自 MQ 和多进程调度开销，判定不影响正确性。

**加分话术**：「联调不只测"能不能跑完"，还会看探索率曲线、总步数、有效步数、效率、均衡度这些指标（存进 `simulation_run_stats`），看多车负载是否均衡。」

**避坑**：800ms 抖动要如实说"偶发"，别当成"稳定 800ms"；也别把 3~5 分钟说成所有场景都这样。

### C3. 问：你（自己）负责的模块怎么测的？

**答案模板**（全项目口径）：
- 若负责 car：单测 19 个（Car 状态机 + 移动执行器），分布式锁/预约锁互斥都写了用例；再联调看多车不撞车。
- 若负责规划：Navigator/TargetPlanner 的算法用纯 BFS 做基线对比测试，配不同障碍密度验证探索率能上 80%+、85% 自动切策略。
- 若负责 common+controller：测 Controller 单实例锁、消息路由、tick 节拍驱动全车队是否按预期状态流转。
- 若负责 display：WebSocketBridge 用 Mock `MqSender` 单测，前端走静态页验证推送、加车、回放、登录等上行指令。

**避坑**：别只答"我单测都过了"，要能说出一两个**具体用例 + 为什么这么设计**。

## D. 分工与角色

### D0. 四人分工一览（必记）

| 成员 | 负责模块 | 一句话 |
|------|----------|--------|
| PersonA | common + controller | 公共库 + 调度核心 + 分布式联调 |
| PersonB | car + 认证 | 小车执行端 + 登录（认证） |
| PersonC | 规划模块（navigator + target-planner + task-configurator） | 地图初始化 + 路径规划 + 目标分配 |
| PersonD | display + launcher | 前端 + WebSocket + 一键启动 |

### D1. 问：你负责哪块？能讲一个你亲手写的、印象深的实现吗？

**答案模板**（把自己的模块填进去）：
> 我负责的是 [PersonX 的模块]。以 [某机制] 为例……（下面给每人一个可套用的"可讲点"）
- PersonA：Controller 的 500ms 节拍怎么驱动全车队状态流转；单实例锁 `SET controller:instance 1 NX EX 30`；Redis 黑板键设计和消息路由。
- PersonB：Car 的 5 态状态机（IDLE→WAITING_ROUTE→READY→MOVING→BLOCKED）+ 三层防冲突；认证用 jBCrypt、SQL Server 存 users/会话、单点登录挤号失效。
- PersonC：加权 Dijkstra/A* 的权值设计（已探索 5 / 未探索 1）、目标分配两阶段策略、<85% 的贪心打分公式。
- PersonD：WebSocket 推送链路（Controller 的 REFRESH_ALL → Display 读快照 → broadcast）、动态加车、回放，静态页 + :8887/:8888。

**避坑**：说"负责某块"一定要能落到**文件/类/机制**级别，否则会被当"只写了文档"。

### D2. 问：你们 4 个人怎么协作？接口怎么对上的？

**答案模板**：
- 分工边界先定死：9 个 Maven 模块 = **7 个独立进程 + 1 个公共库 common + 1 个可选 launcher**。每个人负责的进程之间**只通过 Redis key + RabbitMQ 消息对接**，接口就是"消息类型 + 键的约定"——所以在 `common` 里把共享模型、Redis/MQ 封装、地图算法统一起来，大家只依赖 common。
- 协作方式：先一起定黑板键和消息协议（谁写哪个 `Car{id}:Target`、谁发 `ASSIGN_TARGET`），然后各写各的进程；联调时在同一个局域网连同一套 Redis/RabbitMQ，用"标准配置 30×30/3车/BFS/500ms"作为基准对齐。

**加分话术**：「因为接口就是消息 + 键，所以只要协议不变，四个人可以并行开发、互不阻塞，最后联调基本一次能对上——这是黑板架构这个选型带来的协作收益。」

**避坑**：别说出"我们各写各的也没对齐、最后硬拼"这种话，哪怕事实如此，也要强调"协议先行、定好边界再并行"。

### D3. 问：课程是 4 人小组，你在里面的角色和贡献怎么量化说？

**答案模板**：简历口径「核心开发，2026.05-2026.07」。展开说：「我全程参与，从架构到各模块都做过、都能讲清角色和协作；最透的是调度与算法链路」。贡献量化就落到**模块数 + 关键机制数 + 测试数**，不吹"主导一切"。

**避坑**：课程项目别说"项目负责人/架构师"这种容易露馅的头衔，用"核心开发 + 负责 X 模块"最稳。

## E. 简历措辞（怎么稳妥解释）

### E1. 简历写"核心开发"——怎么解释？

- 口径：「4 人课程项目里的核心开发，负责 [具体模块]。技术栈 Java 17 / Redis / RabbitMQ / SQL Server / WebSocket / Docker。项目共 7 个独立进程 + 1 公共库，我负责其中 [X] 个。」
- 加分：主动把"核心开发"落到**具体模块和机制**，让"核心"有实指。
- 避坑：不要引申成"唯一主力/负责人"，4 人小组里"核心开发"指"承担了核心模块的一名开发"。

### E2. 简历写"全程无碰撞、无重复分配"——怎么解释？

- 口径：这是**演示观察结论**，机制上由三层保证——每车 `SET NX` 分布式锁串行移动、`pos:reserve:{x}:{y}` 预约锁防同格、`isOccupiedByOtherCar` 复查占位；目标侧同 tick 用 `allocatedTargets` 集合去重。
- 避坑：别说成"数学上证明永无碰撞"，正确表述是"由锁 + 预约 + 同 tick 去重保证，演示/联调中观察成立"。

### E3. 简历写"WebSocket 端到端 ≤200ms"——怎么解释？

- 口径：这是**设计目标值**（不是 benchmark 压测结果）。时间特性目标：WS 端到端 ≤200ms、地图初始化 <3 秒（30×30、5 车）、单次移动 <200ms、默认节拍 500ms（可 100~2000ms）。
- 避坑：被追问"是不是实测压测出来的"要诚实：**目标值**，实测有"多车+高密度障碍时偶发单 tick ~800ms"的抖动，判定不影响正确性。

### E4. 简历写"7 个进程"但项目是 9 个 Maven 模块——怎么解释？

- 口径：**7 个独立进程 = TaskConfigurator、Navigator、TargetPlanner、StrategySupervisor、Car、Display、Controller**；外加 **common（公共库，不是进程，被所有业务模块依赖）** 和 **launcher（可选的一键启动器）**。7 + 1 + 1 = 9 个模块。
- 避坑：这是高频"对不上"点，务必能直接背出"7 是进程数、9 是模块数"的对应关系。

### E5. 简历写的技术栈（Redis/RabbitMQ/SQL Server/WebSocket/Docker）——怎么不被问倒？

- 口径：Redis 是黑板（共享状态真相源）、RabbitMQ 是消息总线（Controller 唯一中转到各模块）、SQL Server 是**可选**持久化（登录/回放/统计，密码 jBCrypt）、WebSocket 是 Display 实时推送（Java-WebSocket，:8888 推、:8887 静态页）、Docker 用于打包/部署中间件。
- 避坑：如果面试官问"SQL 是必需的吗"，如实说「SQL 是可选依赖，核心仿真只依赖 Redis + RabbitMQ，去掉 SQL 仿真一样跑」。

## F. 答辩老师常问（怎么实现 / 代码在哪 / 怎么改 bug / 有无某处理）

### F1. 问：这个功能是怎么实现的？代码在哪？

**通用应对**：先给"一句话机制"，再给"代码/文件"定位，最后"时序"收口。
> 这个功能的核心是 [一句话机制]。代码在 [模块/类] 里，对应 [方法]。流程是 [谁发消息 → 谁写哪个 Redis 键 → 谁读]。

**避坑**：答辩/面试最怕"讲得出道理、指不出代码"。考前对着自己的模块把**"类名 + 关键方法"**过一遍，至少能说出 3 个可指认的点。

### F2. 问：某 bug 你怎么改？

**通用应对**（诚实体 + 解法框架）：
> 这个 bug 的现象是 [X]，我定位到根因是 [Y]，临时改法是 [Z]，彻底改法应该是 [W]。
例如 MoveExecutor 停在 MOVING：现象是进程异常退出后 `Car{id}:Status` 卡 MOVING，根因是没有显式回写 READY 的异常兜底，改法是为 MOVING 加心跳超时自愈、异常时重置状态。

**加分话术**：先复现、再定位、再最小修复、最后想根治——按这个顺序讲，比直接给答案更显工程素养。

### F3. 问：有没有做 [某处理]？（如：断线重连 / 并发锁 / 异常兜底 / 幂等）

**通用应对**：
- 做了的：直接讲机制 + 为什么这么设计（参考 A 节相应条目）。
- 没做好的：诚实说「这部分做的是[现有程度]，还不够完善，比如[中间件短暂不可用的恢复不完善]」，再给改进思路。

**避坑**：老师问"有没有做 X"最忌"应该有的吧（含糊）"。要么有机制、要么承认没做完整并给思路，两种都是好答案，含糊才是最差答案。

### F4. 问：这个参数怎么来的？为什么是这些系数？

**通用应对**（针对贪心打分、权值 5/1、阈值 85%、冷静期 10 tick 等）：
> 这些是**启发式参数，靠调出来的**：先定目标（越短、越少重叠、越深入未探索越好、探索率够高后收尾不漏），再按这个目标反复调。不是数学推导出的最优值。
- 关键参数速记：已探索格代价 5 / 未探索 1；监督模块 3/1；<85% 贪心 / ≥85% 聚类；红线 0.3→0.8 随探索率爬升；重叠阈值 50%；`MAX_PATH_LENGTH_RATIO=2.0`；10-tick 冷静期；预约锁 `EX 3`；连续失败 3 次转 BLOCKED；单实例锁 `EX 30`；tick 默认 500ms（100~2000ms）。

**避坑**：被问"为什么是 5 不是 10"，大大方方说"调参 + 观察探索效率定的，没有理论最优"，这比硬编理由可信。

### F5. 问：答不上来时怎么得体应对？

**模板**：
> 这个点我目前没有直接做过/记不太清，但我的思路是 [先怎么定位 → 再去哪查 → 大概怎么改]，如果现在让我做，我会 [具体动作]。
- 加分：答不上就"诚实承认 + 给解决思路 + 表明会去验证"，不要硬编、不要长时间沉默绕圈子。
- 避坑：**绝不编造一个不存在的实现细节**——被当场追问会连锁崩。宁可说"这块我做得浅，但我知道大方向"。

## G. HR / 行为面

### G1. 问：你们团队有没有过冲突 / 意见分歧？怎么解决的？

**答案模板**：
> 分歧主要出现在**接口设计**上：比如黑板键的命名、某种消息该由 Controller 转还是模块直连、tic 参数定多长。我们最后是"以协议为准提前对齐"——先把消息类型和 Redis 键在 common 里定死写成文档，大家各自按约定实现；真有分歧就回到"哪个方案更解耦、更好联调"这个标准来定，而不是各持己见。
- 避坑：不要回答"我们完全没冲突"（显得假），也不要指名道姓抱怨队友；把分歧落在**技术选型/接口**而非**对人**。

### G2. 问：进度延期了怎么办？

**答案模板**：
> 课程项目时间紧、又是 AI 辅助，其实中途有过一次联调卡壳（比如基础设施配置不对导致 Controller 一直等 TASK_READY、错误提示不明显，排查了很久）。我们后来做了两件事：① 先把"最小可用链路"跑通，再往上叠功能；② 约定"标准配置 30×30/3车/BFS/500ms"作为统一的联调基准，所有人都先对齐这一条。
- 加分：强调"砍范围保核心"和"统一基准"两个动作，比讲"我们加班"更有说服力。

### G3. 问：最有成就感的一件事？

**答案模板**：
> 最有成就感的是看到**四个人各自写、彼此不 import 的 7 个进程，第一次联调就按 Controller 的节拍联动起来**，多辆小车在浏览器上实时铺开地图、探索率一路涨到 100%，中间没有撞车、没有重复抢目标。那一步验证了黑板架构"解耦"这个选择是成立的。
- 避坑：成就感落点选"**验证了某个架构/机制的正确性**"，而不是"我写了很多代码/很累"。

### G4. 问：这个项目大量用 AI 辅助开发，你怎么看 / 是不是 AI 写的？

**答案模板**（务必坦诚）：
> 是的，这个项目确实大量借助 AI 辅助开发，这是课程的真实情况，我不会回避。AI 帮我们加快了样板代码和排查，但我认为**思路和取舍是人做的**：架构怎么拆成 7 个进程、黑板用 Redis、消息怎么由 Controller 中转、路径规划为什么用加权代价去主动探索、协作的三层锁——这些设计决策是我们定下来的，AI 更多是"提词 + 改 bug 加速器"。
- 加分话术：「正因为有 AI 省下了写代码的时间，我反而有精力把"为什么这么设计"想清楚——这也是我今天能把这些讲出来的原因。」
- 避坑：**他是问"是不是 AI 写的"，你要把落点转到"设计决策是我做的、我能讲清楚为什么"**，既不撒谎、也证明你对项目有真实掌控。

### G5. 问：这个项目有什么收获/你学到了什么？

**答案模板**：
> 最大的收获是**理解了"解耦"和"架构约束"不是抽象概念**：7 个进程只靠 Redis + RabbitMQ 就能协同，任何模块挂了别的还能跑，代价是引入了一致的消息协议、中间件依赖和排查成本。也学会了"先定协议再并行开发"的协作节奏，以及 AI 辅助下怎么守住"自己要对每个设计负责"。
- 避坑：不要说"我学会了 Java/Redis 的 API"这种太浅的收获，落到**架构意识 + 协作方法 + 自省**。

## H. 一页纸速查（考前扫一眼）

- **数字**：3 学分 / 4 人；7 进程 + 1 公共库 + 1 launcher = 9 模块；tick 500ms（100~2000ms）；探索率 100% 约 3~5 分钟（30×30/3车/BFS/500ms）；85% 切聚类；权值 已探索5/未探索1（监督 3/1）；红线 0.3→0.8；重叠>50% 重分；`MAX_PATH_LENGTH_RATIO=2.0`；10-tick 冷静期；预约锁 `EX 3`、连续失败 3 次 BLOCKED；单实例锁 `EX 30`；3D 最大 70×70；WS ≤200ms（目标值）。
- **诚实三件套**：课程项目 / AI 辅助 / 非生产级。
- **三个"口径"**：「无碰撞无重复分配」= 机制保证 + 演示观察；「≤200ms」= 设计目标值非 benchmark；「7 进程 9 模块」= 7 进程 + common + launcher。
- **被问缺点**：先承认 + 给改进思路（B 节 5 条 + 总基调）。
- **答不上来**：诚实承认 + 定位思路 + 改进方向，不硬编。
