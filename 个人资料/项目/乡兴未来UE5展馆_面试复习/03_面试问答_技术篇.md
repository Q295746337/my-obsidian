## A 项目整体与背景（4 题）

### A1. 用一句话介绍这个项目。（必问）
**答：** 乡兴未来是一个以 UE5 为引擎、以河北省阜平县骆驼湾村为原型的红色乡村数字孪生项目：做了两套高精度三维场景（总书记走访重点房屋精细化场景 + 骆驼湾村全域 1:1 复刻），一套工程兼容 PC / Android / VR 三端，再配套一个线上宣传网站，融合数字孪生、VR、人机交互、AI 导览和网页服务，服务红色研学与乡村振兴宣传。

**追问（你们到底交付了什么）：** 两套 UE5 场景 + 三端可运行包（exe / apk / 连接 VR 自动进 VR 模式）+ 已部署的网站 http://LuoTwoWan.cn + 一套 AI 向导。功能包括漫游、讲解、答题、电视播放、灯光、天气、传送、自动门等。

### A2. 为什么选骆驼湾村？项目背景是什么？（必问）
**答：** 骆驼湾村是河北省阜平县太行山深处的村庄，2012 年 12 月总书记踏雪走访、发出脱贫攻坚动员令，是全国脱贫攻坚的标志性起点之一。它曾是贫困发生率近 70%、人均可支配收入仅 950 元的深山村，如今面貌巨变。这个"从贫困到振兴"的对比本身就有很强的教育意义，所以我们想用数字技术把这段红色历史和乡村新貌保存、展示出来，做乡村振兴宣传和红色研学。

**追问（为什么不用普通网页/视频，偏要做 3D 虚拟展馆）：** 文字和视频是线性叙事，而 3D 展馆可以让人自主漫游、自由探索、互动答题，更有沉浸感和代入感，尤其适合"重走走访路"这类场景教育。

### A3. 怎么理解"用数字技术保存红色文化"这个定位？（常问）
**答：** 现实中的村落会变、实物会老化，我们做的是把骆驼湾村的建筑、院落、道路、地貌用可交互的三维形式复刻下来，形成一份可长期保存、可远程访问的"数字档案"。配套 AI 向导和讲解，让不在现场的人也能沉浸式了解这段历史，这是数字孪生在文化保存和传播上的一个具体落地。

**追问（你们有哪些红色文化内容）：** 总书记走访的重点房屋精细场景、红色文化虚拟展馆、电视机里播放脱贫攻坚纪录片和总书记走访影像、展板图文讲解等。

### A4. 项目规模和你的角色是什么？（必问）
**答：** 这是大创项目（立项级别以立项文件为准），3 人团队。项目分两条线：**美术建模线（房屋/家具/贴图/光照/场景）是队友在做，工程线我负责**——UE 蓝图/C++ 交互、AI 向导、网站前后端、三端打包和网页接入。这些我都实际做过、能讲原理，但深度是"够用"的程度；真正钻得最深的是 **AI 向导**。队友分别负责建模表现层，以及传送/打包等环节。

> 口径提示：结题报告书团队为李财源（负责人）、王子欢、刘倚岐，指导教师王绚（工程师）、王秀梅（教授）。正式立项时间按简历 **2024.11–2026.04** 统一说即可。

**追问（3 个人怎么把一个体量不小的项目做下来）：** 一是靠分工明确、各自负责一个模块；二是大量复用 UE5 现成能力和素材资产，不重复造轮子；三是把范围控制在"展示 + 基础设施级交互"，不追求做成商业级产品。

## B UE5 与三维（6 题）

### B1. 什么是数字孪生？你们做到什么程度？（必问）
**答：** 数字孪生的核心是"物理实体的虚拟镜像 + 与实体的数据联动"。我们在项目中做的主要是它的**展示层/几何复刻层**：按骆驼湾村的布局、建筑、道路、山地地形做高精度三维重建，并叠加材质、光照、天气、交互，让人在虚拟空间里沉浸漫游。严格说，完整数字孪生还需要实时传感数据回流和双向映射（比如实时客流、温湿度传感器数据），这部分我们没做，所以我会坦诚表述为"数字孪生展示 / 数字复刻"，而不是完整的数字孪生平台。

**追问（怎么向非技术的人解释）：** 就是给真实的骆驼湾村在电脑里建一个"看得见、走得进、能交互"的高精度三维副本。

### B2. 蓝图和 C++ 各自干哪些活？为什么这么分工？（必问）
**答：** 项目标题就叫"基于 UE 蓝图/C++"。实际以**蓝图为主**：事件驱动、可视化连线，非常适合快速搭建自动门、答题机、电视开关这类交互，也方便非纯程序方向的队友协作。C++ 用在需要更强性能控制、更复杂逻辑或复用底层的部分。分工原则是"开发快、易维护的用蓝图，性能敏感或底层扩展的用 C++"。

**追问（蓝图和 C++ 怎么互调）：** 蓝图可以调用 C++ 暴露出的函数/事件，C++ 也能通过 UFUNCTION 宏把类和方法暴露给蓝图使用，两者共用同一套反射系统。

### B3. 两套场景怎么做建模、怎么"1:1 复刻"？（常问）
**答：** 两套场景侧重点不同：① 重点房屋精细化场景，做的是总书记走访的那户人家的房屋外观、院落、内饰、家具、农具、人物、动物、车辆、植被等全细节，外加一座红色文化虚拟展馆；② 全域复刻场景，做的是整个村庄的布局、民居、道路、山地地形和植被（一号院、二号院、村会议室、民宿，以及篮球场、公路、湖泊桥梁等环境基建）。建模流程是：资料采集→参照照片/数据建模型→展 UV→贴图→导入 UE→布景打光。所谓"1:1"我理解为**比例和布局的还原**，我们没有激光点云这种测绘级数据，是基于实地调研照片和公开资料做的比例还原，这一点我会如实说。

**追问（为什么不两套合成一套）：** 精细化场景细节重、适合"走进去细看"，全域场景范围大、适合"俯瞰整体"，两者性能预算和展示目标不同，分开做更能兼顾效果和运行流畅度。

### B4. 材质、光照、动画是怎么处理优化的？（常问）
**答：** 光照用定向光加天空大气来模拟昼夜交替，配合天气系统（风雨天、水雾天）切换氛围；材质用 PBR 流程，控制粗糙度/金属度/法线贴图来还原砖墙、木门、农具等质感；动画以简单移动和门开合、NPC 行走劳作这类基础动画为主，不追求骨骼级复杂动画，控制成本。优化的核心是"按可见距离换精度"：远景模型降精度、植被控制密度、烘焙静态光照减少实时开销。

### B5. Niagara、MPC、3ds Max 在项目里是什么角色？（可能）
> 口径提示：简历上写了这三样，但结题书和软著说明都没点名。先核实自己到底用没用。

**答：** 我按"应该是什么角色"讲，但会先诚实声明实际使用情况：
- **Niagara** 是 UE5 的粒子/特效系统，用来做雨、雪、水雾、粒子云这类天气氛围效果。项目确有"风雨天、水雾天"功能，但文件只写了天气变化，没点名 Niagara——需要确认当时是用 Niagara 还是普通粒子/后期做的。
- **MPC（Material Parameter Collection）** 是全局材质参数集合，用于统一联动控制一批材质的参数（比如天气切换时统一调光照和氛围感）。面试按 06「糊弄话术」答即可（用在哪 + 简单原理，不深入）。
- **3ds Max** 是通用三维建模软件，用于建场景/建筑/道具模型再导入 UE。文件只写"三维建模"，未点名具体软件。

**建议口径：** 面试时主动说"天气效果我做了风雨/水雾/昼夜，具体用的是 UE 的粒子与材质参数方案"，而不是背书式报软件名。报了自己没用过的工具被追问会当场露馅。

### B6. 队友简历写的"C++ 构建交互状态机模型"合适吗？（可能）
> 口径提示：这是队友夸张点。请核实项目里到底是显式状态机实现，还是蓝图里用枚举 + Branch 做的状态切换。

**答：** 从"交互的本质"讲，自动门（关闭/开合/关闭）、答题机（待机/提问/答对/答错）、电视（播放/暂停）、天气（晴/雨/雾/昼夜）确实都是**事件驱动的状态切换**，用"状态"来描述是合理的。但我要诚实说明实现方式：我们是主用蓝图，靠布尔量、枚举变量和分支逻辑来表现这些状态，而不是某套严谨的 C++ 状态机框架。面试时我会说"用枚举 + 分支把交互拆成有限状态来管理"，而不吹"C++ 状态机模型"这种大词。

## C 多端与 VR（6 题）

### C1. 三端适配怎么做？"一套工程"怎么兼容？（必问）
**答：** UE5 本身是跨平台的，底层渲染对 PC / Android / VR 是同一套，真正的差异在三块：输入、UI 和性能档位。我们的做法是：把核心玩法和场景逻辑写在共享层，输入统一抽象（键盘鼠标 / 触屏 / VR 手柄都映射到同一套动作），然后按平台做不同的打包配置——Windows 出 LTW.exe、Android 出 LTW.apk，检测到 SteamVR 设备自动进入 VR 模式。这样一套工程能出三个端，不用维护三份代码。

**追问（三个端是共用一份关卡还是各自有：** 共用同一场景和交互逻辑，只在输入映射、UI 分辨率和画质档位上做平台区分。

### C2. PC / Android / VR 的输入差异怎么处理？（常问）
**答：** Windows 用键盘 WASD/方向键移动 + 鼠标环视，加一组快捷键（E 答题、H 看展板、G 灯、Tab 唤醒 AI、数字键传送、ESC 设置）；Android 用触摸（虚拟摇杆/滑动环视/点按交互）；VR 用手柄 + 头显 6DoF。策略是**用输入动作做抽象层**：逻辑代码绑定"移动""环视""交互"这些抽象动作，而不是绑定具体按键，各平台再把自己的输入源映射进来，这样交互代码只有一份。

### C3. 6DoF 和瞬移传送是怎么实现的？（常问）
**答：** 6DoF 指六个自由度（三个方向平移 + 三个方向旋转），由 SteamVR 通过头显和手柄的追踪实时给到位姿。移动上我们提供了**平滑移动 + 瞬移传送**两种方式：平滑移动用摇杆推动角色，瞬移用手柄射线指定落点后把角色瞬间传送过去。做两种是为了缓解 VR 晕动症——有人摇杆走路会晕，瞬移更舒适。

**追问（怎么做防眩晕）：** 保持高帧率是第一位的，帧率掉下来最易晕；其次提供瞬移选项、控制移动加速度，避免突然的视角转动。

### C4. 打包 exe / apk 踩过哪些坑？（常问）
**答：** 我们确实经历了好几次打包报错的攻坚过程，我总结成一套排查思路，而不是报几个编造的 bug：**看日志定位 → 按"环境 → 项目配置 → 资源 → 插件"逐层排除 → 做最小化复现 → 查官方文档和社区**。常见的坑集中在这几类：Android 的 SDK/NDK 环境配置、APK 体积过大和纹理压缩、添加的特殊插件在打包时没勾选、资源路径带中文或特殊字符、着色器编译失败等。这题我主要讲"方法"，再配我们"从打包报错到最终三端跑通"的真实过程。

**追问（APK 体积怎么控制）：** 纹理压缩格式、精简白名单资源、只打包用到的关卡和资产、降低不必要的高模精度。

### C5. 项目的最低配置是什么？怎么保证"流畅运行"？（常问）
**答：** 我们定的最低配置：PC 是 i5-8400 / GTX 1060 / 8GB 内存 / Win10 64 位；Android 是骁龙 845 / 4GB / Android 8.0 以上。为了在这档硬件上流畅，核心手段是：LOD 分级、远景与植被降密度、纹理压缩、烘焙部分光照减少实时计算、控制单帧 DrawCall。这里的"流畅运行"是我们测试时的自述目标，不是第三方压测数据，我会如实说。

### C6. 云渲染 / Pixel Streaming 的原理和优缺点？"网页免部署"到底怎么实现？（常问）
> 口径提示：这是**本项目最需要核实的一句话**。两份文件都只写了"网页点击虚拟展馆→加载并进入→系统自动识别设备类型"，**没有点名 Pixel Streaming 或 WebSocket**。队友简历里的"云原生实时渲染推流/免部署接入"是包装，不要默认属实。

**答：** 先区分两件事，诚实讲：
1. **确认过的事实**：线上网站（http://LuoTwoWan.cn）确有"虚拟展馆"入口，网页端能加载并进入 3D 展馆，且会按访问设备类型做识别。这是文件明确写的。
2. **需要核实的技术路线**：具体是"网页在线流式渲染（Pixel Streaming）"还是"识别设备后引导下载对应版本"，我需要回去确认。我面试时会先讲清楚第 1 条，不擅自说第 2 条。

**如果确实用了 Pixel Streaming，可这样讲原理**：服务端在带 GPU 的机器上跑 UE 应用做渲染，把画面实时编码成视频流（一般走 WebRTC）推给浏览器解码，同时把浏览器收到的键盘鼠标触屏输入传回服务端。用户只要有个浏览器和网络就行，**免下载安装、免本地高性能 GPU**。优点是集中更新、跨端一致、保护内容；缺点是**对带宽和延迟敏感、服务端 GPU 成本高、并发受服务器实例数限制、弱网体验差**——这也是为什么它适合做"演示/预览"，不适合高并发大规模商用。

**追问（WebSocket 在不在项目里）：** 同样核实口径。如果确实做了"UE 端与网页端实时通信"，WebSocket 是合适的方案（全双工长连接，把网页指令传进引擎、把状态回传）；若没做，就老实说网页与 3D 展馆的交互按实际实现讲，别背队友简历里的"WebSocket/HTTP 实时通信"。

## D AI 向导（6 题）

### D1. DeepSeek API 是怎么接入 UE 的？（必问）
**答：** 用 DeepSeek 的对话接口，走 HTTP 请求：带上 API Key、model、messages 和 system 提示词，发 POST 请求。在 UE 里通过 HTTP 模块（如 FHttpModule，以你工程实际为准）发异步请求，回调里拿返回结果渲染到 UI 上。关键点是**异步处理**——不能同步阻塞游戏主线程，否则画面会卡。

**追问（异步怎么处理）：** 发请求后用回调/委托接收结果，UI 先显示"回答中"状态，等返回再刷新文本，保证渲染线程不被网络等待卡住。

### D2. 多轮对话的上下文是怎么维护的？（常问）
**答：** DeepSeek（和主流 chat 接口一样）是无状态的，多轮对话要靠客户端把历史消息带上。我的做法是维护一个消息队列，每次请求把 system + 历次 user/assistant 消息一起按 messages 数组发过去，接口根据完整历史生成下一句。同时给队列设长度上限、必要时裁剪最早的历史，避免 token 超限和延迟变高。

### D3. "村民身份提示词"是怎么设计的？（常问）
**答：** 核心是 system prompt 里的角色设定，也就是 persona：告诉模型"你是骆驼湾村的一位村民/向导，口吻亲切朴实、熟悉当地历史和脱贫攻坚故事，用村民身份跟来访者讲解"。这样回答就有拟人化、贴合乡村场景的效果。**需要强调：这是提示词层面的角色设定，不是模型的预训练或微调**——我们没有重新训练模型。

### D4. 方言和普通话"自动切换"是怎么做的？（常问）
**答：** 诚实拆成两层：我们主要做的是**文本侧的口吻控制**——在提示词里要求"根据提问用村民口吻/适当带方言词回答，普通话提问就普通话答、方言味重的提问就方言味回"，让输出贴合村民身份。DeepSeek 本身是文本大模型，"方言"是靠 prompt 引导出来的口语化风格，不是我们训练了方言模型。如果进一步做语音输入输出才需要接 ASR/TTS，我们目前以文字对话为主。

**追问（用户输入是文字还是语音）：** 使用时是 Tab 键唤醒对话框、输入问题，输入输出以文本为主。

### D5. "延迟 < 1.5 秒、准确率 98%"这个指标哪来的？（常问）
> 口径提示：这两个数字是《使用说明书》里明示的项目自述指标，不是第三方压测结果。

## E 网站全栈（3 题）

### E1. 网站前后端各自负责什么？（常问）
**答：** 前端是宣传展示性质：主页、发展时间轴、虚拟展馆入口、功能介绍（图文/动图/短视频 + 点赞评论）、下载中心（Win/Android/VR 三端下载）、留言板。后端是管理后台：留言审核、下载统计、内容管理这几类接口。整体是"前端展示 + 后端管理"的简单前后端分离结构。

### E2. 留言审核、下载统计、内容管理是怎么实现的？（常问）
**答：** 留言：用户提交后先不入库直接展示，而是存成"待审核"状态，后台审核通过才在前端留言板上显示，防止垃圾内容。下载统计：用户在下载按钮触发时记录一条下载日志（时间/版本/设备等字段），后台做统计汇总。内容管理：后台提供接口对页面内容（时间轴、功能介绍等）做增删改，前端读接口渲染，避免改内容要动代码。

### E3. 部署上线是怎么做的？（可能）
**答：** 网站已部署在 http://LuoTwoWan.cn，是域名 + 服务器 + HTTP 服务的常规部署。需要诚实的点是：当前能满足展示和个人/小范围使用，**高并发承载不是强项**（结题书里明确列了这条不足），如果大规模推广，要提升服务器性能和加载速度。

## F 综合追问（3 题）

### F1. 讲一次你印象最深的排查/攻坚经历。（必问）
**答：** 整个项目经历过好几次典型攻坚：从早期打包报错、VR 适配失败，到后来双地图上线、三端运行、网站开通。我讲打包那次：先看报错日志定位到具体环节，然后按"环境→配置→资源→插件"的顺序逐层排除，用最小可复现的方式缩小范围，再查官方文档和社区。核心收获是养成了"先看日志精确定位、再分层验证、不靠猜"的排查习惯，这也是我把好几类报错最终都解决掉的原因。

**追问（遇到不会的怎么办）：** 第一反应先自己复现和定位，第二查官方文档和社区同类问题，第三把问题拆小一步步做减法，实在不行记录清楚再请教别人，而不是甩手。

### F2. VR 适配失败当时是怎么排查的？（常问）
**答：** 按依赖链从外到内查：设备驱动 → SteamVR 本身能否正常运行 → 项目的 VR 插件是否启用 → 头显有没有被识别 → 6DoF 输入是否正常映射 → 渲染帧率够不够导致眩晕。每层都用"能/不能"来二分定位，找到断在哪一层再处理。VR 的坑经常不在业务逻辑，而在"设备-运行时-引擎插件"这条链路上。

### F3. 如果让你优化加载速度和体验，你会怎么做？未来改进方向？（常问）
**答：** 加载速度：LOD 分级、纹理压缩、异步加载和关卡流式加载（Level Streaming）、精简初始加载的资产、控制首屏精度。体验与能力扩展上，结题书里我们自己就列了三条不足，我会直接讲：① 部分场景细节和模型精度还有优化空间（远景模型、植被密度、光影）；② VR 交互可继续扩展（目前以漫游和讲解为主，未来可加手势交互、多人同步参观）；③ 网站高并发承载能力待加强。

**追问（这是故意问缺点的题吗）：** 主动讲清楚不足，反而说明你对项目有判断、知道迭代方向，比硬吹"产品级"可信得多。这几条不足正是结题报告书里的"存在问题"，面试直接引用既真实又不怕被追问。
