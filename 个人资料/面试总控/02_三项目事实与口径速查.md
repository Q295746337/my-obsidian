## 1. 伊岐优选

### 1.1 简历原文（不可改）

> **伊岐优选 核心开发 2026.06–2026.08**
>
> 项目介绍：基于 SpringBoot 开发的本地生活服务平台，提供商家信息查询、优惠券秒杀与 AI 智能客服等功能，帮助用户发现优惠、帮助商家推广引流。
>
> 技术栈：SpringBoot、MyBatis Plus、MySQL、Redis、Lua、Kafka、Caffeine、LangChain4j。
>
> 技术细节：
> - 秒杀下单与异步处理：基于 Redis+Lua 原子校验秒杀资格（库存判断 + 一人一单），Kafka 异步下单、削峰；SpringTask 定时关闭超时未支付订单，乐观锁解决支付与关单的并发冲突，保证库存不超卖、订单不重复。
> - 缓存与数据一致性：采用 Caffeine+Redis 二级缓存，逻辑过期方案防热点 Key 击穿、缓存空值防穿透；更新数据库后删除缓存，删除失败经 Kafka 重试、TTL 兜底，保证缓存与数据库一致。
> - 接口限流：基于 Redis+AOP+注解实现滑动窗口限流，支持全局、IP、用户多维度，防止刷券、爬虫与系统过载。
> - AI 智能客服：基于 LangChain4j 接入大模型，通过 Function Calling 调用店铺查询、预约到店等工具，Redis 存储多轮会话记忆，实现自动答疑与业务办理。
>
> 项目成果：
> - 完成优惠券秒杀全链路，Redis+Lua 保证不超卖、一人一单，Kafka 异步削峰配合缓存与限流，保障高并发下系统稳定。
> - AI 智能客服支持多轮对话，可自动查询店铺信息、完成预约到店，覆盖核心业务咨询与办理场景。

### 1.3 四条技术主线

#### A. 秒杀下单与异步处理

| 要点 | 具体做法 | 面试追问 |
|---|---|---|
| 资格校验 | Redis + Lua 原子执行：判断库存 > 0、`SISMEMBER` 判断一人一单、预减库存、记录用户 | 为什么用 Lua？Redis 单线程 + 脚本原子性，避免“判断-扣减”中间被并发打断 |
| 库存存储 | String：`seckill:stock:{voucherId}` | 为什么不用 MySQL 扣库存？热点行锁竞争，QPS 上不去 |
| 一人一单 | Set：`seckill:order:{voucherId}` 存 userId；一人 N 单可改 Hash 记录次数 | Set 大 Key 怎么办？单券库存一般不大；真大就拆分 key |
| 异步下单 | 资格通过后发 Kafka 消息，消费者扣 MySQL 库存、生成订单 | 为什么异步？秒杀接口只做资格判断，扣库存/建单可延迟 |
| 幂等 | 订单 ID 唯一（主键），重复消费插入失败即跳过 | Kafka 至少一次，重复消费怎么办？唯一订单 ID 幂等 |
| 关单 | SpringTask 定时扫描未支付超时订单，`update ... where status='未支付'` | 重复关单/重复加库存？where 状态条件保证只成功一次 |
| 支付 vs 关单 | 乐观锁：两个更新都带 `status='未支付'`，只有一个成功 | 关单成功但用户已支付？原路退款；库存已释放，不能改回已支付 |

**可讲的数据**：JMeter QPS 1000、200 库存，同步方案平均 500ms → Redis+Lua 方案 176ms（笔记压测，本地环境）。

#### B. 缓存与数据一致性

| 要点 | 具体做法 | 面试追问 |
|---|---|---|
| 二级缓存 | Caffeine 本地 + Redis 分布式；先本地、再 Redis、最后 DB | 本地缓存集群不一致怎么办？设短 TTL，或广播失效 |
| 击穿 | 热点 key 逻辑过期：不设 TTL，value 里存过期时间；过期后抢锁、异步重建，其他请求返回旧值 | 为什么不用互斥锁？可用性优先，允许短暂旧数据；强一致场景才用互斥锁 |
| 穿透 | 查不存在的数据也缓存空值，设短 TTL | 为什么不用布隆过滤器？实现复杂、有误判、无法删除；商铺量不大 |
| 一致性 | 更新 DB 后删除缓存；删除失败发 Kafka 重试；TTL 兜底 | 为什么先更新 DB 后删缓存？避免脏数据长期存在；最终一致不是强一致 |
| 兜底 | 重试达到上限告警/人工介入 | 消息一直失败怎么办？记录失败次数、告警、人工排查 |

**可讲的数据**：MySQL 18,970 req/s → Redis 57,769 → Caffeine+Redis 93,930；平均延迟 52.47ms → 17.19ms → 10.53ms；较 MySQL 4.95×、较 Redis 1.63×（笔记压测）。

#### C. 接口限流

| 要点 | 具体做法 | 面试追问 |
|---|---|---|
| 实现 | Redis + AOP + 自定义注解 `@RateLimiter`；切面拦截，Lua 脚本统计窗口 | 为什么用滑动窗口？固定窗口临界问题会放行双倍流量 |
| 维度 | 全局、IP、用户 | 维度怎么取？方法签名/注解参数/用户上下文 |
| 算法 | 滑动窗口；了解令牌桶/漏桶/固定窗口 | 为什么不用 Sentinel？项目规模小，自己实现更轻；Sentinel 功能更全但引入成本高 |
| 目的 | 防刷券、爬虫、系统过载 | 限流被绕过的 IP 怎么办？结合黑名单/验证码/风控 |

#### D. AI 智能客服

| 要点 | 具体做法 | 面试追问 |
|---|---|---|
| 接入 | LangChain4j + 大模型（qwen-plus 兼容接口），流式返回 | 为什么用 LangChain4j？统一模型接入、工具调用、记忆/RAG 生态 |
| 工具调用 | Function Calling：查店铺、查优惠券、预约到店、查预约 | 模型怎么知道调用哪个工具？工具描述 + 参数 schema；模型输出工具调用，后端执行 |
| 会话记忆 | Redis：窗口（最近 30 条给模型）+ 归档（完整历史）+ 用户会话索引 ZSet | 窗口和归档为什么分开？窗口控 token，归档给用户看 |
| 会话隔离 | memoryId 由后端生成，格式 `user:{userId}:{sessionId}`；Controller 校验归属 | 怎么防止看别人会话？userId 前缀校验，越权 403 |
| RAG | Redis 向量库 + 文档切分/embedding；意图路由：业务数据走工具，泛知识走向量检索 | RAG 和 Function Calling 怎么分工？一个答资料，一个查实时数据 |
| 安全 | 手机号服务端绑定，工具不接收手机号；预约全链路校验；API Key 环境变量 | 模型被诱导查别人券怎么办？查询主体从登录态取，模型改不了 |
| 工程细节 | N+1 批量查询、ThreadLocal 清理、Nginx 关缓冲支持流式 | 为什么关缓冲？不关会影响逐字输出 |

## 3. 分布式探索仿真系统（变电站）

### 3.1 简历原文（不可改）

> **分布式探索仿真系统 核心开发 2026.05–2026.07**
>
> 项目介绍：针对变电站多车协同巡检场景，开发分布式探索仿真系统，支持多车自动探索、路径规划、实时可视化及单机 / 多机联机演示。
>
> 技术栈：Java 17、Redis、RabbitMQ、SQL Server、WebSocket、Docker。
>
> 技术细节：
> - 分布式架构：基于黑板模式将系统拆分为 7 个独立的进程模块，以 Redis 为共享黑板 + RabbitMQ 总线解耦，模块间零直接调用，由调度器 500ms 节拍驱动，Docker Compose 编排、可独立部署。
> - 多车协同规划：实现加权 Dijkstra / A* 路径规划（对未探索区加权），贪心前沿 + 聚类等，重叠惩罚防扎堆，分布式锁 + 位置预约锁防冲突，WebSocket 推送车辆与地图快照。
>
> 项目成果：
> - 3 车 30×30 地图约 3～5 分钟探索率达 100%，全程无碰撞、无重复分配，WebSocket 端到端延迟 ≤200ms。
> - 完成 4 人 4 机联调，初始化 <3 秒，覆盖多档车数/障碍率，支持动态加车、回放与 Canvas/Unity 双视图。

### 3.3 架构与模块

| 模块 | 类型 | 职责 |
|---|---|---|
| TaskConfigurator | 进程 | 任务初始化：生成地图/障碍、计算密封区、分配出生点、写 TaskConfig |
| Navigator | 进程 | 路径规划：加权 Dijkstra/A*，写 Car RouteList |
| TargetPlanner | 进程 | 目标分配：贪心前沿 + 聚类 |
| StrategySupervisor | 进程 | 路线监督：去重叠 + 加权重规划 |
| Car | 进程（可多实例） | 小车执行端：5 态状态机、移动、碰撞检测 |
| Display | 进程 | HTTP :8887 静态页 + WebSocket :8888 推送、动态加车、回放 |
| Controller | 进程（单实例） | 唯一调度器：500ms 节拍驱动全车队 |
| common | 公共库 | Redis 黑板、MQ、SQL、共享模型、地图算法、认证/分析/回放 |
| launcher | 可选启动器 | 一键拉起各进程 |

### 3.4 关键机制速记

- **一次 tick**：ASSIGN_TARGET → PLAN_ROUTE →（可选监督优化）→ TICK_MOVE → REFRESH_ALL（Fanout）。
- **路径**：BFS 档实际 WEIGHTED_DIJKSTRA；ASTAR 档加权 A*（gCost + 曼哈顿）；已探索 5 / 未探索 1；纯 BFS 只在单测。
- **目标分配**：<85% 逐格前沿贪心；≥85% 聚类收尾；同 tick `allocatedTargets` 去重。
- **打分公式**：路径长度 + 6×重合 + 20×贴边 − 4×连通块 − 2×路径未探索 − 4×深度。
- **防冲突**：每车锁 `SET NX` + 位置预约锁 `pos:reserve:{x}:{y}` `SET NX EX 3`（连续失败 3 次 BLOCKED）+ `isOccupiedByOtherCar` 复查。
- **单实例**：`SET controller:instance 1 NX EX 30`；没有心跳续期，不是高可用主备。
- **密封区**：不可达空格；探索率分母剔除。
- **推送**：REFRESH_ALL（Fanout UpdateView）→ Display 读 Redis 快照 → WebSocket 广播；不是轮询。
- **存储**：Redis 实时态；SQL Server 可选（users/registration_requests/operation_logs/simulation_runs/simulation_run_stats；jBCrypt）。
