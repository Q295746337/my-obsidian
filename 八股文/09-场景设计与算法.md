## CAP 与 BASE

### 分区容错性(P）

分区容错性指当网络发生分区（节点间通信中断） 时或者部分节点故障时， 系统仍能继续运行，不因部分节点失联而整体崩溃。它是分布式系统的 “生存底线”。

### 可用性(A）

可用性即服务一直可用，且响应时间正常。

一般在衡量一个系统的可用性时， 是通过停机时间来计算的

| 可用水平(%) | 年可容忍停机时间 |
| --- | --- |
| 99.9999 | < 1 min |
| 99.999 | < 5 min |
| 99.99 | < 53 min |
| 99.9 | < 8.8 h |
| 99 | < 3.65 d |

**为了实现可用性：**

- 冗余设计： 多节点部署， 避免单点故障。
- 负载均衡：将请求分发到健康节点。
- 熔断机制：故障时快速拒绝请求， 防止雪崩。

### 一致性(C）

在分布式系统中，一致性指所有节点在同一时刻看到的数据是相同的（强一致性）

BASE 理论是对 CAP 理论的延伸， 强调通过放松一致性（Consistency） 的要求，换取分布式系统的高可用性和良好的性能。核心思想是虽然无法做到强一致性 (CAP的一致性就是强致性)，但应用可以采用适当的方式达到最终一致性(Eventual Consistency)。

BASE 是指

- 基本可用(Basically Available)
- 软状态(Soft State)
- 最终一致性(Eventual Consistency)

### 基本可用 (Basically Available)

**什么是基本可用呢？假设系统， 出现了不可预知的故障，但还是能用， 相比较正常的系统而言：**

1. 响应时间上的损失：正常情况下的搜索引擎0.5秒即返回给用户结果， 而基本可用的搜索引擎可以在2秒作用返回结果。
2. 功能上的损失：在一个电商网站上， 正常情况下， 用户可以顺利完成每一笔订单。但是到了大促期间， 为了保护购物系统的稳定性， 部分消费者可能会被引导到一个降级页面。

### 软状态

什么是软状态呢？允许系统中的数据存在中间状态（临时不一致性），不同节点的数据副本可以暂时不一致。

### 最终一致性

系统不可能一直是软状态， 必须有个时间期限。在期限过后， 应当保证所有副本保持数据一致性，从而达到数据的最终一致性。这个时间期限取决于网络延时、系统负载、数据复制方案设计等等因素。

## 微服务调用链日志追踪

### 背景

微服务架构是一个分布式架构， 它按业务划分服务单元， 一个分布式系统往往有很多个服务单元。由于服务单元数量众多，业务的复杂性， 如果出现了错误和异常， 很难去定位。

主要体现在， 一个请求可能需要调用很多个服务， 而内部服务的调用复杂性， 决定了问题难以定位。

所以微服务架构中， 必须实现分布式日志链路追踪，

去跟进一个请求过程中有哪些服务参与， 参与的顺序，从而达到每个请求的步骤清晰可见， 出了问题，极速定位。

### 实现

目的：调用方每一次向系统服务发起请求时， 要生成这一次调用产生的相关调用链日志

1. 全局 traceID 的生成和传递： 当请求到达首个后端服务或网关服务时， 服务会生成一个唯一全局traceID， 然后放入到请求的 Header 中， 通过 Header 传递给下个调用服务。
2. 获取和保存traceID：下游服务可通过设置过滤器或者拦截器， 接收全局 traceID， 记录到类似
ThreadLocal 线程私有的地方， 确保同一线程内所有日志自动关联 traceId。（注意：服务内部若有异步线程， 应该把 traceID 复制给异步线程）

3. 打印日志：在打印日志信息时带上traceID。
4. 分布式日志聚合：一般会有一个分布式日志系统平台，在上面可以根据 traceID 去查询请求链路日志
**日志文件都是服务器各自生成在本地的， 如何把多个服务的服务器的日志聚合在一起？**

因此每个服务都要接入分布式日志系统平台，所以每个服务要把日志文件在服务器上的路径告诉日志平台。

分布式日志系统再到服务器上收集日志文件内容。

## 负载均衡

### 基于软件的负载均衡分为三个大类

1. DNS LoadBalancer - DLB
2. NetWork LoadBalancer - NLB 在网络层做的负载均衡
3. Application LoadBalancer - ALB 在应用层做的负载均衡

### 负载均衡架构案例

为了有效支持全球化部署、HTTPS、高并发场景的需求， 负载均衡的架构应该是怎么样的？用某公司的负载均衡架构举例 (读者可以将其当做你们公司的负载均衡架构)

DNS负载均衡（粗粒度的机房选择）

-> 网络层负载均衡（例如LVS四层负载）

-> 应用层负载均衡（例如Nginx七层负载）

1. DNS负载均衡
  - 作用： 作为全局流量的第一层调度，根据用户地理位置将请求导向距离最近的机房。

2. 网络层负载均衡（如LVS）
  - 作用： 在机房入口 Virtual IP 接收流量， 通过四层转发规则（DNAT目的地址转写） 将请求分发至后端的 Nginx 集群。LVS提供高可用高性能的四层转发。

3. 应用层负载均衡（如Nginx）
  - 作用： 在七层处理请求， Nginx 再基于请求路径的分发到后端集群。

#### 基于 DNS 的负载均衡——DNS LoadBalancer - DLB

DNS是一个网络协议，本身就是将域名转换为IP返回。当服务是全球化分布的集群时，会有不同区域的机房。

- 思路：在域名解析的过程中，将这个域名随机的解析成不同的区域的机房的IP地址， 这样用户请求就自然的被分发到不同的区域的机房。是地理位置和机房级别的负载均衡
- 优点：配置非常清晰简单， 帮助找到距离用户物理地址最近的机房的IP地址
- 缺点： 当修改DNS的转发策略， 因DNS有多级缓存， 其更新生效有一定延时，但机房IP不会有太多变更， 配置相对稳定， 因此影响不大
- 应用场景：在负载均衡架构中是作为 [第一道] 的负载均衡， 是地理位置和机房级别的负载均衡

#### 基于网络层的负载均衡——NetWork LoadBalancer - NLB

常见实现有： LVS

- 思路：请求先发到一个机房入口 Virtual IP地址，接收到请求后会进行 DNAT，也就是目标地址转换， 简单说就是请求的目的地址会被转变成后台实例的IP地址， 一般都是私有LAN网络里面的IP地址，对外是不可见的
- 优点：性能好，不需要查看请求数据包的数据，不需要解密
- 缺点：路由转发没有路径分发那么灵活， 一般只能基于目标的端口号或者协议来制定分发规则

#### 基于应用层的负载均衡——Application LoadBalancer - ALB

常见实现有： Nginx、HaProxy

- 思路：基于Http的请求路径来进行分发到不同实例
- 优点：基于路径分发请求很灵活

## 全局分布式 ID

### 定义 & 特性

全局分布式ID 即分布式系统下的唯一标识

核心目标是解决分库分表后单机自增ID的局限性（如重复ID问题）， 并满足高并发、高可用场景下对唯一标识的需求。例如， 电商订单、用户ID、消息流水号等场景均需全局唯一且有序的ID来保证数据一致性

分布式ID 尽量具备的特性

1. 全局唯一性：ID必须全网唯一， 避免重复（基本要求）
2. 趋势递增：ID 整体按时间或业务规则递增，提升数据库写入性能（避免页分裂）
3. 高性能与高可用： 生成速度快（低延迟、高QPS）， 系统可用性需达到5个9（99.999%）
4. 信息安全：ID 需避免连续或可预测， 防止恶意爬取业务数据
5. 长度适中：通常为64位或更短，便于存储和查询

### 生成方案和原理

#### UUID

UUID 全局唯一标识符， 是指在一台机器上生成的数字， 它保证对在同一时空中的所有机器都是唯一的

标准的UUID格式为：xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx (8-4-4-4-12)， 共32个字符UUID 是基于当前时间、计数器、机器的mac地址等数据计算生成的

优点：生成性能比较高，不依赖网络，本地就可以生成

缺点：没有任何含义， 排查调试困难、非递增 写入数据库可能导致页分裂， 造成额外的性能开销

#### Redis 生成

Redis 的 incr 或 incrby 命令实现 ID 的原子性自增优点：

- 基于内存性能高
- ID自增缺点：
- Redis 可能存在数据丢失的情况， 无论是哪种持久化机制，都无法完全避免
- 安全性： 自增生成的ID容易被猜测， 可以在前缀加入一些特定字符或时间戳

#### 雪花算法

雪花算法是一种分布式ID生成算法， 可以生成全局唯一且递增的ID

核心思想：将一个64位的ID划分成多个部分， 由 时间戳、机器标识和序列号等组成。

**具体组成：**

1. 符号位（1bit）：预留的符号位，始终为0， 占用1位
2. 时间戳（41bit）：精确到毫秒级别，41位的时间戳容纳的毫秒数是2的41次幂， 支持约69年
3. 机器标识（10bit）：可以用来区分不同的机器（即雪花算法服务最多能部署在1024台服务器上）
4. 序列号（12bit）：所以单台机器使用雪花算法支持每毫秒最多生成4096个不同的分布式ID
**优点：**

- 高性能高吞吐：每秒钟单台服务能生成百万自增ID，不依赖网络，本地就可以生成
- ID自增：
  - 如果<雪花算法生成分布式ID>服务是部署单台机器，那么生成的ID是自增的
  - 如果<雪花算法生成分布式ID>服务集群部署的，则不能保证生产的ID是在全局上是自增的

因为当同一毫秒内，A机器和B机器先后生成ID的 时间戳是相同的，仅机器标识一定不同，但无

大小关系

**雪花算法的问题：**

时钟回拨问题

雪花算法使用服务器时间戳作为生成ID的一部分， 如果系统时钟回拨， 可能会导致生成的ID重复

**系统时钟回拨指的是网络时间校准或人工设置**

**解决方案：**

1. 方案一：若发现时钟回调了，就直接抛异常出来或阻塞线程， 直到系统追平最后一次生成ID的时间（但短时间内就无法生成分布式ID， 即服务不可用， 只能适用于能够容忍短暂中断的场
景）

2. 方案二： 改造雪花算法的ID构造
- 将 10位 机器码 拆分改造成 3位时钟序列 + 7位机器码
  - 影响: 10位->7位 机器码， 意味着原先能部署1024个<雪花算法生成分布式ID>的服务节点，现在只能部署128个<雪花算法生成分布式ID>的服务节点（需要自行评估是否需要这么多的节点）
- 当发生时钟回拨时， 可以递增时钟序列， 我们有3位时钟序列， 意味着可以递增8次时钟序

列， 即单台机器可以解决8次时钟回拨问题， 一定程度上可以缓解时钟回拨问题， 如果3位时钟序列还不能满足要求，则应该根据实际业务场景的并发量判断是否需要12位的序列号(单台机器1ms就能生成4096个ID)， 如果并发量没有这么大，则可以减少序列号的位数，转而增加时钟序列的位数。

**Tips:**

- 机器标识（10bit），用于标识不同的机器节点， 是可以自定义分配的， 并不一定要从机器属性中获取，例如通过ZooKeeper、etcd等系统动态分配唯一ID， 节点启动时注册并获取ID，宕机后释放。

## CPU 飙高的排查思路

1. 使用 top 命令，查看各进程占用CPU的情况 => 得到占用CPU过高的进程PID
2. 使用 top -H -p 进程PID 命令，查看该进程中的各线程占用CPU的情况 => 得到占用CPU过高的线程ID
3. 使用 jstack 进程PID 命令可以打印出Java进程中的线程的堆栈跟踪信息
- jstack 进程PID 打印出的线程ID是以16进制展示的
- top -H -p 进程PID 打印出的线程ID是10进制展示的
- 因此要先把10进制的线程ID转换成16进制的形式：使用linux命令即可完成转换
- 因此最终使用 jstack 进程PID | grep 16进制线程ID，打印出该线程的堆栈跟踪信息

4. 确定问题代码， 可能是死锁或者死循环导致CPU飙高
内存泄漏： 对象因引用未被释放而无法回收

堆(内存泄漏->内存溢出)：OutOfMemoryError：java heap space

可能存在对象一直不被回收，存在内存泄漏， FullGC后依然空间不足， 最终堆空间溢出

**步骤：**

1. 获取堆内存快照dump
2. VisualVM去分析dump文件 (VisualVM可以加载离线的dump文件， 即可查看堆快照信息)
3. 通过查看堆信息的情况，定位堆内存溢出问题

## 与外部服务交互的稳定性

在很多业务中，都需要和外部的一些机构进行交互， 比如在电商场景，在发货环节， 需要和各个快递公司做交互进行发货、物流更新。聚合支付场景需要和外部支付渠道做交互实现支付等。

很多时候， 我们自己的服务的可用性会有一些保障的，但是，外部机构的可用性是没办法保证的，比如双十一大促期间， 支付方式除了支付宝之外， 还可能用银行卡支付，但是很难保证银联系统可以抗这么高的并发。

**那么， 遇到这样的情况，外部机构不可靠时， 如何避免自己的应用不被拖垮呢？**

**主要有几个思路：**

1. 异步交互
2. 文件交互
3. 超时机制
4. 限流降级熔断

### 异步交互

首先比较容易想到的就是和外部机构之间不要进行同步交互， 同步交互的话会把所有的流量都发送到外部合作方， 并且本系统还要同步等结果，不仅会浪费自己的系统资源， 还会让自己的系统整体响应变慢。

在有些场景中， 可以考虑和机构进行异步交互。

比如， 我们在电商网站上购买商品， 附带会有运费险，那么当用户下单以后，要给买家投保一笔运费险。

像这个场景， 如果每一个订单都去调用保险公司的话，那大概率他们是扛不住这个业务量的。而运费险投保如果稍微晚一会，在小时级别的话，理论上对业务是无损的， 因为一般不太可能几个小时

内就发货， 收货， 退货。

所以， 我们就可以异步的和外部的保险公司进行交互， 通过定时任务或者延迟消息的方式，和保险公司交互， 这样可以起到削峰填谷的作用， 并且这个链路可以不断重试， 即使失败了，也不会影响到正常的下单主流程

### 文件交互

文件交互是一种异步交互的极端例子，在异步的基础上增加了批次的概念。

即把之前的每单异步， 变成了批量异步

比如电商业务中， 商家发货时， 需要生成快递单号，但是这些快递单号如果实时去快递公司获取的话，那就有一定的失败的概率

所以就可以事先 先从快递公司申请一个批次的快递单号，然后自己本地发货时直接使用，然后在批量的通知给快递公司就行了

这种批量通知给快递公司可以是一个接口调用，也可以用文件。用文件的好处就是甚至都不需要接口交互， 只需要把文件生成好上传到FTP中，对方自己下载后解析就行了

### 超时机制

在做外部接口交互时， 并不是所有的情况都可以做异步， 比如说高德的聚合打车。

当我们输入完出发点和目的地之后开始叫车时，他就需要实时的和各个租车平台对接交互，然后分发这笔订单。

这个过程就要同步交互，但是我们需要给每个第三方平台都设置一个请求的超时时间， 比如2秒钟，超过2秒钟就自动中断了。而不是让用户一直在前端的等。

并且根据这种外部接口的响应时间的数据， 我们可以做一些动态的负载均衡， 把更多的流量分发给性能更好的服务商

### 限流降级熔断

接口如果超时很严重， 我们也需要对他做限流、降级和熔断。

限流：就是假如他的接口就能扛100QPS，那么我们就不能给他超过100的并发请求，那样他会处理不过来， 导致整体性能下降。

降级：假如查询一个用户中心的服务查用户名，但是接口响应慢，那么就可以暂时降级， 直接返回"陌生人"或者 “用户名加载中”等信息。

熔断：假如外部某个接口特别慢，那么就可以干脆就不要再调他了。

这样做对业务是有损的。比如大促当天，银联的接口性能太差了， 我们把银联去掉，那么用户就会无法用银联支付了。对用户来说就少了个选择。

但是对于我们的系统来说，起到了很好的保护作用。可以在外部接口性能恢复以后再恢复调用就行了。

## 如何实现 A 网站登录后， B 网站自动登录

有这么个场景， 公司下有多个不同域名的站点， 我们期望用户在任意一个站点下登录后，在打开另外几个站点时，也是已经登录的状态， 这么一过程就是单点登录。

因为多个站点都是用的同一套用户体系，所以单点登录可以免去用户重复登录，让用户在站点切换的时候更加流畅， 甚至是无感知。

题述问题，本质上是 单点登录 的问题

单点登录（Single Sign-On， 简称 SSO）：是一种用户认证机制， 允许用户在一次登录后，访问多个系统或应用程序而无需再次登录

### 基于 Cookie

适用情况： A网站和B网站必须是同一域名下的两个网站， 如 a.example.com 和 b.example.com可以通过共享 Cookie 的方式来实现 SSO

优点是实现起来简单， 浏览器天然就支持

缺点是限制必须不能跨域， 如果是两个不相关的网站，就不能通过Cookie实现SSO

### 基于 Token

使用标准化的令牌（如 JWT）来携带用户认证信息。用户登录后， 服务端颁发一个令牌

（Token） 给到前端， 前端在访问其他的网站的时候， 把这个 Token 放到 HTTP Header 中带过去，然后就可以基于这个Tokne来验证用户身份了

这个方案可以解决跨域的问题， 只要支持HTTP的协议即可。

但是缺点是Token可能会被泄漏。存在一定的安全隐患。

1. 登录阶段：
  - 用户访问服务器登录
  - 服务器生成JWT令牌（包含用户ID、有效期等）

示例令牌：○eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyX2lkIjoiMTI

zNDUiLCJleHAiOjE2...

2. 访问任意系统：
  - 前端在请求头携带令牌：

```http
Authorization: Bearer eyJhbGci...

```

  - 各个业务系统自行验证令牌：
    - 检查签名是否有效（使用预共享密钥）
    - 检查有效期
    - 直接解析令牌获取用户信息

### 基于共享 Session

用户登录后， 系统将用户信息存储到公共的第三方存储， 如Redis或数据库

例如使用Redis，那么所有业务系统都必须知道该公共Redis的实例信息，才能够访问获取用户信息

### 通过 CAS

CAS 是 Central Auth Service，也就是认证中心服务

> 注：注意和并发编程中的 Compare And Swap 区分

多个需要实现单点登录的系统，都接入这个统一认证中心，所有的登录、认证都通过这个认证中心来实现

1. 用户访问子系统时重定向到 CAS 服务器登录
2. CAS 服务器验证用户身份并返回一个票据（Ticket）
3. 子系统使用票据向 CAS 验证， 获取用户信息
这个方案一般适合于企业内部做集成， 可以让业务系统不再关心登录、授权， 而是只关注业务逻辑， 只需要做一次接入就行了。比如说公司的很多内部平台之间，就可能是用了同一个登录服务。

优点就是接入成本低， 缺点就是这个认证中心本身的开发成本还是挺高的。

## 如何预估接口上线后的 QPS

### 问题引入

这个问题其实是一个非常实际的问题， 因为我们在开发需求后，例如：新增了一个接口有一个步骤是值得做的，那就是预估这个接口的QPS

因为我们是可以去调配对应服务器的数量和运行配置的

- 例如我可以从2个节点新增为4个节点
- 例如我可以将节点的内存从2G变成4G， 2核CPU变成4核CPU

如果因为 没有正确的预估 以及 没有正确的调整， 导致接口的QPS过高，扛不住系统崩溃，那就是严重的外网事故了

注意，这里说的预估QPS，是假设有一个真实的项目、真实的环境，预估这个接口上线后会有多少 QPS

而不是在预估我们的系统接口本身能抗住多少QPS而不崩溃

### 如何预估

预估一个接口的 QPS，本质上是在考虑这个接口被调用的频繁程度

1. 分析业务
- 业务类型： 不同的业务类型的QPS是不太一样的， 再细化一些，接口的做的事情是不同的，QPS是不同的，例如这个接口是 获取商城首页数据（QPS估计会高）、删除好友（QPS估计会低）
- 活跃用户： 有多少活跃用户， 活跃用户多（QPS估计会高）， 活跃用户少（QPS估计会低）

2. 计算平均的QPS：根据活跃用户数和业务类型估算

```java
a. 假设有100w个活跃用户（数值由活跃用户决定）
b. 假设经过历史数据的统计，每个用户平均每天产生10次请求（数值由业务类型决定）
c. 则可估算出平均每秒请求量（QPS） 为 （10 * 100w） / 86400= 116

```

3. 计算峰值的QPS：假设业务类型是有峰值情况(特殊事件带来的流量波动)的， 即我们的接口可
能会达到更高的QPS

- 峰值情况通常是的平均值的数倍，假设峰值为平均值的3倍，则峰值QPS约为348

通过预估接口上限后可能的峰值QPS后，就可以相对应的调整服务器节点的数量、服务器的运行配置

需要能抗住峰值QPS，记得给自己留点缓冲， 即把值设置的略大一些

### 与哪些因素有关

1. 后端服务器集群节点数量，数量越多，QPS越高
2. 后端服务器节点的运行配置：运行内存、Cpu核数等等，硬件资源决定单节点处理能力
3. 接口本身做的事情
- 做的事情多耗时长 （预估QPS会相对应低）
- 做的事情少耗时短（预估QPS会相对应高）

4. 系统架构：
- 完善的流量负载均衡架构， 实现流量的有效分发和负载均衡， 避免成为QPS瓶颈
- 缓存技术，减轻数据库的压力， 避免数据库成为QPS瓶颈
- 集群模式的数据库， 避免数据库成为QPS瓶颈
- 静态资源通过CDN加速， 避免成为QPS瓶颈

### 如何预估？

首先需要知道一个请求处理完毕的时间（这个请求里可能做很多事情，但是这个我们暂时不管），一个请求处理完毕的时间我们是可以知道的。（我们去调用这个接口多次得到平均值即可）

理论计算公式

1. QPS（单节点） = 线程数（如 Tomcat 线程池）/ 平均请求处理时间（秒）

```java
a. 例如：若线程池大小为 200， 单个请求处理时间为 50ms（0.05秒）
i. SprigBoot 默认使用Tomcat， 而Tomcat线程池的最大线程数就是200，所以在默认配置下， SprigBoot 应用可以并发处理 200 请求
b. 则 QPS（单节点） = 200 / 0.05= 4000

```

2. QPS（集群）= QPS（单节点）* 节点数
- 例如集群有4个节点，则 QPS（集群） = 4000 * 4 = 16000

单个请求处理的时间是受到

“系统架构”、“接口本身做的事情”“后端服务器节点运行配置”“后端服务器节点数量”

等等因素共同影响的 但这实际上是一个近似已知值（我们去调用这个接口多次得到平均值即可）

### QPS 瓶颈

我们想想QPS的瓶颈在哪？其实很多方面，就像前面说的QPS与哪些因素有关但一般来说 QPS 最可能的瓶颈在于数据库 (例如MySQL)

### 应该说多少 QPS

**面试官如果问接口的QPS多少， 如何回答比较合理？**

首先我们一定可以知道这个接口处理的平均耗时是多久？假设是200ms一些项目背景暂时假设为如下情况， 因个人而定

- 假设有 n 台后端服务器
- 假设后端服务器的配置是 2核4G内存
- 假设接口做了一些事情
- 假设对于一些系统架构上，做了一些优化、或者没有做优化那么

1. QPS（单节点） = 线程数（如 Tomcat 线程池）/ 平均请求处理时间（秒）
- 若线程池大小为 200， 单个请求处理时间为 100ms（0.01秒）
- 则 QPS（单节点） = 200 / 0.01= 2000

2. QPS（集群）= QPS（单节点）* 节点数 = 2000 * n
没有压测的情况下，我们就可以说这个理论计算得出的值。但是理论仅仅是理论

如果有压测，那其实是另外更好的一种情况， 因为压测得到的数据往往是更加准确的。

例如压测过程：使用 JMeter 进行了压力测试， 逐步增加并发线程数， 直到接口的响应时间超过预设阈值（如 200ms） 或错误率超过 1%。此时就可以知道接口可以抗住的QPS

**示例：**

面试官： “你在项目中负责的订单查询接口，QPS 是多少？”

**你的回答：**

“订单查询接口的 QPS 在 ‘双11’大促期间峰值达到 5,000， 日常平均 QPS 约为 1,200。我们通过以下步骤得出这一数据：

1. 压测阶段：JMeter 进行了压力测试， 逐步增加并发线程数，发现当 QPS 达到 2,000 时， 响应时间达到300ms。
2. 瓶颈分析：通过 Arthas 追踪发现，80% 的请求耗时在数据库查询上。
3. 优化措施(仅为举例，具体情况依据个人而定)：
  - 引入 Redis 缓存热点商品数据， 缓存命中率提升至 90%；
  - 对订单表按用户 ID 进行分库分表， 单表数据量从 1 亿减少到 1 千万；
  - 将日志记录改为异步写入 Kafka，减少主线程耗时。

4. 优化结果：最终压测 QPS 提升到 5,000，且响应时间稳定在 80ms 以内。
此外， 线上监控显示， 实际高峰期的 QPS 与压测结果基本一致， 系统未出现超时或宕机。”

## 订单\<未支付&到期\>关闭如何实现？

这个问题本质的模型是： 过一段设定的时间 或 检测到未执行某个操作 后执行某个操作

例如

- 订单未支付10分钟内自动取消/关闭
- 商品发货7天后自动确认收货
- 购买的团购券某个日期后自动失效并退款

方案一般是有很多种实现方式的，但要记住一个点：

方案的选择要结合实际场景考虑多方面， 并不是仅以完成功能为目标， 需要考虑

- 方案正确性、成本、方案复杂性、后期业务发展后 能否持续承载业务完成功能

### 实现方式

#### 被动关闭

思路： 当订单未支付时， 当用户来访问这个订单， 系统再判断订单的时间是否到期， 如果过期了就进行关闭操作和提示用户。

优点：简单

***端：**

- 无法主动推送：关闭依赖于用户， 无法主动推送订单关闭消息
- 未处理数据可能堆积：关闭依赖于用户， 如果用户一直不访问订单怎么办， 如果是大量用户都不访问，那么会有大量未处理/未关闭的数据堆积在数据库中
- 查时写：在用户查询的过程中进行关闭， 进行写操作， 第一是耗时会增长， 第二是如果写操作失败，你关闭失败又怎么处理， 如果在用户查询的时候系统背后重试关闭，耗时会进一步增

加。

应用场景：这种方式是非常不推荐的，例如涉及到钱款的一般需要系统主动退回， 而非用户访问才退回

#### 定时任务扫数据库

思路：开启定时任务， 内容是 扫描数据库的订单表， 获取订单状态为未支付的且过期的订单，执行关闭。

优点：简单

***端：**

- 时间不精确：定时任务调度依赖于固定的频率， 可能订单已经到期，但定时任务的调度时间还没到
- 数据库压力： 当数据库的数据量很大时，扫表获取订单状态为未支付的且过期的订单，对数据库造成压力， 可能会影响到线上业务的正常运行
- 分库分表情况： 当数据库的数据量很大时，做了分库分表， 这时候扫表整个定时任务的耗时非常长

应用场景：适合对于时间精确性要求不高、业务量不是很大的场景。

#### RocketMQ 延迟消息

RocketMQ 支持延迟消息： 当消息写入Broker后，不会立即被消费， 需要等待指定时长后才可以被消费者处理， 这种消息称为延迟消息

思路： 当订单创建后，例如业务规定订单10分钟未支付则关闭，则发送一个10分钟的延迟消息，在10分钟后， 消息就会被消费者消费，检查订单状态，然后关闭订单。

优点：时间较精确、解耦、即使业务持续发展也可始终完成功能

***端：**

- 如果原先没有RocketMQ，则需要引入RocketMQ，成本问题
- 引入MQ之后随之也会有消息丢失等问题，提升系统复杂度应用场景：适用于绝大多数场景

#### 定时任务 + Redis Zset

> 注：zset是一个有序集合，每个元素关联一个分数，且自动根据分数排序

思路：可以借助 Redis 的 Zset 数据类型来实现

- 新建订单：元素member设置为订单号，分数score设置为订单的超时的时间点的时间戳。 Redis的Zset自动会根据分数/到期时间戳 排序。
- 关闭过期订单：定时任务获取 Zset 中 “ 当前时间戳 > 分数score” 的数据， 即只要获取比当

前时间戳小的数据， 关闭订单， 关闭订单后再删除Zset中对应的元素优点：巧妙利用Redis的Zset， 实现高效的"关闭过期订单"

***端：**

- 时间不精确：定时任务调度依赖于固定的频率， 可能订单已经到期，但定时任务的调度时间还没到

**面试时最后总结一下：**

我认为利用在 大型系统中、数据量很大的情况下 使用 RocketMQ 等具有延迟消息功能的消息队列来完成是比较合适的， 而在数据量不大， 时间精确性要求不高的情况下，使用定时任务扫描MySQL数据库处理是比较简单合适的，不需要引入消息队列， 降低成本， 避免提升系统复杂度。

> 注：面试时多说几种方案，分析清楚优缺点， 可以展现思维的广度和扎实的基础

## 1 亿个数据取出最大前 100 个

**背景知识：**

- 堆的逻辑结构和完全二叉树一致，但底层实现是数组（完全二叉树的层序遍历结果存储在数组中）
- 堆每次弹出元素， 是从堆顶弹出
- 堆又名优先队列，例如 Java 中的 Priority Queue
- 小顶堆：堆顶元素是整个堆中的最小值
- 大顶堆：堆顶元素是整个堆中的最大值

**问题解决：**

使用堆(Heap) 数据结构来实现，那么要用小顶堆还是大顶堆

问题要求取出最大的前100个，则堆里应该保留下最大的100个，所以应该用小顶堆

1. 创建一个最小堆
2. 遍历1亿个数据，循环内：
- 判断堆的大小size是否小于100
- 若小于100， 把元素加入堆
- 若大于等于100，则判断当前遍历的元素和堆顶元素的 大小关系

1. 遍历元素 > 堆顶元素，则弹出堆顶元素 (此时弹出的是堆里最小的元素)，加入遍历的元素
2. 否则不做处理
3. 当遍历完成后，堆中的元素就是前100个最大的数据

```java
for(int num : nums){
    if(minHeap.size() < 100){
        minHeap.offer(num); // 若小于100，把元素加入堆
    }else{
        if(num > minHeap.peek()){
            // 遍历元素  > 堆顶元素，则弹出堆顶元素   (此时弹出的是堆里最小的元素)，加入遍历的元素
            minHeap.poll();
            minHeap.offer(num);
        }
}
}

```

时间复杂度是O(n*log100)， 其中n是数据总数

- 遍历所有数据加入堆：O(n)
- 在堆中始终只维护了100个元素，每一次调整的时间复杂度是O(log100)比将所有数据排序的时间复杂度要低得多

Tips： 当说完这个后， 面试官可能会问 你使用的数据结构 堆是什么，堆的原理是什么，堆的插入元素、删除元素是怎么实现的

(1) 插入元素

1. 将新元素添加到数组末尾
2. 从该位置开始，与父节点比较
  - 小顶堆：若新元素 < 父节点， 交换位置。
  - 大顶堆：若新元素 > 父节点， 交换位置。

3. 重复步骤2， 直到堆序性质恢复。
(2) 删除堆顶元素

1. 将堆顶元素与数组末尾元素交换，删除末尾元素。
2. 从堆顶开始，与子节点比较：
  - 小顶堆：选择较小的子节点交换。
  - 大顶堆：选择较大的子节点交换。

3. 重复步骤2， 直到堆序性质恢复。

https://blog.csdn.net/qq_58240849/article/details/132579105

## 大文件排序

问题分析：大文件小内存， 文件内存储的是数字， 要求对文件内容进行排序， 主要面临内存不足无法一次性加载整个文件进行排序的问题。

核心思路：分块排序+多路归并

**解决思路：**

1. 分块排序：
- 将大文件分成多个小文件， 每个小文件的大小不超过内存限制
- 每个文件读取到内存中进行高效排序
- 将每个文件的排序结果写回磁盘， 最终生成多个有序的文件
- 这些文件仅是文件内局部有序， 全局上是无序的，所以还需要做全局排序
- 多线程优化：可采用多线程技术， 同时对多个小块进行排序， 提高排序效率

2. 多路归并 (对排序后的小块文件进行归并)：

```java
a. 假设分块步骤中分成了9个文件，则打开这9个文件， 预读数据到文件各自的输入缓冲区
b. 从每个文件的输入缓冲区中取第一个元素，与各自的文件标识， 一起插入小顶堆
c. 弹出堆顶元素， 写入(结果文件的)输出缓冲区（当输出缓冲区满了则写入结果文件）， 同时记录元素来源文件标识（假设来自文件 i）
d. 从文件 i 的输入缓冲区取下一个元素， 再插入小顶堆
e. 再回到 c 步骤顺序执行， 直到所有的文件都被读取完毕

```

核心思路就是先把大文件分成多个小文件， 每个文件的大小不超过内存大小， 每个文件在内存中高效排序再写回。

对多个小文件进行外部归并排序， 得到最终结果文件。

问题： 如果分块要分成很多个文件(单个文件大小不超过内存限制)，假设分成1000个文件

如果无法同时对1000个文件进行多路归并，则可以分批依次对50个文件多路归并， 最终得到20个有序的新文件

再对20个新文件进行多路归并， 得到最终文件

## 数据一致性

**缓存一致性问题指的是：在数据要更新时， 如何保证MySQL数据和Redis缓存的数据一致性？**

### 更新数据库+同步删除缓存

在代码中 更新MySQL数据后， 紧接着删除Redis缓存， 同时缓存需设置TTL。优点：简单实现， 如果能够删除Redis缓存成功，数据不一致的时间非常短

缺点：缓存删除失败可能导致一定时间的数据不一致

1. 为什么是先更新MySQL，后删除Redis缓存？会不会有数据不一致的问题
- 首先更新MySQL数据 —— 删除Redis缓存， 中间这一段时间当然是数据不一致的，但是因为是同步删除， 间隔时间极短， 几乎忽略不计。
- 另外当高并发情况下， 可能存在因为并发读写导致数据不一致的情况，分析如下

ⅰ. 读请求：缓存未命中，读取数据库的值为20

ii. 写请求：更新数据库的值为21，删除缓存

ⅲ. 读请求：将20写回缓存

- 但上述情况出现的概率很小： 因为 更新MySQL的耗时 >> 写入Redis缓存的耗时， 正常流程下不应该在经过了写请求之后，读请求才把旧值写回缓存， 当并发量不大的情况下，几乎不会发生
- 但如果先删除Redis缓存，后更新MySQL的数据， 虽然理论上避免了一小段时间的数据不一致，但是在并发读写的场景下又会出现数据不一致的概率会大很多，分析如下

ⅰ. 写请求：删除缓存

ii. 读请求：缓存未命中、读取数据库的值，更新缓存值为20

ⅲ. 写请求：更新数据库的值为21

- 因为更新MySQL的耗时 >> 删除Redis缓存的耗时，所以很有可能会有并发读请求在"删除缓存"和"更新数据库" 之间执行， 导致数据不一致。

2. 为什么是删除Redis缓存，而不是更新？
- 删除缓存更简单耗时更短， 而更新缓存如果涉及到复杂的数据聚合，则耗时很长
- 如果在写写并发的场景下更新Redis缓存， 可能会出现数据不一致的问题

3. 如果删除Redis缓存失败了怎么办？
- 依赖TTL到期自动删除缓存
- 两种改造方法：
- 消息队列重试

ii. 订阅BinLog + 消息队列重试

消息队列重试

1. 在代码里，更新MySQL数据， 同步删除缓存， 如果删除失败，则发送一个消息队列的删除缓存的消息
2. 再由一个消费者监听对应的消息，将缓存数据删除
3. 如果删除失败，触发重试机制， 重试删除。如果重试超过一定次数，则需要记录异常且告警。该方法对代码入侵性比较强，且引入了消息队列，提升了系统的复杂性，提高了服务的风险性。
订阅BinLog + 消息队列重试

1. 在代码里，更新MySQL数据， 同步删除缓存
2. 另外需要引入中间件 (例如Canal) 模拟MySQL主从复制的交互协议， 把自己伪装成一个
MySQL 的从节点， 由于主从数据同步，所以Canal 可以获取到BinLog，相当于拿到了数据库更新的记录

3. 下游服务订阅 Canal 的数据，然后发送一个消息队列的删除缓存的消息
4. 由消费者监听消息将缓存删除， 同理会有重试机制和告警机制
该方法解除了代码入侵的问题。缺点是引入的组件比较多，提升了系统的复杂性，提高了服务的风险性。

### 延迟双删

**延迟双删指：**

1. 先删除缓存
2. 更新数据库
3. 延迟一定时间后，删除缓存
**第一次先删除缓存的原因：**

只要是先更新数据库， 再删除缓存， 一定会在两个操作之间存在一段时间是MySQL数据和Redis缓存数据不一致的。在这段时间内有概率读取到旧的缓存值

但是如果先删除缓存， 再更新数据库，理论上就不会有这样一段数据不一致的时间，避免读取到旧值

**更新数据库：**

但是先删除缓存， 再更新数据库，在并发量大的情况下，也比较容易由于读写并发导致数据不一致1. 写请求：删除缓存

2. 读请求：缓存未命中、读取数据库的值，更新缓存值为20
3. 写请求：更新数据库的值为21
此时也是数据不一致的，在第二步之后的所有的读请求都是读取旧值， 直到第二次删除缓存

**第二次删除缓存的原因：**

为了解决读写并发请求导致数据不一致的情况，所以要再删除一次缓存（延迟）。

**为什么要延迟一段时间再进行第二次删除缓存如果不延迟， 可能存在如下情况：**

1. 写请求：删除缓存
2. 读请求：缓存未命中、读取数据库的值20
3. 写请求：更新数据库的值为21
4. 写请求：第二次删除缓存
5. 读请求：更新缓存值为20
还是会导致数据不一致，所以第二次删除缓存需要延迟一段时间， 直到 并发的读请求都已经将旧值缓存好

这时候再去删除， 可以删除掉旧的缓存值

需要延迟多久

这个时间非常不好设定， 因为我们不知道并发的读请求写入缓存什么时候能够结束， 能够保证第二次删除缓存是能够删除旧值， 经验值一般设置为500ms-1s， 如果发生了并发读请求，那么在这段时间内数据是不一致的，外界读取的是旧值

**第二次删除就一定能成功吗**

如果第二次删除失败了怎么办，会导致长时间的数据不一致，所以还是要引入重试机制（消息队列重试）

**延迟双删的问题&总结：**

1. 第一， 先删除缓存， 再更新数据库， 虽然避免了一段数据不一致的时间，但是一旦有并发读请求， 比较容易出现读写并发导致数据不一致， 因为更新数据库往往比较耗时， 给了一段比较长的空窗期使得并发读请求可以读取到旧值写入缓存， 导致数据不一致
2. 第二，延迟多久时间，不好设定， 如果出现因为并发读写请求导致数据不一致， 如果设置为太长，则数据不一致的时间长， 如果设置太短， 可能第二次删除又无法删除到旧值，使得还是数据不一致
3. 第三， 如果没有发生并发读写请求导致数据不一致，那么第二次删除可能删除了正确的缓存值
4. 第四， 第二次删除不一定成功， 还是需要引入消息队列来重试保证成功，所以系统的复杂性并没有降低

### 总结

1. 上述方法都不能保证MySQL数据和Redis缓存的数据强一致性， 只是保证最终一致性
2. 方案的选择还需要考虑团队的技术栈，例如是否熟悉Canal， MQ消息队列
3. 综合来说
- 我认为 先更新数据库，再删除缓存，若删除失败使用消息队列重试的方案 + TTL 更优，同步删除保证数据不一致的时间段很短， 另外删除失败重试机制保证，TTL兜底（甚至可以再优化，发现多次删除失败，则进行数据一致性校验， 强行修改缓存数据）
- 如果使用 订阅BinLog + 消息队列重试 系统复杂度高
- 如果使用延迟双删，则延迟时间难以确认

4. 无论选择哪种方案都需要为缓存设置TTL，作为兜底
5. 另外可以定期对比缓存和数据库的数据是否一致
**Tips：**

- 注意使用消息队列重试或订阅BinLog + 消息队列重试 都是基于同步删除的前提下， 如果没有同步删除，则这个数据不一致的窗口时间会大一些（因为消息队列消费、拉取binlog数据都需要一定时间）

## 如何设计一个 RPC 框架

1. 定义RPC接口： 定义服务接口及其方法。这是RPC的核心， 决定了客户端可以调用哪些方法。
2. 选择通信协议： 选择合适的通信协议， 如HTTP/REST、TCP、UDP等。不同的协议有不同的优劣势， 取决于你的应用需求。
3. 选择序列化协议： 选择序列化协议，将数据转换为字节流以在网络上传输。常见的有JSON、 Protobuf、Thrift等。考虑效率、可读性和平台兼容性。
4. 实现远程调用： 实现将RPC请求发送到远程服务并接收响应的机制。这可能涉及到网络通信、数据解析和错误处理。
5. 服务注册与发现： 提供服务注册中心，使服务能够动态注册和发现。Zookeeper、Consul、 etcd等工具可用于服务注册与发现。
6. 负载均衡： 实现负载均衡机制，确保请求在多个服务节点之间分布均匀。常见的负载均衡算法有轮询、随机、最小连接数等。
7. 安全性： 考虑数据在传输中的安全性， 可以使用加密协议（如TLS/SSL）来保护通信。
8. 错误处理： 设计良好的错误处理机制， 包括定义错误码、异常传播和日志记录。确保客户端能够得知发生了什么问题。
9. 性能优化： 考虑并发性、延迟和吞吐量等性能方面的问题。使用连接池、异步IO等技术进行优化。
10. 监控和日志： 实现监控和日志记录， 以便及时发现问题并进行故障排除。集成日志系统和监控工具， 如Prometheus、Grafana等。
想要设计一个本地缓存，考虑点主要在数据用何种方法存储， 能存储多少数据， 多余的数据如何处理等几个点，下面我们来详细的介绍每个考虑点：

1. 数据结构
首要考虑的就是数据该如何存储，用什么数据结构存储。最简单的就直接用Map来存储数据， 或者复杂的如Redis一样提供了多种数据类型哈希， 列表，集合，有序集合等，底层使用了双端链表，压缩列表，集合，跳跃表等数据结构。

2. 对象上限
因为是本地缓存， 内存有上限，所以一般都会指定缓存对象的数量比如1024， 当达到某个上限后需要有某种策略去删除多余的数据。

3. 清除策略
上面说到当达到对象上限之后需要有清除策略， 常见的比如有LRU(最近最少使用)、FIFO(先进先出)、LFU(最近最不常用)、SOFT(软引用)、WEAK(弱引用)等策略。

4. 过期时间
除了使用清除策略， 一般本地缓存也会有一个过期时间设置， 比如redis可以给每个key设置一个过期时间， 这样当达到过期时间之后直接删除， 采用清除策略+过期时间双重保证。

5. 线程安全
像redis是直接使用单线程处理，所以就不存在线程安全问题。而我们现在提供的本地缓存往往是可以多个线程同时访问的，所以线程安全是不容忽视的问题， 并且线程安全问题是不应该抛给使用者去保证。

6. 简明的接口
提供一个傻瓜式的对外接口是很有必要的，对使用者来说使用此缓存不是一种负担而是一种享受，提供常用的 get， put， remove，clear，getSize 等方法即可。

7. 是否持久化
这个其实不是必须的， 是否需要将缓存数据持久化看需求。本地缓存如ehcache是支持持久化的，而guava是没有持久化功能的。分布式缓存如redis是有持久化功能的， memcached是没有持久化功能的。

8. 阻塞机制
我们使用缓存的目的就是因为被缓存的数据生成比较费时， 比如调用对外的接口，查询数据库，计算量很大的结果等等。这时候如果多个线程同时调用get方法获取的结果都为null，每个线程都去执行一遍费时的计算， 其实也是对资源的浪费。最好的办法是只有一个线程去执行， 其他线程等

待，计算一次就够了。但是此功能基本上都交给使用者来处理，很少有本地缓存有这种功能。

1. 秒杀系统场景特点
- 秒杀一般是访问请求数量远远大于库存数量， 只有少部分用户能够秒杀成功
- 秒杀时大量用户会在同一时间同时进行抢购， 网站瞬时访问流量激增
- 秒杀业务流程比较简单， 一般就是下订单减库存

2. 秒杀架构设计理念
- 限流： 鉴于只有少部分用户能够秒杀成功，所以要限制大部分流量， 只允许少部分流量进入服务后端秒杀程序。
- 削峰：对于秒杀系统瞬时会有大量用户涌入，所以在抢购一开始会有很高的瞬间峰值。高峰值流量是压垮系统很重要的原因，所以如何把瞬间的高流量变成一段时间平稳的流量也是设计秒杀系统很重要的思路。实现削峰

的常用的方法有前端添加一定难度的验证码，后端利用缓存和消息中间件等技术。

- 异步处理：秒杀系统是一个高并发系统， 采用异步处理模式可以极大地提高系统并发量， 其实异步处理就是削峰的一种实现方式。
- 内存缓存：秒杀系统最大的瓶颈一般都是数据库读写， 由于数据库读写属于磁盘IO，性能很低， 如果能够把部分数据或业务逻辑转移到内存缓存，效率会有极大地提升。
- 可拓展： 当然如果我们想支持更多用户，更大的并发， 最好就将系统设计成弹性可拓展的， 如果流量来了，拓展机器就好了。像淘宝、京东等双十一活动时会增加大量机器应对交易高峰。

3. 设计思路
- 将请求拦截在系统上游， 降低下游压力：秒杀系统特点是并发量极大，但实际秒杀成功的请求数量却很少，所以如果不在前端拦截很可能造成数据库读写锁冲突， 甚至导致死锁， 最终请求超时
- 充分利用缓存：利用缓存预减库存，拦截掉大部分请求
- 消息队列：这是一个异步处理过程，后台业务根据自己的处理能力，从消息队列中主动的拉取请求消息进行业务处理

4. 前端方案
- 页面静态化：将活动页面上的所有可以静态的元素全部静态化， 并尽量减少动态元素。通过CDN来抗峰值。
- 禁止重复提交：用户提交之后按钮置灰， 禁止重复提交
- 用户限流：在某一时间段内只允许用户提交一次请求， 比如可以采取IP限流

5. 后端方案
服务端控制器层(网关层)

限制u id（UserID） 访问频率：我们上面拦截了浏览器访问的请求，但针对某些恶意攻击或其它插件，在服务端控制层需要针对同一个访问uid， 限制访问频率。

6. 服务层
上面只拦截了一部分访问请求， 当秒杀的用户量很大时， 即使每个用户只有一个请求， 到服务层的请求数量还是很大。比如我们有100W用户同时抢100台手机， 服务层并发请求压力至少为100W。

- 把需要秒杀的商品的主要信息以及库存初始化到redis缓存中
- 做请求合法性的校验（比如是否登录）， 如果请求非法， 直接给前端返回错误码， 进行相应的提示
- 进行内存标识的判断 (true 已经秒杀结束，false 未秒杀结束，下面第4步会写入)， 如果内存标识为true， 直接返回秒杀结束
- redis中使用 decr 进行预减库存操作， 判断：如果decr后库存量小于0，则把内存标记置为true (已经秒杀结束， 第3步会用到)， 且返回秒杀结束
- 用 redis的布隆过滤器来判断是否已经秒杀到了（下面第7步会写入）， 防止重复秒杀， 如果重复秒杀， 直接返回重复秒杀的错误码。具体做法是：先用 redis的布隆过滤器来判断是否秒杀过， 如果布隆过滤器判断已经秒杀过了， 则再次查库确认是否秒杀过了， 之所以再次查库确认是因为布隆过滤器对可能存在的数据是有误判率的；但是它对不存在的数据的判断是百分百准确的，所以如果redis的布隆过滤器判断没秒杀过，就直接放过去进行秒杀
- 发送成功秒杀到的MQ消息给相应的业务端进行处理， 并给用户端返回排队中， 如果客户端收到排队中的消息，则自动进行轮询查询， 直到返回秒杀成功或者秒杀失败为止
- 相应的业务端进行处理：真正处理秒杀的业务端， 再次进行校验（比如秒杀是否结束，库存是否充足等）、将用户和商品id作为key存入redis的布隆过滤器来标识该用户秒杀该商品成功

（第5步会用到）、减库存（这里的是真正的减库存， 操作数据库的库存）、生成秒杀订单、返回秒杀成功

注意：就算请求走到了真正处理业务的这一端，也有可能秒杀失败， 比如秒杀结束，库存不足， 真正减库存失败，秒杀单生成失败等等， 一旦失败，则返回秒杀结束

优化：将秒杀接口隐藏：用户点击秒杀按钮的时候，根据用户id生成唯一的加密串存入缓存并返回给客户端，然后客户端再次请求的时候带着加密串过来，后端进行校验是否合法，若不合法， 直接返回请求非法

限制某个接口的访问频率：可以用拦截器配合自定义注解来实现， 这么做可以和具体的业务分离减少入侵，使用起来也非常方便

7. 数据库层
- 数据库层是最脆弱的一层， 一般在应用设计时在上游就需要把请求拦截掉，数据库层只承

担 “能力范围内” 的访问请求。所以，上面通过在服务层引入队列和缓存，让最底层的数据库高枕无忧

- 为防止秒杀出现负数订单数大于真正的库存数，所以在真正减库存， update 库存的时候应该加上 where 库存 > 0， 而且需要给秒杀订单表加上用户id和商品id联合的唯一索引

## 秒杀场景下如何增加库存

秒杀的方案，是扣减库存

- Redis 预扣减库存 （借助Lua脚本的原子性， Redis执行命令的单线程特性）
- 发送MQ消息异步扣减MySQL库存
- 若消费失败借助重试机制重试，若失败次数达到重试最大次数，触发告警人工介入排查

### 归并排序

时间复杂度：O(nlogn) 归并排序和初始序列是没有关系的， 因此最好、最坏、平均时间复杂度相同

空间复杂度：O(n) 临时保存归并后的数组

稳定性：归并排序是稳定的

思路： “先分后合”，将大问题拆解为小问题解决， 再将结果合并，整个过程分为 分 和 治 两步实现步骤

1. 分：将数组递归地分成左右两半， 直到子数组只剩一个元素（天然有序）
2. 治：合并两个有序数组：从两个子数组的头部开始比较， 选择较小的元素放入临时数组， 直到
所有元素合并完成。

![归并排序](file:///D:/Java/data/八股文/09-场景设计与算法/e4222ed3e5af.png)

```java
public class Main {
    public static void main(String [] args) {
        int [] arr = new int []{20, 10, 50, 30, 80, 50, 70, 40};
        int [] tempArr = new int [arr.length];
        mergeSort(arr, tempArr, 0, arr.length - 1);
        for (int i : arr) {
            System.out.println(i);
        }
}
    public static void mergeSort(int [] arr, int [] tempArr, int begin, int end) {
        if (begin >= end) {
            return;
        }
        int mid = (begin + end) >>> 1;
        mergeSort(arr, tempArr, begin, mid);
        mergeSort(arr, tempArr, mid + 1, end);
        mergeArr(arr, tempArr, begin, mid, end);
    }
    // 合并arr数组中的 两个有序的子数组(从begin-mid,从mid+1到end), 使得新的arr数组从begin到end是有序的
    public static void mergeArr(int [] arr, int [] tempArr, int begin, int mid, int end) {
        int leftPos = begin; // 左子数组的起始点
        int rightPos = mid + 1; // 右子数组的起始点
        int tempArrPos = begin; // 临时数组存储这次合并的结果 ,起始点从begin开始
        // 比较依次两个有序子数组的首元素 ,逐个加入tempArr临时数组中
        while (leftPos <= mid && rightPos <= end) {
            tempArr [tempArrPos++] = arr [leftPos] <= arr [rightPos] ? arr [leftPos++] : arr [rightPos++];
        }
        // 到这里一定会有某个子数组还有剩余元素 ,因此把剩余元素也加到tempArr中
        while (leftPos <= mid) {
            tempArr [tempArrPos++] = arr [leftPos++];
        }
        while (rightPos <= end) {
            tempArr [tempArrPos++] = arr [rightPos++];
        }
        // 把有序的数组tempArr放回原始数组arr
        for (int i = begin; i <= end; i++) {
            arr [i] = tempArr [i];
        }
}
}
```

### 快速排序

时间复杂度：最好：O(nlogn) 最坏：O(n^2) 平均：O(nlogn)

稳定性：快速排序是不稳定的

思路：快速排序每一次都排定一个元素，使其放到最终应该在的位置，然后递归地去排它左边的部分和右边的部分，依次进行下去， 直到数组有序

**实现步骤**

1. 选定Pivot中心轴
2. 将大于Pivot的数字放在Pivot的右边
3. 将小于Pivot的数字放在Pivot的左边
4. 分别对被Pivot划分出的左右子序列重复前三步操作

```java
public class Main {
    public static void main(String [] args) {
        int [] arr = new int []{20, 10, 50, 30, 80, 50, 70, 40};
        quickSort(arr, 0, arr.length - 1);
        for (int i : arr) {
            System.out.println(i);
        }
}
    public static void quickSort(int [] arr, int low, int high) {
        if (low >= high) {
            return;
        }
        int left = low; // 左指针
        int right = high; // 右指针
        int pivot = arr [low]; // 基准位置的值 ,固定选择首元素
        while (left < right) {
            // 移动右指针
            while (left < right && arr [right] >= pivot) {
                // 移动右指针的过程中发现 右指针指向的数一直大于基准数 ,符合预期 ,右指针一直移动
                right--;
            }
            // 出了循环有两种可能情况： 1.left==right 或 2.arr[right] < pivot
            if (left < right) {
                // 移动右指针的过程中发现 右指针指向的数小于基准数 ,将右指针的数移动到左指针的位置
                arr [left] = arr [right];
            }
            // 程序走到这里 ,可能有两种情况 : 1.left==right 或 2.left<right 且 右指针指向的元素已经进行了一次移动 ,则接下来要移动左指针了
            while (left < right && arr [left] <= pivot) {
                left++;
            }
            // 出了循环有两种可能情况： 1.left==right 或 2.arr[left] > pivot
            if (left < right) {
                // 移动左指针的过程中发现 左指针指向的数大于基准数 ,将左指针的数移动到右指针的位置
                arr [right] = arr [left];
            }
            // 最后一种情况的处理 ,即left==right
            if (left == right) {
                arr [left] = pivot;
            }
}// 递归基准点的左右两半子数组
        quickSort(arr, low, right - 1); quickSort(arr, right + 1, high);
    }
}
```

快速排序的时间复杂度是由什么影响的

快速排序的时间复杂度主要由分区的平衡性决定

即每次划分数组时基准值（pivot） 能否将数组分成大小相近的两部分。

1. 最好情况时间复杂度
- 条件：每次分区后左右子数组长度大致相等（即基准值接近中位数）
- 例如场景：数组元素随机分布， 基准值始终接近中位数
- 递归深度为 O(logn)，每层遍历 O(n) 元素，总操作次数为 O(nlogn)

2. 最坏情况时间复杂度
- 条件：每次分区后一个子数组为空， 另一个子数组包含剩余元素（如基准值为极值）
- 例如场景：
  - 数组已完全升序或降序，且基准值固定选择首元素/末元素
  - 所有元素相同，且基准值固定选择首元素/末元素
- 递归深度为 O(n)，每层遍历 O(n) 元素，总操作次数为 O(n ^2)

针对特殊测试用例：顺序数组或者逆序数组， 一定要随机化选择基准点（pivot）， 否则在输入数组是有序数组或者是逆序数组的时候，快速排序会变得非常慢（等同于冒泡排序或者「选择排

序」）

### 栈和队列

#### 如何用两个栈模拟一个队列

是很经典的常问的题目 (我的面试被问过几次)

面试时要求口述 入队操作和出队操作 的流程即可

假设有a栈和b栈

**入队操作：直接将元素加入a栈出队操作：**

- 1. 如果b栈为空，则将a栈的所有元素取出加入b栈
- 2. 弹出b栈的一个栈顶元素

```java
import java.util.Stack;
class MyQueue<T>{
    private Stack<T> stackIn;
    private Stack<T> stackOut;
    public MyQueue(){
        stackIn = new Stack<>();
        stackOut = new Stack<>();
    }
    public void enQueue(T e){
        stackIn.push(e);
    }
    public T deQueue(){
        if(stackOut.isEmpty()){
            // 把stackIn的内容加入stackOut
            while( !stackIn.isEmpty()){
                stackOut.push(stackIn.pop());
            }
}
        return stackOut.pop();
    }
}
public class Main {
    public static void main(String [] args) {
        MyQueue<Integer> q = new MyQueue<>();
        // 先进先出
        q.enQueue(1);
        q.enQueue(2);
        System.out.println(q.deQueue());
        q.enQueue(3);
        q.enQueue(4);
        System.out.println(q.deQueue());
        System.out.println(q.deQueue());
        System.out.println(q.deQueue());
    }
}
```

## 分库分表

分库分表实习/校招面试官一般不会直接问， 而是由某个点触发的例如当我们说到慢SQL优化的架构优化方面——分库分表，此时你可以引导面试官：从架构方面读写分离、Redis缓存、分库分表 ...但分库分表需要慎重使用， 因为引入它会带来问题面试官听到你这样说，很可能会继续追问：那你觉得分库分表要在什么时候用，要注意什么问题等等此时你都可以以订单数据为例去说明

分库分表是针对高并发、数据量大的场景下的技术优化方案

分库分表的本质就是数据分片，按照某个纬度把存放在单个数据库/表中的数据进行拆分，将其分散地存放到多个数据库/表中以达到提升性能的效果

水平拆分和垂直拆分

| 拆分类型 | 拆分对象 | 拆分逻辑 | 核心目的 |
| --- | --- | --- | --- |
| 水平分表 | 单张表的数据行 | 按行数据分布规则拆分到多张表(均匀分散) | 解决单表数据量过大问题 |
| 垂直分表 | 单张表的字段 | 按字段访问频率拆分到多张表 | 减少单行数据宽度，提升查询效率 |
| 水平分库 | 单个数据库的数据行 | 按行数据分布规则拆分到多个库(均匀分散) | 解决单库存储和并发压力 |
| 垂直分库 | 数据库的业务模块 | 按业务功能拆分到不同库 | 业务解耦， 资源隔离 |

但我们面试时， 一般指的分库分表，都是指 水平分表、水平分库因此后文所指的分库分表都是指水平方向的拆分

**其实分库分表分为：**

- 分库：
  - 当并发量很大时， 单台数据库实例的负载很高 （包括CPU、内存）
  - 当并发量很大时，数据库的连接数是有限的、单台数据库实例的连接数不足
  - 所以要分库， 即多个数据库实例， 共同承载高负载压力， 共同提供更多的可用数据库连接
- 分表：
  - 当单表数据量很大时， 即使没有高并发的情况，但是存储和查询的性能都达到瓶颈了
  - 所以要分表， 以此让单表的数据量降下来
- 分库且分表：
  - 当并发量很大 && 单表数据量很大时，就需要分库且分表"分库"和"分表"所解决的问题是不同的

### 分片键选择

分片键是指在分库分表的过程中， 结合 分片算法决定数据存储位置的字段

选择分片键的核心原则：分析业务场景和数据分布

1. 高频查询，业务场景中的多数查询 都依赖于该字段， 避免扫描所有分片
2. 数据均匀，分片键的值应当离散分布， 防止数据倾斜
目的：如果分片键字段的值 是相同的 多个行记录 可以存到同一个表/库中，提高查询性能

举个例子： 电商场景，针对于订单数据，应该用什么分片键：卖家ID、用户ID、订单ID需要分析业务场景和数据分布

1. 业务场景：
- 最高频的场景是 用户去查询自己的订单
- 其次是商家去查看自己售卖的订单

2. 数据分布：
- 天猫、苏宁易购等商家的 订单量非常多， 占整个数据集的比重很大， 而小商家订单量少具体分析：
- 如果选择卖家ID为分片键
  - 第一，天猫的订单（数据量很大）都会被分到同一张表或数据库， 造成数据倾斜
  - 第二，最高频的场景，用户查看自己的订单， 结果a订单在A表/库， b订单在B表/库，此时需要多表/库扫描才能得到用户的订单集合，性能比较低
- 如果选择订单ID为分片键
  - 虽然不会存在数据倾斜，但是仍然是没有考虑到用户查看自己订单这样一个最高频的场景，仍然需要多表/库扫描才能得到用户的订单集合，性能比较低
- 如果选择用户ID为分片键
  - 第一，不可能有一个用户买了很多很多商品， 以致于数据倾斜， 因此数据分布是均匀的
  - 第二，符合业务的最高频场景， 当用户查看自己的订单时， 由于同一个用户ID的订单都会被分到同一张表/一个库， 因此只需要去这一张表/库中查询，性能高

所以应该选择以用户ID为分片键

### 分片算法

分片键选择完毕，那么如何根据分片键把数据分到某张表上——分片算法

#### Hash 取模分片

思路：先对分片键求Hash值， 再对分片数量取模

例如对用户ID求出Hash值，若分片数量为8个库，每个库128张表则该Hash值对分库数量8取模，得到该数据要存到哪个库上

再该Hash值对分表数量128取模，得到该数据要存到哪个表上，以及要查询时也通过此定位到对应的表

#### 一致性 Hash 分片

问题引入： Hash取模分片的问题： 当分库分表的 库/表 的数量不足时， 需要二次扩容， 即增加

库/表的数量

此时Hash值要取模的数变动了，所以数据应该存入到哪个库/表都会变动，就涉及到数据迁移

数据库全部数据大量迁移，成本很高， 我们想要避免这种问题，就需要在一开始使用一致性Hash分片算法

一致性哈希：是一种用于分布式系统中数据分片和负载均衡的算法。它的目标是在节点的动态增加或删除时，尽可能地减少数据迁移和重新分布的成本。

具体实现

1. 实现一致性哈希算法首先需要构造一个哈希环，
2. 把他划分为固定数量的虚拟节点， 如2^32。那么哈希环上的虚拟节点编号就是 0-2^32-1
3. 把表作为节点映射这些虚拟节点上
- 即通过 hash(表编号) 对 2^32 取模 得到 表的虚拟节点位置

4. 存储数据时，对分片键也映射到哈希环上
- 即通过 hash(分片键) 对 2^32 取模 得到 表的虚拟节点位置

5. 此时哈希环上有两部分数据：表编号、数据，数据应该分配到哪个表上呢？
- 规则是：按照数据的位置， 沿着顺时针方向查找，找到的第一个分表节点就是数据应该存放的表

![一致性Hash分片](file:///D:/Java/data/八股文/09-场景设计与算法/6a90e6cdec39.png)

那么当要增加表时，例如加入表(node5)，此时不再需要全部数据大量的迁移而是只影响了一小部分数据：影响的是原本属于node4的一部分数据

![一致性Hash分片](file:///D:/Java/data/八股文/09-场景设计与算法/eac6c195e31e.png)

总结：一致性哈希算法将整个哈希空间视为一个环状结构，将节点和数据都映射到这个环上。每个节点通过计算一个哈希值，将节点映射到环上的一个位置。而数据也通过计算一个哈希值，将数据映射到环上的一个位置。

当有新的数据需要存储时， 首先计算数据的哈希值，然后顺时针或逆时针在环上找到最近的节点，将数据存储在这个节点上。当需要查找数据时， 同样计算数据的哈希值，然后顺时针或逆时针在环上找到最近的节点，从该节点获取数据。

## 非分片键查询

如果查询时，查询条件带有分片键字段，那么查询时直接定位到一张表/一个库，查询性能比较高但不可避免的，会有如下场景：查询条件中没有分片键，而是其他字段，此时叫做非分片键查询例如上述电商场景的订单数据， 如果我要根据订单号查询呢？这也是一个比较高频的业务场景

**方案选择：**

1. 方案一：扫描所有表/库，查询出数据， 再聚合，性能低
2. 方案二： 基因法，性能高

### 基因法

我们前面已经按照 用户ID(用户ID) 进行分片， 即同一个用户的订单会在同一个表/库中但此时要根据订单ID查询， 我们希望直接定位到 具体的某一个表/库

所以订单ID就有讲究了，生成订单ID时， 我们要对其做基因编辑

**在数学上，有这样一个规律：**

数A 对 数B 进行取余，且数B是2的n次幂的情况下， 最终结果是 数A的二进制形式的后n位

- 9 % 4 = 1（9的二进制：1001， 结果是 01）
- 10 % 4 = 2 （10的二进制：1010， 结果是 10）
- 15 % 8=7 (15的二进制1111， 结果是 111)由此激发

1. 我们的分库数量、分表数量都必须是 2的n次幂，假设我们有16个库，每个库64张表， 正常的哈希取模分片算法：hash(用户ID) % 16 定位库的位置， hash(用户ID) % 64 定位表的位置
2. 生成订单ID时，要对用户ID提取一个基因 % 64 也就是二进制的最后6位， 把这个最后6位二进制也作为订单ID的二进制最后6位， 这样就能保证订单ID的路由结果与用户ID的路由结果完全一致
3. 所以当用户根据订单ID查询时，也可以通过
- hash(订单ID) % 16 定位库的位置， hash(订单ID) % 64 定位表的位置
- 其本质是因为订单ID中蕴含了用户ID的基因

### 兜底策略

如果不带分片键查询、另外也不使用基因法，此时会有兜底的策略

大型互联网公司用的比较多的方案是使用分布式数据仓库来实现，也就是说会把数据同步到像

TiDB、PolarDB、AnalyticDB等这些数据库中， 或者同步到ES中，然后在这些数据库中做数据的聚合查询。

## 分库分表的常见问题

### 什么时候分库分表

主键索引树中的 非叶子节点只存储 主键ID索引和指针

- 如果主键ID为 bigint 类型 （8字节），指针大小为6个字节
- 而每个指针都对应下一层的某个子节点
- 所以一个非叶子节点可以存储 16KB / 14B = 1170 个 元素，该非叶子节点的下一层有1170个子节点

B+ 树实际记录数据的都是在叶子节点

假设一行数据大小是 1KB， 单个叶子结点能存储的数据是 页大小 / 一行数据大小 = 16KB / 1KB = 16 行

所以一个3层的B+树，会有 1170 * 1170 * 16 = 21902400 两千万的数据

如果超过了这个数量级，此时B+树会变成4层的， IO查询次数增加， 导致查询变慢，此时才需要分表

而分库， 是针对并发量太大：数据库连接不足、实例负载过高

### 如何预估分库表的数量

分库分表时的库的数量、表的数量如何预估，尽量避免二次扩容的情况

对于分表的数量

1. 关注存量数据
2. 关注年增长量
3. 关注数据保存年限
例如 某张表已有存量数据2000w，预计每年增长500w，数据需要保留10年所以10年内总共要存储的数据上限是 7000w

假设单表我们存储2000w的数据，那么7000w / 2000w = 3.5 => 4 张表

总结来说：可以理解为 数据保留期限内最大的总数据量 / 单表的数据量 = 分表数量

对于分库数量

1. 关注数据库连接数（即并发能力的要求）

### 数据倾斜

数据倾斜是指：分库分表后，有大量的数据都在同一个表或库，

影响：又会造成单表数据量过大， 单库承载更多的请求压力， 资源利用不均， 其他节点闲置主要的原因是因为分片键选择的不合理

### 分库分表后的全局分布式 ID

分库分表后， 需要引入全局分布式ID， 具体请看《全局分布式ID》文章

### 二次分库/表

如果分表后，业务发展迅速，库/表的数量不足， 还需要二次扩容

解决方案是 在一开始就使用一致性哈希分片算法， 否则就只能进行大量的数据迁移

问题：一个小猴子有100根香蕉， 它要走过50米才能到家，每次它最多搬50根香蕉， 它每走1米就要吃掉一根，请问它最多能把多少根香蕉搬到家里。

提示：他可以把香蕉放下往返的走，但是必须保证它每走一米都能有香蕉吃。例如可以走到n米时，放下一些香蕉， 拿着n根香蕉走回去重新搬50根。

思路：猴子搬箱子的过程其实分为两个阶段

- 第一阶段：来回搬， 当香蕉数目大于50根时，每走一米需要吃掉三根香蕉。
- 第二阶段：香蕉数 <= 50， 直接搬回去，每走一米吃掉1根。

假设把100根香蕉分为两箱，一箱50根

- 第一步， 把A箱搬一米， 吃一根
- 第二步，往回走一米， 吃一根
- 第三步， 把B箱搬一米， 吃一根

这样， 把所有香蕉搬走一米需要吃掉三根香蕉，那么走到第几米时， 香蕉数 <= 50 呢？走到16米的时候， 吃掉48根香蕉， 剩52根香蕉

- 选择一：可以直接搬起50根，距离34m走到终点， 最终剩余16根
- 选择二： 可以再来回搬一次， 到17米的时候，猴子还有49根香蕉，此时距离终点33m， 最终剩余16根

因此答案为 16根

## 高楼扔鸡蛋

问题: 只能使用 2 个鸡蛋，有100 层楼， 可以从任意一层楼向下扔鸡蛋，要找出恰好不会碎的那一层楼

比如在第10层扔鸡蛋， 鸡蛋摔碎了，但是在第9层扔鸡蛋， 鸡蛋没有摔碎

那么鸡蛋不会摔碎的临界点就是9层。如何用最少的尝试次数，找出鸡蛋不会摔碎的临界点？需要注意的是， 只能使用2个鸡蛋，在测试过程中， 如果鸡蛋碎了，就不能再使用了

注意：这道题如果要是一上来就说出正确答案，那说明你的智商不是超过160，就是你做过这题。所以建议你循序渐进的回答， 一上来就说最优解可能不会让面试官满意。

1. 暴力法
**最笨的测试方法：**

- 把其中一个鸡蛋，从第1层开始往下扔。如果在第1层没碎，换到第2层扔；如果在第2层没碎，换到第3层扔 ... 如果第59层没碎，换到第60层扔；如果第60层碎了，说明不会摔碎的临界点是第59层
- 即从第一层开始往上找
- 在最好情况下， 这个方法需要扔2次
- 在最坏情况下， 这个方法需要扔100次

2. 二分法
**采用类似于 二分査找 的方法：**

- 把鸡蛋从一半楼层 (50层) 往下扔
- 如果第一枚鸡蛋，在50层碎了， 第二枚鸡蛋，就从第1层开始扔， 一层一层增长， 一直扔到第49层
- 如果第一枚鸡蛋在50层没碎了，则继续使用二分法，在剩余楼层的一半 (75层) 往下扔
- 在比较好的情况下， 这个方法大概在6-8次
  - 50、75、87、93、96、98、99、100(碎) 8次
  - 50、75、87、93、96、98、99(碎) 7次
  - 50、75、87、93、96、98(碎)、97 7次
  - 50、75、87、93、96(碎)、94、95(碎) 7次
  - 50、75、87、93、96(碎)、94(碎) 6次
- 在最坏情况下， 这个方法需要尝试50次

3. 均匀法
**如何让最好情况和最坏情况的尝试次数，尽可能均衡且小呢?**

- 很简单，做一个平方根运算，100的平方根是10
- 因此， 我们尝试每10层扔一次：第1次从10层扔， 第2次从20层扔， 第3次从30层...一直扔到100层
- 比较好的情况是在第10层碎掉， 尝试次数为1+9=10次
- 最坏的情况是在第100层碎掉， 尝试次数为 10+9=19次从均匀法我们其实可以看出一点门路：

**它其实是涉及两个参数：**

- 第一(n)次尝试在哪一层扔？ 在这里是第10层
- 如果第一个鸡蛋未碎， 第二(n+1)次尝试与第一(n)次尝试的楼层会有一定的间隔， 这个间隔数如何定？ 在这里间隔数是10

**而两个鸡蛋的作用是什么呢？**

1. 第一个鸡蛋用于快速缩小范围（跳跃式探测）。
2. 第二个鸡蛋用于在第一个鸡蛋破碎后， 线性探测剩余区间。
4. 最优解法
**最优解法核心思路：**

**上述方法中最坏情况的次数都比较大，那么如何把最坏情况下的次数降下来？**

**假设最坏情况下需要x次尝试，为达到这个目的，两个参数应该怎么定？**

- 第一次尝试在哪一层扔？
- 若第一个鸡蛋未碎，下一次尝试的间隔是多少？

**答案是：**

- 第一次扔就要选择第x层， 为什么呢?
- 若第一个鸡蛋未碎，下一次尝试的间隔是x-1， 为什么呢？

先来思考为什么第一次扔就要选择第x层，有两种思考角度

**角度一：**

**从反证法的角度思考？如果不选第x层，会发生什么？**

**假设第一次在第x+1层扔：**

如果第一个鸡蛋碎了，那么第二个鸡蛋只能从第1层开始一层一层扔， 一直扔到第x层这样一来， 我们总共尝试了x+1次，和假设最坏情况下至需要尝试x次相悖。

由此可见， 第一次扔的楼层必须小于x+1层

**假设第一次在第x-1层扔 :**

从前面可知第一个鸡蛋用于快速缩小范围， 而第二个鸡蛋用于在第一个鸡蛋破碎后， 线性探测剩余区间。因此我们其实希望第一个鸡蛋它在未碎的情况下，每次跳跃的间隔尽可能大。所以我们更愿意选择第一次在x层扔

**角度二：**

我们假设第一次是在第y层扔的鸡蛋。

如果第一个鸡蛋碎了，那么第二个鸡蛋只能从第1层开始一层一层扔， 一直扔到第y-1层最坏情况下，恰好第y-1层是不碎的， 我们总共尝试了1+y-1 = y次

而我们一开始设定了最坏情况下的总尝试次数是x次 所以得出 x==y，所以第一次其实就是在第x层扔

上述讨论的只是第一次在哪一层扔的问题， 并不是就能够保证整个过程， 最坏情况是尝试x次确立了第一个参数， 第一次在x层扔

**那么现在考虑第二个参数：若第一个鸡蛋未碎，下一次尝试的间隔是多少？**

我们沿着刚刚的思路。第一次是在第x层扔的，若第一个鸡蛋未碎，假设下一次在第n层扔，如果碎了，此时就只剩下一个鸡蛋了● 而第二个鸡蛋要线性探测的区间是 [x+1,n]● 而第一个鸡蛋已经尝试了2次， 我们前面假设最坏情况下， 一共只能尝试x次● 也就是说第二个鸡蛋 只剩下 x-2 次的尝试机会，所以这个线性探测的区间的差值应该就是 x-2● 所以得出 n = x+1+x-2 = 2x-1 = x+(x-1) 也就是说第二次是在 x + (x-1) 层扔的● 即第一次和第二次扔的楼层间隔是 x-1但如果没碎，那么就要进行第三次扔第一个鸡蛋， 因为已知第二次扔鸡蛋是在 x+(x-1)层扔的所以假设第三次扔是在第m层扔如果碎了，此时就只剩下一个鸡蛋了● 而第二个鸡蛋要线性探测的区间是 [x+(x-1)+1,m]● 而第一个鸡蛋已经尝试了3次， 我们前面假设最坏情况下， 一共只能尝试x次● 也就是说第二个鸡蛋 只剩下 x-3 次的尝试机会，所以这个线性探测的区间的差值应该就是 x-3● 所以得出 m = [x+(x-1)+1]+x-3 = 3x-3 = x+(x-1)+(x-2)● 也就是说第三次是在 x+(x-1)+(x-2) 层扔的● 即第一次和第二次扔的楼层间隔是 x-1， 第二次扔和第三次扔的楼层间隔是 x-2以此类推，在第一个鸡蛋未碎的情况下，每一次扔第一个鸡蛋的间隔是递减的

所以现在已经论证了两个参数的答案， 我们再从正面想一想

- 让第一次尝试的楼层为x层
  - 若第一个鸡蛋碎了，则第二个鸡蛋从第1层开始线性探测， 最坏情况一共需要 (x-1)+1 = x次 注意+1是因为前面有一次尝试
  - 若第一个鸡蛋未碎，则下一次尝试的楼层为 x+(x__1) 层
    - 若第一个鸡蛋碎了，则第二个鸡蛋从 第x+1层开始线性探测， 最坏情况一共需要 [x+ (x__1)] - (x+1) + 2 = x次 <= 最初假设的x次 注意+2是因为前面经过了两次尝试
    - 若第一个鸡蛋未碎，则下一次尝试的楼层为 x+(x-1)+(x-2)

可以看到在第一个鸡蛋一直未碎的情况下， 第一次尝试是在x层， 第二次尝试是在 x+(x-1)层， 第三次尝试是在 x+(x-1)+(x-2)层， 第四层尝试是在x+(x-1)+(x-2)+(x-3)层

第一次尝试是在第x层， 间隔为 x

第一次尝试和第二次尝试的间隔是 x-1

第二次尝试和第三次尝试的间隔是 x-2

第三次尝试和第四次尝试的间隔是 x-3

......

以此类推。若第一个鸡蛋未碎，则下次尝试的间隔递减1，使得最坏情况下的总次数始终等于x次，

**直到间隔递减到1， 即第n次尝试，此时是第 x+(x-1)+(x-2)+(x-3)+...+1层这时候应该怎么考虑？**

第n次尝试意味着是最后一次尝试， 因为间隔已经递减到1了， 再递减就是0了所以此时第n次尝试的楼层，应该使得它能足够覆盖100层。

你想如果第100层都不会碎， 而最后一次尝试不是在第100层，那么这个算法就是有问题的所以得出如下公式： x+(x-1)+(x-2)+(x-3)+...+1 >= 100

转化为（1+x）* x/2 >= 100解方程得：x >=14

而我们一开始就是假设最坏情况下需要x次尝试， 因此x要取最小值， 即14

**意味着第一次尝试扔鸡蛋是在14层， 如果第一个鸡蛋一直未碎，会经过怎么样的序列？**

14， 27， 39， 50， 60， 69，77，84， 90， 95， 99，100举例子验证

- 假如鸡蛋不会碎的临界点是65层，那么第一个鸡蛋扔出的楼层是 14， 27， 39， 50， 60， 69。这时候啪的一声从69层扔下去的鸡蛋碎了。第二个鸡蛋继续，从61层开始， 61、62、 63、64、65、66、啪的一声从66层扔下去的鸡蛋碎了， 因此得到不会碎的临思点是65层，总尝试次数是6+6=12<=14
- 假设鸡蛋不会随的临界点是98层，那么第一个鸡蛋扔出的楼层是 14， 27， 39， 50， 60，

69，77，84， 90， 95， 99。这时候啪的一声从99层扔下去的鸡蛋碎了。第二个鸡蛋继续，从96层开始， 96、97、98， 因为98层依旧未碎，所以得到不会碎的临思点是98层，总尝试次数是11+3=14<=14

- 假设鸡蛋不会随的临界点是99层，那么第一个鸡蛋扔出的楼层是 14， 27， 39， 50， 60，

69，77，84， 90， 95， 99，100。这时候啪的一声从100层扔下去的鸡蛋碎了。因次得到不会碎的临思点是99层，总尝试次数是12<=14

所以最优解法的结果， 最坏情况下尝试次数是14次， 比前面所有的解法都更优

## 火枪手决斗

问题：彼此痛恨的甲、乙、丙三个枪手准备决斗。甲枪法最好， 十发八中； 乙枪法次之， 十发六

中；丙枪法最差， 十发四中。如果三人同时开枪， 并且每人每轮只发一枪；那么枪战后，谁活下来的机会大一些？

一般人认为甲的枪法好， 活下来的可能性大一些。但实际上枪法最糟糕的丙活下来的几率最大

**我们先来分析一下各个枪手的策略：**

只要乙没死， 甲一定会瞄准乙打， 因为乙对甲的威胁要比丙对甲的威胁更大， 这是甲的最佳策略

只要甲没死， 乙一定会瞄准甲打， 因为甲对乙的威胁要比丙对乙的威胁更大， 这是乙的最佳策略

只要甲没死，丙一定会瞄准甲打， 因为甲对丙的威胁要比乙对丙的威胁更大， 这是丙的最佳策略

我们根据分析来计算一下三个枪手在上述情况下的存活几率：

第一轮： 甲射乙， 乙射甲，丙射甲

- 甲的存活率为 24% (乙不中40% X 丙不中60%)
- 乙的存活率为 20% (甲不中20%)
- 丙的存活率为 100% (无人射丙，丙在第一轮中100%存活)

经过第一轮后会有哪些情况

情况1： 甲活乙死 (24%X80%=19.2%) 第二轮： 甲射丙，丙射甲——甲的活率为60%，丙的活率为20%

情况2： 乙活甲死 (20%X76%=15.2%) 第二轮： 乙射丙，丙射乙——乙的活率为60%，丙的活率为40%

情况3： 甲乙同活 (24%X20%=4.8%) 第二轮：重复第一轮

情况4： 甲乙同死 (76%X80%=60.8%) 枪战结束第二轮，各个枪手的存活率是

- 甲的存活率为 情况1(19.2%X60%) + 情况3(4.8%X24%) = 12.672%
- 乙的存活率为 情况2(15.2%X60%) + 情况3(4.8%X20%) = 10.08%
- 丙的存活率为 情况1(19.2%X20%) + 情况2(15.2%X40%) + 情况3(4.8%X100%) + 情况4(60.8% X100%) = 75.52%

通过对两轮枪战的详细概率计算， 我们发现枪法最差的丙存活的几率最大， 其次是甲， 最后是乙

甲和乙的存活率一直衰减， 而丙的存活率一直增长， 因此结论一致

## 水桶取 X 升水

问题：水资源无限， 3L和5L水桶各一个， 怎样取4L的水?

**方法一：**

第一步： 向5L桶倒满水

第二步：将5L桶的水倒入3L桶，此时5L桶中还剩下2L水

第三步：将3L桶中的水全部倒掉

第四步：将5L桶中的2L水倒入3L桶中

第五步： 向5L桶倒满水

第六步：将5L桶的水倒入3L桶中，此前3L桶中已经有2L水， 因此只可再倒入1L水操作结束， 5L桶中有4L水

**方法二：**

第一步： 向3L桶倒满水

第二步：将3L桶的3L水倒入5L桶

第三步： 向3L桶倒满水

第四步：将3L桶的水倒入5L桶，但是当5L桶满时，停止倒水，此时3L桶还余有1L的水

第五步：将5L桶里的水全部倒掉

第六步：将3L桶的1L水倒入5L桶

第七步： 向3L桶倒满水

第八步：将3L桶的3L水倒入5L桶操作结束， 5L桶中有4L水

## 喊数抢 30 的必胜策略

问题：游戏规则是 第一个人喊 “ 1 ”或 “ 2 ”， 第二个人要接着往下喊一个或两个数，然后再轮到第一个人。两人轮流报数，每人每次只能报1个或2个数， 最后谁报到 “三十 ”谁获胜。问喊数字的必胜策略

**解析：**

- 倒着看， 其实， 喊 27 时，就决定胜负了。假设 A 喊了 27， B 只能喊 28 或 29，下个回合，A 一定可以喊30。也就是说， 喊 27 者必胜
- 再倒着看， 其实， 喊 24 时，就决定胜负了。假设 A 喊了 24， B 只能喊 25 或 26，下个回合 A 一定可以喊 27， 由于喊 27 者必胜， 因此喊 24 者也必胜

以此类推， 需抢到21、18、15、12、9、6、3；

至此可以发现， 取得胜利的关键是控制 “3 ”及3的倍数，

无论AB， 只要谁报到3及3的倍数，且一直坚持报3的倍数，谁最后就会胜利；

- 如果A先报数， 只要B一直控制3及3的倍数， 最后一定是B赢
- 如果B先报数， 只要A一直控制3及3的倍数， 最后一定是A赢

**答案：**

1. 让对手先报数
2. 对手报一个数， 我就报两个数；对手报两个数， 我就报一个数，始终使得自己报的数是3的倍数

## 取最后一本书的必胜策略

**问题：100本书，两个人轮流拿，每次拿1~5本，你先拿， 如何保证你可以拿到最后一本？**

**解析：**

- 倒着想，最后我拿一次之后， 只要剩下6本， 无论对方怎么拿， 我都能拿到最后一本
- 所以现在要如何分配前面的94本呢？
- 我们以轮次来看， 一轮表示 你拿一次，我拿一次，我能控制的是什么呢？能控制的是， 一轮拿取的总书本数， 已知条件是每次拿1-5本， 因此我可以控制每轮总拿取的书本数是6（你拿1我拿5、你拿2我拿4，你拿3我拿3，你拿2我拿4，你拿1我拿5）
- 但是知道了每轮(你拿、我拿)能控制总数是6本有什么用处呢？我们现在的问题是如何分配前面的94本
- 针对前面要分配的94本， 因为我先拿，所以第一次我拿4本， 剩余90本
- 然后开始以轮次的视角拿书，你拿N本， 我拿6-N本，使得每轮拿取的总数是6
- 为什么这样做？ 因为 90÷6 = 15
- 也就是说， 我先拿了4本， 剩余90本，然后经过15轮 (你拿N本， 我拿6-N本)， 90本全部拿完
- 此时， 台面上还剩余6本，轮到你拿， 最后我赢

答案：我第一次先拿4本

## 取石子的必胜策略

问题：取两堆石子，游戏双方轮流从其中的任意一堆拿走一粒或几粒石子 (甚至把这堆石子一次拿光)，但每次不准一粒不拿，也不准同时从两堆中各拿几粒，谁拿到最后一粒或几粒石子，谁就获胜给出取胜策略

**解析：**

- 假设有两堆石子且数量不相同
  - 如果甲先拿， 甲的最佳选择是取走多的那堆石子中多出来的那几个，使得两堆石子数量相同
  - 这样，不管乙怎么取，下一次甲都可以在另一堆中取相同的个数
  - 比如有两堆石子， 第一堆有3个， 第二堆有5个， 这时候甲要拿走第二堆的2个，两堆石子都变成了3个， 这时乙无论怎么操作， 甲都可以 “ 学 ”， 学是指： 比如乙在第一堆拿走两

个， 甲就在第二堆拿走两个， 始终保证两堆石子的数量是一致的， 最后乙一定会拿掉某一堆的最后一粒石子， 而甲就可以拿走另外一堆的最后一粒石子 (获胜)， 即先拿者是必赢的。

- 假设有两堆石子且数量相同， 先拿者是必败的， 逻辑和上述一致

举例：假设有A堆有5粒， B堆有3粒

甲先拿，从A堆里拿2粒——A堆剩余3粒， B堆剩余3粒乙拿，从A堆里拿1粒——A堆剩余2粒， B堆剩余3粒

甲拿，从B堆里拿1粒——A堆剩余2粒， B堆剩余2粒乙拿，从B堆里拿1粒——A堆剩余2粒， B堆剩余1粒甲拿，从A堆里拿1粒——A堆剩余1粒， B堆剩余1粒乙拿，从A堆里拿1粒——A堆剩余0粒， B堆剩余1粒

甲拿，从B堆里拿1粒——A堆剩余0粒， B堆剩余0粒 甲胜

答案：输赢决定于两堆石子的数量关系，及谁先拿

- 若两堆数量不同， 先拿者获胜， 方法：先拿者 把两堆拿成等同的数量
- 若两堆数量相同，后拿者获胜， 方法：后拿者 模仿对方，从另外一堆拿同样的数量

## 乒乓球称重

问题：有8个乒乓球， 其中有一个稍微重， 只有一个天平， 最少需要几次才能找到重的乒乓球?

答案：两次

- 先把8个乒乓球分成3份， 第一份3个， 第二份3个， 第三份2个
- 先拿第一份的3个和第二份的3个称重 (第一次)， 之后分析有两种情况
  - 若第一份的3个和第二份的3个重量相等，那么， 把第三份的2个乒乓球各放到天平称可知哪个较重(第二次)， 结束。
  - 若第一份的3个和第二份的3个重量不等， 把重的那3个分成 1、1、1 个。任意把其中2个再称一次(第二次)，若两个一样重， 剩下的那个就是重的乒乓球，若一重一轻， 重的就是要找的球。
