## 单例模式

好处：对象复用，避免了频繁创建和销毁对象的开销，减少内存占用和 GC 压力

**实现方式：**

- 饿汉式：
  - 时机：在类加载时就初始化对象
  - 好处：①天然线程安全， 无需额外控制；②在需要调用时可直接返回， 无性能损耗
  - 坏处：①拖慢启动速度；②如果后续未使用则导致资源浪费
- 懒汉式：
  - 时机：在需要调用对象时，才初始化对象。
  - 好处：按需加载， 避免资源浪费
  - 坏处：需要额外的控制保证线程安全

### 饿汉式

1.饿汉式-静态成员变量的方式

```java
public class Singleton {
    //1、私有构造方法 :外界无法使用构造方法来创建本类的实例对象
    private Singleton(){}
    //2、静态成员变量的方式 : 创建本类对象
    private static Singleton instance = new Singleton();
    //3、提供一个获取单例的入口 ，注意是  public 和  static
    public static Singleton getInstance(){
        return instance;
    }
}
```

2.饿汉式-静态代码块的方式

```java
public class Singleton {
    //1、私有构造方法 :外界无法使用构造方法来创建本类的实例对象
    private Singleton(){}
    //2、声明一个成员变量
    private static Singleton instance;
    //3、在静态代码块中进行赋值
    static {
        instance = new Singleton();
    }
    //4、提供一个获取单例的入口 ，注意是  public 和  static
    public static Singleton getInstance(){
        return instance;
    }
}
```

3.饿汉式-枚举方式-极力推荐

```java
public enum Singleton {
INSTANCE;  // 外界调用时使用   Singleton.INSTANCE 即可
}

```

- 枚举是天然的单例
- 枚举的写法非常简单
- 枚举类型是所有单例实现中唯一一种不会被破坏的单例实现模式（反射也无法破坏）
- 如果不考虑内存空间的浪费的话， 首选枚举方式实现单例模式

**枚举为什么是天然的单例？**

枚举类型在编译后会被转换为一个继承自 java.lang.Enum 的 final 类。每个枚举常量是该类的静态实例，且在类加载时初始化

### 懒汉式

1.懒汉式-双重检查锁+volatile的方式

```java
public class Singleton {
    //1、私有构造方法 :外界无法使用构造方法来创建本类的实例对象
    private Singleton(){}
    //2、声明一个成员变量    注意  volatile是为了防止指令重排序导致对象未初始化就被使用
    private static volatile Singleton instance;
    //4、提供一个获取单例的入口 ，注意是  public 和  static
    public static Singleton getInstance(){
        // 第一次检查 : 如果instance不为null,不需要抢占锁 ,可以直接返回对象
        if(instance == null){
            // 如果为null, 说明首次访问需要创建实例对象，使用synchronized同步代码块
            // 锁对象 :当前类的字节码对象
            synchronized (Singleton.class){
                // 某个线程抢到锁之后 ,需要再次判断instance是否为null,保证单例安全
                if(instance == null){
                    instance = new Singleton();
                }
}
        }
        return instance;
    }
}
```

2.懒汉式-静态内部类方式-优秀

```java
public class Singleton {
    //1、私有构造方法
    private Singleton(){}
    //2、定义一个静态内部类
    private static class SingletonHolder{
        // 在内部类中声明并初始化外部类的对象
        // 加final关键字是  为了防止外界对其进行修改
        private static final Singleton INSTANCE = new Singleton();
    }
    //3、提供一个获取单例的入口 ，注意是  public 和  static
    public static Singleton getInstance(){
        return SingletonHolder.INSTANCE;
    }
}
```

实例由静态内部类创建

由于 JVM 在加载外部类的过程中， 是不会加载静态内部类的， 只有内部类的 属性/方法 被调用时才会初始化加载静态内部类。JVM 在加载和初始化类时， 可以确保同一时刻只有一个线程能执行类的初始化逻辑。所以本质上是通过JVM的类加载机制来保证单例的线程安全

静态内部类单例模式是一种优秀的单例模式， 是开源项目中比较常用的一种单例模式。在没有加任何锁的情况下，保证了多线程下的安全， 并且没有任何性能影响和空间的浪费。

## 策略模式

### 定义

策略模式 属于行为型设计模式， 它定义了一系列算法， 把它们单独封装起来， 并且使它们可以互相替换，使得算法可以独立于使用它的客户端而变化， 这些算法所完成的功能类型是一样的，对外接口也是一样的， 只是不同的策略使得环境角色表现出不同的行为。

### 主要构成

- 策略接口(Stragety)：策略接口定义了算法的抽象， 具体的策略类实现了这个接口
- 具体策略类(ConcreteStragety)：具体策略类实现了策略接口， 封装了具体的算法
- 环境类(Context)：用来操作策略的上下文环境类，环境类的构造函数包含了 Strategy 类， 通过多态传进来不同的具体策略 (ConcreteStrategyA或ConcreteStrategyB) 来调用不同策略的方法

### 实现步骤

1. 定义一个策略接口，声明算法的抽象方法
2. 创建具体的策略类， 实现策略接口， 封装具体的算法
3. 创建环境类， 包含对策略接口的引用， 以及一个用于设置具体策略对象的方法
4. 在客户端中创建环境类的对象， 并调用其方法来执行具体的算法

### 优缺点

优点：使用策略模式可以避免使用多重条件转移语句。多重转移语句将算法或行为的逻辑混合在一起，不易维护。使用策略模式可以降低复杂度，使得代码更容易维护

缺点：可能需要定义大量的策略类， 并且客户端必须知道所有的策略类， 并自行决定使用哪一个策略类， 策略模式只适用于客户端知道所有的算法或行为的情况。

### 具体应用

例如 ThreadPoolExecutor 的构造函数需要 传入 任务拒绝策略参数

RejectedExecutionHandler 是一个接口 （策略接口）， 有四个具体实现类（具体策略类）

使用哪一种实现类（具体策略类）， 是在客户端创建ThreadPoolExecutor (环境类) 时去指定的

## 观察者模式

### 观察者模式 · 定义

观察者模式 属于行为型设计模式， 它定义了一种一对多的依赖关系，让多个观察者对象同时监听某一个主题对象。这个主题对象在状态变化时，会通知所有的观察者对象，使观察者执行自己的逻辑。

### 观察者模式 · 主要构成

- Subject(主题)：主题是被观察的对象， 它包含了一组观察者对象， 并提供了添加、删除和通知观察者的方法。主题通常有一个状态， 当状态改变时， 通知所有观察者。
- Observer(观察者)：观察者是依赖于主题的对象， 当主题的状态发生改变时，观察者得到通知并进行相应的更新。观察者的具体实现类需要实现更新的方法。
- ConcreteSubject(具体主题)：具体主题是主题的具体实现类， 它维护了一个状态， 并在状态改变时通知观察者。
- ConcreteObserver(具体观察者)：具体观察者是观察者的具体实现类， 实现了更新的方法，以便在接收到通知时进行相应的处理

### 观察者模式 · 实现步骤

1. 定义主题接口(Subject)， 包括注册、移除和通知观察者的方法。
2. 定义观察者接口(Observer)， 包括自身的逻辑方法。
3. 创建具体主题类(Concrete Subject)， 维护一组观察者对象， 并在状态改变时通知观察者
4. 创建具体观察者类(Concrete Observer)， 实现观察者自身的逻辑方法。
5. 客户端代码中创建主题对象和观察者对象， 注册观察者到主题中，然后通过主题改变状态，观察者得到通知并进行自身逻辑。

### 观察者模式 · 优缺点

优点：使用该机制可以将相互耦合的代码解耦，从而方便功能的拓展和调整。

主逻辑只需要执行关键路径， 附带的(不断扩展的)操作可以由观察者监听事件发布后完成

缺点：调试复杂， 而且在Java中消息的通知一般是顺序执行，那么一个观察者卡顿，会影响整体的执行效率，在这种情况下， 一般会采用异步实现。

### 观察者模式 · 具体应用

观察者模式，也称为发布-订阅模式，Spring 中也有对应的机制： 事件发布-监听机制

存在着一对多的关系， 多个观察者监听 (订阅) 某个事件， 当这个事件被发布时， 多个观察者就能监听到， 进而去做观察者的逻辑

## 幻觉产生原因：语言模型的“填空”机制

- Transformer 语言模型本质上是一个“填空预测器”它是根据概率预测来选择下一个输出的词， 而不是在 “思考”正确答案

训练数据存在缺陷

- 训练数据本身可能包含 错误信息、不完整数据、偏见信息， 导致模型学到不真实的内容
- 训练数据可能过时，例如，GPT-4 的数据 截止到 2023 年初， 无法回答最新时事缺乏事实验证能力
- 语言模型在生成文本时， 并不会主动去 查证答案的真实性长文本记忆力有限
- 由于上下文窗口有限 (如GPT-4-turbo约128k tokens)， 当文本过长时，AI可能遗忘前面提到的信息

## 解决幻觉

解决幻觉的一些方案

1. RAG， 通过RAG的方式，让大模型在回答问题之前先检索真实数据， 再让模型进行回答
2. Fine-tuning， 即微调， 通过微调的方式， 给模型学习专业领域的知识，让他更好的回答
3. 限制AI的回答， 比如在提示词中告诉他如果你不知道， 直接就回答不知道
4. 通过标注和反馈不断优化模型。并把反馈可以给到模型让模型调整
5. 让同一个模型多次生成同一个内容的答案，然后选择一个最终版本
6. 在问题回答之后，让 AI自己检查自己的答案， 并标记不确定的部分
7. 联网， 在 AI生成答案之前， 先通过网络查询最新数据
8. 让 AI 先写下推理过程， 再得出最终结论， 而不是直接给出答案

## 定义与特点

定义：大模型通常指基于深度学习的大规模人工智能模型

例如像 GPT-4 大语言模型 （LLM， Large Language Model）

**特点：**

- 大模型的"大"主要体现在参数规模大。传统深度学习模型的参数规模通常在百万级到千万级，而大模型的参数量达到了 百亿级、千亿级， 甚至万亿级。以 GPT-4 为例，参数规模可能达万亿级

> 注：如我们通常说的7B模型，指的就是他的参数量达到了70亿

- 大模型的核心是基于 深度学习 和 神经网络， 通常采用 Transformer 架构
  - Transformer 通过 " 自注意力机制（Self-Attention） " 和 "多头注意力机制（Multi-

Head Attention） "实现高效的信息处理，相比于传统的 RNN（循环神经网络） 和 CNN （卷积神经网络）， 具有更强的并行计算能力和更长的上下文理解能力。(了解即可)

## 应用场景

不要简单的认为大模型就只是AI对话，他的应用方向非常广泛，

涵盖 自然语言处理(NLP)、计算机视觉(CV)、语音识别、科学计算、自动驾驶等 领域

| 应用领域 | 代表应用 | 典型模型 |
| --- | --- | --- |
| 1.NLP 语言 AI | ChatGPT、翻译、代码生成 | GPT-4、LLaMA 3、Claude |
| 2.计算机视觉(CV) | 图像生成、 目标检测 | Stable Diffusion、DALL·E、 ViT |
| 3.语音AI | 语音识别、语音克隆 | Whisper、VALL-E、 Tacotron |
| 4. 自动驾驶&机器人 | 无人车、机器人导航 | Tesla FSD、Gato、 Perceiver |
| 5.科学计算&医疗 | 药物研发、医学影像 | AlphaFold、Med-PaLM 2 |
| 6.推荐系统&广告 | 电商推荐、精准营销 | DeepFM、DINO、YouTube AI |

大模型擅长做生成内容、代码编写、文本处理、多模态任务

但它对高精度计算、事实准确性、实时数据获取存在局限性

### 擅长方向

1. 文本理解：能阅读、总结、分析文章， 如阅读理解、问答系统
2. 文本生成：能撰写高质量 文章、小说、新闻、代码、法律合同等
3. 机器翻译：可以翻译多种语言，质量接近专业翻译水平 (如 DeepL、Google Translate)
4. 信息提取：能从文档中提取关键信息， 如 法律、医学、财务报告分析
5. 代码生成： 自动编写 Python、JavaScript、C++代码，辅助开发者 (如 GitHub Copilot)
6. 代码调试：帮助找出代码中的 Bug、优化代码性能
7. 代码解释：能解释复杂代码的逻辑， 帮助学习和维护遗留代码
8. 广泛知识问答：大模型掌握 百科知识、历史、科技、医学、经济等 领域的信息
9. 图像识别 & 生成 (如 DALL·E、Stable Diffusion)：生成艺术作品、设计海报
10. 语音识别 & 语音合成 (如 Whisper、VALL-E)：实现 语音转文字(ASR)、AI语音播报
11. 视频生成 (如 Sora)：基于文本输入，生成高质量视频
12. 总结长文档：如会议纪要、论文总结
13. 从非结构化文本中提取信息：如将文章转换成 表格、JSON 数据

### 不擅长方向

1. 无法进行精确 数值计算， 如 大数运算、金融精算、密码学计算 (如3.9和3.11那个大?)
2. 可能犯逻辑错误，推理链条过长时， 可能得出错误结论
3. 容易 “编造”信息， 即使信息看起来可信，但可能并不存在
4. 可能给出 错误的医学、法律、科技等专业知识(如医学诊断、法律条文)
5. 对 长尾知识（冷门信息、最新论文、特定行业信息） 缺乏准确性
6. 训练好的大模型不会像人类一样主动学习新知识， 无法实时更新

## 关键问题

目前，大模型遇到的一些关键问题有以下几个

- 数据和隐私问题：大模型训练涉及大量数据， 可能存在隐私泄露风险
- 幻觉：模型可能生成虚假或不准确的信息
- 能耗高： 训练一次大模型可能消耗数千吨二氧化碳当量的能源
- 可控性和安全性：如何让模型可靠、透明地运作是一个重要挑战

## Agent 概念

### 1. 什么是 Agent / 怎么理解 Agent / 与大模型有什么区别

#### 1.1. 面试时简洁地回答

核心公式：Agent = LLM 大脑 + Tools 工具调用 + Memory 记忆 + Planning 规划调度

- LLM：大脑， 负责理解、推理、生成自然语言、结构化计划
- Tools：感官和四肢， 如搜索、代码执行、API 调用等
- Planning：拥有多步推理 & 自我纠错的能力
- Memory：短期上下文会话记忆 + 长期持久知识记忆，保证会话连贯和复用过往结果及个性化偏好

#### 1.2. 帮助个人理解（也应对面试官的追问）

1.2.1. Tools

大模型擅长回答问题，但是无法感知或者改变外界环境

（例如大模型本身无法读取你的项目代码， 也无法修改你的项目代码） 那么如何解决这个问题呢？给大模型接上工具即可

例如读写文件内容的工具、运行终端的工具， 工具就像是大模型的感官和四肢（有了工具， 大模型就可以读取你的项目代码， 直接修改你的项目代码）

把 一些工具和一个大模型 组装起来， 变成一个能感知和改变外界环境的智能程序

1.2.1.1. 工具如何定义

工具是给大模型外接的可被调用的能力接口， 提前定义好名称、功能描述、入参格式、出参结构。本质是把现实能力标准化、函数化， 让 LLM 看得懂、会调用， 比如联网搜索、代码执行、文件读写、数据库

查询、API 接口、计算器等都属于 Agent 工具。

1.2.1.2. 工具与模型如何交互

1. 模型决策： LLM 理解用户需求后， 判断是否需要调用工具、调用哪个工具、传什么参数；
2. 格式输出：模型按约定格式输出工具调用指令（函数名 + 参数）；
3. 框架调度：Agent 解析指令，触发对应工具执行；
4. 结果回传：工具把执行结果返回给 LLM；
5. 二次推理： LLM 结合工具返回结果， 再整理答案、继续规划下一步动作， 形成闭环。
小白误区：上文提到的工具是由开发工程师去开发实现的， 大模型只负责决策

1.2.2. Planning 规划调度

普通大模型仅能单点问答， 难以处理复杂模糊的多步骤任务。

而大模型 Agent 具备规划拆解、多步推理与自我纠错能力，

可将复杂大目标拆分为有序子任务， 并依据工具执行结果动态调整。

1.2.2.1. 推理技术

规划能力依托大模型推理的能力， 推理技术常见的有两种：

1. CoT 思维链：
- 核心： 让模型分步输出推理过程， 而非直接给答案， 大幅提升复杂问题推理效果。（在Prompt中加一句“给出思考过程/一步步推导思考”）
- 特点：纯内部思考、无工具调用、无分支、无回溯。

2. ToT 思维树：
- 核心：在推理节点衍生多条思考分支， 评估筛选最优路径推进， 适配复杂决策场景，但计算成本更高
- 特点：全局探索、可回溯、适合有多种解法的难题。

可以把CoT理解成「一条路走到底」，ToT理解成「走到岔路口先看看几条路， 选最好的那条再往前」

1.2.2.2. 规划模式

在有了这些推理技术的基础之上，Agent 的规划 在实际运作中有两种主流模式

**Agent 规划执行主要分两种模式：**

1. 先规划后执行 Plan-and-Execute 模式：提前生成完整任务步骤， 结构清晰、便于人工审核；但应变性差， 中间结果异常时原有计划易失效。
2. 边执行边规划 ReAct 模式：单步执行后实时决策下一步， 灵活性强； 易陷入局部最优， 偏离整体目标。
工程实践中常融合两种模式， 先制定整体粗略规划把控方向，执行阶段再动态微调。

有了 Cot、Tot 为什么还有 Plan-and-Execute 和 ReAct

Cot和Tot都是依靠大模型训练时学到的知识去进行推理， 无法感知外界、无法与外界交互， 是纯推理的范式

而 ReAct 和 Plan-and-Execute 在能力上有了补全， 有了手脚工具， 能感知外界与交互

1.2.3. Memory 记忆能力

大模型本身是无状态的， 大模型只有输入和输出

所以除非我们传递了上下文， 否则大模型完全不会记得上一次对话说了什么

Agent 引入记忆机制， 一般分为短期会话记忆和长期持久知识记忆

- 短期保存当前对话上下文，保证会话连贯交互
- 长期存储用户偏好、历史任务、业务知识，不用每次重复交代背景， 复用过往结果， 减少重复提问和重复执行， 让 Agent 越用越懂用户。

## Agent 范式

### 1. ReAct 范式

#### 1.1. 核心定义

```properties
ReAct = Reasoning（推理）+ Acting（行动）， 是 边执行边规划 的闭环范式，推理与行动交替循环， 直到完成任务。

```

#### 1.2. 核心三步循环（Reasoning → Acting → Observation）

1. 思考 Reasoning：LLM 基于上下文做推理， 明确下一步要做什么
2. 行动 Acting：根据上一步推理结果 调用工具，与外部环境交互
3. 观察 Observation：接收工具返回结果，作为新输入进入下一轮推理这三个步骤不断循环重复， 直到完成任务或触发终止条件

#### 1.3. 优缺点

- 优势：减少幻觉、复杂任务成功率高、推理轨迹清晰、可解释可调试。
- 局限：
  - 多轮循环导致延迟升高、效率低，效果依赖工具质量与稳定性
  - 缺少全局思维， 是局部贪心策略， 容易陷入死胡同、迷失问题
- 适合做动态实时性强的任务

### 2. Plan-and-Execute 范式

#### 2.1. 核心定义

Plan-and-Execute 先规划后执行： 先由 LLM 生成完整步骤清单， 再按顺序执行

#### 2.2. 优缺点

- 优势：结构清晰、便于人工审核、整体目标明确。
- 局限：灵活性差， 中间结果异常时计划易失败， 需要重新规划。
- 适合做步骤明确的长期复杂任务

### 3. Reflection 范式

#### 3.1. 核心定义

Reflection（反思） 是 Agent 自我纠错与迭代优化的能力的体现

在 Agent 完成 子任务或整个任务后， 进行反思：即再调用一次LLM来判断评估任务执行过程和结果是否符合预期

如果评估不通过，则重试或者执行其他策略。

Reflection 通常不单独使用， 而是作为增强层叠加在 ReAct 或 Plan-and-Execute 之上

#### 3.2. Reflexion 实现方案

评估不通过时， 生成反思结论， 存入记忆供后续复用， 主动规避重复错误。

#### 3.3. 优缺点

- 优势：显著降低错误率、提升鲁棒性、输出更可靠。
- 局限：增加 LLM 调用次数， 带来额外延迟与成本。
- 关系：通常作为增强模块，与 ReAct/Plan-and-Execute 结合使用

### 4. 如何抉择

这三种范式该如何选择

- 实时交互、动态不确定、需要随时查资料 / 调工具 → 选 ReAct
- 流程固定、长链路复杂任务、需要可控可审核 → 选 Plan-and-Execute
- 对结果正确率要求高、允许增加成本、需要自我纠错 → 叠加 Reflection

在实际应用中，也可以结合起来使用

- 用 Plan-and-Execute 做整体规划
- 每个步骤内部用 ReAct 来执行
- 关键步骤再加上 Reflection 做质量把关

## Workflow 与 Agent

### 1. 核心定义

Workflow 即工作流：全链路 if/else、固定分支、固定接口调用， 无大模型自主决策， 完全规则驱动完全由人来设计每个节点如何执行

### 2. Agentic Workflow 智能体工作流

通过前文的内容， 我们大概可以感受到 Agent 在很大程度上仍然是一个黑盒， 自由度很高， LLM 来做推理和决策

而在现实中的企业级的业务应用， 极少有这样的存在

因为纯 Agent 系统：可控性差、成本无法预估、出现问题难以排查处理而纯 Workflow 系统 无法理解多样化的情景或语境， 因此也有局限性。

因此 Agentic Workflow 诞生了， 成为了业界主流方案，Agentic Workflow 是上层的编排框架， 把

Agent、LLM、Tools 组织成一条确定性流程， 每个节点做什么、按什么顺序流转都是开发者设计写好的

- 骨架 = 固定 Workflow（可控、可运维、可排查）
- 血肉 = 局部 Agent 能力 （LLM 推理、动态决策）

例如我们最常见的业务系统， 智能客服， 它就不是一个 纯 Agent 的系统， 而是 Workflow比如其完整业务链路

- 用户提问→ 意图分类→ 分支路由（订单问题 / 售后问题 / 账号问题）→ 查业务数据（订单、会员、权限）→ 知识库检索→ 答案组装输出
- 以上 整体流转、分支、先后顺序、依赖关系，全是代码 / 配置写死的标准 Workflow。

但在其中也融入了Agent的能力

- 意图理解 & 问题归类 → 【Agent 能力】
  - 传统工作流：关键词匹配、正则、固定词库， 死板容易漏
  - Agent 能力： 由 LLM 自主语义推理， 理解口语化、歧义、多意图、啰嗦话术， 动态判断用户真实诉求
- 动态检索策略 & 文档筛选 → 【Agent 能力】
  - 流程规定：「必须检索知识库」是固定流程；但：
    - 检索哪些知识库？召回几十条文档， 哪些有用、哪些过滤？是否需要多轮补充检索、扩写关键词？这部分不靠硬编码 if/else， 靠 LLM 推理判断 → Agent 行动决策。
- 业务结果 + 规则文档 融合生成回答 → 【Agent 能力】
  - 流程固定：必须拼接订单数据 + 平台规则；但：
    - 怎么改写话术、口语化、规避敏感词；如何结合用户上下文做个性化回答； 哪些信息省略、哪些重点强调； 由 LLM 自主组织语言、逻辑整合 → 生成式 Agent 能力。
- 异常兜底、反问澄清 → 【Agent 能力】
  - 固定流程只会报错 / 固定话术；
  - Agent 可以自主判断： 问题信息不全， 主动反问用户补充信息， 动态调整后续流程走向。

### 3. 总结

整体流转、步骤顺序、核心分支、系统交互 是 Workflow，保证企业可控、好排查、成本可控、不跑偏。

在 Workflow 的节点中： 语义理解、意图推理、动态筛选、内容改写、模糊决策、灵活交互 是 Agent能力

Agentic Workflow = 固定流程框住边界 + 在边界内让 LLM 做智能决策不让 AI 乱跳流程

（解决纯 Agent 不可控）， 又让 AI 在关键环节有理解和灵活能力 （解决传统工作流太僵硬）

Single-Agent 即单个Agent 完成任务

而 Multi-Agent 是多个独立的Agent 通过协作完成复杂任务

每个 Agent 专注于特定角色或职能， 类比人类的团队分工协作

## Multi-Agent

### 1. 为什么需要 Multi-Agent

单个 Agent 在完成复杂任务时，任务的所有步骤都由同一个Agent完成， 可能会有几种情况

- 任务太长，信息量太大，上下文窗口容纳不下， 导致信息遗忘
- 不同的步骤的专业领域不同， 单个Agent不够专、精
- 任务中存在多个并行子任务，但单个Agent只能穿行执行因此单个Agent无法很好的完成任务

### 2. Multi-Agent 如何实现实现 Multi-Agent 主要有两种核心架构模式

- Orchestrator-Subagent 模式（主流）： 一个编排 Agent（Orchestrator） 负责全局规划和任务分发， 多个子 Agent（Subagent） 并行或串行执行具体子任务， 最终由 Orchestrator 汇总输出。
- Peer-to-Peer 模式：Agent 之间平等对话、相互审查， 适合需要辩论或验证的场景

2.1. Orchestrator-Subagent 模式

编排 Agent（Orchestrator） 会负责全局规划和任务调度分发

每个子Agent的职责清晰， 如果出现问题， 可通过Orchestrator的调度记录来排查问题， 可控可追踪

2.2. Peer-to-Peer 模式

没有总调度， 多个Agent是平等关系， 自行协商通信， 共同完成任务缺点：

- 无统一调度，Agent 间易出现分工混乱， 甚至出现任务重复或遗漏；
- 问题排查困难， 无全局调度记录， 出现错误时无法定位具体是哪个Agent的问题；
- 可控性差，Agent 间协商结果不可预知， 难以满足企业级应用的合规、可管控需求；
- 效率不稳定，若 Agent 间意见分歧， 需反复协商， 导致任务延迟。

## 了解 Function Calling 吗

### 1. 面试时简洁地回答

Function Calling（函数调用） 是大模型的“工具调用能力 ”

可以理解为 “让大模型像程序员一样调用预设函数 / 工具来解决问题”

**但它和普通编程里的函数调用又有核心区别：**

普通编程中的函数调用是开发者硬编码指定（比如写 calculate(1,2)，程序就一定会执行这个函数）；

而大模型的 Function Calling 是 大模型通过识别意图自主决策调用哪个函数， 比如

- 我们先告诉模型 “有哪些可用函数、每个函数的功能和参数”即 工具列表
  - （例如有一个函数功能是： 向MySQL中写入数据）
- 大模型会根据用户的问题，识别判断出 “是否需要调用函数、调用哪个函数、传什么参数”
- 但大模型不会直接调用这些函数， 而是生成一个函数调用指令
- 由后端程序解析函数指令， 再去执行调用这个函数， 拿到结果 框架封装好了会帮我们解析和调用
- 将函数调用结果传给大模型，大模型生成最终回答

2.2. Function Calling 的*端

- 依赖精准的函数定义与提示词设计：使用 Function Calling 我们需要提前写好工具函数，大模型的决策完全依赖提前告知的 “ 函数列表、功能描述、参数格式”，若定义模糊（如未明确参数必填项） 或提示词不清晰， 可能会导致模型 “误调用、漏调用 ”。
- 性能损耗与响应延迟：相比纯文本生成， Function Calling 多了 “模型决策→ 函数执行 ”，若函数执行耗时（如复杂查询、外部接口调用）， 会导致用户等待时间显著增加。
- 模型决策能力有限，复杂场景难覆盖：面对多意图、模糊需求时，模型可能判断失误：
  - 多函数联动：用户问 “查 XX 奶茶店是否营业，若营业帮我预约明天 3 点 ”，模型需先调⽤ “查询营业状态” 函数， 再根据结果决定是否调用 “预约” 函数， 复杂逻辑下易出错；
  - 隐含需求：用户说 “想喝 XX 奶茶， 明天有空”，模型可能无法识别出 “需要先查营业状态 + 预约” 的隐含逻辑， 需用户明确指令。
- 安全性风险：若未对函数调用权限、参数做校验， 可能出现风险：
  - 越权调用：模型误调用 “删除数据” 类高危函数；
  - 参数注入： 用户输入恶意参数（如 SQL 注入字符），模型直接传入函数执行， 导致安全漏洞。

## 了解 MCP 吗

### 了解 MCP 吗 · 1. 面试时简洁地回答

在没有 MCP 之前，使用 Function Calling 时， 我们需要定义工具， 并且把工具列表给到大模型， 这样大模型才知道可用工具列表、参数、用途等等，但这一套工具接入大模型的规范， 对于每个大模型都不一样

- 如果用的是 chatgpt， 那么需要按照 Openai 的规范接入工具， 写一套接入代码
- 如果用的是 claude， 那么得按照 Anthropic 的接入规范再写一套代码
- 如果用的是 gemini， 那么得按照 Google 的接入规范再写一套代码同一个工具， 要写多遍， 因为每个大模型的接入标准都不一样

所以才有人想能不能整一个统一的标准， 让所有的大模型都遵循这个标准这样， 工具的开发者只需要写一次代码， 就可以在所有的大模型上使用了

因此 MCP 诞生了

MCP（Model Context Protocol，模型上下文协议） 是一套 标准化的通信协议／接入规范

可以理解为一套统一的工具接入标准， 有了MCP之后， 工具的开发者只需要按照MCP的规范开发一次工具，

这个工具就可以被所有大模型使用， 这就是MCP的由来， 以及MCP解决的核心问题

### 了解 MCP 吗 · 2. 帮助个人理解（也应对面试官的追问）

MCP 实现 “统一标准” 的核心逻辑

MCP 靠 “三层组件 + 统一协议规范” 实现跨模型标准化， 核心是屏蔽不同大模型的接口差异具体逻辑如下：

1. 统一工具描述规范： MCP 定义了标准化的工具注册格式， 要求所有工具必须包含「工具名称、功能
描述、参数类型与约束、返回值格式、错误码」等固定字段。不管是知识库检索工具， 还是数据库查询工具， 都要按这套格式定义， 大模型和工具之间的 “沟通语言 ” 被统一。

2. 统一交互流程规范： MCP 规定了「请求 - 调用 - 响应」 的端到端标准化流程， 和具体大模型无关：
- MCP Client（嵌入大模型宿主） 接收用户请求后，按 MCP 格式打包 “ 问题 + 工具列表” 发给大模型；
- 大模型按 MCP 规范生成工具调用指令（格式全一致，不再区分 OpenAI/Claude）；
- MCP Client 解析指令， 调用 MCP Server 上的工具；
- 工具执行结果按 MCP 标准格式返回给大模型， 生成最终回答。

3. 三层组件解耦，屏蔽模型差异
- MCP Server： 负责按 MCP 规范封装工具， 对外提供标准化接口， 和底层大模型完全解耦；
- MCP Client：作为中间层， 一头对接 MCP Host（大模型应用）， 一头对接 MCP Server，核心作用是协议转换—— 把大模型的指令转成 MCP 标准格式， 也把工具结果转成大模型能识别的格式；
- MCP Host：运行大模型的应用 （如 ChatGPT 客户端、 自定义 AI 助手）， 只需内置 MCP Client， 就能无缝调用所有 MCP Server 上的工具，不用关心工具的具体实现和模型差异。

## Agent Skill 从使用到原理全面解析

### 1. Agent Skill 的本质是什么

- Agent Skill 是大模型可调用的说明文档
- 每个 Skill 定义了特定任务的执行规范
  - 例如会议总结需包含参会人员、议题、决定三项内容
  - 用户无需重复输入指令，模型通过查询 Skill 自动遵循规则
- Skill 超越传统提示词， 形成结构化能力封装
  - 不仅描述“做什么”， 还规定“怎么做”
  - 支持示例引导和条件判断逻辑
  - 实现行为一致性与输出标准化

### 2. 如何创建和使用 Agent Skill

- 创建 Skill 需在指定目录下建立文件夹与文件
  - 路径为用户目录下的 .cloud-skill
  - 文件夹名称即 Skill 名称， 必须与内部元数据一致
  - 核心文件为 skill.md， 包含元素和指令两部分
- 元数据（Metadata） 定义 Skill 基本信息
  - 包含 name 和 description 两个关键字段
  - name 必须与文件夹名完全相同
  - description 向模型说明该 Skill 的用途
- 指令（Instruction） 部分定义具体行为规范
  - 明确模型在执行任务时应遵守的格式与逻辑
  - 可加入输入输出示例帮助模型理解
  - 如规定会议总结必须按固定结构输出

### 3. Agent Skill 的基础工作流程

- 用户发起请求后系统启动三阶段处理机制
  - 第一阶段：Cloud Code 将所有 Skill 的元数据发送给模型
    - 模型仅看到各 Skill 的名称和描述， 相当于浏览轻量级目录
    - 判断当前请求是否匹配某个 Skill
  - 第二阶段：模型识别匹配 Skill 并请求调用
    - Cloud Code 接收到响应后加载对应 Skill 的完整内容
    - 读取 skill.md 中的全部指令
    - 将用户请求与完整指令一起发回给模型处理
  - 第三阶段：模型依据详细指令生成结果
    - 结果经由 Cloud Code 返回给用户
    - 整个过程实现自动化决策与执行
    - 用户获得符合预设规范的输出

### 4. 渐进式披露机制的核心设计

- 第一层：元数据层 —— 始终可见的目录索引
  - 所有 Skill 的 name 和 description 永久加载
  - 占用极小 token 开销， 便于快速路由
  - 模型据此判断请求归属哪个 Skill
- 第二层：指令层 —— 按需加载的行为规范
  - 仅当 Skill 被选中时才加载其完整 skill.md 内容
  - 避免无关指令污染上下文
  - 显著节省 token 使用量
- 第三层：资源层 —— 条件触发的深层依赖
  - 包含 reference （引用文件） 和 script （脚本）
  - 只有满足特定条件时才会加载或执行
  - 实现“按需中的按需”加载策略

### 5. 高级功能之 Reference：条件性知识注入

- Reference 用于引入外部参考文档
  - 如财务手册、法务条款等专业资料
  - 文件独立存放，不直接写入 skill.md
  - 仅在相关场景下被动动态加载
- 触发机制基于指令中的条件判断
  - 例如“ 当提及预算时读取集团财务手册”
  - Cloud Code 在解析指令后判断是否需要加载
  - 若无相关内容则文件不会进入上下文
- Reference 加载会消耗 token
  - 因为其内容会被送入模型上下文供推理使用
  - 适合存储静态知识类信息
  - 实现精准的知识调用， 避免资源浪费

### 6. 高级功能之 Script： 自动化代码执行

- Script 支持运行本地脚本完成实际操作
  - 如上传文件、同步数据、调用 API 等
  - 在 skill.md 中声明触发条件与执行方法
  - 例如“当需要上传时运行 upload.py”
- 脚本执行不占用模型上下文
  - Cloud Code 仅执行脚本并获取结果
  - 不读取代码内容， 几乎零 token 消耗
  - 即使万行代码也不会影响推理效率
- 安全性依赖于清晰的执行说明
  - 若未明确运行方法，模型可能尝试阅读代码
  - 导致意外加载脚本内容至上下文
  - 建议在指令中详尽描述调用方式

### 7. Reference 与 Script 的加载差异

- Reference 是 “读取型”资源
  - 内容被加载进上下文参与推理
  - 占用 token， 适用于知识增强
  - 如合规审查、政策比对等场景
- Script 是 “执行型”资源
  - 仅运行脚本并返回结果，不暴露代码
  - 几乎不消耗 token， 适合自动化操作
  - 如文件传输、状态更新等动作类任务
- 两者共同构成资源层的双轨机制
  - 实现知识与行动的能力分离
  - 提升系统效率与安全性
  - 构建更复杂的智能代理行为链

### 8. Agent Skill 与 MCP 的核心区别

- MCP 主要功能是连接外部数据源
  - 提供实时数据查询能力， 如订单状态、销售记录
  - 相当于为模型接入数据库接口
  - 解决“获取什么数据” 的问题
- Agent Skill 专注于数据处理规范
  - 教会模型如何使用数据完成特定任务
  - 如规定报告格式、审批流程等
  - 解决“怎么处理数据” 的问题
- 官方定位： MCP 连接数据，Skill 教会使用数据
  - 二者互补而非替代关系
  - MCP 提供原材料，Skill 定义加工方式
  - 共同构建完整的 AI 工作流

### 9. 如何选择 Agent Skill 与 MCP

- 轻量级任务优先使用 Agent Skill
  - 如格式化输出、简单脚本执行、本地自动化
  - 开发成本低， 部署简便
  - 适合个人开发者与小型项目
- 数据密集型或高安全要求场景选用 MCP
  - 如企业级 API 对接、敏感数据访问控制
  - 更强的安全隔离与权限管理
  - 适合团队协作与生产环境
- 多数情况下建议结合使用
  - MCP 获取数据 → Agent Skill 处理数据 → 输出结果
  - 发挥各自优势， 构建完整闭环
  - 实现真正意义上的智能代理

### 10. Agent Skill 的演进与行业影响

- 最初为提升 Cloud 特定任务表现而设计
  - 官方初期定位较为克制
  - 仅作为内部优化工具
  - 未预料到其通用潜力
- 行业迅速采纳并扩展支持
  - VS Code、Codex、Cursor 等工具相继集成
  - 形成跨平台复用趋势
  - 推动标准化进程
- 2025年12月正式发布为开放标准
  - 支持跨产品、跨平台复用
  - 成为 AI Agent 领域通用设计模式
  - 标志着能力封装范式的成熟
- 展望未来： 向模块化智能生态发展
  - Skill 商店、共享市场可能出现
  - 开发者可发布、订阅各类 Skill
  - 加速 AI 应用落地与普及

## RAG

### 1. RAG 是什么

```properties
RAG = Retrieval-Augmented Generation、中文： 检索增强生成

```

**一句话理解：**

让大模型在回答前， 先去查一份 “外部知识库”， 查到的内容 会整合到 Prompt 提示词中再输入给大模型

**详细解释：**

RAG 是先将知识作为向量存储到向量数据库

再将用户输入的提示词 去和 向量数据库中的 知识向量进行相似度匹配，检索出相关的片段最后将检索出来的内容 + 用户提示词 一起发送给大模型， 生成最终回答

### 2. 为什么会有 RAG？

RAG的目的是通过从外部知识库检索相关信息来辅助大语言模型生成更准确、更丰富的内容

**大模型本身有 3 个问题：**

- 知识过时（只学到训练截止日期之前的内容）
- 存在幻觉（会胡编乱造）
- 不知道内部私有数据（你的文档、业务规则等）

**RAG 就是用来解决这三件事的：**

- 答案更准， 通过检索外部知识库， 融入最新、最准确信息， 提高回答的可靠性。
- 减少模型幻觉， 基于真实检索结果生成内容， 避免输出无根据或错误信息。
- 能使用内部的数据

RAG 中文名叫 检索增强生成、其中包含了三个词， 分别是检索、增强、生成，下面分别解释一下

#### 3.1. 检索

检索：指的是从向量知识库中检索与问题相关的信息。为后续的生成过程提供有用的上下文信息和知识支撑。

**3.1.1. 向量知识库？**

**数据准备与知识库构建：**

1. 收集数据：首先， 需要收集与问答系统相关的各种数据， 这些数据可以来自文档、网页、数据库等多种来源， 比如：公司内部文档（PDF、Word、Markdown）、FAQ列表、产品手册等。
2. 数据清洗：对收集到的数据进行清洗， 去除噪声、重复项和无关信息， 确保数据的质量和准确性。
3. 知识库构建：将清洗后的数据构建成知识库。通常将文档按照一定策略切块， 如固定大小， 语义分块等，使用Embedding 模型 将这些片段（chunks） 转换成向量， 并将这些向量存储在向量数据库（如FAISS、Milvus等） 中。
**3.1.2. 从知识库检索？**

**检索包括：**

1. 问题向量化： 当用户输入查询问题时，使用 Embedding 模型 将问题转换成问题向量
2. 相似度检索：在向量数据库中检索与 问题向量 最相似的知识库片段（chunks）。这通常通过计算向量之间的相似度（如余弦相似度） 来实现。
3. 结果排序：根据相似度得分对检索到的结果进行排序， 选择最相关的片段作为后续生成的输入。

#### 3.2. 增强

增强： RAG 中增强是将从外挂知识库中检索到的信息用作 大模型的上下文输入(即Prompt提示词)， 以增强模型对特定问题的理解和回答能力。这一步的目的是将外部知识融入生成过程中，使生成的文本内容更加丰富、准确和符合用户需求。通过增强步骤， LLM模型能够充分利用外部知识库中的信息。

增强 可以理解为 将检索到的相关片段与原始问题合并， 形成更丰富的上下文信息

#### 3.3. 生成

生成：即通过前文中提到的提示词进行生成回答

#### 3.4. 小结

**RAG 的 “检索、增强、生成”，从哪里检索？增强了什么？谁生成了答案？**

- 是从外部知识库中检索到的相关的知识
- 增强了 提示词（prompt）， 将检索到的相关片段与原始问题合并， 形成更丰富的上下文信息
- 大模型 拿着增强后的 Prompt 生成了问题答案。

**RAG 的优势：**

- 提升回答质量：通过检索外部知识库， 融入最新、最准确信息， 提高回答的可靠性。
- 减少模型幻觉：基于真实检索结果生成内容， 避免输出无根据或错误信息。

**RAG 的缺点：**

- 依赖知识库质量及系统设计：系统回答的效果与外部知识库质量和整体系统设计有较大关系，若设计不合理可能导致答案偏差。
- 系统复杂度增加， 增加计算开销：大规模的知识库检索会让整体系统更加复杂， 并且会延长系统性响应时间， 对耗时敏感的业务可能产生性能瓶颈。研究表明，检索环节占RAG总耗时的60%以上。

### 4. 召回率

在 RAG 检索系统中， 召回率指的是在所有真正相关的文档中， 有多少被成功地检索了出来。计算方式：召回率 = 检索到的相关内容数量 ÷ 所有相关内容的总数量

举个例子，假设你有一个技术文档知识库， 某个用户提问：“如何在 Kubernetes 上部署？ 力

假设知识库中有 6 条与这个问题高度相关的内容，但系统只返回了其中 3 条。那么， 召回率就是 3 ÷ 6 = 50%。

在 RAG 系统中， 召回率尤为关键， 因为大模型能不能“答对”， 很大程度取决于有没有拿到相关内容；召回率越高， 大模型 在生成答案时能参考的有效信息就越多， 回答的质量和准确性也就越有保障。

RAG 工程落地计算流程

1. 构造测试数据集（Question + 人工标注相关 chunk 列表）
2. 每条问题走检索流程， 得到召回 chunk 列表
3. 逐题统计召回率
4. 计算平均召回率
但想要统计出有意义的召回率

测试数据集一般项目至少需要200-500条测试用例专业项目至少需要上千条测试用例

因此统计召回率并没有那么容易， 需要大量的测试用例数据
