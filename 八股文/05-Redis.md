## 数据结构

### Dict 哈希表

![Dict 哈希表](file:///D:/Java/data/八股文/05-Redis/65808cf9e60c.png)

Dict 哈希表 底层存在 两条哈希表（数组+链表实现哈希表）

一条哈希表存储的是当前数据， 另外一条哈希表一般是空，在哈希表扩容 Rehash 时会使用到

Dict 哈希表会扩容或者收缩，此时就需要重新计算key存储的位置，也称为rehash在rehash过程中， 如果用户想要请求数据，

- 新增操作，则直接写入 ht[1] 即新哈希表
- 查询、修改、删除，则会在 ht[1] 新哈希表 和 ht[0] 旧哈希表 上依次查找并执行

### ZipList 压缩列表

一种连续内存空间的双端链表， 因存储格式而节省空间，但由于连续内存

如果元素太多， 内存不容易分配，效率低，所以当元素过多时，都会转为另外一种数据结构且 ZipList 压缩列表存在连锁更新的问题

### QuickList 快速列表

一种双向链表，每个节点是一个压缩列表

### SkipList 跳表

无论是 ZipList 还是 QuickList，在访问时，本质都是一个个遍历的访问，他们在查找首尾结点时性能高。但是要做范围查找时， 只能一个一个遍历直到范围的起始点。

SkipList 跳表 是一种多层链表

- 元素按 score 分数进行升序排序存储
- 一个节点内可能包含多个指针，每个指针的跨度不同。链表遍历慢的原因就是因为指针的跨度为1
- 当做范围查找时，利用高层级的指针，快速跳过大量无关节点，快速定位到范围的起始点
- 跳表通过牺牲少量内存空间（存储多层指针），换取了更高效的范围查找性能

![SkipList 跳表](file:///D:/Java/data/八股文/05-Redis/9f898043a3af.png)

### listpack

和 ZipList 压缩列表几乎一样，但解决了连锁更新的问题，所以是新设计出来取代 ZipList 压缩列表的

## 分布式锁

### 基于 Redis 的 SetNx 命令

SetNX 如果key已存在，则结果返回0。如果key不存在，则结果返回1。

**实现：**

1. 加锁：set unique_key 机器码+线程ID NX EX TTL （unique_key 一般是业务唯一标识）
- 加锁成功：执行命令结果返回1
- 加锁失败：执行命令结果返回0
- 能实现互斥且设置了TTL， 可以通过TTL到期删除key， 自动释放锁， 防止死锁情况

2. 释放锁：执行 del 删除 key 的命令。
- 先 Get key 拿到 value 判断当前锁是否是本机器本线程加上的
- 若是， 可以正常删除锁

ii. 若不是，则不需要处理

> 注：判断锁是否是本线程加上的， 是为了防止锁误删的情况

举例： 线程1业务阻塞，锁的TTL到期， Redis key 自动删除，则锁释放，然后线程2获取到

了锁。在线程2正常执行时， 线程1恢复运行， 如果线程1不判断当前锁是否是自己加上的， 直接把

锁删除了，就出现问题——线程1误删了线程2的锁，会有其他线程获取到锁， 导致有多个线程并行

执行。

- 用Lua脚本来完成：判断是否是当前线程的锁 + 删除key释放锁 两个操作，保证原子性

判断锁归属 和 删除key， 这两个操作应是一个原子性操作。

> 注：举例： 当线程1判断完是自己的锁，要去删除，此时因为某个原因（例如FullGC） 导致线程1阻 塞， Redis 锁的TTL 到期，锁被迫释放，然后线程2获得锁，此时线程1去删除锁 (前面已经判

断过了)，此时出现了误删的情况，会有其他线程获取到锁， 导致线程并行。

**问题：**

1. 由于业务执行耗时太长，TTL到期，锁被迫释放，存在多个线程并行的情况
2. SetNX 线程不可重入
3. TTL不好设置，业务到底要执行多长时间， 我们不太确定。

### 基于 Redisson

Redisson 是市面上成熟的分布式锁组件，相对于用 SetNx 命令实现的分布式锁更加强大和完善。

#### Redisson 可重入锁原理

即一个线程可以多次获取锁。利用Hash结构，记录获取锁的线程和获取锁的次数

1. 获取锁的逻辑：
- 判断 key（unique_value一般是业务唯一标识） 是否存在， 即判断是否有线程持有锁
- 如果key不存在，代表没有线程持有锁，则获取锁， 即设置一个Hash结构的 （field， value），field是机器码+线程ID，value是 次数 1。
- 如果key存在，代表有线程持有锁，此时判断持有锁的线程是否是当前线程， 如果是当前线程，则重入次数+1。

2. 释放锁的逻辑：
- 重入次数-1， 如果重入次数为0，删除key，释放锁。

#### 超时续约机制(看门狗机制)

为了解决TTL不好设置， 如果分布式锁的key设置了TTL， 又因为业务阻塞原因， 导致当前线程的业务未完成，TTL到期了， 导致被迫释放锁，此时就会有其他线程抢占锁， 导致有线程并行执行，违背了加分布式锁的初心。

当 Redisson 获取锁没有指定锁的TTL时， 默认会使用超时续约机制(看门狗WatchDog)机制。

**续期规则：**

- 默认 TTL 为 30 秒，后台线程（定时任务） 每隔 10 秒 检查业务是否完成。
- 若未完成 → 通过 Lua 脚本重置锁 TTL（续期至 30 秒），保证锁不被释放， 等到业务执行完。

#### Redisson 分布式锁的数据未同步导致线程安全主从问题：

- 主节点宕机时，若从节点未同步 锁 数据 → 新主节点可能允许其他线程重复加锁 → 锁失效。解决方案：
- 此时需要部署多个 Redis 主节点， 多主多从架构， 向多个主节点都去获取锁
- MultiLock 联锁方案：要求 所有主节点加锁成功， 否则立即失败并释放已获取的锁
- RedLock 红锁方案：要求 半数主节点以上（如 3/5） 加锁成功， 否则立即失败并释放已获取的锁。

## 持久化

在 Redis 的默认配置文件（redis.conf） 中， RDB 是 默认开启 的， 而 AOF（Append- Only File） 需要手动配置开启。

### RDB

#### 定义

RDB: Redis Database Backup File (Redis数据备份文件)，也被叫做Redis数据快照。

把内存中的所有数据都记录到磁盘文件中， 当Redis实例故障重启后，读取磁盘快照文件，恢复数据。

Redis有触发RDB的机制，可以在redis.conf 配置文件中找到

- save 900 1 # 900秒内， 如果至少有1个key被修改，则执行 bgsave 命令
- save 300 10 # 300秒内， 如果至少有10个key被修改，则执行 bgsave 命令
- save 60 10000 # 60秒内， 如果至少有10000个key被修改，则执行 bgsave 命令除此之外，可以手动执行命令，触发RDB
- save 命令： 由Redis主进程来执行RDB，会阻塞所有命令
- bgsave命令： 开启子进程执行RDB， 避免主进程受到影响

#### RDB 异步持久化的底层原理

RDB异步持久化 即bgSave 就是开启一个子进程， 由子进程读取内存数据，并写入RDB文件。

bgSave 对主进程几乎是0阻塞的，但是有一个过程是阻塞主进程的，那就是 bgSave 刚开始时， fork 主进程得到子进程 (主要是把页表复制给子进程)， 子进程共享主进程的内存数据， 这个 fork的过程是阻塞的， Redis在 fork 中只能做这一件事。不能去接收用户请求。

子进程在执行 bgSave 时读取共享内存的数据， 主进程如果在写内存数据， 可能会造成冲突。因此为了避免这个问题。底层会使用一种 copy-on-write的技术：

- 内存数据会被标记为Read-Only是只读的
- 当主进程执行写操作时，则会拷贝一份数据，在拷贝的数据上执行写操作

#### 优缺点

优点：宕机后恢复速度快、文件体积小

**缺点：**

- 数据安全性有问题， 因为RDB执行间隔时间长，两次RDB之间写入的数据有丢失风险。但是

RDB的间隔时间又不能设置的过短， 因为RDB的过程是比较耗时的， 如果间隔时间过短，根本忙不过来。

- fork子进程（复制页表）、写出RDB文件都比较耗时。

### AOF

#### AOF · 定义

AOF全称为Append Only File (追加文件)。Redis处理的每一个写命令都会记录在AOF文件。所以可以把Aof文件看做命令日志文件。

AOF执行的频率，写日志文件的频率。默认是每秒钟做一次AOF。

- always： 同步刷盘， 写日志文件的操作是由主进程在写入内存数据后完成，性能影响大
- everysec：每秒刷盘， 写内存后先把命令放入Aof缓冲区，然后每隔一秒将缓冲区数据写入AOF文件
- no：操作系统控制， 写内存后把命令放Aof缓冲区， 由操作系统决定何时将缓冲区内容写入AOF文件

#### AOF 文件重写

因为是记录命令，AOF文件会比RBD文件大得多， 而且AOF会记录对同一个key的多次写操作，但只有最后一次写操作才有意义。通过执行bgrewriteaof命令， 可以让AOF文件执行重写功能，用最少的命令达到相同的效果，但这个过程会占用大量的资源。

可以配置触发 BgReWriteAof 的阈值。

1. 文件增长百分比：AOF文件比上次文件 增长超过多少百分比则触发重写AOF文件
2. 文件体积最小多大以上才触发重写AOF文件

#### AOF · 优缺点

优点：数据安全性更高，例如everysec策略， 只会丢失1秒以内的数据

**缺点：**

- 宕机后恢复速度慢， 因为AOF文件记录的是命令， 需要依次执行
- 文件体积大， 需要进行AOF文件重写，此时会占用大量资源

### 混合持久化

AOF 和 RDB 各自有优缺点， 为了同时拥有上述两种持久化的优点Redis 4.0 推出了 RDB-AOF 混合持久化， 以AOF持久化为基础

开启混合持久化后， 当 AOF 文件重写时

1. 将当前内存数据以 RDB 格式 写入新 AOF 文件的开头
2. 后续增量数据以 AOF 格式 追加到文件末尾
文件结构：[RDB 数据块][AOF 命令流]

混合持久化结合了 RDB 和 AOF 持久化的优点， 开头为 RDB 的格式，使得 Redis 可以更快的启动，

同时结合 AOF 的优点， 又减低了大量数据丢失的风险，提高了数据安全性。

但AOF文件格式变化导致混合持久化是不能向下兼容的

## 内存淘汰策略

### 策略

一类是只针对有TTL的key进行淘汰：lru、lfu、random、ttl

- volatile-lru：从设置了过期时间的 key 中， 淘汰 最久未使用 的 Key（基于最后一次访问时间）
- volatile-lfu：从设置了过期时间的 key 中， 淘汰 访问频率最低 的 Key（基于访问次数统计）
- volatile-random：从设置了过期时间的 key 中， 随机选择一个 key 删除除
- volatile-ttl：从设置了过期时间的 key 中， 选择剩余时间最短的 key 删除一类是针对所有Key进行淘汰： lru、lfu、random
- allkeys-lru：从所有 key 中， 淘汰 最久未使用 的 Key（基于最后一次访问时间）
- allkeys-lfu：从所有 key 中， 淘汰 访问频率最低 的 Key（基于访问次数统计）
- allkeys-random：从所有 key 中， 随机选择一个 key 删除还有一种 noeviction
- noeviction：不会淘汰任何键值对， 而是直接返回错误信息共8种内存淘汰策略

### 策略选择建议

- 缓存场景：理论上所有数据都可以淘汰，所以优先使用 allkeys-l ru 或 -allkeys lfu， 避免内存写满导致服务不可用。
- 存在数据长期保存场景：部分未设置过期时间的数据是要长期保存的， 为了保留关键数据，所以使用 volatile-l ru 或 volatile-lfu。
- 严格数据保护：使用 noeviction，但需确保有监控和扩容机制。

### 淘汰流程

1. 客户端执行写入命令触发内存检查
2. Redis 检查当前内存使用是否已超出 maxmemory(配置文件设置的值)
3. 根据配置的策略选择待淘汰键
4. 删除键并触发相关事件（如 evicted 通知）

## 缓存击穿/穿透/雪崩

### 缓存击穿

通常发生在高并发场景下，某个热点数据在缓存中过期（失效）的瞬间，大量请求到达数据库， 导致数据库瞬时压力过大甚至崩溃。

**解决方案：**

1. 互斥锁
- 思路：只允许一个线程去查询数据库并重建缓存， 其他线程阻塞等待， 这个方案可以避免大量请求都想重建缓存， 给数据库带来压力
- 具体实现：
- 当一个线程从 Redis 获取为空时， 先加分布式锁，加锁成功，然后从数据库加载， 写回 Redis 缓存， 再释放锁。
- 另外一个线程从 Redis 获取也为空时，想要获取锁，此时获取锁失败， 先阻塞，然后等到锁释放， 再进行 double check 此时会成功获取到 Redis 的数据

2. 永不过期+逻辑过期
- 思路：缓存key不设置TTL， 实际上在Value中多存储一个属性：过期时间
- 具体实现：
- 缓存数据时附加过期时间字段（如 expireTime） - 请求命中缓存后检查过期时间字段是否过期。

1. 如果没过期， 直接返回
2. 如果过期了则开启一个异步线程去获取互斥锁重建缓存，本线程则先返回旧数据。

### 缓存穿透

缓存穿透关键在一个透字， 透过去了， 即数据在 Redis 缓存和数据库中都不存在这样缓存永远不会生效，请求都会打到数据库。

**解决方案：**

- 缓存空值(TTL)
- 布隆过滤器
  - 即在插入数据时， 通过n个哈希函数依次对Key进行计算，得到数据Key的特征
  - Key的特征就是一长串二进制串上的那些1就是特征
  - 通过布隆过滤器判断数据是否存在时， 再用 n个哈希函数对Key进行计算，
  - 分别判断二进制串上位置的01是否是1，若都是1则认为数据可能存在， 否则一定不存在

### 缓存雪崩

大量key同时过期或缓存服务宕机，大量请求到达数据库， 导致数据库瞬时压力过大甚至崩溃解决方案：

- 均匀设置过期时间，例如加随机数
- Redis集群提高服务可用性

定义：热Key是指在短时间内被高频访问的Key

**影响：**

1. 导致Redis实例的负载激增， 可能引发性能瓶颈或服务不可用。
2. 甚至在Key过期时， 可能导致缓存击穿。
**解决方案：**

1. 本地缓存：例如Java的Caffeine地本地缓存，减少Redis的压力， 注意设置过期时间
2. Key分片，将热Key拆分成多个子Key，分散到不同的Redis实例上
3. 读写分离(含主从架构)，读请求分流到多个从节点
注意监控（工具发现） 和提前预防（经验）

**为什么需要多节点架构？**

1. 单节点 Redis 内存有上限， 无法支持数据量大的业务场景， 内存大小成为瓶颈
2. 单节点 Redis 存在宕机风险， 可用性低
3. 单节点 Redis 的带宽成为瓶颈，大量客户端与 Redis 通信
4. 客户端和 Redis 之间的连接数和请求处理可能带来的性能问题。尤其是对于高并发的客户端请求， Redis 单节点可能会受到过多连接和请求的压力
**为什么分主从？ 为什么不是直接使用Redis集群？**

**为什么不把每个Redis节点设计为相同的节点？即可能在每个节点上读， 可能在每个节点上写**

背景： 主从架构， 一般随之而来的是读写分离， 而Redis一般应用场景下，读操作明显多余写操作。

1. 性能优化
- 通过读写分离， 主节点可以专注于处理写请求，从节点则可以专注于读请求， 反之如果一个节点需要执行读和写， 由于写操作（可能引发持久化导致阻塞） 可能会影响读的效率。
- 应对高并发读，且读明显多余写的场景：让更多的节点（即多个从节点） 去承担提供读的职

责， 而少的节点（主节点） 承担提供写的职责。

2. 数据一致性和数据同步
- 主从架构， 写操作只在主节点上进行， 主节点同步数据给从节点即可。
- 如果所有节点是相同的且都允许读写操作，那么需要保证多个节点之间数据一致， 问题的复杂程度增加。

主从架构的问题

1. 读写分离带来的问题就是实时性，slave 同步 master 的数据存在延时性
2. 如果 slave 节点过多， master 节点全量同步的压力很大， 可演化成主-从-从的架构
3. 如果 master 节点宕机怎么办， 还需要有故障恢复机制
4. 只有一个master节点， 无法应对高并发写的需求

## Redis 哨兵（非重点）

![Redis 哨兵（非重点）](file:///D:/Java/data/八股文/05-Redis/5e380d69921a.png)

**为什么需要哨兵机制？ 它的作用是什么？**

Redis 提供了哨兵机制来实现主从集群的自动故障恢复

1. 监控：哨兵会不断的检查 master 和 slave 是否正常工作
2. 自动故障恢复：如果 master 故障， 哨兵会将一个 slave 提升为 master。同时哨兵会去重启master 尝试让其恢复
3. 通知：哨兵充当 Redis 客户端的服务发现来源， 当集群发生故障转移时，会将最新消息推送给 Redis 客户端， 通知的信息包括：主节点信息、从节点信息， Redis 客户端收到信息才能做读写分离
**哨兵机制具体如何监控 Redis 主从集群？**

哨兵集群基于心跳机制监测服务状态，每隔1秒向集群的每个实例发送ping命令

- 主观下线：如果某哨兵节点发现某实例未在规定时间响应，则认为该实例 “主观下线”
- 客观下线：若超过指定数量的quorum哨兵节点都认为该实例 “主观下线”，则该实例视为 “客观下线”，quorum是可配置的值。
- 哨兵节点既可以监测 master 节点，也可以监测 slave 节点。

![Redis 哨兵（非重点）](file:///D:/Java/data/八股文/05-Redis/3277712c52b9.png)

当 master 宕机后， 哨兵如何选举新的 master？选举规则依次排列如下：

1. 判断 slave 节点与 master 节点断开时间长短， 如果超过指定值，则会排除该 slave 节点
2. 判断 slave 节点的 slave-prioity 值，越小优先级越高， 如果是0则永不参与选举， 默认情况下所有节点的 slave-prioity 值都是相同的是1
3. 判断 slave 节点的 offset 值，越大说明数据越新，和 master 的数据差异越小，优先级越高
4. 最后判断 slave 节点的运行id大小，越小优先级越高。（运行id是Redis随机生成的） 即到最后就随机选择一个 slave 节点选举为 master 节点
选举出新的 master 节点后， 哨兵让新的 master 节点 执行命令 slaveof no one， 变成新的

master，然后哨兵广播让所有节点都执行 slaveof 新master， 最后修改故障节点的配置文件，添加slaveof 新master

**哨兵机制仍然存在的问题？**

哨兵机制只是解决了节点故障恢复的问题。

1. 依然没有数据分片功能： 当数据集过大时， Redis单个节点无法承载。
2. 只有一个master节点， 无法应对高并发写的需求

## Redis Cluster（重点）

![Redis Cluster （重点）](file:///D:/Java/data/八股文/05-Redis/625dc8902ed6.png)

**分片集群的特征：**

- 集群中有多个master，每个master保存不同数据
- 每个master都可以有多个slave节点， 并且之间存在主从数据同步
- 故障监测和自动恢复：集群之间通过心跳机制互相监测彼此的健康状态
  - 主节点之间互相心跳监测
  - 主节点定期向它的从节点发送ping消息， 并等待pong响应。主节点确认它所管理的从节点是否正常
- 客户端如何访问？客户端可以请求任意节点， 最终都会被转发到正确节点上

**数据分片——散列插槽的原理？**

Redis 会有16384个插槽，分别分配给不同的 master 节点

存入 Redis 的数据， key 是与插槽绑定的， 而不是与节点绑定。

Redis 会根据 key 的有效部分计算插槽值， 以此判断 key 是和哪个插槽绑定的。

- 如果key中包含{},且{}中至少包含1个字符，则{}中的部分是有效部分。
- 如果key中不包含{}，则整个key都是有效部分。

计算插槽值: 使用 CRC16 算法根据key有效部分计算出hash值，然后对16384取余，得到 slot 插槽值

当要写入数据或读取数据时， 通过知道key对应的插槽值，就可以找到对应的Redis节点

**为什么将数据与插槽绑定来实现分布式存储？**

与之对应的方案是，数据固定绑定在Redis节点上。

1. 负载均衡： 当集群伸缩（增加或减少节点） Rediscluster 将哈希槽重新分配，保证数据和负载的均匀分布。
2. 快速查找：通过将数据与插槽绑定， 可以通过计算key对应的插槽值，快速定位到数据所在的Redis节点， 避免全局查询， 并且即使集群伸缩或故障恢复后都可以根据插槽值找到新的数据所在的Redis节点。
**当扩容新加入节点时， 槽位重分配， 槽位信息怎么同步到集群中所有节点？**

在 Redis Cluster 中，扩容并加入新节点时，槽位会重新分配，集群中的每个节点（包括主节点和从节点）都会更新自己负责的槽位信息。这些信息通过集群协议（如 Gossip 协议） 和槽位迁移机制同步到集群中的所有节点，确保数据在集群中的一致性和可访问性。

**Redis cluster 的优点？**

1. 实现了数据分片， 通过多master和散列插槽的机制， 允许承载更大的数据量
2. 实现了故障检测和自动恢复：通过心跳机制监测集群节点健康状态
3. 支持集群伸缩，支持水平扩展：可新增master节点(及其slave节点)， 可应对更高的读写需求(注意：Redis主从和Redis哨兵都不支持水平扩展)
**总结：**

- Redis 主从是一主多从架构
- Redis 哨兵是一主多从+哨兵集群架构
- Redis Cluster 实现的是一个 多主多从 架构

## Codis (非重点内容，拓展， 可不看)

简介：Codis 是一个分布式 Redis 解决方案，对于客户端来说， 连接到 Codis 和连接原生的

Redis Server 没有明显的区别，上层应用可以像使用单机的 Redis 一样使用 Codis（而Codis实际底层是多主多从的架构），Codis 会处理请求的转发，底层的Redis实例信息对于前面的客户端来说是透明的

### 整体架构

![整体架构](file:///D:/Java/data/八股文/05-Redis/b7a05e2272a3.png)

Codis Proxy

**Codis Proxy是什么？**

- Codis Proxy 本身是一个无状态的服务， Proxy因为是无状态的所以天然支持扩展。Proxy起到接受 Redis Client 请求， 并且根据用户请求信息进行计算，得到相应的slot插槽， 并且把

Redis Client的请求正确路由到背后的Redis物理实例上。

**Proxy具有哪些信息？**

- Proxy需要进行路由请求的操作，且读写分离
- 因此Proxy具有所有slot插槽信息，slot分配给哪一个server-group信息。一个sever-group

中的Redis实例谁是master，谁是slave

- Proxy的信息来源自 codis-dashboard 的推送，codis dashborad的元数据信息又是来源于Storage

Codis Dashboard

Codis 的管理工具， 支持添加/删除 Redis 节点、添加/删除 Proxy 节点，发起数据迁移等操作。用户可以直接在浏览器上观察 Codis 集群的运行状态；

另外 Codis Dashboard 会把集群元信息广播到codis proxy中

Sentinel

和 Redis 哨兵一样，Codis也有哨兵，用于监控底层Redis实例的健康状态以及主从切换同时 Codis Proxy 会监听Sentinel， 感知到主从切换的信息后，更新自己存储的信息

同时 Codis Dashboard 也会监听Sentinel， 感知到主从切换的信息后，更新到ZK或Etcd

Storage

存储Codis集群实例元信息

### 分片原理

1. Codis 默认划分为1024个槽位slot， 首先CodisProxy对客户端传过来的key进行crc32运算计算哈希值，得到的值再对1024取模得到的余数就是key对应的槽位值slot， 由Codis Proxy进行请求的转发，转发到底层正确的Redis实例上(ServerGroup)
2. Codis底层的Redis实例被分为逻辑概念ServerGroup，每个ServerGroup中是一主多从架构，每个ServerGroup绑定一定范围的槽位slot
3. Codis将槽位和ServerGroup的绑定关系存储在Storage（Zookeeper或者etcd分布式配置存储数据库） 中， 并且提供了一个Dashboard可以观察和修改槽位关系
4. 当槽位关系变化时，CodisProxy会监听到变化并重新同步槽位关系，从而实现多个CodisProxy之间共享相同的槽位关系配置

### 集群伸缩

**集群伸缩， 会造成槽位重新分配， 同时带有数据迁移， 如何平滑迁移， 正在迁移的key的读写请求怎么办？**

刚开始 Codis 后端只有一个 Redis 实例，1024 个槽位全部指向同一个 Redis。然后一个 Redis实例内存不够了，所以又加了一个 Redis 实例。这时候需要对槽位关系进行调整，将一半的槽位划分到新的节点。这意味着需要对这一半的槽位对应的所有 key 进行迁移， 迁移到新的 Redis 实例。

**那 Codis 如何找到槽位对应的所有 key 呢？**

Codis 对 Redis 进行了改造，增加了 SLOTSSCAN 指令， 可以遍历指定 slot 下所有的 key。 Codis 通过 SLOTSSCAN 扫描出待迁移槽位的所有的 key，然后挨个迁移每个 key 到新的 Redis 节点。

问题！

在迁移过程中，Codis 还是会接收到新的请求打在当前正在迁移的槽位上， 因为当前槽位的数据同时存在于新旧两个槽位中，Codis 如何判断该将请求转发到后面的哪个具体实例呢？

解决方案！

Codis 无法判定迁移过程中的 key 究竟在哪个实例中，所以它采用了另一种完全不同的思路。当Codis 接收到位于正在迁移槽位中的 key 后，会立即强制对当前的单个 key 进行迁移， 迁移完成后， 再将请求转发到新的 Redis 实例。迁移单个key的操作是原子性的。

### Codis 与 RedisCluster

**与 Redis cluster对比坏处：**

- Codis 因为增加了 Proxy 作为中转层，所以在网络开销上要比客户端直连 Redis 大， 毕竟数据包多走了一个网络节点，整体在性能上要比 非Proxy Based 的架构的性能有所下降。但是这部分性能损耗不是太明显， 可以通过增加 Proxy 的数量来弥补性能上的不足。
- Codis 的集群配置中心使用 zk 来实现， 意味着在部署上增加了 zk 运维的代价好处：
- Codis 在设计上相比 Redis Cluster 官方集群方案要简单很多， 因为它将槽位绑定节点实例信息这个分布式的问题交给了第三方 zk/etcd 去负责， 自己就省去了复杂的分布式一致性代码的编写维护工作。而 Redis Cluster 对于槽位绑定的信息的同步的内部实现非常复杂， 它为了实现去中心化， 混合使用了复杂的 Raft 和 Gossip 协议（即节点间定期交换信息）

对客户端来说，使用 Redis Cluster，客户端需要是 smart client， 需要感知数据分片信息， 需要知道后方实例信息、需要支持集群协议， 直接与节点通信。无法支持跨节点的操作。

对客户端来说，使用 Codis， 通过Proxy层转发请求，客户端不需要感知集群实例信息。就像使用一个单机Redis一样， 可以支持跨节点的操作(由Proxy帮助处理)。

## 主从数据同步原理与实践优化

### 全量同步原理

主从建立连接后的第一次数据同步——全量同步

![全量同步原理](file:///D:/Java/data/八股文/05-Redis/be1f031b935e.png)

**全量同步流程：**

1. slave 请求数据同步， master 判断是否第一次同步
2. master 判断是第一次同步， master 返回数据版本信息 replid 和 offset，slave 保存版本信息
3. master 执行 bgSave，生成 RDB 文件， 并且在生成文件期间，将主进程收到的所有命令记录到repl_baklog 即内存的缓冲区
4. master 向 slave 发送 RDB 文件，slave 清空本地数据，加载 RDB 文件
5. master 向 slave 发送 repl_baklog内存缓冲区中的命令，slave 收到命令执行
master 如何判断 slave 节点是否第一次来做数据同步

1. Replication_id：简称 replid， 是数据集的标记， 如果两个节点的 replid 一致，则说明是两个节点是同一个数据集。每一个 master 节点都有唯一的 replid，slave 节点则会继承 master 节点
的 replid

2. offset：偏移量， 随着记录在 repl_baklog 中的数据增多而逐渐增大。slave 完成同步时也会记录当前同步的 offset。如果 slave 的 offset 小于 master 的 offset，说明 slave 数据落后于master， 需要更新。
结论： 因此slave做数据同步，必须向 master声明自己的 replid 和 offset， master 才可以判断到底是全量同步还是增量同步， 以及增量同步需要同步哪些数据。

- 使用 Replication_id 来判断 slave 节点是不是第一次来做数据同步， 如果 replid 一样，说明不是第一次， 如果 replid 不一样说明是第一次做数据同步。
- offset量只能说明 repl_baklog 数据缓冲区中的数据同步的进度。

### 增量同步原理

增量同步在 slave 节点断开又恢复连接主节点时，会执行增量同步

![增量同步原理](file:///D:/Java/data/八股文/05-Redis/b6aa8b3e7ecb.png)

**增量同步流程：**

1. slave 请求数据同步， master 判断是否第一次同步
2. master 判断不是第一次同步， master 返回 continue
3. master 根据 offset 向 slave 发送 repl_baklog内存缓冲区中的命令，slave 收到命令执行特殊情况：
repl_baklog 内存缓冲区大小有上限，环形数组， 写满后会覆盖写入， 如果 slave 断连太长时间，导致尚未同步的数据被覆盖，则无法进行增量同步， 只能再次全量同步。

### 实践优化

全量同步执行较为耗时， 需要执行生成RDB文件（磁盘IO）， 需要发送RDB文件（网络IO）

**针对全量同步的优化思路：**

1. 在master中配置 repl-diskless-sync yes 启动无磁盘复制， 避免全量同步时的磁盘IO， 即不生成RDB文件， 而是直接将其全量数据通过网络发送到 slave，减少磁盘IO提高效率
2. 控制Redis单节点上内存占用不要太大，减少全量同步时的磁盘IO和网络IO
3. 减少全量同步的概率
- 适当提高 repl_baklog 内存缓冲区的大小，发现 slave 宕机时尽快实现故障恢复， 避免全量同步

4. master 同步的压力， 如果太多的 slave 节点都去找 master 进行数据同步，那么 master 压力很大
- 限制一个 master 上的 slave 节点数量， 如果实在太多 slave 节点， 可以采用主-从-从链式结构， 即从节点去找从节点进行数据同步。

![实践优化](file:///D:/Java/data/八股文/05-Redis/16823e3bb393.png)

## Redis 为什么这么快

1. 基于内存(最主要的原因)：Redis 是一种基于内存的数据库，数据存储在内存中，数据的读写速度非常快， 内存访问速度比硬盘访问速度快得多
2. 执行命令是单线程模型：Redis 使用单线程模型， 这意味着它的所有操作都是在一个线程内完成的，不需要进行线程切换和上下文切换。这大大提高了 Redis 的运行效率和响应速度
3. 多路复用 I/O 模型：Redis 在单线程的基础上， 采用了I/O 多路复用技术， 实现了单个线程同时处理多个客户端连接的能力，从而提高了 Redis 的并发性能
4. 高效的数据结构：Redis 提供了多种高效的数据结构， 如哈希表、有序集合、列表等， 这些数据结构都被实现得非常高效， 能够在较低的时间复杂度内完成数据读写操作

### Redis 是单线程还是多线程

如果我们聊的仅仅是Redis的核心业务部分（即命令处理部分：数据读写操作）， 答案是单线程如果我们聊的是整个Redis， 其他的包括如持久化存储、集群支撑，那么答案就是多线程。

在Redis版本迭代过程中，在两个重要的时间节点上引入了多线程的支持。

- Redis v4.0：引入多线程异步处理一些耗时较长的任务， 即一些后台处理任务，例如我们处理一些Redis的BigKey， 我们直接去删除的话耗时较久， 可能导致主线程阻塞。因此采用一种异步删除，就是unlink命令，后台开启线程异步删除这个BigKey。还有一些持久化方式中用到的bgSave、bgrewrite。
  - 当时整个Redis的网络模型还是单线程的。但是他底层采用的是IO多路复用的这种机制，单机模式下性能依然很好。每秒数万的并发。
- 随着业务的发展，和各种硬件设备的提升， 我们的服务器往往可以做到16核、32核、64核，硬件性能越来越好， 如果Redis仍然采用单线程，就没有办法去充分的利用这种高性能的硬件设备， 虽然可以搭建集群，但是集群往往会引入一些其他的问题。
- Redis v6.0：在核心网络模型中引入多线程， 进一步提高对于多核CPU的利用率。继续提高这种网络并发量

### Redis 为什么使用单线程执行命令

核心业务命令处理部分还是单线程。

**抓住问题本质， 我们得关注整个系统的瓶颈在哪里？提升服务响应速度的瓶颈在哪里？**

- 抛开持久化不谈， Redis是纯内存操作，执行命令速度非常快， 它的性能瓶颈是网络延迟，而不是执行速度， 因此多线程并不会带来巨大的性能提升。(这就类似Cpu的运算速度和磁盘IO速度相比， IO速度太慢， 即使再提升CPU的运算速度，也不能提升整个系统的性能。)
- 多线程会导致过多的上下文切换 (例如CPU单核的情况下， 线程越多，CPU切换线程的频率越高， 多线程也会带来一些额外的内存消耗)，整体来说会带来不必要的开销，反而导致性能下降。
- 即使Redis引入了多线程，但是估计线程数也不会太多，往往和CPU的核数相对应， 可能是1到2倍。为的就是尽可能减少这种多线程导致的上下文切换。
- 引入多线程会面临线程安全问题，必然要引入线程锁这样的安全手段， 实现复杂度就会大大提高， 而且性能也会大打折扣。

### Redis 6.0 为什么引入多线程

Redis 6.0 中的多线程， 是针对处理网络请求过程采用多线程， 而数据的读写命令，仍然是单线程处理的。

Redis 的网络模型采用 多路复用IO模型技术， 为什么还需要多线程?限制 Redis 的性能的主要瓶颈出现在网络 IO 上

Redis6.0 在网络模型中引入多线程， 目的是为了提高 IO 读写效率。

因此在解析客户端命令、写响应结果时采用了多线程。

**具体分析如下：**

真正的性能瓶颈在于

1. 监听到客户端可读， 服务端读取客户端的请求数据时， 这种网络IO， 是比较慢的。
2. 最后处理完毕，将响应结果输出返回给客户端， 这种网络IO，也是慢的。
因此Redis v6.0在网络模型中引入多线程，就是在这两部分引入多线程来提高性能。

1. 假设主线程在IO多路复用模块监听到大量的客户端可读， 高并发的情况下， 无数的客户端请求都在等待读。此时， 如果主线程一个一个去读取客户端的数据， 这种单线程的IO就可能忙不过来了。于是此时会去开启多线程，然后主线程会以轮询的形式， 把多个不同的客户端分发给不同的线程， 由他们并发地区解析客户端请求中的数据，然后解析为命令，找到对应的命令函数command， 真正执行命令时， 还是交给主线程一个人去执行， 线程安全。 因此，这里的多线程主要是为了在解析大量的、高并发的客户端命令时，提高IO读写效率。
2. 假设数据处理完毕后，在可写的客户端队列中有非常多的可写客户端，就是可以返回数据给客户端，此时如果又是主线程一个人去遍历的取可写客户端然后返回数据， 这里的IO也是比较慢的。因此在此时去开启多线程，让他们去可写的客户端中去取客户端然后IO返回输出结果。这样也没问题。这里的多线程主要就是为了在写大量的客户端响应结果时，提高了IO读写效率。
在这两个地方引入多线程，就能大幅度的提高， Redis 对于处理客户端请求的一个性能，减少因为单线程&&网络IO导致的性能影响。

虽然单次请求的响应时间没有缩短，但是整体的吞吐量，相对于单线程模式， 还是有不少的提升的。

### Redis 是 AP 还是 CP

Redis 是AP的

Redis 的设计目标是高性能、高可扩展性、高可用性

- 当发生网络分区时或者部分节点故障不可用时， Redis 仍然允许接受读写请求，保证可用性(A)
- Redis 是保证最终一致性， 即在某个时间点读取的数据可能并不是最新的，但最终会达到一致的状态。
- Redis 主从数据同步采用的是异步复制， 这导致在节点之间存在数据同步延迟和不一致的可能性。

但Redis官方说明 即使主从数据同步改成采用同步复制，也无法保证强一致性，原因复杂。

### Redis 支持事务/回滚吗

Redis 支持事务，但它的事务只保证多个命令执行的原子性，且事务不支持回滚。

**Redis 不支持事务回滚：**

- Redis 的设计思路是简单高效：如果引入事务回滚会让系统的复杂性升高， 并且影响性能
- Redis 的定位：主要用于缓存、高速计数、分布式锁等场景，对严格事务需求较低。
- 替代方案：如需强一致性事务，应选择关系型数据库（如MySQL） 或支持ACID的NoSQL数据库（如MongoDB 4.0+）。
